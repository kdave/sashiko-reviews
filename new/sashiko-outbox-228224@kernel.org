> btrfs: interrupted subvolume drop resets drop_progress to 0, next mount aborts with "has 0 references" (-117)
>
> Hello btrfs kernel team,
>
> Impact:
> after an interrupted drop of a deleted subvolume, every later rw mount
> aborts the transaction (-117) and forces the fs read-only; it cannot be
> used rw anymore and btrfs check reports ~1000 extent ref errors (all on
> the deleted subvolume; remaining data readable ro). Hit twice in the
> field by a bare-metal restore tool, i.e. a freshly restored system is
> unusable.
> Plain userspace sequence, no fault injection needed; current master is
> affected.
>
> Details:
> A resumed snapshot/subvolume drop can write drop_progress = 0 /
> drop_level = 0 back to the root item after earlier runs already dropped
> the leftmost subtrees. If the snapshot sharing those subtrees COWs them
> before the next resume, the drop restarts at slot 0, finds a block with
> 0 references and aborts the transaction (-EUCLEAN). Seen in the wild
> after bare-metal restores (btrfs receive -> rw snapshot -> delete
> received subvol -> short mount/umount cycles -> writes), reproduced on
> 6.12.100 (Debian), 6.19.10 and 7.2.13 (Fedora), code unchanged in
> current master. Downstream report with forensics:
> https://bugzilla.redhat.com/show_bug.cgi?id=2496404
>
> Cause: in btrfs_drop_snapshot(), the resume branch (drop_progress != 0)
> only seeds wc->update_progress. wc->drop_progress / wc->drop_level stay
> zero from kzalloc. The loop does
>
> if (wc->stage == DROP_REFERENCE) { set wc->drop_level / wc->drop_progress }
> btrfs_cpu_key_to_disk(&root_item->drop_progress, &wc->drop_progress);
> btrfs_set_root_drop_level(root_item, wc->drop_level);
> if (btrfs_should_end_transaction(trans) ||
> btrfs_need_cleaner_sleep(fs_info))
>         btrfs_update_root(...);   /* and -EAGAIN when closing */
>
> When the resumed walk first descends into a shared node, the first
> iteration ends in UPDATE_BACKREF, zeros are copied into the root item
> and, if the fs is unmounted at that moment (btrfs_need_cleaner_sleep()
> true while closing), committed. kprobe on btrfs_update_root after a
> resume with saved progress (5421 INODE_ITEM 0) level 2:
> btrfs_drop_snapshot rootid=256 (resume) btrfs_update_root rootid=256
> dp=0 dlvl=0 <-- first write after resume btrfs_update_root rootid=256
> dp=16032 dlvl=2
>
> On the next resume check_ref_exists() would skip already dropped blocks,
> but if they were freed by COW from the sharing snapshot,
> btrfs_lookup_extent_info() returns refs 0 and do_walk_down() returns
> -EUCLEAN first.
>
> Reproducer (btrfs-drop-resume-repro.sh attached, self-contained, two
> loop images): mkfs.btrfs -n 4096; receive a large (~1.5M files)
> subvolume; snapshot it rw; delete the received subvolume; umount mount
> -o commit=1; sleep 3; umount # drop runs, progress saved (level 3)
> mount; umount # resume interrupted -> drop_progress 0 on disk mount;
> touch many files in the snapshot; umount mount # "bytenr X has 0
> references, expect > 0", abort -117 Results: 7.2.13-200.fc44 (untainted,
> QEMU): 3/3 drop_progress reset to 0, 0/3 aborts same, target behind
> dm-delay 1 ms: 2/2 drop_progress reset to 0, 2/2 aborts 6.19.10-300.fc44
> (SATA SSD, no delay): reset + abort in the first iteration same
> sequence, fixed module: 4/4 clean, progress kept, drop completes Debian
> 6.12.100 in QEMU (throttled disk): stock aborts, fixed build 60 cycles
> clean The reset happens reliably; the abort additionally needs the COW
> in the snapshot to free the already dropped nodes before the resumed
> drop skips past them, so slow storage makes it likely.
