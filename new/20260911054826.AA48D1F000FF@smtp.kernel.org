btrfs: introduce a new ioctl to force updating the device name

This commit introduces a new ioctl BTRFS_IOC_RENAME_DEV to allow userspace
to explicitly force updating a btrfs device path. By pushing the responsibility
to the end user, it aims to resolve historical corner cases in btrfs device
name resolution.

[Severity: Low]
Does BTRFS_IOC_RENAME_DEV permit renaming a device to its exact same
current path?

When force_rename is true in device_list_add() in fs/btrfs/volumes.c,
if the ioctl is called with the exact same path the device already uses, it
seems it will unnecessarily allocate a new string, swap the RCU pointer,
free the old string, and log a misleading message indicating a rename to
the same name.

[Severity: High]
Can this new force_rename path trigger a PROVE_RCU lockdep splat?

By allowing execution to reach the previously unreachable btrfs_info() call
further down in device_list_add():

fs/btrfs/volumes.c:device_list_add() {
    ...
    if (device->bdev) {
        ...
        btrfs_info(NULL,
            "devid %llu device path %s changed to %s scanned by %s (%d)",
            devid, btrfs_dev_name(device),
            path, current->comm,
            task_pid_nr(current));
    }
    ...
}

This calls btrfs_dev_name(device) without holding rcu_read_lock(). Since
force_rename makes this path reachable via BTRFS_IOC_RENAME_DEV, it exposes
a violation of RCU locking rules.
