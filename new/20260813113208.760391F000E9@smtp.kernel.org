Subject: btrfs: keep mixed block group writable for relocation setup commit

This commit modifies mixed block group relocation to keep the target
writable until the setup transaction finishes. It introduces a fenced setup
boundary to gate non-metadata operations while allowing setup metadata COW.
The read-only transition and relocation control publish are deferred to the
transaction tail.

[Severity: High]
Could this lead to -ENOSPC failures when the filesystem is nearly full?

The fenced setup in btrfs_relocate_block_group() bypasses the normal
btrfs_inc_block_group_ro() call, which handles fallback chunk allocations.
When the transaction tail later calls btrfs_bg_reloc_setup_finish(), it
invokes __inc_block_group_ro() with force=false.

Without the buffering from a prior chunk allocation, could this return
-ENOSPC and unexpectedly abort the balance operation?

[Severity: Medium]
Will the background block group reclaimer collide with an active fenced
relocation here?

Since bg->ro is 0 during the fenced setup, but BLOCK_GROUP_FLAG_RELOC_SETUP
isn't checked in this condition, the cleaner thread might proceed to call
btrfs_relocate_chunk() concurrently.

Calling btrfs_relocate_chunk() returns -EINPROGRESS because
BTRFS_FS_RELOC_RUNNING is already set. Does this result in spurious
kernel error logs and inflate the reclaim_errors counter?

[Severity: Medium]
Can the balance thread hang here if a transaction aborts during relocation
setup?

If btrfs_commit_transaction() aborts, it might return an error without ever
reaching TRANS_STATE_COMPLETED. Without checking TRANS_ABORTED(trans) in this
wait condition, the thread could be left in an uninterruptible sleep until
the transaction kthread cleans it up.
