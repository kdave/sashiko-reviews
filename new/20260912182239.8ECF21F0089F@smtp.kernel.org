btrfs: derive f_fsid with dev_t only when temp_fsid is active

This commit limits the mixing of dev_t into f_fsid to cloned filesystems
where temp_fsid is active. This restores backward compatibility for standard
mounts so that their statfs f_fsid remains consistent across reboots or
device reattachments.

[Severity: High]
This isn't a bug introduced by this patch, but this is a pre-existing issue.
Can dereferencing fs_info->fs_devices->latest_dev and its bdev here trigger
a use-after-free during a concurrent device replacement?

It looks like btrfs_statfs() evaluates latest_dev without holding
rcu_read_lock() or the device_list_mutex. If a concurrent device replace
operation occurs:

btrfs_dev_replace_finishing()
   ... updates latest_dev ...
   btrfs_rm_dev_replace_free_srcdev()
      synchronize_rcu()
      ... frees the old device ...

Since btrfs_statfs() does not hold rcu_read_lock(), the synchronize_rcu()
call will not wait for it. If the thread is preempted right after reading
the pointer, could statfs resume and dereference the freed device to access
bdev->bd_dev, triggering a use-after-free and potentially leaking kernel
memory into the f_fsid returned to userspace?
