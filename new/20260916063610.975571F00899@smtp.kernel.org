[Severity: Medium]
Does calling check_remount() before check_leftover_items() inadvertently
destroy the very leaked items this test tries to detect?

In check_rollback(), the script deletes a 1GB filler file which frees up space
on the filesystem. When check_remount() subsequently calls _try_scratch_mount,
Btrfs will automatically run orphan cleanup during the mount.

Since space is now available again, won't the mount-time cleanup successfully
remove any orphan or verity items left behind by the failed fsverity enable?

If the remount cleans up the leaked items first, check_leftover_items() might
incorrectly pass even if the kernel bug it is testing for is present.
