btrfs: introduce BTRFS_RAID_STRIPE_PARITY_KEY

This commit introduces BTRFS_RAID_STRIPE_PARITY_KEY to hold parity information
for a specific tuple inside the RAID stripe-tree. The parity information uses
the same on-disk format as DATA stripes. It also updates btrfs_print_leaf()
to print the new key type.

[Severity: High]
This is a pre-existing issue, but I noticed a potential problem in
update_raid_extent_item() in this file when it modifies the metadata leaf
buffer.

After using btrfs_search_slot() to obtain a writable leaf and updating the
stripe extent via write_extent_buffer(), it doesn't call
btrfs_mark_buffer_dirty():

fs/btrfs/raid-stripe-tree.c:update_raid_extent_item() {
    ...
	leaf = path->nodes[0];
	slot = path->slots[0];

	write_extent_buffer(leaf, stripe_extent, btrfs_item_ptr_offset(leaf, slot),
			    item_size);

	return ret;
}

If the buffer was already COW'd earlier in the same transaction,
btrfs_cow_block() returns it without re-dirtying it. If the flusher thread
already wrote this buffer to disk and cleared its dirty flag, could these new
modifications only exist in memory and be silently discarded when the
transaction commits?

[Severity: High]
Since this key shares the exact same on-disk layout as BTRFS_RAID_STRIPE_KEY,
does it also need to be added to the switch statement in check_leaf_item() to
ensure it gets validated?

Currently, check_leaf_item() only validates BTRFS_RAID_STRIPE_KEY:

fs/btrfs/tree-checker.c:check_leaf_item() {

Without adding BTRFS_RAID_STRIPE_PARITY_KEY here, parity keys read from disk
will bypass check_raid_stripe_extent(). Could this allow malformed keys to be
