[Severity: Medium]
Does btrfs_zoned_dev_avail_bytes() discard the total - used argument
passed here?

btrfs_zoned_dev_avail_bytes() overwrites its avail parameter with
total - device->bytes_used:

fs/btrfs/zoned.c:btrfs_zoned_dev_avail_bytes() {
	...
	avail = total - device->bytes_used;
	if (avail <= sb_bytes)
		return 0;

	return avail - sb_bytes;
}

When a chunk is removed in the current transaction, device->bytes_used is
smaller than device->commit_bytes_used while the freed device extents
remain in the commit root until transaction commit.  Ignoring
device->commit_bytes_used counts those uncommitted zones as available and
allows a data chunk allocation to consume the last committed free zone.

> +		dev_stripes = avail_bytes / stripe_size;

[Severity: High]
Both avail_bytes and stripe_size are u64, so will this plain division
fail to link with an undefined reference to __udivdi3 on 32-bit builds?
Using div64_u64(avail_bytes, stripe_size) avoids the 64-bit division
helper.

> +		if (dev_stripes >= 2)

> +		else if (dev_stripes == 1)
> +			nr_one++;
> +	}
> +
> +	if (nr_two + nr_one < raid->devs_min)
> +		return false;
> +
> +	return (2 * nr_two + nr_one) >= 2 * raid->devs_min;

[Severity: High]
Can this check still allow a data chunk allocation to consume the last
free zone across all devices on striped RAID profiles where
raid->devs_max is 0 (RAID0, RAID10, RAID5, RAID6)?

Comparing against 2 * raid->devs_min assumes the new chunk will only
allocate from raid->devs_min devices.  For profiles with
raid->devs_max == 0, init_alloc_chunk_ctl() sets ctl->devs_max to
BTRFS_MAX_DEVS(fs_info), and do_chunk_alloc() stripes the chunk across
all writable devices with free space.  For example, on a 2-device RAID0
filesystem (devs_min == 1) where each device has 1 free zone left
(nr_two == 0, nr_one == 2), (2 * nr_two + nr_one) >= 2 * raid->devs_min
is true, and do_chunk_alloc() then consumes the last zone on both
devices, leaving no free zones for relocation.
