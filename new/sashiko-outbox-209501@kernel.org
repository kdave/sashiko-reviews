[Severity: High]
Is fs_devices->seed_list safe to walk under rcu_read_lock() alone?

When the last device of a seed btrfs_fs_devices is removed in
btrfs_rm_device() or btrfs_rm_dev_replace_free_srcdev(), synchronize_rcu()
runs before the seed btrfs_fs_devices is unlinked, and the seed_list entry
is then removed with list_del_init() and freed immediately without an RCU
grace period:

fs/btrfs/volumes.c:btrfs_rm_device() {
    ...
	synchronize_rcu();
	btrfs_free_device(device);
    ...
	if (cur_devices->num_devices == 0) {
		list_del_init(&cur_devices->seed_list);
		ASSERT(cur_devices->opened == 1, "opened=%d", cur_devices->opened);
		cur_devices->opened--;
		free_fs_devices(cur_devices);
	}
}

A concurrent btrfs_ioctl_dev_info() reader can therefore loop forever on
the self-linked seed_list entry or dereference cur_devices after it is
freed:

CPU0                                  CPU1
btrfs_rm_device()                     btrfs_ioctl_dev_info()
  list_del_rcu(&device->dev_list)
  synchronize_rcu()
  btrfs_free_device(device)
                                        rcu_read_lock()
                                        btrfs_find_device_rcu()
                                          seed_devs = cur_devices
  list_del_init(&cur_devices->seed_list)
  free_fs_devices(cur_devices)
    kfree(cur_devices)
                                          dev_args_match_fs_devices(...,
                                            seed_devs)  <-- use-after-free
                                          /* or next iteration follows
                                           * cur_devices->seed_list.next
                                           * back to cur_devices forever */

Similarly, btrfs_rollback_sprout() calls list_del_init() on
seed_devices->seed_list right before list_splice_init_rcu(...,
synchronize_rcu) (which can deadlock if a reader is spinning on the
reinitialized seed_list entry), restores device->fs_devices after the
grace period has already elapsed, and frees seed_devices before the outer
synchronize_rcu() in btrfs_init_new_device() runs, while
btrfs_setup_sprout() and btrfs_init_dev_replace_tgtdev() publish new list
entries with plain list_add() instead of list_add_rcu().
