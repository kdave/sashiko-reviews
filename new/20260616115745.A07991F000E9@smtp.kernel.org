Author: Christian Brauner <brauner@kernel.org>
btrfs: don't leave dev-replace STARTED after an early finishing failure

This patch ensures that btrfs_dev_replace_finishing() demotes the dev-replace
state from STARTED to SUSPENDED when returning early due to failures in
btrfs_start_delalloc_roots() or btrfs_start_transaction(). This prevents the
operation from getting stuck in STARTED without an active scrub.

Cc: stable@vger.kernel.org

[Severity: High]
This isn't a bug introduced by this patch, but returning early here leaves the
dev_replace->replace_task pointer dangling because it is not cleared.

If the thread terminates and the slab allocator reuses its task_struct for a
new thread performing btrfs I/O, btrfs_map_block() could match the
replace_task pointer:

if (dev_replace->replace_task != current)
    down_read(&dev_replace->rwsem);

Would this allow the new thread to bypass the read lock, potentially leading
to a NULL pointer dereference on dev_replace->srcdev->devid if an administrator
runs "btrfs replace cancel" while the rogue thread is executing?

[Severity: High]
This is also a pre-existing issue, but further down in
btrfs_dev_replace_finishing() the replace_state is eagerly set to FINISHED:

	dev_replace->replace_state =
		scrub_ret ? BTRFS_IOCTL_DEV_REPLACE_STATE_CANCELED
			  : BTRFS_IOCTL_DEV_REPLACE_STATE_FINISHED;
	...
	dev_replace->item_needs_writeback = 1;

Immediately after, if btrfs_set_target_alloc_state() fails, the code jumps
to the error label:

	if (!scrub_ret) {
		scrub_ret = btrfs_set_target_alloc_state(src_device, tgt_device);
		if (scrub_ret)
			goto error;

Since the error path does not revert replace_state back to CANCELED or
SUSPENDED, and item_needs_writeback is already 1, will the next transaction
commit permanently persist the FINISHED state to disk, even though the
replacement was rolled back?
