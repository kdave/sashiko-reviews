[Severity: High]
Can this cause a deadlock by calling handlers that allocate memory with
GFP_KERNEL while holding the transaction handle?

Since btrfs_inode_inherit_props() and btrfs_set_prop() are called with an
active btrfs_trans_handle, they subsequently call h->validate() and h->apply()
which map to prop_compression_validate() and prop_compression_apply().

Both of these handlers allocate memory using kmemdup_nul(..., GFP_KERNEL):

fs/btrfs/props.c:prop_compression_validate() {
    ...
    value_str = kmemdup_nul(value, len, GFP_KERNEL);
    ...
}

GFP_KERNEL allows direct reclaim, which can attempt to flush dirty filesystem
data, requiring locks already held by the active transaction (an A-A deadlock).

Since this path is reachable by unprivileged users setting compression xattrs
or creating subvolumes, could this be exploited for a local DoS?

Should these allocations use GFP_NOFS instead?
