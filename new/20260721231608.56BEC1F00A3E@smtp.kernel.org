btrfs: use %pe for error code output

This commit converts numeric error codes to human-readable strings across
various btrfs logging sites by utilizing the %pe format specifier combined
with ERR_PTR().

[Severity: Medium]
Since the iterate callback in iterate_leaf_refs() can return positive
control-flow constants to signal an early exit, such as
BTRFS_ITERATE_EXTENT_INODES_STOP which evaluates to 5, does this cast to
ERR_PTR() cause a loss of debug information?

The commit message notes that positive numbers will be output as a hashed
pointer value. However, in this specific btrfs_debug() call, logging the
exact positive control-flow value was the intended behavior. Will formatting
this positive value as a hashed pointer string obscure the actual reason the
iteration stopped?
