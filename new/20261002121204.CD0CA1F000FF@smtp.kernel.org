fstests: btrfs: add a test case for deleting partially owned qgroup

There is a bug report that, when deleting a partially owned qgroup,
btrfs will delete the on-disk items but leave the in-memory rb-tree and
sysfs entries untouched. Introduce a regression test for it to verify
the behavior.

[Severity: High]
Will this execution fail due to an undefined command?

The standard fstests framework uses $BTRFS_UTIL_PROG rather than a _btrfs
wrapper function. Executing this will result in a command not found error.

[Severity: Medium]
Could the output of this command cause a golden output mismatch?

Commands like subvolume create print status messages to stdout by default.
Because this output is not redirected to /dev/null or $seqres.full, the
printed text will be compared against 358.out, which expects only
"Silence is golden". This will cause the test to spuriously fail on both
patched and unpatched kernels.

> +_pwrite_byte 0x00 0 1M "$SCRATCH_MNT/subv1/data1" &> /dev/null

[Severity: High]
Could silencing stderr here hide I/O failures and cause a false negative test
result?

Using &> /dev/null silences both stdout and stderr. If _pwrite_byte fails
due to ENOSPC or I/O errors, no error will be reported and the file will
remain empty.

Since the test's core logic relies on populating 1M of shared data so that
rfer > excl for partial ownership, an empty file would mean rfer == excl.
Deleting a fully owned qgroup does not trigger the kernel inconsistency
bug, which would cause the test to erroneously pass on unpatched kernels.

[Severity: Medium]
Will this test terminate incorrectly and be reported as a failure?

_exit is not a bash built-in nor a standard fstests helper, which will throw
a command not found error.

Additionally, because status=0 is not explicitly set before exiting, the
EXIT trap from common/preamble will execute with the default failure status,
falsely reporting a test failure.
