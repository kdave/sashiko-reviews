btrfs: fix the wrong direction for BTRFS_IOC_DEVICES_READY

This commit changes the ioctl direction for BTRFS_IOC_DEVICES_READY from
_IOR to _IOW. This ensures it matches userspace expectations, as userspace
is writing the btrfs_ioctl_vol_args structure.

[Severity: Critical]
Does changing this ioctl command from _IOR to _IOW alter the integer value of
the command, creating an incompatible ABI?

Older userspace tools, such as btrfs-progs invoked by udev rules, will still
send the legacy _IOR version of BTRFS_IOC_DEVICES_READY.

Looking at btrfs_control_ioctl() in fs/btrfs/super.c, there is no fallback
case to gracefully handle the legacy _IOR variant:

fs/btrfs/super.c:btrfs_control_ioctl() {
	...
	switch (cmd) {
	...
	case BTRFS_IOC_DEVICES_READY:
		mutex_lock(&uuid_mutex);
	...
}

Without a fallback handler for the old command number, older binaries will
be rejected with -ENOTTY. Could this prevent multi-device volumes from
assembling automatically on boot?

[Severity: High]
This is a pre-existing issue, but does btrfs_control_ioctl() unconditionally
read 4096 bytes from userspace before checking the ioctl command?

fs/btrfs/super.c:btrfs_control_ioctl() {
	...
	vol = memdup_user((void __user *)arg, sizeof(*vol));
	if (IS_ERR(vol))
		return PTR_ERR(vol);
	ret = btrfs_check_ioctl_vol_args_path(vol);
	if (ret < 0)
		goto out;

	switch (cmd) {
	...
	case BTRFS_IOC_GET_SUPPORTED_FEATURES:
		ret = btrfs_ioctl_get_supported_features((void __user*)arg);
		break;
	...
}

BTRFS_IOC_GET_SUPPORTED_FEATURES expects a much smaller memory structure
(72 bytes).

If a privileged user calls BTRFS_IOC_GET_SUPPORTED_FEATURES with a 72-byte
buffer, could the unconditional 4096-byte read (sizeof(*vol)) cause a
spurious -EFAULT if the buffer is near the end of a mapped page? Furthermore,
if the read succeeds but the trailing uninitialized memory lacks a null byte,
could btrfs_check_ioctl_vol_args_path() incorrectly return -EINVAL?
