btrfs: zoned: skip the append only metadata writeback path for conventional block groups

This patch introduces btrfs_zoned_bg_is_append_only() and
btrfs_zoned_meta_is_append_only() to bypass sequential metadata writeback
serialization, active zone tracking, and freed tree block zeroout for
metadata block groups backed only by conventional zones. It also tracks
the number of sequential and conventional metadata block groups in
fs_info so that btrfs_zoned_meta_is_append_only() only performs a block
group lookup when both types are present.

in fs_info->zoned_seq_meta_bgs or fs_info->zoned_conv_meta_bgs if the
caller fails before inserting the block group into
fs_info->block_group_cache_tree?

Because the matching btrfs_zoned_account_meta_bg(block_group, -1) is only
called in btrfs_remove_block_group() when erasing the block group from
fs_info->block_group_cache_tree, an error in exclude_super_stripes(),
btrfs_add_new_free_space(), or btrfs_add_block_group_cache() frees cache
without decrementing the counter. Since create_chunk() recovers from
btrfs_make_block_group() failure without aborting the transaction, the
counter remains skewed for the lifetime of the mount and disables the
fast path in btrfs_zoned_meta_is_append_only().

Would it be safer to account the block group when inserting it into
fs_info->block_group_cache_tree in btrfs_add_block_group_cache() to match
the removal in btrfs_remove_block_group()?

[Severity: High]
Can btrfs_zoned_bg_is_append_only() and btrfs_zoned_meta_is_append_only()
return false for a metadata block group that is written to a sequential
zone on a device-replace target device?

On a zoned filesystem, btrfs_init_dev_replace_tgtdev() validates tgtdev
via btrfs_check_device_zone_type(), which allows replacing a regular
block device (emulated conventional zones) or a zoned device with
conventional zones at a given offset with a zoned device that has
sequential write required zones at that offset.

However, btrfs_load_block_group_zone_info() only inspects
map->stripes[i].dev when setting BLOCK_GROUP_FLAG_SEQUENTIAL_ZONE and
updating fs_info->zoned_seq_meta_bgs and fs_info->zoned_conv_meta_bgs:

fs/btrfs/zoned.c:btrfs_load_block_group_zone_info() {
	for (i = 0; i < map->num_stripes; i++) {
		ret = btrfs_load_zone_info(fs_info, i, &zone_info[i], active, map, new);
		if (ret)
			goto out;

		if (zone_info[i].alloc_offset == WP_CONVENTIONAL)
			num_conventional++;
		else
			num_sequential++;
	}

	if (num_sequential > 0)
		set_bit(BLOCK_GROUP_FLAG_SEQUENTIAL_ZONE, &cache->runtime_flags);
}

And when device replace finishes,
btrfs_dev_replace_update_device_in_mapping_tree() swaps srcdev with
tgtdev in map->stripes[i].dev without updating
BLOCK_GROUP_FLAG_SEQUENTIAL_ZONE on the affected block groups or
adjusting fs_info->zoned_seq_meta_bgs and fs_info->zoned_conv_meta_bgs:

fs/btrfs/dev-replace.c:btrfs_dev_replace_update_device_in_mapping_tree() {
		for (int i = 0; i < map->num_stripes; i++)
			if (srcdev == map->stripes[i].dev)
				map->stripes[i].dev = tgtdev;
}

If a metadata block group was backed only by conventional zones on srcdev
but maps to a sequential zone on tgtdev, both during write duplication in
handle_ops_on_dev_replace() and after btrfs_dev_replace_finishing()
completes, btrfs_zoned_bg_is_append_only() and
btrfs_zoned_meta_is_append_only() will treat the block group as
non-append-only. As a result, btrfs_clear_buffer_dirty() will skip
setting EXTENT_BUFFER_ZONED_ZEROOUT on freed dirty tree blocks and
write_meta_extent_buffer() / btrfs_check_meta_write_pointer() will issue
out-of-order writes to the sequential zone on tgtdev, causing -EIO and a
transaction abort.
