[Severity: High]
Does this code risk an ABBA deadlock?

btrfs_inode_inherit_props() holds an active transaction handle (trans) and
subsequently calls h->validate() and h->apply() with the extracted value.

For compression properties, prop_compression_validate() and
prop_compression_apply() allocate memory using kmemdup_nul() with GFP_KERNEL:

fs/btrfs/props.c:prop_compression_validate() {
    ...
	value_str = kmemdup_nul(value, len, GFP_KERNEL);
    ...
}

This allows the memory allocator to enter direct reclaim, which may attempt to
write back dirty filesystem pages or block on the very transaction currently
held.

This can be triggered here during inode creation, or when setting a btrfs
compression property via xattr (btrfs_xattr_handler_set_prop ->
btrfs_set_prop).

Since this is reachable by any local user with permissions to set xattrs or
create files in directories with inherited compression, it could render the
filesystem partially or fully unresponsive.

Should these allocations use GFP_NOFS or be wrapped in a
memalloc_nofs_save()/memalloc_nofs_restore() scope?

Note that this bug was introduced by a previous patch in this series and has
not been fixed by the end of the series.
