Can sampling BTRFS_QGROUP_RUNTIME_BIT_CANCEL_RESCAN here report "qgroup scan
cancelled" after btrfs_qgroup_rescan_worker() has already cleared
BTRFS_QGROUP_STATUS_BIT_INCONSISTENT and written the cleared status to disk?

When qgroup_rescan_leaf() finishes the last leaf (ret == 1), the loop
condition

	while (!ret && !(stopped = rescan_should_stop(fs_info)))

short-circuits on !ret without calling rescan_should_stop().  If
qgroup_mark_inconsistent() runs concurrently during that final leaf scan or
btrfs_commit_transaction(), it sets INCONSISTENT, CANCEL_RESCAN, and
NO_ACCOUNTING (causing remaining extents to be skipped).  Because ret > 0 and
CANCEL_RESCAN is not checked before updating the status flags,
btrfs_qgroup_rescan_worker() clears BTRFS_QGROUP_STATUS_BIT_INCONSISTENT and
persists it via update_qgroup_status_item(), then sees cancelled == true here
and logs "qgroup scan cancelled".

consumes CANCEL_RESCAN and logs "qgroup scan cancelled" while leaving

[Severity: Medium]
Does returning early on cancelled or stopped before checking ret < 0 suppress
the "qgroup scan failed with %pe" error message?

Most qgroup failures call qgroup_mark_inconsistent(), which unconditionally
sets BTRFS_QGROUP_RUNTIME_BIT_CANCEL_RESCAN:

fs/btrfs/qgroup.c:qgroup_mark_inconsistent() {
	set_bit(BTRFS_QGROUP_STATUS_BIT_INCONSISTENT, &fs_info->qgroup_flags);
	set_bit(BTRFS_QGROUP_RUNTIME_BIT_CANCEL_RESCAN, &fs_info->qgroup_flags);
	set_bit(BTRFS_QGROUP_RUNTIME_BIT_NO_ACCOUNTING, &fs_info->qgroup_flags);
}

If btrfs_commit_transaction() on the final leaf fails in btrfs_run_qgroups(),
or if btrfs_start_transaction() or update_qgroup_status_item() fails with
ret < 0 after a rescan is cancelled or paused, cancelled or stopped is true
 alongside ret < 0, so the worker now logs an informational cancelled/paused
message instead of btrfs_err().
