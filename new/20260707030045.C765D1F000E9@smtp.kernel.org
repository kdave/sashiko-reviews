Subject: btrfs: fix a regression where PAGECACHE_TAG_DIRTY is never cleared

This commit reverts from using folio_test_dirty() back to
folio_clear_dirty_for_io() inside extent_write_cache_pages(). This is intended
to fix a regression where PAGECACHE_TAG_DIRTY is never cleared for subpage
blocks.

[Severity: Critical]
Can this premature clearing of the dirty flag cause data loss if an early
error occurs in extent_writepage()?

By calling folio_clear_dirty_for_io() here, the folio's dirty flag is
cleared before writeback is guaranteed to start. If extent_writepage()
subsequently fails early, for example when set_folio_extent_mapped()
encounters a failure:

fs/btrfs/extent_io.c:extent_writepage() {
    ...
	ret = set_folio_extent_mapped(folio);
	if (ret < 0)
		goto done;
    ...
}

The code jumps to the done label and unlocks the folio without calling
folio_start_writeback() or folio_redirty_for_writepage().

Because the folio was already marked clean by folio_clear_dirty_for_io(),
would it remain clean and allow its data to be silently dropped when it
is reclaimed? Could this also leave the PAGECACHE_TAG_DIRTY tag permanently
leaked?

>  			}
