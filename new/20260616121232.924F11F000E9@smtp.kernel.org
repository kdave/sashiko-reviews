btrfs: deny freezing a device while it is being added

This commit adds btrfs_open_device_deny_freeze() to forbid freezing
a filesystem through a new device being added before it is fully
committed as a member. The block device freeze deny spans the
entire duration of the add operation.

[Severity: High]
This isn't a bug introduced by this patch, but does this unwind path
leave the filesystem in an inconsistent state?

For a seeding device, btrfs_commit_transaction() is called earlier
and successfully makes the new device part of the filesystem on disk.
If btrfs_attach_transaction() then fails, the code jumps to error_sysfs.

The error_sysfs label destructively tears down the in-memory device
representation, completely removing it from the in-memory lists while
it remains committed to disk. Could this desynchronization between
memory and disk lead to crashes or data corruption when subsequent
operations attempt I/O on the missing device?

[Severity: High]
This is a pre-existing issue, but is there a use-after-free risk
during this error teardown sequence?

Under the error_sysfs label, the device is unlinked from the
filesystem's device list using an RCU-safe deletion:

error_sysfs:
	...
	list_del_rcu(&device->dev_list);

Following this, the code jumps or falls through to error_free_device
which frees the device synchronously.

If btrfs_free_device() does not defer the memory deallocation via an
RCU grace period, could concurrent readers actively iterating over
the device list access the freed memory?
