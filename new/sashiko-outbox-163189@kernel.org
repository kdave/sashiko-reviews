btrfs: unwind device add when sysfs registration fails

This commit modifies btrfs_init_new_device() to check the return value
of btrfs_sysfs_add_device(). If it fails, it unwinds the device addition
instead of ignoring the error and proceeding.

[Severity: High]
Does this error path need to wait for the kobject release to complete?

If kobject_init_and_add() fails after initializing the kobject,
kobject_put() will trigger the release callback. Since the btrfs_device
struct containing this kobject is freed shortly after in the error path,
could this cause a use-after-free if the delayed release callback
executes after the device is freed?

For example, btrfs_sysfs_remove_device() handles this by calling:
    wait_for_completion(&device->kobj_unregister);

[Severity: High]
Can this error path cause a use-after-free for concurrent RCU readers?

Earlier in btrfs_init_new_device(), the device is added to the
RCU-protected list:
    list_add_rcu(&device->dev_list, &fs_devices->devices);

When btrfs_sysfs_add_device() fails, the goto error_unwind_device path
removes the device:
    list_del_rcu(&device->dev_list);

Then it falls through to error_free_device and frees it synchronously:
    btrfs_free_device(device); -> kfree(device);

Since the memory is freed without waiting for an RCU grace period (no
synchronize_rcu() or kfree_rcu() used), could concurrent RCU readers
traversing fs_devices->devices dereference the freed device?
