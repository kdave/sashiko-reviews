Subject: btrfs: use kvmalloc() for stripe buffer of scrub_stripe

This patch replaces folio array allocations with a single kvmalloc() call
for the 64K scrub stripe buffer. The new approach eliminates cross-page
handling and simplifies bio assembly and checksum verification.

[Severity: Critical]
Will this assertion trigger kernel panics if kvmalloc falls back to kmalloc
and SLUB debugging or KASAN is enabled? 

When BTRFS_STRIPE_LEN is less than or equal to KMALLOC_MAX_CACHE_SIZE (for
example, on architectures with 64K pages where BTRFS_STRIPE_LEN is exactly
one page), the allocation can be serviced by SLUB. If SLUB debugging like
redzoning or KASAN is active, the returned pointer is offset by metadata
and will not be page-aligned, causing this assertion to fail immediately.

[Severity: Critical]
Could this offset calculation cause memory corruption on non-debug builds?

If the buffer returned by kvmalloc happens to be unaligned, using
offset_in_page(offset) instead of offset_in_page(stripe->buffer + offset)
means the bio will be mapped using an offset from the start of the page
rather than the actual buffer start. This would artificially shift the IO
backwards, potentially overwriting SLUB metadata and adjacent objects instead
of writing to the allocated buffer.
