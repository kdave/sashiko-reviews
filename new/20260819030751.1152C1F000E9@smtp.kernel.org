btrfs: unlock inode and extent in caller when uring read extent fails

This commit moves the unlocking of the inode and extent on failure paths
from btrfs_uring_read_extent() into its caller. This matches the error
handling path for copy_to_user() and fixes an issue where a pages-array
allocation failure returned -ENOMEM without unlocking at all.

This isn't a bug introduced by this patch, but could the copy_to_user()
call just above this block in btrfs_uring_encoded_read() cause a deadlock?

If sqe_addr points to a memory-mapped region of the exact same Btrfs file
and extent being read, wouldn't a write page fault trigger
btrfs_page_mkwrite()?

Since the extent lock is already held by the current thread at this point
when ret == -EIOCBQUEUED, this seems like it could create an unrecoverable
self-deadlock.
