> btrfs: abort the transaction to avoid half deleted qgroup relationship
>
> In __del_qgroup_relation(), if the relationship item for (src, dst) was
> deleted successfully, but the item for (dst, src) failed to be deleted
> due to other reasons (EIO, ENOMEM etc), we just return the error without
> updating the in-memory relationship.
>
> This can lead to minor inconsistency between in-memory structures and
> on-disk metadata.
>
> E.g. the second deletion failed with ENOMEM, but the on-disk metadata
> has no such item. In this particular case we can continue deleting
> in-memory structure.
>
> Fix it by aborting the transaction if the first deletion succeeded, and
> the second deletion failed for reasons other than ENOENT.
>
> By this we still keep the best-effert deletion attempt. E.g if one
> relationship item is not found, we can still continue delete whatever
> left and remove the relationship completely.
>
> Link: https://sashiko.dev/#/bug/linux-8878868a-a948-4f35-a459-2ba8be379061
> Signed-off-by: Qu Wenruo <wqu@suse.com>

This problem wasn't introduced by this patch, but can its caller
btrfs_remove_qgroup() similarly leave a half-deleted qgroup on disk and leak
the in-memory struct btrfs_qgroup [1]?

fs/btrfs/qgroup.c:btrfs_remove_qgroup() {

	if (ret && ret != -ENOENT)

	while (!list_empty(&qgroup->groups)) {
		list = list_first_entry(&qgroup->groups,
					struct btrfs_qgroup_list, next_group);

If del_qgroup_item() succeeds (or an earlier iteration of the loop removes a
relation) and __del_qgroup_relation() then fails on its first
del_qgroup_relation_item() call, __del_qgroup_relation() returns the error
without aborting the transaction.  btrfs_remove_qgroup() jumps to out,
skipping del_qgroup_rb() and kfree(qgroup), and btrfs_ioctl_qgroup_create()
closes the transaction with btrfs_end_transaction(), allowing the partial
quota tree deletion to be committed while leaving the in-memory qgroup out
of sync.
