[Severity: Medium]
Can btrfs_can_scan_disk() race with disk registration and approve a
partitioned whole disk before its partitions have been scanned?

In __add_disk(), device_add() publishes the disk on block_class before
add_disk_final() calls disk_scan_partitions() and sets GD_ADDED:

CPU0                              CPU1
__add_disk()
  device_add(ddev)
  add_disk_final()
    bdev_add(disk->part0, ...)
    disk_scan_partitions()
      ...
                                  btrfs_scan_all_devices()
                                    btrfs_can_scan_disk(disk, bdev)
                                      xa_for_each_start(&disk->part_tbl, ...)
                                      --> sees empty part_tbl, returns true
                                    btrfs_scan_one_device()
      add_partition()
    set_bit(GD_ADDED, &disk->state)

While check_partition() is doing synchronous I/O to read the partition
table, disk->part_tbl is still empty, so btrfs_can_scan_disk() returns true
for the whole disk.  btrfs_scan_one_device() then waits on disk->open_mutex
and scans the whole disk once disk_scan_partitions() finishes, registering
the whole disk instead of the partition if a btrfs superblock sits at
64 KiB (or failing with -ENXIO if opened between device_add() and
bdev_add()).  Checking test_bit(GD_ADDED, &disk->state) in
btrfs_can_scan_disk() would skip disks that have not finished registration.

[Severity: Low]
Will formatting path with dev_name(dev) fail to open block devices whose
names contain '/' or use a custom devnode callback?

When a block driver uses '/' in disk->disk_name (such as cciss, ida, or
aoe), kobject_set_name_vargs() replaces '/' with '!' in dev_name(dev),
whereas devtmpfs_create_node() calls device_get_devnode() to translate '!'
back to '/' when creating the node under /dev.  Using dev_name(dev)
directly produces a path with '!' that fails in btrfs_scan_one_device()
with -ENOENT; using "/dev/%pg" with bdev (or device_get_devnode()) matches
the devtmpfs path.
