btrfs: remove the trailing zeros from compressed inline extent

This commit restores the previous behavior of passing the file range up to
the inode size into btrfs_compress_bio() rather than the sector size. This
avoids trailing zeros in compressed inline extents and improves the
compression ratio, which was previously impacted by a regression in the lzo
compression path.

[Severity: High]
Could passing an unvalidated i_size here instead of blocksize lead to out
of bounds folio accesses or log spam?

The 64-bit i_size is passed as the length for inline extent compression, but
looking at the signature of btrfs_compress_bio() in fs/btrfs/compression.c:

struct compressed_bio *btrfs_compress_bio(struct btrfs_inode *inode,
                                          u64 start, u32 len, 
                                          unsigned int type, ...

The 64-bit size is silently truncated to a u32 length. If a user extends
the file size to a multiple of 4GB, the length becomes 0, which can trigger
an ASSERT(len) panic in debug builds.

Furthermore, if the file size is very large (e.g., after a sparse write at
1GB and a single sector write at offset 0), the compression loop will
attempt to fetch uninstantiated and unlocked folios past the dirty range.
This results in the following rate-unlimited log spam in
btrfs_compress_filemap_get_folio():

btrfs_crit(inode->root->fs_info,
           "failed to get page cache, root %lld ino %llu file offset %llu",
           ...

Since an unprivileged user can trigger this via standard POSIX file
operations (write, fsync), this looks like a potential DoS vector.

Because can_cow_file_range_inline() eventually rejects inline extents
larger than the sector size anyway, would it be safer to bound the
compression input length to the locked sector size instead of the
unbounded i_size?
