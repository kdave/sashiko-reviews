block: do not warn when doing greedy allocation in folio_alloc_greedy()

This commit adds the __GFP_NOWARN flag to folio_alloc() inside
folio_alloc_greedy() for high-order allocations. This prevents unnecessary
allocation failure warnings since the function naturally retries with
smaller orders on failure.

[Severity: High]
This isn't a bug introduced by this patch, but does the malformed bio
construction in bio_iov_iter_bounce_read() cause bio_iov_iter_align_down()
to corrupt refcounts and leak pinned pages?

When an unaligned read triggers bio_iov_iter_bounce_read(), it places a
kernel bounce folio at index 0 and user bvecs starting at index 1, while
bio->bi_vcnt only tracks the number of user bvecs:

block/bio.c:bio_iov_iter_bounce_read() {
        bvec_set_folio(&bio->bi_io_vec[0], folio, bio->bi_iter.bi_size, 0);
        if (iov_iter_extract_will_pin(iter))
                bio_set_flag(bio, BIO_PAGE_PINNED);
        return bio_iov_iter_align_down(bio, iter, minsize - 1);
}

It then calls bio_iov_iter_align_down(), which incorrectly assumes the bvecs
occupy indices 0 through bi_vcnt - 1:

block/bio.c:bio_iov_iter_align_down() {
        struct bio_vec *bv = &bio->bi_io_vec[bio->bi_vcnt - 1];

        if (nbytes < bv->bv_len) {
                bv->bv_len -= nbytes;
                break;
        }

        if (bio_flagged(bio, BIO_PAGE_PINNED))
                unpin_user_page(bv->bv_page);
}

Could this access the wrong index due to the missing offset? If bi_vcnt is
1, it appears this would truncate the wrong bvec and incorrectly unpin the
kernel bounce folio, corrupting its refcount.

[Severity: High]
This is a pre-existing issue, but do bounce folios leak when
bio_iov_iter_align_down() drops bvecs or returns an error?

If bio_iov_iter_align_down() drops all bvecs because the total length is
less than minsize, it returns -EFAULT. Both bio_iov_iter_bounce_read() and
bio_iov_iter_bounce_write() directly return this error:

block/bio.c:bio_iov_iter_bounce_read() {
        ...
        return bio_iov_iter_align_down(bio, iter, minsize - 1);
}

block/bio.c:bio_iov_iter_bounce_write() {
        ...
        return bio_iov_iter_align_down(bio, iter, minsize - 1);
}

Since the caller will go to the error path and call bio_put() without
freeing the attached folios, does this leak the kernel-allocated folios?

Furthermore, if bio_iov_iter_align_down() succeeds but decrements bi_vcnt
(dropping a bvec entirely), would the dropped folio also leak because
bio_free_folios() only iterates up to the modified bi_vcnt?
