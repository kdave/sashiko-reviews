[Severity: High]
This isn't a bug introduced by this patch, but while we are addressing NOWAIT
direct I/O, does the bio allocation still risk sleeping?

In iomap_dio_alloc_bio(), we unconditionally use GFP_KERNEL:

fs/iomap/direct-io.c:iomap_dio_alloc_bio() {
    ...
    return bio_alloc(iter->iomap.bdev, nr_vecs, opf, GFP_KERNEL);
}

Similarly, in iomap_dio_bio_iter_one(), fscrypt context allocation uses
GFP_KERNEL:

    fscrypt_set_bio_crypt_ctx(bio, iter->inode, pos, GFP_KERNEL);

Since GFP_KERNEL includes __GFP_DIRECT_RECLAIM, won't these memory
allocations block waiting for direct reclaim if the memory pool is
exhausted, thereby breaking the non-blocking guarantee of IOMAP_NOWAIT?

[Severity: High]
This is a pre-existing issue, but I noticed the bio operational flags
might be missing REQ_NOWAIT for non-polled requests.

In iomap_dio_bio_iter(), bio_opf is initialized without REQ_NOWAIT:

    blk_opf_t bio_opf = REQ_SYNC | REQ_IDLE;

And the only place where REQ_NOWAIT seems to be conditionally added is for
polled requests in iomap_dio_submit_bio():

    if ((iocb->ki_flags & IOCB_HIPRI) && !is_sync_kiocb(iocb)) {
        bio_set_polled(bio, iocb);
    }

If IOMAP_NOWAIT is specified but polling is not requested (!IOCB_HIPRI),
does iomap fail to add the REQ_NOWAIT flag to the bio? Could this cause
the block layer to sleep waiting for tags or hardware queues to drain?

[Severity: High]
This is also a pre-existing issue, but does the error handling during
tail zeroing overwrite the error code?

If iomap_dio_bio_iter_one() returns a negative error code like -ENOMEM,
the loop breaks:

    ret = iomap_dio_bio_iter_one(iter, dio, pos, alignment, bio_opf);
    if (unlikely(ret < 0)) {
        break;
    }

Then, if tail zeroing is required, iomap_dio_zero() is called:

    if (need_zeroout || ...) {
        pad = pos & (fs_block_size - 1);
        if (pad)
            ret = iomap_dio_zero(iter, dio, pos, fs_block_size - pad);
    }

If iomap_dio_zero() succeeds and returns 0, won't it overwrite the original
error code stored in ret? If the failure occurred on the first iteration,
could the function silently return 0 instead of accurately reporting the
error?
