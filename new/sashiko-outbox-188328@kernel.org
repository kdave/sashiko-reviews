This commit marks data block groups being reclaimed with
BLOCK_GROUP_FLAG_ZONED_RECLAIM and resets their zones in place after
relocation so they can be reused as the next data relocation target instead

btrfs_discard_extent() -> do_discard_extent(), which skipped missing devices

btrfs_dev_is_sequential() before issuing REQ_OP_ZONE_RESET, followed by

With this change, btrfs_zoned_reuse_reclaimed_bg() drops both read-only

On a degraded multi-device mount where a stripe's device is missing
(stripe->dev->bdev == NULL) while the allocation profile still matches
bg->flags (for example, a 3-device RAID1 with 1 missing device), won't

[Severity: High]
Can a concurrent scrub or unused-block-group reset race with
btrfs_zoned_reuse_reclaimed_bg() after space_info->lock and bg->lock are
dropped?

In btrfs_relocate_chunk(), btrfs_scrub_continue(fs_info) is called right
after btrfs_relocate_block_group() and before btrfs_relocate_chunk_finish()
calls btrfs_zoned_reuse_reclaimed_bg(bg). Because scrub does not acquire
BTRFS_EXCLOP_BALANCE or fs_info->reclaim_bgs_lock, scrub_enumerate_chunks()
can run concurrently once bg->lock is dropped after
btrfs_zoned_can_reuse_bg(bg):

1. If scrub_enumerate_chunks() calls btrfs_inc_block_group_ro(bg, ...) before
   the two btrfs_dec_block_group_ro(bg) calls, bg->ro goes from 2 to 3 and is
   then decremented twice to 1 (without restoring bg->zone_unusable).
   zoned_reset_bg_in_place() then issues blkdev_zone_mgmt(...,
   REQ_OP_ZONE_RESET, ...) on the device stripes before acquiring bg->lock
   and checking if (bg->ro). That resets the hardware write pointer to 0
   while scrub holds bg read-only, and then returns early with *reclaimed = 0
   while bg->alloc_offset remains bg->zone_capacity.

2. While zoned_reset_bg_in_place() is sleeping in blkdev_zone_mgmt() with
   bg->ro == 0 and bg->zone_unusable == bg->length, scrub_enumerate_chunks()
   can increment and decrement bg->ro on the empty block group, observe
   !cache->ro && cache->reserved == 0 && cache->used == 0, and call
   btrfs_mark_bg_unused(bg) to place bg back onto fs_info->unused_bgs. A
   concurrent flush_space(..., RESET_ZONES) ->
   btrfs_reset_unused_block_groups() can then pop bg from fs_info->unused_bgs
   and run a second concurrent zoned_reset_bg_in_place(bg, ...), which can
   either issue a second REQ_OP_ZONE_RESET after bg was already promoted or
   read *reclaimed = bg->alloc_offset == 0 after the first call zeroes
   bg->alloc_offset and hit ASSERT(*reclaimed == bg->zone_capacity) in
   zoned_reset_bg_in_place().

[Severity: High]
When btrfs_reclaim_block_group() relocates a block group whose live extents
only partially fill the target fs_info->data_reloc_bg, won't
data_race(!fs_info->data_reloc_bg) evaluate to false here?

During btrfs_relocate_block_group(), live extents from bg are written into
the active relocation block group (fs_info->data_reloc_bg) in reloc_sinfo
(fs_info->data_sinfo->sub_group[0]). At the end of
btrfs_relocate_block_group(), btrfs_zone_finish() is called on the source
block group bg rather than fs_info->data_reloc_bg, and on ordered extent
completion btrfs_zoned_release_data_reloc_bg() only clears
BLOCK_GROUP_FLAG_ZONED_DATA_RELOC while btrfs_clear_data_reloc_bg() is only
called from do_zone_finish() if the destination zone was filled to capacity.

Thus, whenever the relocated extents do not completely fill the current
fs_info->data_reloc_bg, fs_info->data_reloc_bg is still non-zero when
btrfs_relocate_chunk_finish() calls btrfs_zoned_reuse_reclaimed_bg(bg):

1. data_race(!fs_info->data_reloc_bg) is false (and btrfs_set_data_reloc_bg()
   also refuses to set a new data_reloc_bg while fs_info->data_reloc_bg is
   non-zero).

2. zoned_reset_bg_in_place(bg, false, &reclaimed) resets bg in place, leaves
   bg in fs_info->data_sinfo, and calls btrfs_return_free_space(data_sinfo,
   *reclaimed), handing the space to regular data allocations in data_sinfo
   instead of reloc_sinfo.

3. btrfs_zoned_reuse_reclaimed_bg() still returns true, so
   btrfs_relocate_chunk_finish() skips btrfs_remove_chunk() and does not free
   bg's underlying device zones back to unallocated device space (nor does
   data_sinfo->total_bytes decrease below old_total in
   btrfs_reclaim_block_group()).

When the next block group in btrfs_reclaim_block_groups() has more live data
than the remaining space in the partially filled fs_info->data_reloc_bg, data
relocation allocations (which only search reloc_sinfo and allocate new chunks
from unallocated device space via btrfs_chunk_alloc(trans, reloc_sinfo, ...))
cannot use the block group that was left in data_sinfo and will fail with
-ENOSPC if no unallocated device zones remain.
