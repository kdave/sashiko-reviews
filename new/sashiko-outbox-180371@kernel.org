[Severity: Medium]
Should zoned_bg_reclaimable() also check that bg->used > 0 and that
bg->reserved and bg->pinned are zero?

During flush_space() -> btrfs_zoned_reclaim_sweep(),
zoned_sweep_space_info() treats any full block group where
zoned_bg_reclaimable() returns true as a relocation candidate and credits
its bg_garbage toward the two-zone garbage target in
btrfs_zoned_reclaim_sweep().

However, when btrfs_reclaim_block_groups() subsequently calls
btrfs_reclaim_block_group() in fs/btrfs/block-group.c, it skips block
groups with active reservations, pinned bytes, or zero used bytes without
relocating them:

fs/btrfs/block-group.c:btrfs_reclaim_block_group() {
    ...
	if (bg->reserved || bg->pinned || bg->ro) {
		spin_unlock(&bg->lock);
		spin_unlock(&space_info->lock);
		up_write(&space_info->groups_sem);
		return 0;
	}

	if (bg->used == 0) {
		if (!btrfs_test_opt(fs_info, DISCARD_ASYNC))
			btrfs_mark_bg_unused(bg);
		spin_unlock(&bg->lock);
		spin_unlock(&space_info->lock);
		up_write(&space_info->groups_sem);
		return 0;
	}
    ...
}

For a full block group where all extents have been freed (bg->used == 0
and zoned_bg_garbage(bg) == bg->zone_capacity), or one with bg->pinned > 0
or bg->reserved > 0, zoned_bg_reclaimable() still returns true. In
addition, if an empty block group is already linked on
fs_info->unused_bgs, calling btrfs_mark_bg_to_reclaim() in
zoned_sweep_space_info() is a no-op, yet garbage is still incremented by
bg_garbage.

Can counting these non-relocatable block groups toward the two-zone target
prevent btrfs_zoned_reclaim_sweep() from queuing actual relocatable
candidates from cands[], causing RECLAIM_ZONES to reclaim nothing and fail
waiting data tickets with -ENOSPC?

[Severity: Medium]
Should the reclaim threshold in zoned_sweep_space_info() be calculated
against bg->zone_capacity instead of bg->length?

On zoned devices where zone_capacity is smaller than zone_size, the region
[bg->zone_capacity, bg->length) is never writable and is permanently
accounted in bg->zone_unusable, so bg->used can never exceed
bg->zone_capacity.

In fs/btrfs/free-space-cache.c, __btrfs_add_free_space_zoned() scales the
reclaim threshold against block_group->zone_capacity (see commit
d8da0e85673a ("btrfs: zoned: tweak reclaim threshold for zone capacity")):

fs/btrfs/free-space-cache.c:__btrfs_add_free_space_zoned() {
    ...
	reclaimable_unusable = block_group->zone_unusable -
			       (block_group->length - block_group->zone_capacity);
	/* All the region is now unusable. Mark it as unused and reclaim */
	if (block_group->zone_unusable == block_group->length) {
		btrfs_mark_bg_unused(block_group);
	} else if (bg_reclaim_threshold &&
		   reclaimable_unusable >=
		   mult_perc(block_group->zone_capacity, bg_reclaim_threshold)) {
		btrfs_mark_bg_to_reclaim(block_group);
	}
    ...
}

By passing bg->length to mult_perc() here, the threshold is inflated by
the unusable slack between bg->zone_capacity and bg->length. On ZNS
devices where zone_capacity is at or below thresh_pct percent of
bg->length (for example, with the default 75% threshold), wouldn't
bg->used < mult_perc(bg->length, thresh_pct) evaluate to true for every
full block group with non-zero garbage, queuing all of them
unconditionally and bypassing the candidate sorting and two-zone target?
