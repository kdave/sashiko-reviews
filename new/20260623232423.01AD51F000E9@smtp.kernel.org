extent_buffer readahead should not be able to painfully stall a
search_slot and hog tree locks by getting stuck in direct reclaim.

This commit updates btrfs_readahead_tree_block to use NOWAIT semantics
for extent buffer preallocation. The goal is to prevent the readahead
thread from stalling in direct reclaim while holding tree locks.

[Severity: High]
This is a pre-existing issue, but does this patch fully prevent the
stalls in direct reclaim it aims to address?

While extent buffer allocation will now correctly avoid blocking by using
supports_nowait, btrfs_readahead_tree_block later makes the following
call on the newly allocated buffer:

    ret = read_extent_buffer_pages_nowait(eb, 0, &check);

Since read_extent_buffer_pages_nowait internally allocates a bio via
btrfs_bio_alloc (which hardcodes GFP_NOFS) and submits it without
REQ_NOWAIT, couldn't the readahead thread still stall waiting for memory
or block layer congestion?

Under memory pressure, this might still lead to hogging tree locks while
stuck in direct reclaim, leaving the primary goal of the patch unfulfilled.
