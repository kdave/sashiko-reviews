btrfs: fix false IO failure after falling back to buffered write

This commit resolves an issue where a false I/O failure is reported when a
direct I/O short write falls back to buffered I/O. It introduces a helper to
mark the unsubmitted direct I/O ordered extent as truncated, allowing proper
reclaim without setting an error on the address space mapping.

[Severity: Critical]
By passing uptodate=true to btrfs_finish_ordered_extent() here, does this
prevent setting the BTRFS_INODE_COW_WRITE_ERROR flag on the inode?

When falling back to buffered I/O, the direct I/O path will unlock the inode.
If a concurrent fast fsync occurs, won't it skip synchronously waiting for
the ordered extents to complete because BTRFS_INODE_COW_WRITE_ERROR isn't set?

Could this cause btrfs_sync_file() to immediately log the unwritten extent
map (found in modified_extents) into the log tree, potentially exposing stale
data on crash replay if it happens before btrfs_finish_one_ordered() drops
