[Severity: High]
This isn't a bug introduced by this patch, but since this patch modifies
compress_file_range() in fs/btrfs/inode.c, does this function have a
read-modify-write race condition?

Further down in compress_file_range(), under the mark_incompressible label:

	if (!btrfs_test_opt(fs_info, FORCE_COMPRESS) && !inode->prop_compress)
		inode->flags |= BTRFS_INODE_NOCOMPRESS;

This non-atomic bitwise-or operation modifies inode->flags without holding
inode_lock() or spin_lock(&inode->lock). Background writeback executes
compress_file_range() asynchronously on a worker thread.

Concurrently, if an unprivileged user writes to a file to trigger background
writeback, and an administrator runs chattr +i to secure it,
btrfs_fileattr_set() in fs/btrfs/ioctl.c updates the flags while holding
inode_lock():

	inode->flags = inode_flags;
	btrfs_update_inode_mapping_flags(inode);
	btrfs_sync_inode_flags_to_i_flags(inode);
	inode_inc_iversion(&inode->vfs_inode);
	inode_set_ctime_current(&inode->vfs_inode);
	ret = btrfs_update_inode(trans, inode);

If compress_file_range() reads the flags before chattr updates them, and
writes them back after chattr stores the new flags, can important security
flags like the immutable flag be silently overwritten?

It appears that btrfs_fileattr_set() would then sync this state to the virtual
file system and persist it to disk, resulting in a loss of those security
flags.
