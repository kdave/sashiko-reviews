[Severity: High]
This isn't a bug introduced by this patch, but does this custom data
allocation leak if the async request is cancelled?

If the async request is punted to io-wq and later cancelled (for example,
due to task exit or ring destruction), io-wq will fail it with -ECANCELED.

Because this code allocates data and stores it in bc->data instead of using
io_uring's native async data lifecycle via req->async_data, io_uring's
generic cleanup in io_clean_op() won't free it:

fs/btrfs/ioctl.c:btrfs_uring_encoded_read() {
    ...
    data = kzalloc_obj(*data, GFP_NOFS);
    ...
    bc->data = data;
    ...
}

Could this leave the data structure permanently leaked? This pattern also
appears to affect btrfs_uring_encoded_write().

[Severity: High]
This is a pre-existing issue, but is there a risk of self-deadlock
during copy_to_user() slightly earlier in this function?

If btrfs_encoded_read() queues the read to execute asynchronously, it
returns -EIOCBQUEUED while leaving both the VFS i_rwsem and the Btrfs
extent lock held. Immediately following this, copy_to_user() is called:

fs/btrfs/ioctl.c:btrfs_uring_encoded_read() {
    ...
    ret = btrfs_encoded_read(...);
    // ret is -EIOCBQUEUED, locks remain held

    if (copy_to_user(sqe_addr + copy_end, ...)) {
        if (ret == -EIOCBQUEUED) {
            btrfs_unlock_extent(...);
            btrfs_inode_unlock(...);
        }
    ...
}

If a user space application passes a pointer that targets a memory-mapped
region of the exact same file, the copy_to_user() call will trigger a page
fault. The VFS fault handler invokes btrfs_page_mkwrite(), which attempts
to acquire the inode's i_rwsem.

Since rw_semaphores and extent locks are not reentrant, won't this cause
the fault handler to block indefinitely waiting for the lock that the
faulting thread already holds?
