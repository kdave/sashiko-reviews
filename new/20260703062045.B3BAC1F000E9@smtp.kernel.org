btrfs: zoned: fix deadlock between metadata writeback and transaction commit

[Severity: High]
This isn't a bug introduced by this patch, but does this still leave a
latent transaction state deadlock between fsync and the transaction commit
thread?

When btrfs_sync_file() starts a transaction, it acquires an extwriter
reference. If it then calls btrfs_sync_log(), triggering tree-log writeback,
btree_writepages() calls check_bg_is_active().

To activate the zone, btrfs_zone_finish_one_bg() is called, which leads to
btrfs_inc_block_group_ro().

In fs/btrfs/block-group.c:btrfs_inc_block_group_ro():

	if (test_bit(BTRFS_TRANS_DIRTY_BG_RUN, &trans->transaction->flags)) {
		// ...
		ret = btrfs_wait_for_commit(fs_info, transid);

This blocks the fsync thread on btrfs_wait_for_commit().

Concurrently, the transaction commit thread sets BTRFS_TRANS_DIRTY_BG_RUN
and blocks waiting for extwriter_counter to reach 0:

In fs/btrfs/transaction.c:btrfs_commit_transaction():

	wait_event(cur_trans->writer_wait,
		   extwriter_counter_read(cur_trans) == 0);

Could this sequence cause a system hang on zoned filesystems during fsync?

This is a pre-existing issue, but I have a question about the branch
immediately following this code in check_bg_is_active().

When dropping zoned_meta_io_lock in the active_bg pivot path, is it possible
for concurrent threads to cause a use-after-free on the tgt block group?

If thread A reads tgt = *active_bg and drops the lock without taking a local
reference, could thread B concurrently enter check_bg_is_active() and assign
the same tgt pointer?

If thread A finishes its asynchronous work, re-acquires the lock, and calls
btrfs_put_block_group(tgt), and the block group was concurrently removed,
this could drop the last reference and free the block group memory while
thread B is still executing wait_eb_writebacks(tgt) or do_zone_finish(tgt).

Can this memory corruption occur under heavy concurrent metadata writeback?
