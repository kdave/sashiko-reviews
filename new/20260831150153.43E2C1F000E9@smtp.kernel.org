    btrfs: validate properties before setting them

We set the xattr and then attempt to apply the property. If the apply
fails we then attempt to delete the xattr to avoid an inconsistency.
However we don't verify if the deletion succeed, so if it fails we
leave an inconsistency between the state in the btree and the in-memory
inode.

[Severity: High]
Will this new validation step trigger an unintended transaction abort
in the ioctl path?

If a user creates a file on a mount with -o nodatasum (which sets
BTRFS_INODE_NODATASUM without NODATACOW), and then calls ioctl(FS_IOC_SETFLAGS)
to set the compression flag, handler->validate() (prop_compression_validate())
returns -EINVAL because btrfs_inode_can_compress() returns false.

This -EINVAL is then returned to the caller in fs/btrfs/ioctl.c:
btrfs_fileattr_set(), which treats it as a fatal error since it is inside an
active transaction:

fs/btrfs/ioctl.c:btrfs_fileattr_set() {
    ...
	if (comp) {
		ret = btrfs_set_prop(trans, inode, "btrfs.compression",
				     comp, strlen(comp), 0);
		if (unlikely(ret)) {
			btrfs_abort_transaction(trans, ret);
			goto out_end_trans;
		}
	}
    ...
}

Could an unprivileged user with write access to their own file exploit this to
crash the filesystem by triggering a transaction abort?
