btrfs: zoned: flush active metadata block group at btree_writepages() start

This patch flushes active metadata and system block groups at the start of
btree_writepages() on zoned filesystems. It aims to prevent transaction
aborts with -EAGAIN during block group pivoting when the active block group
still has unsent IO.

[Severity: High]
Does this prematurely abort the flush if btrfs_check_meta_write_pointer()
returns -EBUSY?

If another thread concurrently writes an extent buffer in the active block
group, btrfs_check_meta_write_pointer() will return -EBUSY. By aborting
the entire flush operation on any non-zero return, the remaining unwritten
dirty extent buffers in the active block group will be left unflushed. This
causes the later pivot in the main loop to fail with unsent IO and abort
the transaction with -EAGAIN, circumventing the fix intended by this patch.

Should we skip the already-written buffer and continue here, similar to the
handling in the main btree_writepages() loop?

> +				eb_batch_release(&batch);
> +				return;
> +			}
> +
> +			if (!lock_extent_buffer_for_io(eb, wbc))
> +				continue;
> +
> +			if (ctx->zoned_bg)
> +				ctx->zoned_bg->meta_write_pointer += eb->len;

[Severity: High]
Is a call to btrfs_schedule_zone_finish_bg() missing here?

In the main loop of btree_writepages(), btrfs_schedule_zone_finish_bg() is
called to mark the last extent buffer when a block group reaches its
capacity. Because flush_active_meta_bg() duplicates the write submission
logic but omits scheduling the zone finish, the dirty tags for these buffers
will be cleared. The main loop will then skip these extent buffers, and the
zone will never be scheduled for finishing. Could this lead to open/active
zone leaks and eventual mount or allocation failures?
