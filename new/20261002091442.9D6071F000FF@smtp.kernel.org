btrfs: zoned: requeue block group if zone reset bails out

This commit modifies btrfs_reset_unused_block_groups() to requeue a block group
back to fs_info->unused_bgs if the zone reset operation fails. It adds the
block group to a temporary retry_list on failure, then splices it back to the
unused_bgs list at the end of the function.

[Severity: High]
Does this code corrupt the list if the block group was concurrently added to
another list?

While the block group is unlocked during the slow I/O (blkdev_zone_mgmt),
could the periodic reclaim worker iterate block groups, call
btrfs_mark_bg_to_reclaim(bg), and successfully link the empty bg->bg_list into
fs_info->reclaim_bgs?

If this underlying I/O fails, the error path jumps to requeue and blindly
calls list_add_tail() on a stack-allocated list head (retry_list):
