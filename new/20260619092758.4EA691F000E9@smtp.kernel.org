[Severity: High]
Does enabling RAID56 here expose an arithmetic underflow in zoned allocations?

Looking at btrfs_load_block_group_raid56() in fs/btrfs/zoned.c,
bg->alloc_offset is calculated from the sum of all zone write pointers:

fs/btrfs/zoned.c:btrfs_load_block_group_raid56() {
        ...
        u64 row_bytes = (u64)map->num_stripes << BTRFS_STRIPE_LEN_SHIFT;
        u64 nr_rows = div64_u64(wp_sum + row_bytes - 1, row_bytes);

        bg->alloc_offset = wp_sum -
                (((u64)nr_rows * nr_parity) << BTRFS_STRIPE_LEN_SHIFT);
        ...
}

If a crash occurs after writing a small amount of data but before the parity
stripe's write pointer is advanced, could wp_sum be arbitrarily small?

If wp_sum is smaller than the subtracted full parity capacity, this
calculation would underflow, resulting in an alloc_offset near U64_MAX.

Would this cause btrfs_load_block_group_zone_info() to detect an impossibly
large offset and fail the block group load with -EIO, rendering the
filesystem unmountable and bypassing recovery mechanisms?


[Severity: Critical]
This is a pre-existing issue, but does enabling RAID56 for the stripe-tree
expose a transaction use-after-free and double-free on memory allocation
failure?

If kzalloc() fails in btrfs_insert_one_raid_extent(), it prematurely ends
the transaction:

fs/btrfs/raid-stripe-tree.c:btrfs_insert_one_raid_extent() {
        ...
        stripe_extent = kzalloc(item_size, GFP_NOFS);
        if (unlikely(!stripe_extent)) {
                btrfs_abort_transaction(trans, -ENOMEM);
                btrfs_end_transaction(trans);
                return -ENOMEM;
        }
        ...
}

This frees the transaction handle and returns -ENOMEM to callers like
btrfs_finish_one_ordered(). The caller's error path then unconditionally
accesses the freed trans pointer:

fs/btrfs/inode.c:btrfs_finish_one_ordered() {
        ...
        ret = btrfs_insert_raid_extent(trans, ordered_extent);
        if (ret)
                goto out;
        ...
out:
        if (ret < 0 && trans)
                btrfs_abort_transaction(trans, ret);

        if (trans)
                btrfs_end_transaction(trans);
        ...
}

Will this result in btrfs_abort_transaction() accessing a freed pointer,
followed by a double-free when btrfs_end_transaction() is called again?
