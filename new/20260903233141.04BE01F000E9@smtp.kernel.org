loop: Fix NULL pointer dereference in lo_rw_aio()

This commit introduces a grace period for flushing outstanding I/O by deferring
the loop device teardown to a workqueue during lo_release(). This is intended
to avoid lockdep warnings when flushing I/O without holding disk->open_mutex.

[Severity: High]
Does deferring the teardown to a workqueue introduce a userspace ABI
regression here?

By scheduling the teardown asynchronously instead of running it synchronously
in lo_release(), the final close() on the loop device will return to userspace
before the backing file is actually released via fput().

Could subsequent userspace operations interacting with the backing file, such
as unmounting a layered filesystem, fail spuriously with -EBUSY? The commit
message mentions that this asynchronous approach was previously reverted for
breaking userspace tests like xfs/259; does re-introducing this queue_work()
call also re-introduce that regression?
