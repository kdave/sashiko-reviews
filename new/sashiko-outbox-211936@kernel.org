commit d554a66f400dd27d23c7001cdc25c192a503fc36
Author: Qu Wenruo <wqu@suse.com>

> btrfs: do not unwind a committed device in btrfs_init_new_device()
>
> Sashiko reported an use-after-free bug during error handling of
> btrfs_init_new_device(), that error from btrfs_attach_transaction() can
> cause use-after-free:
>
>  btrfs_init_new_device()
>  |-btrfs_commit_transaction()
>  | ^^^ device is now in the chunk tree, chunks are allocated on it
>  |     and the fsid is changed
>  |
>  |-mutex_unlock(&uuid_mutex);
>  | ^^^ uuid_mutext unlocked.
>  |
>  |-btrfs_attach_transaction()
>  | ^^^ fails with -ENOMEM for allocation failure or -EROFS for
>  |     aborted transaction.
>  |
>  \-goto error_sysfs
>    |-btrfs_sysfs_remove_device()
>    |-list_del_rcu(&device->dev_list)
>    |
>    |-btrfs_rollback_sprout()
>    | ^^^ asserts uuid_mutex, which is not held anymore
>    |
>    \-btrfs_free_device()
>      ^^^ chunk maps still point to the freed device
>
> Since the device can not be unwound once committed, do not go through
> the unwind path. We have no transaction handle to abort, so call
> btrfs_handle_fs_error() to force the fs read-only (a no-op if it
> already is), release the freeze protection and return the error.
>
> Also let the -ENOENT and attach failure exits run btrfs_forget_devices()
> and update_dev_time() like the success path, as the device is committed.
>

[Severity: Medium]
This problem wasn't introduced by this patch, but does btrfs_rm_device() leak
the freeze-deny reference on device->bdev [1] when
btrfs_remove_dev_stat_item() fails?

fs/btrfs/volumes.c:btrfs_rm_device() {
	...
	if (device->bdev) {
		ret = bdev_deny_freeze(device->bdev);
		if (ret)
			return ret;
	}
	...
	ret = btrfs_rm_dev_item(trans, device);
	if (unlikely(ret)) {
		...
		btrfs_abort_transaction(trans, ret);
		btrfs_end_transaction(trans);
		if (device->bdev)
			bdev_allow_freeze(device->bdev);
		return ret;
	}

	ret = btrfs_remove_dev_stat_item(trans, device->devid);
	if (unlikely(ret)) {
		btrfs_abort_transaction(trans, ret);
		btrfs_end_transaction(trans);
		return ret;
	}
	...
}

Unlike the btrfs_rm_dev_item() error path right above it, the error branch
for btrfs_remove_dev_stat_item() returns without calling
bdev_allow_freeze(device->bdev).  Because unmount closes remaining member
devices via btrfs_close_bdev() without calling bdev_allow_freeze(),
bd_fsfreeze_count stays permanently elevated and later attempts to freeze the
block device fail with -EBUSY.

[1] https://sashiko.dev/#/bug/linux-05adc2aa-31a7-40cc-8073-d1a99e4d7a31
