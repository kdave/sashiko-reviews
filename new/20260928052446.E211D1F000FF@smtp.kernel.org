btrfs: write back a folio extent-by-extent instead of block-by-block

This commit optimizes folio writeback to use an extent-by-extent submission
approach rather than a block-by-block iteration. It introduces new helpers
to iterate through ordered extents beyond EOF and to find the next contiguous
write range. The write sector submission logic is also open-coded for better
control over each range.

[Severity: High]
Can this cause an integer underflow if there is a gap in ordered extents?

If an ordered extent creation previously failed, btrfs_lookup_first_ordered_range()
could return an ordered extent that starts strictly after cur. If
ordered->file_offset > cur, the subtraction cur - ordered->file_offset will
underflow to a large positive value.

On production builds where the ASSERT is compiled out, min() would then
leave ordered->truncated_len unmodified instead of correctly truncating it
to zero. Could this result in metadata corruption by leaving an ordered
extent beyond EOF?

[Severity: High]
Does this error path clean up and finish ordered IO for the entire cur_len
chunk rather than just a single block?

If find_next_write_range() finds a multi-block contiguous dirty range of
size cur_len, and the first block lacks an ordered extent, the error path
clears dirty and writeback state and manually finishes ordered IO for the
entire cur_len chunk.

However, since the loop only advances cur by blocksize, will the remaining
cur_len - blocksize range be erroneously processed again in the next
iterations?

Any valid ordered extents in that remaining range would have IO submitted
and be completed a second time upon IO completion. This could trigger an
underflow of bytes_left and double-queue the completion work, potentially
causing workqueue list or ordered tree corruption.

Should this only clean up blocksize instead of cur_len, or should it advance
cur by cur_len?
