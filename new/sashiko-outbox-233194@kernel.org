[Severity: Medium]
If zoned_reset_bg_in_place() is called on a block group in reloc_sinfo
and it does not become data_reloc_bg, does bg remain stranded in
reloc_sinfo?

When promote is false, btrfs_return_free_space(space_info, *reclaimed)
above has already granted the reclaimed space to any tickets waiting on
reloc_sinfo before reaching this else-if block, so
btrfs_inc_block_group_ro_notrans(bg) fails with -ENOSPC and bg cannot be
moved to data_sinfo.  Similarly, when promote is true on a reloc_sinfo
block group and btrfs_set_data_reloc_bg() returns false because
fs_info->data_reloc_bg was set concurrently, migrate is false inside
btrfs_set_data_reloc_bg() and this else-if branch is skipped, leaving bg
with bg->alloc_offset == 0 stranded in reloc_sinfo where neither regular
data writes nor relocation (while another data_reloc_bg is active) can
use it.

When zoned_reset_bg_in_place() promotes the reset block group to

Promoting bg moves it out of data_sinfo into reloc_sinfo without returning
any free space to data_sinfo or advancing data_sinfo->tickets_id.  If bg
was the only unused block group (or satisfied num_bytes), RESET_ZONES
finishes without granting any data_sinfo tickets, and because RESET_ZONES
runs after RECLAIM_ZONES in data_flush_states[],
do_async_reclaim_data_space() when data_sinfo->full is true proceeds
to maybe_fail_all_tickets() and fails waiting data writes with -ENOSPC
without retrying RECLAIM_ZONES using the new data_reloc_bg.
