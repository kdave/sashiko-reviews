[Severity: High]
Will cache invalidation completely abort here if there is a pending or
concurrent writeback error?

If a directory has a pending writeback error, filemap_invalidate_pages()
will call filemap_write_and_wait_range(), which returns the pre-existing
mapping error.

When that happens, filemap_invalidate_pages() returns immediately without
calling invalidate_inode_pages2_range(). Since the return value is ignored
here, the invalidation is silently aborted, permanently leaving stale data
in the page cache.

Previously, invalidate_inode_pages2() attempted to invalidate every page
regardless of whether others failed writeback.

[Severity: High]
Can this cause direct I/O reads to unnecessarily evict clean page cache,
and also cause direct I/O to spuriously fail with -EBUSY?

The replacement here unconditionally calls filemap_invalidate_pages() for
both reads and writes, whereas the original code only invalidated the cache
for writes further down in the function.

Invalidating on direct reads evicts clean pages, degrading performance for
concurrent buffered readers.

Additionally, filemap_invalidate_pages() returns errors propagated from
invalidate_inode_pages2_range(). Because the FUSE launder_folio operation
was deleted in this patch, if a folio is re-dirtied by a concurrent mmap
write between the write-and-wait and invalidation phases,
invalidate_inode_pages2_range() will fail with -EBUSY. Returning this
error directly here can cause the read or write syscall to randomly fail
with -EBUSY.

[Severity: High]
Does this code silently fail to invalidate the page cache when the server
requests invalidation to EOF?

When a FUSE daemon sends a FUSE_NOTIFY_INVAL_INODE request with a length
of 0, it semantically means "invalidate from offset to EOF".

The original code explicitly checked if len <= 0 and set the end page index
to -1 (ULONG_MAX). If len == 0 and offset > 0, the new calculation
offset + len - 1 evaluates to offset - 1.

Inside filemap_invalidate_pages(), filemap_write_and_wait_range() will
immediately return 0 because lend < lstart. Following that,
invalidate_inode_pages2_range() is called with start > end, which also
returns 0 without invalidating any pages. This causes valid invalidation
requests to be completely ignored.
