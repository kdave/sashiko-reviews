btrfs: fix pending delayed iputs when using autodefrag

This commit attempts to fix an issue where delayed iputs are created after
the file system state is marked with BTRFS_FS_STATE_NO_DELAYED_IPUT during
unmount. It flushes delalloc and waits for ordered extents immediately after
parking the cleaner kthread in close_ctree().

Link: https://lore.kernel.org/linux-btrfs/6a1ee507.b4221f80.1326c5.0004.GAE@google.com/

[Severity: High]
Does writeback_inodes_sb() use WB_SYNC_NONE internally, skipping folios locked
by other threads or inodes with I_SYNC set?

If concurrent async reclaim or page faults hold these locks, the skipped
folios might remain dirty. Could they be flushed later by btrfs_commit_super()
with flushoncommit, creating new ordered extents that generate delayed iputs
after the BTRFS_FS_STATE_NO_DELAYED_IPUT flag is set?

> +	btrfs_wait_ordered_roots(fs_info, U64_MAX, NULL);

[Severity: High]
Is this wait occurring before the deferred compressed writes are processed?

For compressed writes, cow_file_range_async() defers the creation of ordered
extents and IO submission to the fs_info->delalloc_workers workqueue. Since
btrfs_wait_ordered_roots() is called here before
btrfs_flush_workqueue(fs_info->delalloc_workers) executes further down in
close_ctree(), will it miss checking for these ordered extents?

If the ordered extents are created later when the workqueue is flushed,
could their completion generate delayed iputs and trigger the same warning
this regression intends to resolve?
