[Severity: Critical]
Does this code create a memory reclaim deadlock?

During memory pressure, kswapd or direct reclaim can initiate data writeback.
In btrfs_submit_chunk(), btrfs_csum_one_bio() is called to compute data
checksums. This function increments the bio's remaining count and offloads
the checksum computation to system_percpu_wq via schedule_work(). The bio's
writeback completion is delayed until this work item finishes.

Because system_percpu_wq lacks the WQ_MEM_RECLAIM flag, it has no rescuer
thread. If all workers in the pool are blocked waiting for memory and
kthread_create() cannot allocate memory to spawn new workers, csum_work will
never execute. This permanently stalls the writeback bio, preventing
PG_writeback from being cleared, which permanently blocks direct reclaim and
deadlocks the system.

Now that the safe fs_info->workers workqueue has been removed, the
schedule_work() path is the default. Could this lead to a system-wide freeze?
