btrfs: unlock inode and extent in caller when uring read extent fails

This commit shifts the responsibility of unlocking the inode and extent
from btrfs_uring_read_extent() back to its caller on failure. Memory
allocation failures now join the out_fail path without leaking locks.

[Severity: High]
This isn't a bug introduced by this patch, but can this cause a deadlock if
the user buffer is mmap'ed to the same file extent?

Later in btrfs_uring_read_finished(), the code calls copy_page_to_iter():

	if (copy_page_to_iter(priv->pages[index], page_offset, bytes,
			      &priv->iter) != bytes) {

If a page fault occurs during copy_page_to_iter() while the extent lock and
i_rwsem are actively held, the fault handler (such as btrfs_filemap_fault or
btrfs_page_mkwrite) might attempt to re-acquire the same locks for the
faulted range, potentially causing a self-deadlock. The synchronous path
seems to avoid this by explicitly dropping the locks before copying.
