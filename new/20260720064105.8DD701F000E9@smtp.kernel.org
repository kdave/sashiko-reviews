btrfs: retry verity reads for not-uptodate Merkle folios

This commit updates btrfs_read_merkle_tree_page() to retry the Merkle item
read when a not-uptodate folio is found in the mapping. This prevents
transient read failures from remaining sticky in the page cache.

[Severity: High]
This isn't a bug introduced by this patch, but on 32-bit systems with
highmem, does passing folio_address(folio) as the dest parameter break the
read?

folio_address() can return NULL for unmapped highmem folios. When it does,
read_key_bytes() treats the NULL dest as a flag to only calculate the size
without copying any data:

fs/btrfs/verity.c:read_key_bytes() {
...
        /* desc = NULL to just sum all the item lengths */
        if (!dest)
                copy_end = item_end;
        else
                copy_end = min(offset + len, item_end);
...
}

This skips the kmap_local_folio() block and data copy, leaving the folio
uninitialized. It also causes the subsequent len -= copy_bytes to underflow
the unsigned len variable, leading to an infinite loop over all b-tree items
for the inode.

Could we fix this by passing a dummy non-NULL value for dest, or by changing
read_key_bytes() to check dest_folio != NULL instead of dest != NULL for
the skipping behavior?
