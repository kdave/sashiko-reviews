Does skipping EOF block cleanup here permanently leak speculative delayed
allocation blocks in the data fork?

When the Merkle tree is written via buffered I/O, it can create delalloc
blocks past EOF. Since the new cleanup code in xfs_fsverity_end_enable()
only drops COW fork delallocs and misses the data fork, disabling blockgc
for verity inodes here means those data fork delalloc blocks could leak.
Will this cause a panic on inode eviction when xfs_inode_free() hits the

[Severity: High]
Can this sequence cause an AB-BA deadlock with background writeback?

By holding XFS_ILOCK_EXCL while calling truncate_inode_pages(), the code
attempts to acquire the Folio Lock. However, the background writeback path
acquires the Folio Lock first and then attempts to acquire XFS_ILOCK_SHARED
(e.g., via xfs_map_blocks()). If background writeback is operating on a
folio at the same time, this lock inversion could lead to a deadlock.
