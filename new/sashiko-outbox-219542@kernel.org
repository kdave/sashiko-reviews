[Severity: Medium]
Does an error after btrfs_load_block_group_zone_info() leak the metadata
block group accounting in fs_info->zoned_conv_meta_bgs?

With conventional metadata block groups now using __btrfs_add_free_space()
instead of __btrfs_add_free_space_zoned(), btrfs_add_new_free_space() in
both read_one_block_group() and btrfs_make_block_group() allocates from
btrfs_free_space_cachep and can fail with -ENOMEM after
btrfs_load_block_group_zone_info() has already called
btrfs_zoned_account_meta_bg(cache, 1).  The error paths only call
btrfs_put_block_group(cache) without undoing that counter increment, leaving
zoned_conv_meta_bgs permanently skewed so btrfs_zoned_meta_is_append_only()
misidentifies the filesystem's metadata block group state.

[Severity: High]
Was this hunk meant for the second LOOP_NO_EMPTY_SIZE check further down in
find_free_extent_update_loop()?

This first check runs before ffe_ctl->loop++ and is the termination guard
after LOOP_NO_EMPTY_SIZE has already completed; if it ever fell through,
ffe_ctl->loop++ would advance ffe_ctl->loop past LOOP_NO_EMPTY_SIZE.
Meanwhile, when ffe_ctl->loop is incremented from LOOP_WRONG_SIZE_CLASS into
LOOP_NO_EMPTY_SIZE, execution reaches the second check at the bottom of the
function:

fs/btrfs/extent-tree.c:find_free_extent_update_loop() {
	...
	if (ffe_ctl->loop == LOOP_NO_EMPTY_SIZE) {
		if (ffe_ctl->policy != BTRFS_EXTENT_ALLOC_CLUSTERED)
			return -ENOSPC;

		/*
		 * Don't loop again if we already have no empty_size and
		 * no empty_cluster.
		 */
		if (ffe_ctl->empty_size == 0 && ffe_ctl->empty_cluster == 0)
			return -ENOSPC;
		ffe_ctl->empty_size = 0;
		ffe_ctl->empty_cluster = 0;
	}
}

Because ffe_ctl->policy is BTRFS_EXTENT_ALLOC_ZONED, that check still
returns -ENOSPC immediately without zeroing ffe_ctl->empty_size or retrying
the allocation in LOOP_NO_EMPTY_SIZE.
