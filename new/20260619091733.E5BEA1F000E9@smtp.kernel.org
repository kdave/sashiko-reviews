btrfs: pass the key type to btrfs_insert_one_raid_extent()

This patch updates btrfs_insert_one_raid_extent() to accept a type parameter 
instead of hardcoding BTRFS_RAID_STRIPE_KEY. Callers are updated to pass 
the explicit type. There is no functional change intended.

[Severity: Critical]
This is a pre-existing issue, but I wanted to ask about the error handling
in this function. If kzalloc() fails, btrfs_insert_one_raid_extent() calls 
btrfs_end_transaction(trans).

Since trans is owned by the caller (which will also call 
btrfs_abort_transaction(trans) and btrfs_end_transaction(trans) when the 
error propagates), doesn't this result in a use-after-free and double-free 
of the trans structure? 

In test environments, trans might even be allocated on the stack, so the 
first btrfs_end_transaction() would attempt a kmem_cache_free() on a stack 
pointer.

This isn't a bug introduced by this patch, but when btrfs_insert_item()
returns -EEXIST, the code calls update_raid_extent_item(trans, &stripe_key,
stripe_extent, item_size).

Does update_raid_extent_item() blindly overwrite the existing item without 
verifying that the on-disk item's size is large enough? It seems to call 
write_extent_buffer() with a newly calculated item_size derived from the 
block group profile:

fs/btrfs/raid-stripe-tree.c:update_raid_extent_item() {
    ...
    write_extent_buffer(leaf, stripe_extent, btrfs_item_ptr_offset(leaf, slot),

adjacent item payloads in the B-tree leaf?
