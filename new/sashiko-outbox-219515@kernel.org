[Severity: Medium]
Does this leak a count in fs_info->zoned_seq_meta_bgs or
fs_info->zoned_conv_meta_bgs if block group creation fails after
btrfs_load_block_group_zone_info()?

In btrfs_make_block_group() (and similarly in read_one_block_group()), the
error paths after btrfs_load_block_group_zone_info() free cache before it
is inserted into fs_info->block_group_cache_tree:

fs/btrfs/block-group.c:btrfs_make_block_group() {
    ...
	ret = btrfs_load_block_group_zone_info(cache, true);
	if (ret) {
		btrfs_put_block_group(cache);
		return ERR_PTR(ret);
	}

	ret = exclude_super_stripes(cache);
	if (ret) {
		/* We may have excluded something, so call this just in case */
		btrfs_free_excluded_extents(cache);
		btrfs_put_block_group(cache);
		return ERR_PTR(ret);
	}
    ...
}

Since the matching btrfs_zoned_account_meta_bg(block_group, -1) is only
called when btrfs_remove_block_group() erases the block group from
fs_info->block_group_cache_tree, a failure in exclude_super_stripes(),
btrfs_add_new_free_space(), or btrfs_add_block_group_cache() leaves the
counter elevated for the rest of the mount.  If that counter was otherwise
zero, btrfs_zoned_meta_is_append_only() will see both counters as non-zero
and fall back to btrfs_lookup_block_group() on every
btrfs_clear_buffer_dirty() call.

Accounting the block group in btrfs_add_block_group_cache() when it is
inserted into fs_info->block_group_cache_tree would pair directly with
btrfs_remove_block_group().
