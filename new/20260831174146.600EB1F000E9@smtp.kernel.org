[Severity: High]
This is a pre-existing issue, but does this accounting logic incorrectly
subtract bg->zone_unusable from space_info->disk_total during block group
migration?

When migrating an empty data block group to a relocation block group during
mount time on a zoned filesystem in btrfs_zoned_reserve_data_reloc_bg() in
fs/btrfs/zoned.c, the code immediately following this lock performs:

    space_info->disk_total -= bg->length * factor;
    space_info->disk_total -= bg->zone_unusable;

Should this be calling btrfs_space_info_update_bytes_zone_unusable() instead
to properly update bytes_zone_unusable? By subtracting from disk_total
directly, it seems to artificially lower disk_total while leaking
bytes_zone_unusable in the original space info. Since bytes_zone_unusable
is counted as used space, could this leak cause the filesystem to falsely
report less free space and trigger premature ENOSPC during data allocations?
