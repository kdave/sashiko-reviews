[Severity: Medium]
Can this still skip btrfs_kill_delayed_inode_items() and leak the delayed
node when btrfs_commit_inode_delayed_inode() fails without
BTRFS_FS_STATE_TRANS_ABORTED set?

btrfs_join_transaction() -> start_transaction() returns -EROFS whenever
BTRFS_FS_ERROR(fs_info) is non-zero, and btrfs_force_shutdown() or a direct
btrfs_handle_fs_error() call sets fs_info->fs_error without setting
BTRFS_FS_STATE_TRANS_ABORTED.  Separately, __btrfs_update_delayed_inode()
returns -ENOENT without aborting the transaction when the on-disk inode
item is missing, releasing the delayed inode update while leaving any
delayed dir index items queued on the delayed_node.

In either case, pending items keep delayed_node->count non-zero, so
btrfs_remove_delayed_node() cannot free the node and btrfs_put_root() later
hits WARN_ON(!xa_empty(&root->delayed_nodes)).  Should this also check
BTRFS_FS_ERROR(fs_info) (or call btrfs_kill_delayed_inode_items()
unconditionally before checking ret)?
