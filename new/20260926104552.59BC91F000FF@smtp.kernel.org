[Severity: High]
Can this lead to reading past the allocated buffer when handling extended
attributes from userspace?

In prop_compression_validate(), the length constraint was dropped when
calling btrfs_compress_is_valid_type(). If a local user calls setxattr()
for the btrfs.compression attribute with a small value without a null
terminator (like a single byte "z"), the VFS layer allocates a buffer of
exactly that size.

Since btrfs_compress_is_valid_type() now uses strstarts() and no longer
bounds the check by the input length, the comparison can read past the
end of the dynamically allocated value buffer. This could trigger KASAN
memory safety splats or a page fault if the allocation boundary aligns
with the end of a mapped page.
