btrfs: zoned: use the regular allocator for conventional metadata block groups

This patch switches metadata and system block groups backed solely by
conventional zones on zoned filesystems to use the regular free space cache
and unclustered allocator instead of the sequential append-only allocator. It
replaces filesystem-wide btrfs_is_zoned() checks in space accounting, free
space tracking, and extent allocation with btrfs_zoned_bg_is_append_only().

[Severity: Medium]
Can this cause a premature -ENOSPC when allocating metadata with a non-zero
empty_size hint (for example during directory defragmentation via
btrfs_ioctl_defrag() -> btrfs_defrag_root() -> btrfs_defrag_leaves() ->
btrfs_realloc_node() -> btrfs_force_cow_block())?

For conventional metadata block groups on a zoned filesystem,
bg_alloc_policy() routes do_allocation() to do_allocation_clustered() ->
find_free_extent_unclustered(), which requires num_bytes + empty_size of free
space and searches for a contiguous hole of that size:

fs/btrfs/extent-tree.c:find_free_extent_unclustered() {
	...
		if (free_space_ctl->free_space <
		    ffe_ctl->num_bytes + ffe_ctl->empty_cluster +
		    ffe_ctl->empty_size) {
			ffe_ctl->total_free_space = max_t(u64,
					ffe_ctl->total_free_space,
					free_space_ctl->free_space);
			spin_unlock(&free_space_ctl->tree_lock);
			return 1;
		}
		spin_unlock(&free_space_ctl->tree_lock);
	}

	offset = btrfs_find_space_for_alloc(bg, ffe_ctl->search_start,
			ffe_ctl->num_bytes, ffe_ctl->empty_size,
			&ffe_ctl->max_extent_size);
	...
}

However, ffe_ctl->policy itself remains BTRFS_EXTENT_ALLOC_ZONED. If the free
space in the conventional metadata block groups is fragmented into holes
smaller than num_bytes + empty_size (even though holes of size num_bytes are
available) and no new metadata chunk can be allocated at LOOP_ALLOC_CHUNK,
find_free_extent_update_loop() advances to LOOP_NO_EMPTY_SIZE and checks
ffe_ctl->policy directly:

fs/btrfs/extent-tree.c:find_free_extent_update_loop() {
	...
	if (ffe_ctl->loop == LOOP_NO_EMPTY_SIZE) {
		if (ffe_ctl->policy != BTRFS_EXTENT_ALLOC_CLUSTERED)
			return -ENOSPC;

		/*
		 * Don't loop again if we already have no empty_size and
		 * no empty_cluster.
		 */
		if (ffe_ctl->empty_size == 0 && ffe_ctl->empty_cluster == 0)
			return -ENOSPC;
		ffe_ctl->empty_size = 0;
		ffe_ctl->empty_cluster = 0;
	}
	...
}

Because ffe_ctl->policy is BTRFS_EXTENT_ALLOC_ZONED, does
find_free_extent_update_loop() return -ENOSPC immediately instead of clearing
ffe_ctl->empty_size to 0 and retrying the allocation for just num_bytes?
