[Severity: Medium]
Does this change introduce a regression for userspace scripts setting the
btrfs.compression xattr with trailing newlines?

Previously, the simple strncmp() checked only up to comp_len, which
allowed strings like "zstd\n" (e.g., from echo zstd | setfattr) to be
accepted.

With this change, btrfs_match_compress_type() strictly rejects any
trailing characters for base compression types, so "zstd\n" now fails
with -EINVAL.

However, strings with levels like "zstd:9\n" will silently pass because
btrfs_compress_str2level() uses kstrtoint(), which explicitly ignores
trailing newlines.

Could this inconsistent validation break backwards compatibility for legacy
configuration scripts?
