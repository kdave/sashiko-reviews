Subject: btrfs: introduce compression for delayed bbio

This patch introduces a compressed write path inside a delayed bbio. It
modifies the regular compression flow to skip touching folio flags on
error, call error handling only once, and avoid sequential execution of
data extent reservation.

[Severity: High]
Does this introduce a data race? Multiple delayed bbios pointing to the
same shared parent ordered extent can be submitted concurrently to the
delayed_write_workers workqueue.

If multiple workers hit an error in try_submit_compressed() simultaneously,
they will both call clear_cleanup_bitmap(). Since bitmap_clear() modifies
the unsigned long word locklessly, this concurrent read-modify-write could
overwrite bits and cause the parent ordered extent to incorrectly execute
cleanup on ranges already handled elsewhere.

[Severity: High]
Will this cause a double-free of delalloc metadata? The parent
BTRFS_ORDERED_DELAYED ordered extent encompassing this chunk is still
alive.

When the parent ordered extent finishes, btrfs_remove_ordered_extent()
will unconditionally release metadata for the entire parent's length. By
releasing it here in the error path as well, it appears the metadata
reservations (like inode->csum_bytes) might be released twice, leading to
accounting corruption.

[Severity: High]
Does this error path leak data space reservations and io_tree bits?

By clearing the parent's cleanup bitmap here, btrfs_finish_one_ordered()
will skip cleaning up the data space and io_tree bits (EXTENT_DELALLOC_NEW)
for this range. However, this out_free_reserve path doesn't seem to call
btrfs_delalloc_release_space() either, permanently leaking the reservations.
