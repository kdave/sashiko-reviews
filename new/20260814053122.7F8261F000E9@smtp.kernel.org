btrfs: preserve the compression property when other inode flags change

This commit fixes an issue where setting unrelated file flags via
FS_IOC_SETFLAGS overwrites the user-selected compression algorithm with
the mount default. It ensures that the algorithm recorded in the
compression property is kept unless compression is explicitly enabled.

[Severity: High]
This is a pre-existing issue, but can this function race with asynchronous
writeback and silently lose file attributes?

In btrfs_fileattr_set(), we cache the inode flags locally earlier in the
function, perform operations that could block (like btrfs_start_transaction),
and then write the cached value back:

fs/btrfs/ioctl.c:btrfs_fileattr_set() {
        ...
        inode_flags = inode->flags;
        ...
update_flags:
        inode->flags = inode_flags;
        ...
}

Concurrently, if the file is undergoing asynchronous writeback, the worker
thread can locklessly modify the flags using a non-atomic operation:

fs/btrfs/inode.c:compress_file_range() {
        ...
        inode->flags |= BTRFS_INODE_NOCOMPRESS;
        ...
}

If the writeback thread performs its read-modify-write while
btrfs_fileattr_set() is executing, wouldn't the attributes set by chattr
(such as FS_IMMUTABLE_FL or FS_SYNC_FL) be unconditionally overwritten in
memory and lost when the cached inode_flags is written back?

>  		inode_flags &= ~(BTRFS_INODE_COMPRESS | BTRFS_INODE_NOCOMPRESS);
>  	}
