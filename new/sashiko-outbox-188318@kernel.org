If Thread A migrates bg from data_sinfo to reloc_sinfo and clears bg->ro while
Thread B enters inc_block_group_ro(bg) (for example from
btrfs_delete_unused_bgs(), scrub, or a concurrent btrfs_set_data_reloc_bg()),
Thread B locks data_sinfo->lock while bg->space_info is reloc_sinfo, adds
bg->ro_list to data_sinfo->ro_bgs, and increments data_sinfo->bytes_readonly.
When Thread B later calls btrfs_dec_block_group_ro(bg), it locks
reloc_sinfo->lock, deletes bg->ro_list from data_sinfo->ro_bgs without holding
data_sinfo->lock, and subtracts available space from
reloc_sinfo->bytes_readonly, underflowing it.

Similarly, if another caller increments bg->ro from 1 to 2 while bg is
temporarily read-only in reloc_sinfo and btrfs_set_data_reloc_bg() takes the
rollback path when fs_info->data_reloc_bg is already set,
zoned_move_bg_to_space_info(fs_info, bg, reloc_sinfo, data_sinfo) fails its
bg->ro != 1 check and its return value is ignored, leaving the empty bg
stranded in reloc_sinfo.

In addition, because btrfs_set_data_reloc_bg() calls
btrfs_inc_block_group_ro_notrans(bg) outside groups_sem before verifying that
bg is still empty, it can transiently toggle bg->ro = 1 and then bg->ro = 0
(after zoned_move_bg_to_space_info() rejects the non-empty bg) while a
concurrent task is freeing a failed reservation via
btrfs_free_reserved_extent() or unpin_extent_range(). Those paths call
btrfs_add_free_space() and btrfs_free_reserved_bytes() under separate
acquisitions of bg->lock:

1. __btrfs_add_free_space_zoned() adds len to bg->zone_unusable under
   bg->lock.
2. btrfs_inc_block_group_ro_notrans() -> inc_block_group_ro() runs before
   btrfs_free_reserved_bytes(), migrating the newly increased bg->zone_unusable
   into bytes_readonly and subtracting it from
   data_sinfo->bytes_zone_unusable (underflowing it because
   btrfs_free_reserved_bytes() has not added len to
   data_sinfo->bytes_zone_unusable yet).
3. zoned_move_bg_to_space_info() sees bg->reserved > 0 and fails, and

What prevents bg from becoming non-empty, full, or read-only before
fs_info->data_reloc_bg is set when migrate is false?

In btrfs_zoned_reserve_data_reloc_bg(), when a new chunk is allocated in
reloc_sinfo (data_sinfo->sub_group[0]) and execution jumps back to again, the
candidate bg is checked under space_info->groups_sem and tmp->lock, and then
both locks are dropped before calling btrfs_set_data_reloc_bg(fs_info, bg).

Because bg->space_info is already reloc_sinfo, migrate is false, so
btrfs_set_data_reloc_bg() skips btrfs_inc_block_group_ro_notrans(bg) and
zoned_move_bg_to_space_info(), and never takes bg->lock to recheck that
bg->alloc_offset == 0, !btrfs_is_block_group_used(bg), and !bg->ro before
setting fs_info->data_reloc_bg = bg->start and calling btrfs_zone_activate(bg).
If a concurrent relocation allocation in reloc_sinfo allocates from or fills
bg after groups_sem is dropped, fs_info->data_reloc_bg can be set to a used or
full block group (triggering the WARN_ON_ONCE(btrfs_zoned_bg_is_full()) in
btrfs_zone_activate()).

Also, because migrate = (bg->space_info == data_sinfo) is evaluated without
locking, if two callers race on the same candidate bg from data_sinfo (such as
btrfs_zoned_reserve_data_reloc_bg() racing with zoned_reset_bg_in_place() in
commit "btrfs: zoned: promote reset data block groups to the relocation
target"), Thread 1 can set bg->ro = 1 and move bg to reloc_sinfo, after which
Thread 2 enters btrfs_set_data_reloc_bg(), sees bg->space_info == reloc_sinfo

fs_info->data_reloc_bg = bg->start while bg->ro is still 1. Thread 1 then sees

this commit, or failing btrfs_set_data_reloc_bg() even with the check added in

[Severity: High]
Can this goto again spin in an infinite loop when btrfs_set_data_reloc_bg()
returns false?

In btrfs_zoned_reserve_data_reloc_bg(), the search loop picks the first block
group tmp on data_sinfo->block_groups[index] matching:

	usable = (tmp->alloc_offset == 0 && tmp->used == 0 &&
		  tmp->reserved == 0 && !tmp->ro);

and passes it to btrfs_set_data_reloc_bg(fs_info, bg), which calls
btrfs_inc_block_group_ro_notrans(bg) -> inc_block_group_ro(bg, false):

fs/btrfs/block-group.c:inc_block_group_ro() {
	...
	} else if (sinfo->flags & BTRFS_BLOCK_GROUP_DATA) {
		u64 sinfo_used = btrfs_space_info_used(sinfo, true);

		if (sinfo_used + num_bytes <= sinfo->total_bytes)
			ret = 0;
	}
}

When bg's free space is needed to back existing reservations in data_sinfo
(such as delalloc reservations in data_sinfo->bytes_may_use),
inc_block_group_ro() returns -ENOSPC without setting bg->ro. The same happens
if bg->swap_extents > 0 (-ETXTBSY), or if zoned_move_bg_to_space_info() fails
because btrfs_is_block_group_used(bg) sees bg->pinned > 0 or
bg->remap_bytes > 0 and zoned_dec_bg_ro(bg) resets bg->ro back to 0.

Because bg is unchanged and remains at the same position in
data_sinfo->block_groups[index], jumping to again restarts the list walk from
the head, selects the exact same bg on every iteration, and loops indefinitely
without advancing to later block groups or reaching the btrfs_chunk_alloc()
fallback.
