btrfs: zstd: avoid a copy in zstd_decompress_bio()

zstd_decompress_bio() gives zstd a sectorsize-sized scratch buffer, and
btrfs_decompress_buf2page() then copies the part overlapping the read bio
into the destination folios. Every delivered byte is written twice.
This patch replaces it by writing directly to the page cache by kmapping
the read bio segments.

[Severity: High]
This is a pre-existing issue, but can this lead to a kernel panic from a
stale workspace pointer being dereferenced?

When a ZSTD workspace is used for a compression or decompression operation
and completes successfully, workspace->in_buf.src is assigned a mapped
address. At the end of the operation, the address is unmapped, but
workspace->in_buf.src is never set to NULL before the workspace is returned
to the pool.

If the same workspace is subsequently allocated for zstd_compress_bio(), the
local variable in_folio is initialized to NULL. If the very first operation,
btrfs_compress_filemap_get_folio(), fails (e.g., -ENOMEM or -ENOENT):

fs/btrfs/zstd.c:zstd_compress_bio() {
    ...
	/* Map in the first page of input data. */
	ret = btrfs_compress_filemap_get_folio(mapping, start, &in_folio);
	if (ret < 0)
		goto out;
    ...
out:
	if (out_folio)
		btrfs_free_compr_folio(out_folio);
	if (workspace->in_buf.src) {
		kunmap_local(workspace->in_buf.src);
		folio_put(in_folio);
	}
	return ret;
}

The cleanup code checks if (workspace->in_buf.src). Since it holds the stale,
non-NULL pointer, the condition evaluates to true. The kernel calls
kunmap_local() on the stale pointer and folio_put(in_folio) where in_folio
is NULL, causing an immediate crash.

The same failure to clear workspace->in_buf.src is present in the "done:"
path of zstd_decompress_bio().

Should workspace->in_buf.src be cleared after it is unmapped?
