btrfs: write back a folio extent-by-extent instead of block-by-block

The current dirty folio writeback is still based on a block-by-block
iteration. This commit optimizes the folio writeback behavior to do an
extent-by-extent submission.

[Severity: High]
What happens to the calculation here if there is a gap in ordered extents?

If btrfs_lookup_first_ordered_range() returns an ordered extent that starts
after cur, ordered->file_offset would be greater than cur.

Wouldn't cur - ordered->file_offset then underflow to a very large number,
bypassing the intended truncation and leaving truncated_len unchanged?

Production builds with assertions disabled would silently skip the ASSERT()
and allow the extent beyond EOF to be fully written and inserted into the
tree. Could this lead to stale data leaks or metadata corruption if the file
is later extended?
