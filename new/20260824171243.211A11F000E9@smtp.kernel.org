btrfs: set space_info before adding new free space in btrfs_make_block_group()

btrfs_make_block_group() calls btrfs_add_new_free_space() before
assigning cache->space_info. On a zoned filesystem that ends up in
__btrfs_add_free_space_zoned(), which dereferences
block_group->space_info and thus hits a NULL pointer dereference when a
non-initial free space range is added (e.g. during relocation).

Assign cache->space_info before the btrfs_add_new_free_space() call.

Signed-off-by: Johannes Thumshirn <johannes.thumshirn@wdc.com>

[Severity: Critical]
Does moving this assignment earlier expose a latent underflow issue in
__btrfs_add_free_space_zoned() that can cause a block group to be dropped
from the transaction?

When a new zoned block group spans excluded extents (like superblocks),
btrfs_add_new_free_space() slices the range. Since the first slice size is
less than the total length, it triggers the reclaim check in
__btrfs_add_free_space_zoned():

fs/btrfs/free-space-cache.c:__btrfs_add_free_space_zoned() {
    ...
    reclaimable_unusable = block_group->zone_unusable -
                           (block_group->length - block_group->zone_capacity);
    ...
}

For a new block group, zone_unusable is 0. If length is greater than
zone_capacity, this unsigned subtraction underflows.

The block group is then erroneously added to reclaim_bgs. Later in
btrfs_make_block_group(), it calls:

    btrfs_link_bg_list(cache, &trans->new_bgs);

Could this silently fail because the list_head is already linked in
reclaim_bgs, preventing it from being added to trans->new_bgs and resulting
in the new block group never being written to the extent tree?

[Severity: High]
This is a pre-existing issue, but does this error path leak memory if
btrfs_add_new_free_space() succeeds for an initial slice but fails for a
subsequent slice (e.g. returning -ENOMEM)?

btrfs_put_block_group() frees the free_space_ctl structure, but does not walk
the rb-tree to free the successfully added extent items or revert discard
