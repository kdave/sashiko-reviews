btrfs: fix creation of compressed inline extents that don't save space

This commit modifies the creation of compressed inline extents to check
the inode's i_size instead of the blocksize. This prevents the creation of
compressed inline extents that don't yield any space benefits.

[Severity: High]
Could passing the potentially unbounded i_size to btrfs_compress_bio()
cause a local denial of service?

If a user creates a large sparse file (for example, using ftruncate() to 4GB)
and triggers writeback only on the first page, the start == 0 and size
constraints in btrfs_run_delalloc_range() can still be met, triggering
run_delalloc_inline(). The massive unvalidated i_size is then passed as the
length into btrfs_compress_bio().

This can cause the compression loop to locklessly read beyond the locked
writeback range. If pages are absent, btrfs_compress_filemap_get_folio()
will emit un-ratelimited btrfs_crit() messages, creating a log flood:

fs/btrfs/compression.c:btrfs_compress_filemap_get_folio() {
        ...
        in_folio = filemap_get_folio(mapping, start >> PAGE_SHIFT);
        if (IS_ERR(in_folio)) {
                struct btrfs_inode *inode = BTRFS_I(mapping->host);

                btrfs_crit(inode->root->fs_info,
                "failed to get page cache, root %lld ino %llu...",
        ...
}

If the pages are present, the loop will waste massive amounts of CPU time
compressing up to 4GB of data synchronously.

Additionally, the size limit enforcement in run_delalloc_inline() occurs
too late:

        if (!can_cow_file_range_inline(inode, 0, i_size, compressed_size)) {

This rejects sizes larger than sectorsize only after the expensive
compression loop has already taken place.
