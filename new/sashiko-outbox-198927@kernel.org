btrfs: fix delayed_refs_rsv leak when realloc shrinks an extent

This commit adjusts pending_csums and delayed_refs_rsv accounting in
update_existing_head_ref() when a freed data extent is reallocated with a
different size before its delayed refs are processed.

[Severity: Medium]
As reported by Sashiko on v1 [1], when a freed data extent is reallocated
with a larger size (new_leaves > old_leaves), does adjusting the reservation
here before updating existing->total_ref_mod introduce two issues?

First, in the common case where old_ref_mod is -1 and existing->total_ref_mod
transitions to 0 in the same call:

btrfs_alloc_reserved_file_extent()
  btrfs_add_delayed_data_ref()
    add_delayed_ref()
      add_delayed_ref_head()
        update_existing_head_ref()

btrfs_delayed_refs_rsv_add() locks fs_info->delayed_refs_rsv.lock, increases
delayed_refs_rsv.size by (new_leaves - old_leaves), updates
delayed_refs_rsv.full, and drops the lock, only for the sign-transition check
at the end of update_existing_head_ref() to immediately release new_leaves:

	if (existing->is_data) {
		u64 csum_leaves =
			btrfs_csum_bytes_to_leaves(fs_info,
						   existing->num_bytes);

		if (existing->total_ref_mod >= 0 && old_ref_mod < 0) {
			delayed_refs->pending_csums -= existing->num_bytes;
			btrfs_delayed_refs_rsv_release(fs_info, 0, csum_leaves);
		}

During the unlocked window between those two calls, can concurrent callers of
btrfs_check_space_for_delayed_refs(), btrfs_delayed_refs_rsv_refill(), or
btrfs_block_rsv_release() observe the temporary size increase and cleared
full flag, causing unnecessary flushing or migrating released space from
other reserves into delayed_refs_rsv?

Second, if old_ref_mod <= -2 so that existing->total_ref_mod remains negative
after adding update->ref_mod, the extra csum reservation stays active after
update_existing_head_ref() returns. Because btrfs_delayed_refs_rsv_add()
directly increments delayed_refs_rsv.size instead of adding to
trans->delayed_ref_csum_deletions, doesn't the subsequent call to
btrfs_update_delayed_refs_rsv(trans) in add_delayed_ref() skip migrating
pre-reserved bytes from trans->delayed_rsv into delayed_refs_rsv.reserved and
bypass the btrfs_is_testing(fs_info) check?

Would it be simpler and avoid btrfs_delayed_refs_rsv_add() altogether to save
old_num_bytes = existing->num_bytes before overwriting existing->num_bytes,
and then handle both the transition and size change in the existing->is_data
block after existing->total_ref_mod is updated (releasing old_leaves when
transitioning from < 0 to >= 0, or adjusting by the difference between
old_leaves and new_leaves via btrfs_delayed_refs_rsv_release() and
trans->delayed_ref_csum_deletions when remaining < 0)?
