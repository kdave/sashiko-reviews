btrfs: send: fix is_current_inode_path() to avoid path resets for common prefixes

This commit updates is_current_inode_path() to avoid path resets when the
current inode's path is a prefix of the given path. It attempts to enforce
an exact match by checking the character after the matching prefix.

[Severity: High]
Can this result in an out-of-bounds read if both paths contain an embedded
null byte before cur_len?

If a crafted filesystem image contains directory items with embedded null bytes,
strncmp() will terminate early at the null byte and return 0. If path->start
is shorter than cur_len (for instance, if path->start uses the fixed 256-byte
inline_buf inside struct fs_path, while cur_len is much larger), accessing
path->start[cur_len] will read past the end of the allocation.

> +		return true;
> +	if (path->start[cur_len] == '/')

[Severity: Medium]
Does returning true here undermine the goal of detecting exact matches?

The commit message states the goal is to prevent the helper from returning
true when the current inode's path is a prefix of the given path. However,
if path is "a/b/c" and cur is "a/b" (cur_len = 3), strncmp() returns 0, and
path->start[cur_len] will be '/'.

By explicitly returning true when path->start[cur_len] == '/', this still
returns true for descendant paths, which contradicts the "exact match"
requirement stated in the commit message.

> +		return true;
> +
> +	return false;
>  }
