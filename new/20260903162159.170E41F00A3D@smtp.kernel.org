btrfs: tree-checker: validate key offset for inode ref keys

For a subvolume tree, the offset of an inode ref key corresponds to an
inode number, and that must always be within the range of
BTRFS_FIRST_FREE_OBJECTID to BTRFS_LAST_FREE_OBJECTID.
This commit adds a check for that condition in check_inode_ref().

[Severity: Low]
Does this cause a signed/unsigned type mismatch?

The format string uses %lld (signed long long), but it is passed
BTRFS_LAST_FREE_OBJECTID, which is defined as -256ULL (an unsigned long long).

While this intentionally prints -256 at runtime due to 2's complement
representation, it technically violates the format specifier's expected type.
In builds using stricter warning flags like -Wformat-signedness (in W=1 or
W=3), this causes a compiler warning.

Could this argument be explicitly cast to (s64) to resolve the mismatch and
match conventions used elsewhere in the Btrfs codebase?

[Severity: High]
Are we missing structural limit checks for extended references here?

This checks that the length doesn't exceed the item boundary, but it omits the
domain-specific validation (namelen == 0 or namelen > BTRFS_NAME_LEN) that is
enforced in check_inode_ref().

Could an attacker mount a crafted image containing a BTRFS_INODE_EXTREF_KEY
with a namelen of 0 or a massive length? Bypassing these bounds could pass
corrupted states downstream, risking kmalloc(0) (which returns ZERO_SIZE_PTR)
or directory logic errors.
