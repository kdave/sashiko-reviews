[Severity: High]
Is it possible for this loop to exhaust the metadata block reserve?

Since btrfs_cleanup_free_space_cache_v1() starts a transaction with 0 reserved
metadata items, this unbounded loop will iterate over every block group and
modify tree items via btrfs_remove_free_space_inode() without ending or
restarting the transaction.

Could this accumulate enough modified tree blocks and delayed operations on
filesystems with a massive number of block groups to cause an ENOSPC
transaction abort, failing the mount operation?

Should this loop use btrfs_should_end_transaction() to replenish the metadata
reserves?
