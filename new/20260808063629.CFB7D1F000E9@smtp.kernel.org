btrfs: free unlinked replace target on initialization failure

btrfs_init_dev_replace_tgtdev() allocates the replacement target before
looking up its block device and initializing its zoned device information.
This patch frees the allocated device on the error path if those lookups fail
so the device does not leak.

[Severity: High]
This is a pre-existing issue, but is it safe to use a non-RCU list_add() when 
adding this device to the list slightly earlier in this function?

btrfs_init_dev_replace_tgtdev() {
    ...
    mutex_lock(&fs_devices->device_list_mutex);
    list_add(&device->dev_list, &fs_devices->devices);
    fs_devices->num_devices++;
    ...
}

Since the device replace operation can run concurrently with ioctls that 
iterate the devices list using RCU (like btrfs_ioctl_fs_info or 
btrfs_ioctl_fitrim), could a concurrent RCU reader observe an uninitialized 
pointer because list_add() lacks the memory barriers of list_add_rcu()?

[Severity: High]
This is also a pre-existing issue, but does the error path in 
btrfs_dev_replace_start() leak the target device?

When mark_block_group_to_copy() fails, the function returns directly:

btrfs_dev_replace_start() {
    ...
    ret = mark_block_group_to_copy(fs_info, src_device);
    if (ret)
        return ret;
    ...
}

Could this early return leave the target device as a zombie in the active 
filesystem device list? It appears to skip the cleanup path that would normally 
handle the newly added target device, which might corrupt the filesystem 
state and cause subsequent replace attempts to fail.
