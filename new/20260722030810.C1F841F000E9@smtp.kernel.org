btrfs: retry verity reads for not-uptodate Merkle folios

This patch modifies btrfs_read_merkle_tree_page() to retry reading the Merkle
item when a not-uptodate folio is found in the mapping, instead of returning
an error. It also unlocks the folio on read_key_bytes() failure so a later
caller can retry the read.

This is a pre-existing issue, but does passing folio_address(folio) as the
dest pointer cause problems for highmem folios?

On 32-bit highmem systems, folio_address() evaluates to NULL for highmem
folios. Looking at read_key_bytes(), if dest is NULL, it skips the memory
mapping and copying logic entirely:

fs/btrfs/verity.c:read_key_bytes() {
    ...

    ...
		if (dest) {

				kaddr = kmap_local_folio(dest_folio, 0);

}

Because read_key_bytes() will return success (PAGE_SIZE) without copying
anything when dest is NULL, will btrfs_read_merkle_tree_page() then skip
zeroing and mark an uninitialized folio as uptodate?

Could this cause fs-verity to read invalid hashes and deterministically reject
