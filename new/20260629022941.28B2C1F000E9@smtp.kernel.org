btrfs: use kvmalloc() for stripe buffer of scrub_stripe

This patch replaces the scrub_stripe::folios array with a kvmalloc() buffer
to store all contents of a stripe. This simplifies cross-page handling, bio
assembly, and checksum verification by avoiding per-page iterations.

[Severity: High]
Could this result in a double free on initialization failure paths?

If a subsequent allocation inside init_scrub_stripe() fails, such as
stripe->sectors = kzalloc_objs(...), it jumps to the error label and calls
release_scrub_stripe(), freeing the buffer.

The error then propagates up to scrub_setup_ctx(), which responds by calling
scrub_free_ctx(). This iterates over all stripes and calls
release_scrub_stripe() again. Since stripe->buffer is not set to NULL after
kvfree(), this might trigger a double free on the same pointer.

[Severity: High]
This isn't a bug introduced by this patch, but is it possible for concurrent
updates to stripe->bitmaps to be lost here?

When the read repair worker submits multiple repair bios for different sectors
in a stripe, these bios can complete concurrently on different CPUs. The
completion handler scrub_repair_read_endio() invokes
scrub_bitmap_set_io_error() or scrub_bitmap_clear_io_error().

These helpers appear to rely on non-atomic __set_bit() and clear_bit()
operations (via custom bitmap_set and bitmap_clear macros). Because multiple
sectors share the same unsigned long word, concurrent handlers could perform
non-atomic read-modify-write operations on the same word, potentially
overwriting a set_error with a clear_error.

[Severity: High]
Does this code calculate the correct offset for non-page-aligned kmalloc
buffers?

If SLUB debugging, redzoning, or KASAN is enabled, large kmalloc buffers
might not be page-aligned. Calling offset_in_page(offset) instead of
offset_in_page(stripe->buffer + offset) passes an incorrect page offset
(such as 0 instead of the SLUB redzone offset) to bio_add_page().

This could cause block device DMA to overwrite the SLUB metadata preceding
the buffer, leading to memory corruption.

Additionally, upon bio completion, calc_sector_number() calculates the
virtual address using the correct offset:

fs/btrfs/scrub.c:calc_sector_number() {
    ...
    kaddr = page_address(virt_to_page(vaddr));
    kaddr += offset_in_page(vaddr);
    
    if (kaddr == bvec_virt(first_bvec))
        break;
    ...
}

Since the bvec contains the incorrect offset from scrub_bio_add_sector(),
this loop might fail to find a match and return stripe->nr_sectors.

This would then cause scrub_read_endio() and scrub_repair_read_endio() to
use an out-of-bounds index when updating the stripe->bitmaps array.
