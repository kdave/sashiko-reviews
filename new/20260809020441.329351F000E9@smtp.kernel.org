[Severity: High]
Can this cause a deadlock?

This function is invoked during inode property initialization:

btrfs_load_inode_props() -> iterate_object_props() -> inode_prop_iterator()

Since iterate_object_props() executes with a read lock held on a B-tree leaf,
using GFP_KERNEL here might allow the allocator to initiate memory reclaim.
This could trigger filesystem writeback that attempts to acquire the exact
same B-tree locks.

[Severity: High]
Will this reject historically valid compression strings?

Before this patch, prop_compression_validate() used strncmp() which
intentionally allowed and ignored trailing characters like newlines. The new
implementation uses btrfs_match_compress_type() which strictly checks that
the string terminates immediately or has a colon exactly at the end of the
algorithm name.

Consequently, a previously valid input like "zstd\n" (which tools like
setfattr or shell echoes often append) now fails validation with -EINVAL.
Inconsistently, "zstd:3\n" remains valid because the downstream kstrtoint()
parser deliberately ignores a single trailing newline. Does this introduce a
userspace ABI regression?

[Severity: Medium]
Is the compression level correctly inherited by child inodes?

When a new file or directory is created inside a directory with the
compression property, btrfs_inode_inherit_props() inherits it by calling the
parent's extract() callback.

Since prop_compression_extract() was not updated in this patch and continues
to return only the base compression type (e.g. "zstd"), won't the compression
level specified on the parent directory be lost during inheritance, causing
the child inode to silently fall back to the default compression level?
