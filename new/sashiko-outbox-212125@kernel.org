[Severity: High]
Does jumping to out before mutex_unlock(&bg->free_space_lock) return with
bg->free_space_lock still held when btrfs_next_leaf() fails?  The out label
only frees entries and space_runs, so any later caller acquiring
bg->free_space_lock will deadlock:

fs/btrfs/relocation.c:create_remap_tree_entries() {
    ...
out:
	kfree(entries);
	kfree(space_runs);

	return ret;
}

[Severity: High]
This problem wasn't introduced by this patch, but can the free-space tree
walk in create_remap_tree_entries() read one slot past the end of a leaf's
item array [1]?

fs/btrfs/relocation.c:create_remap_tree_entries() {
    ...
	key.objectid = bg->start;
	key.type = 0;
	key.offset = 0;

	space_root = btrfs_free_space_root(bg);

	ret = btrfs_search_slot(trans, space_root, &key, path, 0, 0);
    ...
	while (true) {
		leaf = path->nodes[0];

		btrfs_item_key_to_cpu(leaf, &found_key, path->slots[0]);
    ...
		path->slots[0]++;

		if (path->slots[0] >= btrfs_header_nritems(leaf)) {
			ret = btrfs_next_leaf(space_root, path);
    ...
}

Because key.type is 0, searching for a block group whose first free-space
item sits at slot 0 of a non-initial leaf lands in the previous leaf with
path->slots[0] equal to btrfs_header_nritems(leaf).  Checking the slot
bound only at the end of the loop makes the first btrfs_item_key_to_cpu()
read past the item array, either stopping the walk early or treating
garbage as free-space items and corrupting the remap tree.
