btrfs: Fix root reference leak in handle_indirect_tree_backref()

This commit addresses a root reference leak in handle_indirect_tree_backref().
It adds a check to drop the root reference and return -EUCLEAN if the tree
walk reaches BTRFS_MAX_LEVEL without finding a node in the backref cache or
the top of the searched path.

[Severity: Medium]
Does this new condition accidentally reject valid trees that are exactly at
the maximum possible height?

If a valid tree has its root at exactly level 7, the for loop in
handle_indirect_tree_backref() iterates up to that level. Because
path->nodes[7] is populated, the `if (!path->nodes[level])` check is false,
and the loop successfully processes level 7.

After processing, the loop increments the level to 8, which natively
terminates the loop because `8 < BTRFS_MAX_LEVEL` is false (as
BTRFS_MAX_LEVEL is 8). 

At this point, execution hits this newly added condition:

    if (level == BTRFS_MAX_LEVEL) {
        btrfs_put_root(root);
        ret = -EUCLEAN;
        goto out;
    }

Will this mistakenly drop the root and return -EUCLEAN instead of
successfully linking the root for these max-height trees? A level-7 tree is
the maximum valid height defined by the Btrfs format, so it seems this valid
edge case might be incorrectly treated as corrupted.

>  out:
>  	btrfs_release_path(path);
>  	return ret;
