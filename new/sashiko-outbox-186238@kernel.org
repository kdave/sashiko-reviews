btrfs: zoned: promote reset data block groups to the relocation target

This commit promotes data block groups that are reset in place by
btrfs_reset_unused_block_groups() directly to the data relocation block group
when no data relocation target is currently set, avoiding returning their free
space to the data space_info first.

Because data_sinfo->sub_group[0] also has BTRFS_BLOCK_GROUP_DATA set in
space_info->flags, promote remains true and zoned_reset_bg_in_place() skips
btrfs_return_free_space(space_info, *reclaimed).

[Severity: Medium]
Does skipping btrfs_return_free_space() while still decrementing
space_info->bytes_zone_unusable under space_info->lock prevent concurrent data
writes from claiming the reclaimed space before the block group is migrated?

In zoned_reset_bg_in_place(), btrfs_space_info_update_bytes_zone_unusable()
decrements data_sinfo->bytes_zone_unusable while data_sinfo->total_bytes still
includes bg->length, and then spin_unlock(&space_info->lock) drops the lock
before btrfs_set_data_reloc_bg() -> zoned_move_bg_to_space_info() subtracts
bg->length from data_sinfo->total_bytes:

fs/btrfs/zoned.c:zoned_move_bg_to_space_info() {
	spin_lock(&from->lock);
	from->total_bytes -= bg->length;
	from->disk_total -= bg->length * factor;
	...
	spin_unlock(&from->lock);
}

During that window, the reclaimed bytes are visible as available space in
data_sinfo, so a concurrent reserve_bytes() call or another thread calling
btrfs_try_granting_tickets(data_sinfo) can increment data_sinfo->bytes_may_use
against that space. Because bytes_may_use reservations do not touch
bg->alloc_offset, bg->used, or bg->reserved, the still_empty check in
btrfs_set_data_reloc_bg() will still pass and move bg out of data_sinfo,
leaving data_sinfo overcommitted.
