btrfs: introduce more accurate usebackuproot options

This patch introduces finer control over the usebackuproot rescue option
by adding rescue=usebackuproot_0, 1, 2, and 3. This allows users to choose
which specific backup slot to use, with 0 meaning the newest slot.

[Severity: Medium]
Will rescue=usebackuproot_0 fail the mount with -EINVAL if the backup roots are
corrupted, despite its intent to use the main superblock?

While usebackuproot_0 is intended to use the primary roots ('no need to load any
backup root'), it still triggers read_backup_root(fs_info, 0) here. 

If find_newest_super_backup() returns a negative value due to corrupted backup
roots:

read_backup_root() returns -EINVAL, which causes init_tree_roots() to abort the
mount here. A normal mount ignores a corrupted backup array and succeeds.

[Severity: Critical]
Does this unconditionally force loading an older backup root (slot 1) and skip
the main roots entirely, breaking the fallback semantics and causing silent
data loss of the most recent transaction?

In the legacy implementation, the kernel would try the primary roots first and
only fall back to backup roots if loading failed. The new code in this patch
series removes the loop and unconditionally calls read_backup_root() in
init_tree_roots() when these options are used. This overwrites the superblock
roots in memory with the previous transaction's roots, discarding the latest
transaction even if it is completely healthy.

Administrators using a standard rescue command like rescue=all or
rescue=usebackuproot will silently lose the latest transaction.
