[Severity: Medium]
Can this cause btrfs_reset_unused_block_groups() to return without reclaiming
space for the requested space_info when a sub-group block group is on
fs_info->unused_bgs?

On zoned filesystems, create_space_info() creates a sub_group[0] (for data
relocation or tree-log) with the same space_info->flags as the parent primary
space_info.

In btrfs_reset_unused_block_groups(), the search over fs_info->unused_bgs
filters only by type flags rather than matching bg->space_info:

	list_for_each_entry(bg, &fs_info->unused_bgs, bg_list) {
		if ((bg->flags & BTRFS_BLOCK_GROUP_TYPE_MASK) != space_info->flags)
			continue;

Previously, btrfs_reset_unused_block_groups() updated bytes_zone_unusable and
called btrfs_return_free_space() on its space_info argument, whereas
zoned_reset_bg_in_place() now uses bg->space_info.

When flush_space() calls btrfs_reset_unused_block_groups(space_info,
num_bytes) and the loop picks a block group where bg->space_info !=
space_info (for example, an unused tree-log block group when flushing the
primary metadata space_info, or vice versa), zoned_reset_bg_in_place()
returns the reclaimed space to bg->space_info, but
btrfs_reset_unused_block_groups() still deducts reclaimed from num_bytes:

	if (num_bytes <= reclaimed)
		break;
	num_bytes -= reclaimed;

Should the candidate lookup in btrfs_reset_unused_block_groups() check
bg->space_info != space_info so that it only resets block groups belonging to
the target space_info?
