[Severity: High]
This is a pre-existing issue, but is it safe to free the device synchronously
after removing it from the RCU list?

In the error handling path of btrfs_init_new_device(), removing the device
from fs_devices->devices with list_del_rcu() eventually falls through to
error_free_device which calls btrfs_free_device().

btrfs_free_device() directly frees the device:

fs/btrfs/volumes.c:btrfs_free_device() {
    ...
    kfree(rcu_dereference_raw(device->name));
    ...
    kfree(device);
}

Since the device was previously published with list_add_rcu(), wouldn't this
cause a use-after-free for any concurrent RCU readers traversing the device
list because there is no RCU grace period before the kfree()?

>  	list_del(&device->dev_alloc_list);
>  	fs_info->fs_devices->num_devices--;

[Severity: High]
This is a pre-existing issue, but does jumping to error_sysfs tear down the
device in memory after it has already been committed to disk?

Earlier in btrfs_init_new_device(), if a seeding device is added, the code
successfully calls btrfs_commit_transaction(trans). If 
btrfs_attach_transaction() then fails, the code jumps to error_sysfs:

fs/btrfs/volumes.c:btrfs_init_new_device() {
    ...
    ret = btrfs_commit_transaction(trans);
    if (seeding_dev) {
        ...
        trans = btrfs_attach_transaction(root);
        if (IS_ERR(trans)) {
            if (PTR_ERR(trans) == -ENOENT)
                return 0;
            ret = PTR_ERR(trans);
            trans = NULL;
            goto error_sysfs;
        }
    ...
}

By branching to error_sysfs, the in-memory device structures are unlinked and
freed. Could this cause severe state corruption because the device is already
persisted to the on-disk metadata and the global transaction state?
