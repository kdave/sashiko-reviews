[Severity: High]
Can this early flag clearing cause metadata corruption?

Looking at btrfs_rebuild_free_space_tree(), if btrfs_start_transaction()
fails (e.g., due to ENOMEM) during the block group iteration, the code jumps
to out_clear and clears BTRFS_FS_CREATING_FREE_SPACE_TREE. This returns an
error without aborting the transaction.

When this failure occurs on mount or remount, the error propagates up and
eventually triggers close_ctree() which commits the un-aborted dirty
transaction.

During the commit, btrfs_run_delayed_refs() processes the delayed refs
generated during the partial rebuild (e.g., from metadata allocations).
Since BTRFS_FS_CREATING_FREE_SPACE_TREE is now cleared, it does not exit
early, and instead calls btrfs_add_to_free_space_tree().

Because the FREE_SPACE_TREE compat flag is still set, does this result in
modifying the inconsistent, partially rebuilt free space tree, potentially
triggering an ASSERT() or causing silent metadata corruption?
