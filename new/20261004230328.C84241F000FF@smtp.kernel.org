Subject: btrfs: write back a folio extent-by-extent instead of block-by-block

This commit optimizes the btrfs dirty folio writeback to submit IO on an
extent-by-extent basis instead of iterating block-by-block. It introduces
truncate_ordered_extents_beyond_eof() and find_next_write_range() to process
ordered extents in bulk. The changes aim to significantly reduce CPU time
during writeback for large folios.

[Severity: High]
Could this subtraction underflow if there is a gap in ordered extents?

During writeback, if there is a gap in ordered extents beyond the EOF,
btrfs_lookup_first_ordered_range() might return an ordered extent that
starts after cur (ordered->file_offset > cur).

If this happens, the subtraction cur - ordered->file_offset will underflow
to a very large value. The min() macro will then preserve the original
ordered->truncated_len instead of properly truncating it. Can this lead to
writing uninitialized or stale data beyond EOF?
