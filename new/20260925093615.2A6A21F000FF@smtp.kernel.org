    btrfs: add delayed ordered extent support
    
    A delayed ordered extent has the following features:
    
    - A new BTRFS_ORDERED_DELAYED flag
      And this new flag must be set along with the BTRFS_ORDERED_REGULAR flag.
    
    - No allocation of any on-disk space
      As a delayed ordered extent doesn't take any on-disk space yet, it
      won't release any reserved data/meta space either.
    
    - Zero or more real OEs can be added to the parent
      If a real OE is allocated, it must be inside the parent OE.
      And such real OE will go through the regular data/meta space
      reservation path.

[Severity: High]
Does this lockless iteration over the child list race with concurrent
insertions?

When a delayed ordered extent completes its I/O, finish_delayed_ordered()
is executed asynchronously. Before the parent OE is removed from the RB tree,
a new buffered write to the same page can trigger a new writeback.

This new writeback allocates a regular ordered extent, finds the parent OE
still present in the RB tree, and calls add_child_oe(). This concurrently
adds an element to the parent's child_list under the ordered_tree_lock,
while the iteration here modifies the list locklessly.

Can this race corrupt the linked list, leading to kernel panics, infinite
loops, or memory corruption?
