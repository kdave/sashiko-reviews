btrfs: tree-checker: reject file extents with oversized disk_num_bytes

This commit updates check_extent_data_item() to reject regular and
preallocated file extents whose disk_num_bytes exceeds BTRFS_MAX_COMPRESSED
when compressed or 256MiB when uncompressed.

[Severity: High]
Does capping uncompressed disk_num_bytes at SZ_256M cause a regression for
large direct I/O writes?

Unlike buffered writes and fallocate, btrfs_dio_iomap_begin() only caps len
for reads and passes the full write length to btrfs_get_blocks_direct_write()
-> btrfs_new_extent_direct():

	if (!write)
		len = min_t(u64, len, fs_info->sectorsize * BIO_MAX_VECS);
    ...
}

fs/btrfs/direct-io.c:btrfs_new_extent_direct() {
    ...
	ret = btrfs_reserve_extent(root, len, len, fs_info->sectorsize,
				   0, alloc_hint, &ins, true, true);
    ...
	file_extent.disk_bytenr = ins.objectid;
	file_extent.disk_num_bytes = ins.offset;

When a data block group has more than 256MiB of contiguous free space,
btrfs_new_extent_direct() creates an extent_map and ordered extent with
disk_num_bytes > SZ_256M.  If bounce buffering is not used (for example on a
BTRFS_INODE_NODATASUM file) and iomap packs more than 256MiB into a single
bio using multi-page folios or bvecs, btrfs_extract_ordered_extent() leaves
ordered->disk_num_bytes above SZ_256M; similarly, a concurrent fsync()
calling btrfs_log_changed_extents() -> log_one_extent() before bio splitting
logs em->disk_num_bytes > SZ_256M into the log tree.  Write-time tree-checker
validation then rejects the leaf with -EUCLEAN and aborts the transaction.

In addition, existing filesystems with preallocated extents larger than
256MiB created before 24542bf7ea5e ("btrfs: limit fallocate extent
reservation to 256MB") will fail read-time validation.

[Severity: Medium]
Can a crafted extent with disk_bytenr != 0 and disk_num_bytes == 0 still
pass check_extent_data_item()?

0 satisfies both CHECK_FE_ALIGNED() and the new upper-bound check, while
btrfs_extent_item_to_extent_map() only treats disk_bytenr == 0 as a hole.
For a compressed extent with disk_bytenr != 0 and disk_num_bytes == 0,
btrfs_submit_compressed_read() still sees compressed_len == 0 and submits an
empty bio, hitting the same length != 0 assertion failure in
assert_bbio_alignment(), and btrfs_encoded_read_regular() allocates a
ZERO_SIZE_PTR page array for disk_io_size == 0 and dereferences pages[0] in
btrfs_encoded_read_regular_fill_pages().

Should check_extent_data_item() also reject disk_num_bytes == 0 when
disk_bytenr != 0 (or when the extent is compressed or preallocated)?
