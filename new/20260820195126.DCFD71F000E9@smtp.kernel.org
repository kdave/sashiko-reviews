    Remove folio_launder()

    When we do direct I/O, we need to evict any page cache that overlaps
    the range in the file. This patch removes the inconsistency between
    filesystems by checking whether the folio is dirty in the VFS and
    failing the call to folio_unmap_invalidate() instead of laundering it.

[Severity: High]
This patch series replaces invalidate_inode_pages2_range() with
filemap_invalidate_pages() in filesystems like FUSE, NFS, and BTRFS for cache
invalidation. Does this new approach cause a cache coherency regression?

Looking at filemap_invalidate_pages(), it performs bulk writeback and aborts
immediately if filemap_write_and_wait_range() returns an error:

mm/filemap.c:filemap_invalidate_pages() {
    ...
    int ret = filemap_write_and_wait_range(mapping, pos, end);

    if (ret)
        return ret;

    return invalidate_inode_pages2_range(mapping, pos >> PAGE_SHIFT,
                                         end >> PAGE_SHIFT);
}

By returning early on a writeback error, it skips cache invalidation entirely.

Previously, as seen here in invalidate_inode_pages2_range(), the code captured
the error from folio_unmap_invalidate() but deliberately continued the loop to
invalidate the remaining clean pages:

mm/truncate.c:invalidate_inode_pages2_range() {
    ...
    ret2 = folio_unmap_invalidate(mapping, folio, GFP_KERNEL);
    if (ret2 < 0)
        ret = ret2;
    folio_unlock(folio);
    ...
}

For filesystems like FUSE that now use filemap_invalidate_pages():

fs/fuse/inode.c:fuse_reverse_inval_inode() {
    ...
    if (offset >= 0)
        filemap_invalidate_pages(inode->i_mapping, offset,
                                 offset + len - 1);
    ...
}

If a transient storage or network error occurs causing writeback to fail, the
early return in filemap_invalidate_pages() leaves clean, stale pages in the
page cache. Can this lead to silent data corruption and stale reads when
syncing with remote servers?
