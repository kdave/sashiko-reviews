xfs: handle fsverity I/O in write/read path

This commit adds IOMAP_F_FSVERITY support to XFS to handle reading and writing
fsverity metadata past EOF without updating the inode size or skipping folios.
It updates iomap begin and writepage functions to set this flag during

[Severity: High]
Does this code miss propagating IOMAP_F_FSVERITY to srcmap during COW
buffered writes in the non-zoned path?

When evaluating the COW path later in xfs_buffered_write_iomap_begin(),
srcmap is populated with the data fork extent via xfs_bmbt_to_iomap():

fs/xfs/xfs_iomap.c:xfs_buffered_write_iomap_begin() {
    ...
found_cow:
	if (imap.br_startoff <= offset_fsb) {
		error = xfs_bmbt_to_iomap(ip, srcmap, &imap, flags, 0,
				xfs_iomap_inode_sequence(ip, 0));
    ...
}

Because a hardcoded 0 is passed instead of iomap_flags, IOMAP_F_FSVERITY is
dropped from srcmap.

On always_cow mounts or if pre-existing COW extents are found, this can
cause iomap_block_needs_zeroing() to evaluate
srcmap->flags & IOMAP_F_FSVERITY as false. Since the write is past
i_size_read, it returns true, skipping the disk read and zeroing the
folio instead.

Could this regression overwrite valid on-disk data with zeroes when a
sub-folio write occurs (e.g., due to page eviction and subsequent
read-modify-write)?
