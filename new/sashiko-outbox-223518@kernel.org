btrfs: wait for async dio before dirtying folio in btrfs_cont_expand()

This commit adds an inode_dio_wait() call in btrfs_cont_expand() when the
existing file size is not sector-size aligned so that in-flight async
direct I/O writes complete before btrfs_truncate_block() dirties the tail
folio.

[Severity: Medium]
Should inode_dio_wait() live in btrfs_truncate_block() rather than
btrfs_cont_expand()?

When fallocate() extends a file whose i_size is unaligned and
alloc_start <= inode->i_size (for example, fallocating from EOF onward),
btrfs_fallocate() bypasses btrfs_cont_expand() and calls
btrfs_truncate_block() directly before waiting on ordered extents:

fs/btrfs/file.c:btrfs_fallocate() {
	...
	if (alloc_start > inode->i_size) {
		ret = btrfs_cont_expand(BTRFS_I(inode), i_size_read(inode),
					alloc_start);
		if (ret)
			goto out;
	} else if (offset + len > inode->i_size) {
		ret = btrfs_truncate_block(BTRFS_I(inode), inode->i_size,
					   inode->i_size, (u64)-1);
		if (ret)
			goto out;
	}
	...
}

That path still races with completing async direct I/O in
iomap_dio_complete(), triggering dio_warn_stale_pagecache() and marking
the mapping with -EIO for the next fsync().

Other direct callers of btrfs_truncate_block() such as btrfs_punch_hole()
and btrfs_zero_range() also remain exposed despite calling
btrfs_wait_ordered_range() first, because btrfs_dio_end_io() calls
btrfs_finish_ordered_extent() before iomap_dio_bio_end_io(), allowing the
ordered extent to finish before iomap_dio_complete() runs
kiocb_invalidate_post_direct_write() and inode_dio_end().

Calling inode_dio_wait() inside btrfs_truncate_block() once
need_truncate_head or need_truncate_tail is known to be true would cover
all of these paths.
