[Severity: Medium]
Should zoned_bg_reclaimable() also filter out block groups with
bg->used == 0 or with bg->reserved || bg->pinned?

In flush_space() -> btrfs_zoned_reclaim_sweep() -> zoned_sweep_space_info(),
the sweep runs right after COMMIT_TRANS and before btrfs_delete_unused_bgs().
Any full block group whose extents were all freed and unpinned has
bg->used == 0 and zoned_bg_garbage(bg) == bg->zone_capacity.

zoned_sweep_space_info() sees bg->used < mult_perc(bg->length, thresh_pct),
queues the empty block group for reclaim, and adds its entire zone_capacity
to garbage. Two such empty block groups saturate the 2 * fs_info->zone_size
target and prevent actual garbage collection candidates in cands[] from being
queued.

Similarly, if a full block group has bg->reserved > 0 or bg->pinned > 0,
zoned_sweep_space_info() queues it and counts its garbage toward the target,
or if most of the zone is still in bg->reserved (so bg->used is below the
threshold), marks it for reclaim. However, btrfs_reclaim_block_group() in
fs/btrfs/block-group.c does not relocate empty or busy block groups:

	if (bg->reserved || bg->pinned || bg->ro) {
		spin_unlock(&bg->lock);
		spin_unlock(&space_info->lock);
		up_write(&space_info->groups_sem);
		return 0;
	}

	if (bg->used == 0) {
		if (!btrfs_test_opt(fs_info, DISCARD_ASYNC))
			btrfs_mark_bg_unused(bg);
		spin_unlock(&bg->lock);
		spin_unlock(&space_info->lock);
		up_write(&space_info->groups_sem);
		return 0;
	}

Could selecting these block groups prevent reclaimable block groups from
being relocated during RECLAIM_ZONES, or cause a block group whose reserved
bytes convert to used bytes during an earlier relocation in the batch to be
relocated even when bg->used is above thresh_pct?
