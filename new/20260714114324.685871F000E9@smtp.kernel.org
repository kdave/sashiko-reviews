btrfs: fix a lockdep caused by path resolution during device scan

This commit avoids a full path lookup during device scan by comparing the
device dev_t instead. This prevents a circular locking dependency between
device_list_mutex and the VFS inode locks during kern_path().

[Severity: High]
Does changing this to a simple dev_t check break block device rename
tracking?

If a block device node is renamed or moved (e.g. via udev symlink changes
or LVM lvrename) and the old path is deleted, the new path will still have
the same dev_t.

Because device->devt == path_devt in this scenario, the condition evaluates
to false, and device_list_add() will skip updating device->name to the new
path. During a subsequent mount, will btrfs_open_devices() fail with -ENOENT
when it tries to open the cached, stale path?

[Severity: Medium]
Does this change also introduce unreachable code for mounted devices later in
this same block?

For a mounted device, device->name is non-NULL, so we only enter this
if-block when device->devt != path_devt.

Later in this block in device_list_add(), the code does:

[Severity: Critical]
This isn't a bug introduced by this patch, but there appears to be an RCU
list traversal issue in find_fsid_by_device() which is called by
device_list_add() during the device scan.

In fs/btrfs/volumes.c:find_fsid_by_device():

    list_for_each_entry(device, &devt_fs_devices->devices, dev_list) {

The devt_fs_devices->devices list is RCU-protected, with elements freed
after an RCU grace period via synchronize_rcu() in btrfs_rm_device().

Since find_fsid_by_device() iterates this list using the non-RCU-safe
list_for_each_entry() instead of list_for_each_entry_rcu(), and does so
without holding rcu_read_lock() or the device_list_mutex, could a
concurrent device removal result in a use-after-free when the freed
device pointer is dereferenced?
