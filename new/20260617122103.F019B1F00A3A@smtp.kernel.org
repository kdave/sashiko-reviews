btrfs: fix RAID stripe-tree lookup across leaf boundaries

btrfs_get_raid_extent_offset() resolves the stripe extent containing a
logical address by searching for that address and stepping back if there
is no exact match. This patch changes the step-back to use
btrfs_previous_item() to correctly cross leaf boundaries.

[Severity: High]
If the re-search returns greater than 0, is it possible for path->slots[0]
to equal btrfs_header_nritems(leaf)?

The previous code had a fallback decrement (path->slots[0]--) when the exact
key wasn't found, but the new re-search path omits this. If the search key is
larger than all items in the leaf, the loop below could read past the valid
items.

Since btrfs does not zero memory when deleting items, could this result in
parsing stale item headers and mapping I/O to a deleted physical extent?

[Severity: High]
This is a pre-existing issue, but does this loop need to validate that
found_key.type == BTRFS_RAID_STRIPE_KEY?

Looking at the forward scan in btrfs_get_raid_extent_offset(), it accepts
the parsed key based on objectid and offset without checking the item type:

    btrfs_item_key_to_cpu(leaf, &found_key, slot);
    found_logical = found_key.objectid;
    found_length = found_key.offset;

If a corrupted filesystem contains an unexpected item type here,
btrfs_item_size(leaf, slot) might be smaller than 16 bytes. Does this cause
btrfs_num_raid_stripes() to underflow to an enormous value, resulting in
millions of out-of-bounds read_extent_buffer() calls and a soft lockup?
