btrfs: send: fix is_current_inode_path() to avoid path resets for common prefixes

This commit fixes a regression in is_current_inode_path() where it
incorrectly returned true if the current inode's path was a prefix of
the given path. It corrects the issue by replacing strncmp with a length
check followed by strcmp.

[Severity: Low]
This isn't a bug, but does this comment invert the actual scenario being
fixed?

If the given path were a prefix of the current inode's path cur (the
scenario described by the comment), the original strncmp using
fs_path_len(cur) would have correctly returned false, since it would hit
the null terminator in path before finishing the comparison.

The issue seems to occur when cur is a prefix of path. Is the comment
accurate about the roles of the two paths?

> +	if (fs_path_len(path) != fs_path_len(cur))
> +		return false;
> +
> +	return (strcmp(path->start, cur->start) == 0);
>  }

[Severity: Critical]
This is a pre-existing issue, but it looks like a similar prefix-matching
regression might exist in __process_new_xattr().

If name is a user xattr that is a prefix of a special xattr (for example,
