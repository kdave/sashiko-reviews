Subject: btrfs: always wait for ordered extents to avoid OE races

This commit modifies the buffered writeback path to always wait for
any existing ordered extents, regardless of whether the write is beyond
the current isize. This fixes a panic caused by overlapping ordered extents
when direct IO falls back to buffered IO and reverts the isize.

Link: https://syzkaller.appspot.com/bug?extid=ba2afde329fc27e3f22e

[Severity: High]
This is a pre-existing issue, but does this violate IOCB_NOWAIT semantics?

The function btrfs_start_ordered_extent() blocks unconditionally without
checking if nowait is true. A thread requesting a non-blocking write (e.g.
via io_uring or AIO) will be blocked synchronously waiting for disk I/O to
complete when overlapping with an in-flight ordered extent.

While this bug existed before this patch for writes within i_size, this
commit extends the blocking behavior to all append writes by removing the
i_size check. Should this code return -EAGAIN if nowait is true before
starting and waiting for the ordered extent?
