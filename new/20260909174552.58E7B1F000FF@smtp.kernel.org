btrfs: downgrade the reflink source inode lock

This commit optimizes reflink operations by downgrading the source inode's
VFS lock from exclusive to shared. It adds a runtime flag to ensure direct
I/O writes still acquire the lock exclusively when synchronizing with a
reflink source.

[Severity: High]
Could downgrading the source inode's VFS lock to shared here allow
concurrent direct I/O reads to indefinitely starve the reflink operation?

Shortly after this downgrade, the code calls into the prep routines:

btrfs_remap_file_range()
  btrfs_remap_file_range_prep()
    generic_remap_file_range_prep()
      inode_dio_wait()

Because the source lock is now shared, new incoming direct I/O reads can
successfully acquire the shared i_rwsem lock and increment i_dio_count.
If there is a constant stream of DIO reads against the source file,
inode_dio_wait() might never see i_dio_count reach 0.

Since the reflink thread is holding the exclusive i_mmap_lock on both
files, and the exclusive i_rwsem on the destination file, could this
lead to a local Denial of Service by permanently hanging the thread and
blocking all other operations (like page faults or fsyncs) on both files?
