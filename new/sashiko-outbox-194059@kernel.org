[Severity: Medium]
What happens when a regular file is created on a filesystem mounted with
-o nodatacow inside a directory that has the nocompress attribute set (for
example via chattr +m or btrfs property set <dir> compression no)?

In fs/btrfs/inode.c:btrfs_create_new_inode(), directories do not get the
nodatacow flag set when created because that block is guarded by S_ISREG(),
allowing a directory to have BTRFS_INODE_NOCOMPRESS set on a nodatacow mount.
When a regular file is later created under that directory,
btrfs_inherit_iflags() copies BTRFS_INODE_NOCOMPRESS to the new file:

fs/btrfs/inode.c:btrfs_inherit_iflags() {
	if (flags & BTRFS_INODE_NOCOMPRESS) {
		inode->flags &= ~BTRFS_INODE_COMPRESS;
		inode->flags |= BTRFS_INODE_NOCOMPRESS;
	} else if (flags & BTRFS_INODE_COMPRESS) {
...
}

Because the check in btrfs_create_new_inode() only tests for
BTRFS_INODE_COMPRESS, it proceeds to set BTRFS_INODE_NODATACOW alongside
BTRFS_INODE_NOCOMPRESS on the new file.

However, fs/btrfs/ioctl.c:check_fsflags() treats FS_NOCOW_FL and
FS_NOCOMP_FL as mutually exclusive:

fs/btrfs/ioctl.c:check_fsflags() {
	/* NOCOW and compression options are mutually exclusive */
	if ((old_flags & FS_NOCOW_FL) && (flags & (FS_COMPR_FL | FS_NOCOMP_FL)))
		return -EINVAL;
	if ((flags & FS_NOCOW_FL) && (old_flags & (FS_COMPR_FL | FS_NOCOMP_FL)))
		return -EINVAL;
}

Wouldn't any subsequent btrfs_fileattr_set() call on that file (such as
chattr +i or chattr +a) still fail with -EINVAL due to having both flags set,
unless BTRFS_INODE_NOCOMPRESS is also handled when applying the nodatacow
mount option?
