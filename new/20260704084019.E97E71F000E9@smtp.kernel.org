btrfs: fix leaking BTRFS_FS_STATE_REMOUNTING flag

This commit changes the error handling of btrfs_check_options() and
btrfs_check_features() inside btrfs_reconfigure() to go to the restore
label. This prevents the BTRFS_FS_STATE_REMOUNTING flag from remaining

[Severity: High]
This is a pre-existing issue, but does calling btrfs_check_features() before
btrfs_ctx_to_info() validate the features against the old mount options rather
than the newly requested ones?

Since btrfs_check_features() relies on fs_info->mount_opt and
fs_info->compress_type, checking them before btrfs_ctx_to_info() transfers
the new context can allow users to bypass safety constraints during remount.

For example, a user could issue mount -o remount,space_cache=v1 on a subpage
system. btrfs_check_features() would incorrectly pass validation since it
checks the old mount options:

fs/btrfs/disk-io.c:btrfs_check_features() {
    ...
	if (fs_info->sectorsize != PAGE_SIZE && btrfs_test_opt(fs_info, SPACE_CACHE)) {
		btrfs_warn(fs_info,
	"v1 space cache is not supported for page size %lu with sectorsize %u",
			   PAGE_SIZE, fs_info->sectorsize);
		return -EINVAL;
	}
    ...
}

Similarly, enabling a new compression type like ZSTD during remount might
fail to set the appropriate incompat flag, as it checks the old compress_type:

fs/btrfs/disk-io.c:btrfs_check_features() {
    ...
	if (fs_info->compress_type == BTRFS_COMPRESS_LZO)
		incompat |= BTRFS_FEATURE_INCOMPAT_COMPRESS_LZO;
	else if (fs_info->compress_type == BTRFS_COMPRESS_ZSTD)
		incompat |= BTRFS_FEATURE_INCOMPAT_COMPRESS_ZSTD;
    ...
}

Could btrfs_check_features() be adjusted to validate the requested state?

>  	btrfs_remount_begin(fs_info, old_ctx.mount_opt, fc->sb_flags);
