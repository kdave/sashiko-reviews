[Severity: High]
Isn't this initialization of clone_data_offset overwritten unconditionally by
btrfs_file_extent_offset(leaf, ei) before the type != BTRFS_FILE_EXTENT_INLINE
check?

For an inline extent, the inline payload starts at disk_bytenr and the offset
field lies even further into the item.  When a clone source inode has an
inline extent at slot 0 with fewer than 24 bytes of inline data, calling
btrfs_file_extent_offset(leaf, ei) reads past eb->len in btrfs_get_64(),
which indexes eb->folios[] out of bounds or triggers report_setget_bounds().
Moving the btrfs_file_extent_offset() call inside the
type != BTRFS_FILE_EXTENT_INLINE branch avoids reading that field on inline
extents.

[Severity: High]
This problem wasn't introduced by this patch, but can the unguarded
btrfs_file_extent_offset(leaf, ei) call here still trigger the out-of-bounds
read [1] when clone_range() inspects a small inline extent at file
offset 0 positioned at the end of a leaf extent buffer?

Because inline extents do not have an offset field, reading it on a small
inline payload at a leaf boundary accesses memory past the end of the extent
buffer folio, which can cause a KASAN splat or kernel panic.
