[Severity: High]
This isn't a bug introduced by this patch, but will emitting the fileattr
here successfully apply NOCOW and COMPR flags?

Since finish_inode_if_needed() is called after data extents have been
processed (BTRFS_SEND_C_WRITE or BTRFS_SEND_C_CLONE), the file's data has
already been written and i_size > 0. When btrfs receive processes this
command, the kernel's btrfs_fileattr_set() silently ignores setting
BTRFS_INODE_NODATACOW if the file already has data:

fs/btrfs/ioctl.c:btrfs_fileattr_set() {
    ...
			if (inode->vfs_inode.i_size == 0)
				inode_flags |= BTRFS_INODE_NODATACOW |
					       BTRFS_INODE_NODATASUM;
    ...
}

Similarly, applying FS_COMPR_FL after data is written means the existing
data on the destination is not compressed.


[Severity: High]
Can emitting the fileattr here cause btrfs receive to fatally abort?

When a new file is created on the destination, it automatically inherits
flags like FS_COMPR_FL from its parent directory. If the original source
file had FS_NOCOW_FL, this patch will emit BTRFS_SEND_C_FILEATTR with
FS_NOCOW_FL.

When btrfs receive attempts to apply this, check_fsflags() forbids swapping
NOCOW and COMPR in a single ioctl:

fs/btrfs/ioctl.c:check_fsflags() {
    ...
	if ((flags & FS_NOCOW_FL) && (old_flags & (FS_COMPR_FL | FS_NOCOMP_FL)))
		return -EINVAL;
    ...
}

This -EINVAL error will abort the entire btrfs receive operation.
