[Severity: Medium]
Do these new error paths leave path holding a read lock on the space_root
leaf when jumping to out?

The out label only frees entries and space_runs without calling
btrfs_release_path(path) (which the existing !bitmap error path in this
loop also misses).  When create_remap_tree_entries() returns an error,
start_block_group_remapping() unlocks fs_info->remap_mutex and calls
btrfs_end_transaction(trans) while path still holds the tree lock, which
violates lock ordering and can self-deadlock on space_root if
__btrfs_end_transaction() -> btrfs_create_pending_block_groups() ->
btrfs_add_block_group_free_space() runs for a pending block group.  Calling
btrfs_release_path(path) in the out cleanup path would release the leaf on
all error exits.
