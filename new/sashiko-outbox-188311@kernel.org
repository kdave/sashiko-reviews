[Severity: High]
Was this change intended for the second LOOP_NO_EMPTY_SIZE check at the end
of find_free_extent_update_loop() rather than the first one?

After commit 390aa432f326 ("btrfs: decrease indentation of
find_free_extent_update_loop"), find_free_extent_update_loop() has two
separate checks for LOOP_NO_EMPTY_SIZE:

fs/btrfs/extent-tree.c:find_free_extent_update_loop() {
	...
	/* See the comments for btrfs_loop_type for an explanation of the phases. */
	if (ffe_ctl->loop == LOOP_NO_EMPTY_SIZE)
		return -ENOSPC;

	ffe_ctl->index = 0;
	if (ffe_ctl->loop == LOOP_CACHING_NOWAIT &&
	    (!ffe_ctl->orig_have_caching_bg && full_search))
		ffe_ctl->loop++;
	ffe_ctl->loop++;
	...
	if (ffe_ctl->loop == LOOP_NO_EMPTY_SIZE) {
		if (ffe_ctl->policy != BTRFS_EXTENT_ALLOC_CLUSTERED)
			return -ENOSPC;

		/*
		 * Don't loop again if we already have no empty_size and
		 * no empty_cluster.
		 */
		if (ffe_ctl->empty_size == 0 && ffe_ctl->empty_cluster == 0)
			return -ENOSPC;
		ffe_ctl->empty_size = 0;
		ffe_ctl->empty_cluster = 0;
	}

	return 1;
}

When ffe_ctl->loop is incremented from LOOP_WRONG_SIZE_CLASS to
LOOP_NO_EMPTY_SIZE, execution reaches the second check at the bottom of
find_free_extent_update_loop(). Because ffe_ctl->policy is still
BTRFS_EXTENT_ALLOC_ZONED on a zoned filesystem, that untouched check still
returns -ENOSPC immediately without zeroing ffe_ctl->empty_size or running
the LOOP_NO_EMPTY_SIZE pass for allocations with non-zero empty_size (such
as btrfs_alloc_tree_block() callers).

Meanwhile, the first check before ffe_ctl->loop++ is the loop termination
guard reached after LOOP_NO_EMPTY_SIZE has already finished; if it did not
return -ENOSPC, execution would fall through to ffe_ctl->loop++ and advance
ffe_ctl->loop past LOOP_NO_EMPTY_SIZE.
