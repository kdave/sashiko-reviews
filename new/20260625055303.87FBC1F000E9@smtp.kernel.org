btrfs: always wait for ordered extents to avoid OE races

Since commit ff66fe666233 ("btrfs: fix incorrect buffered IO fallback
for append direct writes"), if the direct IO finished short, we will
revert the isize back to the original one, so that append writes can be
respected during the buffered fallback.

This fixes a panic where the direct IO OE is still in the tree when we
insert the OE for the buffered write by making the OE wait unconditional.

Link: https://syzkaller.appspot.com/bug?extid=ba2afde329fc27e3f22e

This is a pre-existing issue, but doesn't this synchronously block the
thread if we are in a NOWAIT context?

If a userspace application submits an IOCB_NOWAIT write that overlaps with
an in-flight ordered extent, lock_and_cleanup_extent_if_need() finds it
and calls btrfs_start_ordered_extent(), which synchronously blocks.

Since this patch removes the start_pos < isize check, this blocking
behavior now extends to append writes as well, which could stall an
io_uring submission task. Should this check the nowait flag and return
-EAGAIN without waiting if it is true?
