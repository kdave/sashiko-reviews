xfs: always prioritize fsverity metadata ioends in ioend completion

This patch modifies ioend processing to prioritize fsverity metadata ioends
over data ioends. By ensuring metadata ioends are processed first, it avoids
a self-deadlock scenario where a metadata ioend holding a folio lock blocks a
data ioend waiting for that same folio. A custom sorting comparison function
is introduced to prioritize offsets beyond i_size.

[Severity: High]
Does this logic break offset-based sorting for same-class ioends?

Since xfs_read_ioend_compare returns 0 instead of falling back to
iomap_ioend_compare for two data ioends or two metadata ioends, it appears
they will be treated as equal. Could this prevent iomap_ioend_try_merge from
coalescing I/O requests properly?

Also, does the strict inequality (> i_size) miss fsverity metadata that
starts exactly at i_size, causing it to lose priority and potentially fail
to prevent the deadlock this patch is intended to address?
