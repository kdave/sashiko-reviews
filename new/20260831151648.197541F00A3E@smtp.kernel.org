btrfs: fix use-after-free on reloc root after error in insert_dirty_subvol()

This commit addresses a use-after-free issue on a reloc root by ensuring
that root->reloc_root is cleared and properly dereferenced if
merge_reloc_root() fails. It clears the pointer before jumping to the error
path where the reloc root is freed.

[Severity: Critical]
This is a pre-existing issue, but does dropping the reference to reloc_root
here without holding fs_info->reloc_mutex leave us vulnerable to a concurrent
use-after-free?

During the error path in merge_reloc_roots(), we call clear_reloc_root(root)
which sets root->reloc_root = NULL, and then drop the reference to
reloc_root. Since this happens without holding fs_info->reloc_mutex, can
another thread modifying the subvolume trigger btrfs_record_root_in_trans()
and take reloc_mutex to call btrfs_init_reloc_root()?

Because btrfs_init_reloc_root() lacks a read memory barrier between checking
BTRFS_ROOT_DEAD_RELOC_TREE and reading root->reloc_root, could the CPU
reorder the read and fetch the old reloc_root pointer?

If so, could merge_reloc_roots() free reloc_root while the concurrent thread
dereferences it via btrfs_set_root_last_trans()?
