btrfs: wait for RCU readers before freeing a new device

This commit addresses a slab-use-after-free by waiting for an RCU grace period
after removing a device from the devices list in the error path of
btrfs_init_new_device(). It adds a synchronize_rcu() call before freeing
the device.

[Severity: High]
This isn't a bug introduced by this patch, but adding synchronize_rcu() here
doesn't fully resolve the use-after-free because the device can still be
reachable.

Earlier in btrfs_init_new_device(), the device is assigned to latest_dev
during sprouting:

	btrfs_assign_next_active_device(fs_info->fs_devices->latest_dev,
					device);

If an operation fails and the code jumps to error_sysfs, latest_dev and
sb->s_bdev are not reverted. Since the device remains accessible through
these pointers, could new RCU readers still access the device after this
synchronize_rcu() grace period ends?

[Severity: Critical]
This is a pre-existing issue on this error path, but is it safe to free the
device here after it has already been committed to the filesystem?

During device sprouting, btrfs_commit_transaction() successfully commits the
new device into the chunk tree and active chunk maps. Shortly after, the code
attempts to attach a new transaction:

		trans = btrfs_attach_transaction(root);
		if (IS_ERR(trans)) {
			if (PTR_ERR(trans) == -ENOENT) {
				bdev_allow_freeze(file_bdev(bdev_file));
				return 0;
			}
			ret = PTR_ERR(trans);
			trans = NULL;
			goto error_sysfs;
		}

If btrfs_attach_transaction() fails, the code jumps to error_sysfs and
eventually calls btrfs_free_device(). Does freeing the device here leave
dangling pointers in the active chunk map stripes, which could cause a
use-after-free during subsequent I/O?
