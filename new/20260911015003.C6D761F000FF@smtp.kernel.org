[Severity: Critical]
This is a pre-existing issue, but I noticed a potential use-after-free
risk here. btrfs_scan_one_device() returns a raw btrfs_device pointer,
which is then dereferenced to access device->fs_devices->num_devices
while only holding the uuid_mutex. 

Could a concurrent btrfs_rm_device() execution free this device before we
access it? btrfs_rm_device() uses device_list_mutex and synchronize_rcu()
for safe removal, but we don't seem to be holding rcu_read_lock() or the
device_list_mutex here, meaning the device could potentially be freed while
we check its totals.

[Severity: High]
Does this UAPI macro define the wrong data transfer direction?

The ioctl accepts a struct btrfs_ioctl_vol_args from userspace, which
implies it should use _IOW (user writes to kernel). By using _IOR (kernel
writes to user), tools like strace, seccomp filters, or emulators (like
qemu-user) may fail to copy the input buffer into the guest kernel,
breaking the ioctl under emulation.
