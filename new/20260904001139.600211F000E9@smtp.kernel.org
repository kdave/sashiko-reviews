[Severity: High]
Is it possible for the asynchronous lo_clr_work to be left unflushed on
error paths, leading to a use-after-free upon module unload or device
removal?

In bdev_release(), if we take the early exit due to an open failure:

block/bdev.c:bdev_release() {
    ...
	if (IS_ERR(holder))
		goto put_no_open;
    ...
}

This jumps over the newly added post_release() invocation, bypassing the
synchronization.

A similar situation occurs in bdev_open() during rollback:

block/bdev.c:bdev_open() {
    ...
put_module:
	module_put(disk->fops->owner);
abort_claiming:
	if (holder)
		bd_abort_claiming(bdev, holder);
	mutex_unlock(&disk->open_mutex);
    ...
}

This error path drops the module reference without invoking post_release()
to flush the newly-queued asynchronous teardown work.

If an autoclear loop device is opened but bdev_open() fails (for example,
when opening an empty partition where blkdev_get_part() fails),
blkdev_put_whole() is called to rollback. This drops bd_openers to 0 and
triggers lo_release(), which queues the lo_clr_work asynchronously.

bdev_open() then jumps to the put_module error path and returns without
calling the post_release() callback. The subsequent VFS cleanup calls
bdev_release() with an error pointer (IS_ERR(holder)), which also bypasses
post_release(). The work remains pending on the workqueue without any flush,
which could allow it to access freed loop_device structures.
