btrfs: use IOMAP_DIO_BOUNCE flag instead of falling back to buffered IO

This patch allows direct writes to utilize the new IOMAP_DIO_BOUNCE flag
to bounce buffer direct I/O when the inode requires stable folios. It
removes the old logic that forced a fallback to buffered I/O in these
cases, significantly improving performance.

[Severity: High]
If a concurrent operation (like a balance) changes the block group profile
between iterations of the again loop in btrfs_direct_write(), could this
cause a partial write to be discarded?

Because need_stable_write() is evaluated dynamically per-iteration, a
transition to a profile requiring stable writes (e.g., RAID1) could cause
this to return ERR_PTR(-EAGAIN) mid-operation.

If that error propagates back to btrfs_direct_write(), it exits the loop
and hits the final return logic:

fs/btrfs/direct-io.c:btrfs_direct_write() {
    ...
again:
    from->nofault = true;
    dio = btrfs_dio_write(iocb, from, written);
    ...
out:
    return ret < 0 ? ret : written;
}

Would this return the negative error code and silently discard any
previously accumulated written bytes?

[Severity: High]
This isn't a bug introduced by this patch, but does btrfs_direct_write()
discard partial write progress when falling back to buffered I/O with
NOWAIT?

If a direct I/O write partially succeeds (written > 0) but a subsequent
iteration falls back to the buffered path, the NOWAIT check unconditionally
overrides ret with -EAGAIN:

fs/btrfs/direct-io.c:btrfs_direct_write() {
    ...
buffered:
    /* ... */
    if (iocb->ki_flags & IOCB_NOWAIT) {
        ret = -EAGAIN;
        goto out;
    }
    ...
out:
    return ret < 0 ? ret : written;
}

Could this cause the successfully written bytes to be discarded entirely,
potentially leading to duplicate writes or data corruption from the
user-space application's perspective?
