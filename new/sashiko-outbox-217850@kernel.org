btrfs: wait for the root filesystem to have all its devices

block devices when mounting a non-degraded multi-device root filesystem with

[Severity: High]
Does btrfs_missing_devices() ever reach zero on a sprouted root filesystem
backed by a seed device?

fs_devices->total_devices comes from the superblock's num_devices and
includes seed devices, whereas fs_devices->num_devices only counts devices
under the sprout fsid and excludes seed devices.  When btrfs_scan_all_devices()
scans a seed device, it registers that device under its own fsid in a
separate btrfs_fs_devices; seed devices are only linked onto the sprout's
fs_devices->seed_list later during open_ctree() -> open_seed_devices().
Consequently, btrfs_missing_devices() remains equal to at least the number
of seed devices even after every device is scanned, causing a bare rootwait
boot to hang indefinitely in btrfs_wait_for_devices().

Also, btrfs_get_tree_super() does not check !fs_devices->opened before
waiting, so a subsequent mount when device->devt matches the root device
would wait again even though device_list_add() rejects adding devices to an
already-opened fs_devices.

[Severity: Medium]
Can btrfs_warn() read uninitialized fields from res if jiffies passes end
before the while loop runs?

end is computed before calling btrfs_info().  With a small rootwait= timeout
and a slow serial console or preemption during btrfs_info(),
!time_after(jiffies, end) can be false on the first check, skipping
btrfs_scan_all_devices(&res) entirely and printing uninitialized stack
values from res.  Using a do-while loop guarantees at least one scan pass
and initializes res on every path that reaches the final btrfs_warn().

[Severity: High]
Does building with CONFIG_BTRFS_FS=m and CONFIG_BTRFS_ROOT_SCAN=y fail at
modpost?

BTRFS_ROOT_SCAN defaults to y whenever BTRFS_FS is enabled, including when
BTRFS_FS=m.  However, root_wait and is_root_dev() (in init/do_mounts.c) as
well as block_class used by btrfs_scan_all_devices() (in block/genhd.c) are
not exported with EXPORT_SYMBOL, causing btrfs.ko to fail to link with
undefined symbol errors.  Should BTRFS_ROOT_SCAN depend on BTRFS_FS=y?

[Severity: Medium]
Can reading device->devt after unlocking uuid_mutex cause a use-after-free?

btrfs_fs_devices_inc_holding() only pins fs_devices, not individual
btrfs_device structs.  Once uuid_mutex is dropped, a concurrent mount or
device removal can free device under uuid_mutex before is_root_dev(device->devt)
is evaluated:

CPU0                                  CPU1
btrfs_get_tree_super()
  mutex_lock(&uuid_mutex)
  device = btrfs_scan_one_device(...)
  btrfs_fs_devices_inc_holding(...)
  mutex_unlock(&uuid_mutex)
                                      /* concurrent mount or device removal */
                                      ...
                                        __btrfs_free_extra_devids()
                                          btrfs_free_device(device)
  is_root_dev(device->devt)  <-- use-after-free

Caching device->devt (or is_root_dev(device->devt)) in a local variable
before releasing uuid_mutex avoids dereferencing device unlocked.

[Severity: Medium]
Does this count every non-btrfs partition as an unreachable /dev node?

When btrfs_scan_one_device() opens a block device that does not contain a
btrfs superblock (such as an EFI System Partition, swap, or ext4),
btrfs_read_disk_super() returns ERR_PTR(-EINVAL).  Because the IS_ERR(device)
branch treats all errors identically and only the else branch increments
opened and found together, res->opened is always equal to res->found and
every non-btrfs device is counted in res->unreachable.  If no btrfs device
can be opened via /dev/<dev_name> on the first pass (for example, if the
root device uses a subdirectory devnode path such as /dev/cciss/c0d0p1),
btrfs_wait_for_devices() sees !res.opened, warns that non-btrfs partitions
have no node under /dev with errno -22 (-EINVAL), and aborts the wait loop
immediately.
