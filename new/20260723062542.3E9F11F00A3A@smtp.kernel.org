btrfs: disable direct reads to avoid dirty folios without fs knowing

This commit attempts to mitigate a denial-of-service vulnerability where
direct reads into memory mapped from a btrfs page cache can lead to dirty
folios without the filesystem's knowledge. It does this by temporarily
disabling btrfs direct reads for non-experimental builds, forcing a fallback
to buffered I/O.

[Severity: High]
This is a pre-existing issue, but does disabling direct reads locally fully
protect Btrfs mmaps from GUP-based pinning when the direct I/O source is on
another filesystem?

Because this mitigation only prevents Btrfs files from acting as the direct
I/O source, an attacker might bypass this by reading from a different
filesystem (e.g., ext4, xfs, or a loop device) with O_DIRECT into the Btrfs
mmap buffer.

In a cross-filesystem scenario, the source filesystem's direct I/O path will
still use get_user_pages() on the Btrfs mmap, and the block layer's
bio_check_pages_dirty() will dirty the Btrfs folios behind the filesystem's
back.

Additionally, io_uring fixed buffers (IORING_REGISTER_BUFFERS) pin Btrfs
mmaps and could expose the same flaw.

Could this mitigation be bypassed by untrusted cross-filesystem I/O?
