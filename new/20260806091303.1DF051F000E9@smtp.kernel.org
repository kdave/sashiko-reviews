This commit fixes an issue where btrfs_encoded_read_regular_fill_pages()
can return a negative errno instead of -EIOCBQUEUED when bios finish early.
Returning the negative errno caused a double-free because both the caller
and the deferred completion path attempted to clean up.

While reviewing this io_uring read path, I noticed a pre-existing issue in
the caller btrfs_uring_read_extent() located in fs/btrfs/ioctl.c:

fs/btrfs/ioctl.c:btrfs_uring_read_extent() {

	nr_pages = DIV_ROUND_UP(disk_io_size, PAGE_SIZE);
	pages = kzalloc_objs(struct page *, nr_pages, GFP_NOFS);
	if (!pages)
		return -ENOMEM;
    ...
}

[Severity: High]
This is a pre-existing issue, but does this direct return skip the lock
release and cause a memory leak?

If the kzalloc_objs() call for pages fails, the function returns -ENOMEM
directly. This bypasses the out_fail cleanup label where btrfs_unlock_extent()
and btrfs_inode_unlock() are called. 

Because the caller btrfs_uring_encoded_read() propagates this -ENOMEM
error without releasing the locks, it seems any subsequent operation that
tries to acquire these locks on the file (such as read, write, or
truncate) will hang forever in uninterruptible sleep. This also appears
to leak data->iov in the caller.

Could this be fixed to ensure the extent and inode locks are properly
released on this allocation failure path?
