btrfs: add "rescue=usebackuproot" into "rescue=all" shortcut

The mount option "rescue=all" should be a shortcut to include all
"rescue=" mount options. But unfortunately "rescue=usebackuproot" is not
included.

Include that option so "rescue=all" has a better chance to mount a
corrupted fs.

[Severity: High]
This isn't a bug introduced by this patch, but adding USEBACKUPROOT to 
rescue=all combines it with IGNOREBADROOTS, which appears to mask sub-tree 
load failures.

In fs/btrfs/disk-io.c:load_global_roots_objectid():

	if (!btrfs_test_opt(fs_info, IGNOREBADROOTS))
		ret = ret ? ret : -ENOENT;
	else
		ret = 0;

If ret is 0, then in fs/btrfs/disk-io.c:init_tree_roots():

	ret = btrfs_read_roots(fs_info);
	if (ret < 0) {
		handle_error = true;
		continue;
	}

Does this short-circuit the USEBACKUPROOT fallback? If a global sub-tree is
corrupted, will IGNOREBADROOTS cause us to skip the backup root entirely and
mount in a severely degraded state instead of utilizing the fallback?

[Severity: High]
This is a pre-existing issue, but does adding more options to rescue=all
exacerbate a problem with remounting?

When mounting with multiple rescue options (like rescue=all),
fs/btrfs/super.c:print_rescue_option() formats them with colons:

	seq_printf(seq, "%s%s", (*printed) ? ":" : ",rescue=", s);

This populates /proc/mounts with a colon-separated list like
rescue=nologreplay:usebackuproot.

During a remount, the mount operation reads this string and passes it to the
kernel. The VFS mount API parse logic for Opt_rescue expects an exact string 
match and cannot tokenize colon-separated lists. Will this cause remount
operations (e.g. mount -o remount,ro /mnt) to fail with -EINVAL?
