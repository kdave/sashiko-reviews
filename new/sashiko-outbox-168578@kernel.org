btrfs: add per-inode compression levels in xattrs

This commit adds support for per-inode compression levels in btrfs by parsing
"algo:level" strings from the compression xattr. It introduces a new
prop_compress_level field in btrfs_inode and updates the writeback and inline
extent paths to apply the configured level.

Does this code introduce a data race between reading the compression type
and level here, and updating them concurrently in prop_compression_apply()?

Since compress_file_range() reads inode->prop_compress and
inode->prop_compress_level locklessly, and prop_compression_apply()
performs independent non-atomic stores to these adjacent fields, a torn
read could occur. This could allow the writeback path to see a newly
updated algorithm type paired with the old compression level.
