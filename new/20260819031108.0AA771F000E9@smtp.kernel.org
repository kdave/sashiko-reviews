btrfs: always return -EIOCBQUEUED after btrfs_uring_read_extent_endio

This commit fixes an issue where btrfs_encoded_read_regular_fill_pages()
returned an I/O status directly instead of -EIOCBQUEUED when all bios finished
early. This previously caused a double-free because btrfs_uring_read_extent()
and btrfs_uring_read_finished() would both unlock and free resources.

Closes: https://lore.kernel.org/linux-btrfs/20260630091609.3414-1-samsun1006219@gmail.com/

[Severity: High]
This isn't a bug introduced by this patch, but I noticed a lock leak in
btrfs_uring_read_extent() in fs/btrfs/ioctl.c when page array allocation
fails:

fs/btrfs/ioctl.c:btrfs_uring_read_extent() {
    ...
    pages = kzalloc_objs(struct page *, nr_pages, GFP_NOFS);
    if (!pages)
        return -ENOMEM;
    ...
}

Does returning -ENOMEM directly here bypass the btrfs_unlock_extent() and
btrfs_inode_unlock() calls at the out_fail label? The caller already
successfully locked the file extent and acquired the inode's i_rwsem, so it
seems this early return would permanently leak both locks.

[Severity: Medium]
This is a pre-existing issue, but does btrfs_uring_encoded_read() in
fs/btrfs/ioctl.c leak data->iov when btrfs_uring_read_extent() fails?

fs/btrfs/ioctl.c:btrfs_uring_encoded_read() {
    ...
    if (ret == -EIOCBQUEUED) {
        ...
        ret = btrfs_uring_read_extent(...);
        goto out_acct;
    }

out_free:
    kfree(data->iov);
    ...
}

If btrfs_uring_read_extent() fails (e.g., due to an -ENOMEM error like the one
above), it returns the error code directly. Does jumping to out_acct then
unconditionally skip the out_free label, leaking the dynamically allocated
data->iov array?

[Severity: High]
This isn't a bug introduced by this patch, but I noticed a potential memory leak
in fs/btrfs/ioctl.c when an io_uring request returning -EAGAIN is cancelled from
io-wq:

fs/btrfs/ioctl.c:btrfs_uring_encoded_read() {
    ...
    data = kzalloc_obj(*data, GFP_NOFS);
    if (!data) {
        ret = -ENOMEM;
        goto out_acct;
    }

    bc->data = data;
    ...
}

When btrfs_uring_encoded_read() returns -EAGAIN, the dynamically allocated
data pointer is stashed in bc->data for reuse on reissue. If the io-wq task
is cancelled before processing, io_clean_op() calls io_uring_cmd_cleanup().

However, since the command isn't marked cancelable via
io_uring_cmd_mark_cancelable(), its driver-specific cancellation callback
won't be invoked. Does this leak both bc->data and data->iov?

[Severity: High]
This is a pre-existing issue, but can btrfs_uring_encoded_read() in
fs/btrfs/ioctl.c deadlock via page fault when copying to user space?

fs/btrfs/ioctl.c:btrfs_uring_encoded_read() {
    ...
    if (copy_to_user(sqe_addr + copy_end,
                     (const char *)&data->args + copy_end_kernel,
                     sizeof(data->args) - copy_end_kernel)) {
    ...
}

When btrfs_encoded_read() returns -EIOCBQUEUED, the inode (i_rwsem shared) and
file extent remain locked. If the user-provided sqe_addr points to a memory
mapped region of the same file, could this copy_to_user() trigger a page
fault (such as btrfs_read_folio or btrfs_page_mkwrite) that attempts to
acquire the exact same non-recursive extent lock, causing a deadlock?
