Does jumping to again when btrfs_set_data_reloc_bg() returns false cause
an infinite loop?

When bg is in data_sinfo, btrfs_set_data_reloc_bg() calls
btrfs_inc_block_group_ro_notrans(bg) -> inc_block_group_ro(bg, false):

fs/btrfs/block-group.c:inc_block_group_ro() {
	...
	} else if (sinfo->flags & BTRFS_BLOCK_GROUP_DATA) {
		u64 sinfo_used = btrfs_space_info_used(sinfo, true);

		if (sinfo_used + num_bytes <= sinfo->total_bytes)
			ret = 0;

If bg's free space is needed to cover existing reservations in data_sinfo
(such as data_sinfo->bytes_may_use from delalloc or bytes_pinned), or if
zoned_move_bg_to_space_info() rejects bg because bg->pinned or
bg->remap_bytes is non-zero (which usable does not check),
btrfs_set_data_reloc_bg() returns false without modifying bg or removing
it from data_sinfo->block_groups[index].  goto again then restarts from
the head of bg_list, picks the same unchanged bg, and spins forever
without advancing to later block groups or reaching btrfs_chunk_alloc().

[Severity: Medium]
What rechecks bg's state in btrfs_set_data_reloc_bg() when migrate is
false?

When btrfs_zoned_reserve_data_reloc_bg() allocates a new chunk in
reloc_sinfo and jumps back to again, space_info is reloc_sinfo, so
migrate = (bg->space_info == data_sinfo) in btrfs_set_data_reloc_bg() is
false.  Because tmp->lock and groups_sem are dropped before calling
btrfs_set_data_reloc_bg(), and the !migrate path never takes bg->lock to
reverify that bg is still empty and writable, a concurrent relocation
allocation can allocate from or fill bg before fs_info->data_reloc_bg is
set and btrfs_zone_activate(bg) is called (triggering the
WARN_ON_ONCE(btrfs_zoned_bg_is_full(block_group)) in
btrfs_zone_activate()).

Also, because migrate = (bg->space_info == data_sinfo) is evaluated
without locking at the start of btrfs_set_data_reloc_bg(), a second
caller racing on the same candidate bg after the first caller moves it to
reloc_sinfo can see migrate == false, win relocation_bg_lock while
bg->ro == 1, and force the first caller into the rollback path.
