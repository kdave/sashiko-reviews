btrfs: defrag: use simple list_del() in defrag_collect_targets()

This commit updates defrag_collect_targets() to use list_del() instead of
list_del_init(). Since the list entry is freed immediately after removal,
initializing it is unnecessary.

[Severity: High]
This isn't a bug introduced by this patch, but looking at the earlier logic
in defrag_collect_targets(), does this size check correctly skip small
inline extents?

For inline extents, em->len represents the sector size rather than the
actual data size. If max_inline is smaller than the sector size, this
condition will evaluate to false.

Could this cause all inline extents to bypass the skip check, becoming
spuriously targeted for defragmentation and converted into regular extents?

Would it be more accurate to compare against em->ram_bytes instead of
em->len here to prevent unnecessary space consumption and I/O?
