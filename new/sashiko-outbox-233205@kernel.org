[Severity: Medium]
Can returning relocation block groups only after the reclaim loop drop the
data RAID profile from fs_info->avail_data_alloc_bits?

If the reclaim loop removes the last block group of a non-SINGLE profile
(such as DUP or RAID1) from data_sinfo->block_groups[index] while the
relocated extents live in reloc_sinfo->block_groups[index],
btrfs_remove_block_group() sees an empty list and calls
clear_avail_alloc_bits().  When btrfs_zoned_return_data_reloc_bgs() then
moves those block groups back to data_sinfo via
zoned_move_bg_to_space_info(), set_avail_alloc_bits() is never called, so
btrfs_zoned_reserve_data_reloc_bg() and later data chunk allocations fall
back to SINGLE.

[Severity: High]
Does allowing a non-empty block group to move to data_sinfo corrupt pinned
and reserved space accounting and race with concurrent extent frees?

If an extent in a finished relocation block group was freed in the current
uncommitted transaction before btrfs_zoned_return_data_reloc_bgs() runs,
bg->pinned is non-zero and accounted in reloc_sinfo->bytes_pinned.
zoned_move_bg_to_space_info() neither checks nor transfers bg->pinned (or
bg->reserved), so when the transaction commits, unpin_extent_range()
subtracts the pinned bytes from data_sinfo->bytes_pinned, underflowing it
and triggering WARN_ON(1) in btrfs_space_info_update_bytes_pinned() while
permanently leaking reloc_sinfo->bytes_pinned.

Even when bg->pinned == 0 at the start of the move, bg->used > 0 allows a
concurrent extent free or transaction commit to race because
btrfs_update_block_group() and unpin_extent_range() read
cache->space_info before locking space_info->lock and cache->lock:

CPU0                                  CPU1
btrfs_update_block_group(bg, ..., false)
  space_info = bg->space_info
  /* reloc_sinfo */
                                      zoned_move_bg_to_space_info()
                                        spin_lock(&data_sinfo->lock)
                                        spin_lock_nested(&reloc_sinfo->lock)
                                        spin_lock(&bg->lock)
                                        reloc_sinfo->bytes_used -= bg->used
                                        data_sinfo->bytes_used += bg->used
                                        bg->space_info = data_sinfo
                                        ...
  spin_lock(&reloc_sinfo->lock)
  spin_lock(&bg->lock)
  reloc_sinfo->bytes_used -= num_bytes  <-- underflows reloc_sinfo->bytes_used
  btrfs_space_info_update_bytes_pinned(reloc_sinfo, num_bytes)

When the transaction later commits, unpin_extent_range() reads
bg->space_info == data_sinfo and unpins num_bytes from data_sinfo instead
of reloc_sinfo.

[Severity: Medium]
Can clearing BLOCK_GROUP_FLAG_ZONED_DATA_RELOC unconditionally here expose
a relocation block group to regular allocations while its hardware write
pointer is still behind bg->alloc_offset?

do_allocation_zoned() sets BLOCK_GROUP_FLAG_ZONED_DATA_RELOC and advances
bg->alloc_offset during preallocation in prealloc_file_extent_cluster(),
and clears fs_info->data_reloc_bg as soon as a subsequent extent does not
fit.  Normally btrfs_zoned_release_data_reloc_bg() clears
BLOCK_GROUP_FLAG_ZONED_DATA_RELOC only after ordered I/O completes up to
bg->alloc_offset.  If relocation fails or is canceled after preallocation
and after fs_info->data_reloc_bg has moved on, the unwritten preallocated
range leaves the zone write pointer behind bg->alloc_offset, so clearing
the flag and returning the block group to data_sinfo allows subsequent
allocations or zone finish operations on a mismatched write pointer.
