btrfs: remove the trailing zeros from compressed inline extent

This commit changes the behavior of btrfs when generating compressed
inline extents by using the file range [0, i_size) instead of
[0, sectorsize). It introduces an early check to reject i_size >=
blocksize to prevent races with btrfs_setsize() expansion while keeping
the i_size stable during writeback.

[Severity: High]
Does this check sufficiently protect against i_size truncation down to 0?

The VFS function truncate_setsize() can update inode->i_size to 0 before
calling truncate_pagecache(). If the background writeback thread has already
locked folio 0 and passed the initial i_size checks in extent_writepage(),
truncate_pagecache() will block waiting for the folio lock.

Writeback then proceeds to run_delalloc_inline(), where it re-reads i_size.
Since i_size is now 0, the check for i_size >= blocksize will pass, allowing
an i_size of 0 to slip through.

[Severity: High]
Can a 0-length request be passed to the compression engine here?

Because i_size was changed to replace the previously safe blocksize parameter,
and an i_size of 0 can pass the earlier checks, btrfs_compress_bio() can be
called with a length of 0.

This leads to a kernel panic on builds with CONFIG_BTRFS_ASSERT enabled,
as the compression engine in lzo_compress_bio() calls ASSERT(len) which fails
when len is 0. On non-debug builds, it passes a 0-length request to the
compression engine, creating a malformed 0-byte inline extent.

This appears reachable by a local user performing a write followed by a
concurrent ftruncate() down to 0 while the system initiates writeback.
