btrfs: fix deadlocks with transaction commit when cloning inline extents

This commit avoids starting a transaction after dirtying an inline extent
folio while the destination range is locked by starting the transaction in
copy_inline_to_page() before creating and dirtying the folio, and updating
i_size while the folio is locked. When the clone range extends past an inline
extent, it defers cloning the inline extent to a second and final pass.

[Severity: High]
When deferring the inline extent to a second pass while cloning into or
beyond EOF, could a failure after later extents have been committed leave an
unmapped gap at [destoff, inline_end) and a permanently stuck disk_i_size on
filesystems without NO_HOLES?

In the first pass (inline_state == CLONE_INLINE_NONE), btrfs_clone() skips
[destoff, inline_end) by setting last_dest_end = inline_end without inserting
an extent or hole item in the subvolume tree and without marking [destoff,
inline_end) as EXTENT_DIRTY in inode->file_extent_tree.

As the first pass processes the remaining range [inline_end, destoff + len),
btrfs_replace_file_extents() inserts extent items starting at inline_end and
clone_finish_inode_update() advances inode->vfs_inode.i_size up to
destoff + olen:

    if (endoff > vfs_inode->i_size) {
        i_size_write(vfs_inode, endoff);
        btrfs_inode_safe_disk_i_size_write(inode, 0);
    }

In the second pass (inline_state == CLONE_INLINE_LAST), because
i_size_read(&inode->vfs_inode) > datal now holds in
clone_copy_inline_extent(), it always takes the copy_to_page path into
copy_inline_to_page(), which must reserve data and metadata space via
btrfs_delalloc_reserve_space() and allocate a folio via
__filemap_get_folio().

If the first pass exits early after committing an extent (for example,
returning -EINTR on fatal_signal_pending(current) or failing on a subsequent
extent) or if the second pass fails in copy_inline_to_page() (such as -ENOSPC
or -EDQUOT in btrfs_delalloc_reserve_space(), or -ENOMEM in
__filemap_get_folio()), vfs_inode->i_size has already been increased past
inline_end while [destoff, inline_end) was never populated.

On filesystems without NO_HOLES (where inode->file_extent_tree is used),
btrfs_inode_safe_disk_i_size_write() requires a contiguous EXTENT_DIRTY range
starting at offset 0:

    found = btrfs_find_contiguous_extent_bit(inode->file_extent_tree, 0, &start,
                                             &end, EXTENT_DIRTY);
    if (found && start == 0)
        i_size = min(i_size, end + 1);
    else
        i_size = 0;
    inode->disk_i_size = i_size;

Because [destoff, inline_end) is neither backed by a hole extent item on disk
nor marked EXTENT_DIRTY in inode->file_extent_tree, inode->disk_i_size
remains stuck at or below destoff even though vfs_inode->i_size and extent
items exist beyond inline_end. Subsequent expanding writes or truncates
beyond vfs_inode->i_size pass oldsize = vfs_inode->i_size to
btrfs_cont_expand(), which only fills holes starting from
ALIGN(oldsize, sectorsize) and never populates [destoff, inline_end), causing
data past destoff to be lost across inode eviction or unmount, and leaving a
missing hole extent item after fsync log replay.
