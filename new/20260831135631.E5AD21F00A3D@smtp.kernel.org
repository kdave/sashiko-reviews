btrfs: protect sb_write_pointer() with invalidate lock

sb_write_pointer() reads the super block from the block device page cache
using read_cache_page_gfp(). This has the same race with BLKBSZSET as the
one fixed by commit 3f29d661e568 ("btrfs: sync read disk super and set
block size").

Take the mapping invalidate lock around read_cache_page_gfp() to
serialize the read against block size changes.

[Severity: High]
This is a pre-existing issue, but while reviewing this fix for
sb_write_pointer(), I noticed the exact same race condition appears to still
exist in btrfs_read_disk_super().

In fs/btrfs/volumes.c:btrfs_read_disk_super(), the primary superblock read
path performs an unprotected page cache read:

    page = read_cache_page_gfp(mapping, bytenr >> PAGE_SHIFT, GFP_NOFS);
    if (IS_ERR(page))
            return ERR_CAST(page);

Since btrfs_read_disk_super() is missing the filemap_invalidate_lock()
protection against the BLKBSZSET race, could a concurrent BLKBSZSET ioctl
during a superblock read still alter mapping->flags and
mapping_min_folio_order() between folio allocation and filemap_add_folio()?

If this occurs, it appears this could lead to a VM_BUG_ON_FOLIO or a NULL
pointer dereference in create_empty_buffers() during mount. The commit
under review correctly protects sb_write_pointer() and notes that upstream
commit 3f29d661e568 fixed the same issue in btrfs_read_disk_super(), but
the current tree does not seem to contain that prerequisite fix.

Should btrfs_read_disk_super() also be protected with
filemap_invalidate_lock() in this tree to fully close this race condition?
