[Severity: High]
This isn't a bug introduced by this patch, but while reviewing the buffered
IO fallback for append direct writes, could there be a pre-existing race
condition in btrfs_direct_write() during the fallback?

In btrfs_direct_write(), the inode lock is dropped before the fallback
path. During this unlocked window, if a concurrent thread appends to the
file, the i_size increases. The fallback code saves the stale position
before calling btrfs_buffered_write():

    pos = iocb->ki_pos;
    written_buffered = btrfs_buffered_write(iocb, from);

Inside btrfs_buffered_write(), the lock is reacquired and
generic_write_checks() updates iocb->ki_pos to the new i_size due to the
IOCB_APPEND flag. Data is then correctly written at the new EOF.

However, when btrfs_buffered_write() returns, btrfs_direct_write() appears
to use the stale pos to calculate the sync range and flushes the wrong
range, potentially leaving the newly appended data unsynced:

    endbyte = pos + written_buffered - 1;
    ret = btrfs_fdatawrite_range(BTRFS_I(inode), pos, endbyte);

Does it then also overwrite the correct file position with the stale value?

    iocb->ki_pos = pos + written_buffered;
