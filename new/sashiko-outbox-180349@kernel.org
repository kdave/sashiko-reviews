btrfs: zoned: promote reset data block groups to the relocation target

This commit updates btrfs_reset_unused_block_groups() and
zoned_reset_bg_in_place() to promote an in-place reset data block group to
be the data relocation target when fs_info->data_reloc_bg is unset, instead
of returning its reclaimed space to the data space_info first.

[Severity: High]
Can a concurrent data reservation or extent allocation still claim this
reclaimed space in fs/btrfs/zoned.c:zoned_reset_bg_in_place() after
bg->lock and space_info->lock are dropped, before btrfs_set_data_reloc_bg()
migrates the block group out of fs_info->data_sinfo?

In zoned_reset_bg_in_place(), bg->alloc_offset is reset to 0 and
space_info->bytes_zone_unusable is decremented by *reclaimed while
space_info->total_bytes still includes bg->length:

	*reclaimed = bg->alloc_offset;
	bg->zone_unusable = bg->length - bg->zone_capacity;
	bg->alloc_offset = 0;
	...
	bg->free_space_ctl->free_space += *reclaimed;
	btrfs_space_info_update_bytes_zone_unusable(space_info, -*reclaimed);
	spin_unlock(&bg->lock);

Skipping btrfs_return_free_space() avoids calling
btrfs_try_granting_tickets(space_info) on this CPU, but reducing
bytes_zone_unusable immediately reduces btrfs_space_info_used(space_info,
true). Once spin_unlock(&space_info->lock) runs, a concurrent buffered
write calling:

  btrfs_check_data_free_space()
    -> btrfs_reserve_data_bytes()
      -> reserve_bytes()

(when no tickets are queued) or a concurrent reservation release calling:

  btrfs_space_info_free_bytes_may_use()
    -> btrfs_try_granting_tickets()

can see used + orig_bytes <= space_info->total_bytes and grant
space_info->bytes_may_use reservations backed by this block group.

When btrfs_set_data_reloc_bg() then runs, its still_empty check only
inspects block-group-level fields:

		down_write(&data_sinfo->groups_sem);
		spin_lock(&bg->lock);
		still_empty = (bg->alloc_offset == 0 && bg->used == 0 &&
			       bg->reserved == 0 && !bg->ro &&
			       bg->space_info == data_sinfo);
		if (still_empty)
			list_del_init(&bg->list);
		spin_unlock(&bg->lock);
		up_write(&data_sinfo->groups_sem);

Because delalloc reservations only increment data_sinfo->bytes_may_use,
still_empty remains true, and zoned_move_bg_to_space_info() then subtracts
bg->length from from->total_bytes:

	spin_lock(&from->lock);
	from->total_bytes -= bg->length;

leaving data_sinfo->bytes_may_use overcommitted and causing subsequent
writeback to hit -ENOSPC. In addition, between spin_unlock(&bg->lock) in
zoned_reset_bg_in_place() and down_write(&data_sinfo->groups_sem) in
btrfs_set_data_reloc_bg(), bg remains on data_sinfo->block_groups with
bg->alloc_offset == 0 and without BLOCK_GROUP_FLAG_ZONED_DATA_RELOC, so a
concurrent find_free_extent() for a normal data write can allocate an
extent from bg and defeat the promotion.

[Severity: High]
Could sampling !fs_info->data_reloc_bg locklessly in
fs/btrfs/zoned.c:btrfs_reset_unused_block_groups() race with concurrent
data relocation allocations in fs/btrfs/extent-tree.c:find_free_extent() ->
do_allocation_zoned() (or another reset caller)?

In btrfs_reset_unused_block_groups(), !fs_info->data_reloc_bg is read
without fs_info->relocation_bg_lock before zoned_reset_bg_in_place() issues
synchronous REQ_OP_ZONE_RESET I/O via blkdev_zone_mgmt() and before
btrfs_set_data_reloc_bg() acquires down_write(&data_sinfo->groups_sem).
Then fs/btrfs/zoned.c:btrfs_set_data_reloc_bg() unconditionally overwrites
fs_info->data_reloc_bg and publishes it before migrating the block group:

	spin_lock(&fs_info->relocation_bg_lock);
	fs_info->data_reloc_bg = bg->start;
	spin_unlock(&fs_info->relocation_bg_lock);
	set_bit(BLOCK_GROUP_FLAG_ZONED_DATA_RELOC, &bg->runtime_flags);

	if (migrate)
		zoned_move_bg_to_space_info(fs_info, bg, data_sinfo->sub_group[0]);

If a concurrent relocation allocation in
fs/btrfs/extent-tree.c:do_allocation_zoned() checks fs_info->data_reloc_bg,
drops fs_info->relocation_bg_lock to call btrfs_zone_activate(block_group),
and then re-acquires fs_info->relocation_bg_lock after
btrfs_set_data_reloc_bg() has changed fs_info->data_reloc_bg to bg->start,
it will trip the assertion in do_allocation_zoned():

	ASSERT(!ffe_ctl->for_data_reloc ||

	       fs_info->data_reloc_bg == 0);

btrfs_set_data_reloc_bg() will overwrite fs_info->data_reloc_bg and strand
the previous block group with BLOCK_GROUP_FLAG_ZONED_DATA_RELOC set so its

bg->list from data_sinfo and publishes fs_info->data_reloc_bg = bg->start
