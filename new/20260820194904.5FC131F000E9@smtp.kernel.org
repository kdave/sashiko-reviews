[Severity: High]
Does removing launder_folio cause read, write, and mmap syscalls to spuriously
fail with -EBUSY during cache invalidation when encountering dirty folios?

If a user process mmaps an OrangeFS file and writes to it, dirtying pages via
orangefs_page_mkwrite, and concurrently another thread calls read, the
cache timeout expiration will trigger orangefs_revalidate_mapping:

fs/orangefs/file.c:orangefs_revalidate_mapping() {
    ...
    unmap_mapping_range(mapping, 0, 0, 0);
    ret = filemap_invalidate_pages(mapping, 0, OFFSET_MAX);
    ...
}

If the mmap thread redirties a page before the invalidation processes it,
folio_unmap_invalidate encounters a dirty folio.

Before this patch, orangefs_launder_folio synchronously wrote out the
redirtied page and freed its private data, allowing invalidation to succeed.

Without launder_folio, folio_unmap_invalidate leaves the private data
attached, causing filemap_release_folio to fail and -EBUSY to be returned,
which propagates up to the VFS.
