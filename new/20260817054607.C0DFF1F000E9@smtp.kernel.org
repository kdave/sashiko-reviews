This commit fixes a missing folio_unlock() in the error path of
btrfs_read_merkle_tree_page(), preventing a permanent hang when subsequent
attempts try to lock the same folio after a read failure.

[Severity: High]
This is a pre-existing issue, but does this code silently fail to copy data
on 32-bit highmem systems?

If the allocated page cache folio comes from the highmem zone,
folio_address(folio) returns NULL. However, read_key_bytes() interprets a
NULL dest argument as a signal to only count sizes and skip copying data:

fs/btrfs/verity.c:read_key_bytes() {
    ...
        /* desc = NULL to just sum all the item lengths */
        if (!dest)
            copy_end = item_end;
    ...
        if (dest) {
            if (dest_folio)
                kaddr = kmap_local_folio(dest_folio, 0);
    ...
}

Since folio_address() evaluates to NULL for unmapped highmem pages,
read_key_bytes() will entirely skip copying the data, leaving the folio
uninitialized but incorrectly marked uptodate later in this function.

>  	if (ret < 0) {
> +		folio_unlock(folio);

[Severity: High]
This isn't a bug introduced by this patch, but does leaving the folio in
the page cache here convert transient read errors into permanent ones?

While this patch correctly unlocks the folio and prevents a hang, the error
path fails to evict the folio from the page cache, leaving it present but
not uptodate.

A subsequent lookup will find this left-behind folio and assume a permanent
read error instead of retrying the read_key_bytes() operation:

fs/btrfs/verity.c:btrfs_read_merkle_tree_page() {
    ...
    folio = __filemap_get_folio(inode->i_mapping, index, FGP_ACCESSED, 0);
    if (!IS_ERR(folio)) {
        ...
        folio_lock(folio);
        /* If it's not uptodate after we have the lock, we got a read error. */
        if (!folio_test_uptodate(folio)) {
            folio_unlock(folio);
            folio_put(folio);
            return ERR_PTR(-EIO);
        }
    ...
}

Could a transient error (like -ENOMEM during btrfs_alloc_path) permanently
break verity file access until the page cache is dropped?

>  	}
