btrfs: fix RAID stripe-tree lookup across leaf boundaries

A stripe-tree lookup resolves the stripe extent containing a logical
address by searching for that address and stepping back to the preceding
item, since the containing extent begins at or before it. That step-back
was confined to a single leaf, so when the search landed on the first
slot of a leaf the containing extent - the last item of the previous
leaf - was never examined and a perfectly valid address returned
-ENODATA.

[Severity: High]
Does this new fallback logic introduce an out-of-bounds read in the leaf's
item array?

When the fallback btrfs_search_slot() is called for stripe_key and the
key is greater than all items in the leaf (or the leaf is empty), it
returns > 0 and sets path->slots[0] to the insertion index, which equals
btrfs_header_nritems(leaf).

The code then unconditionally enters the while (1) loop and immediately
calls btrfs_item_key_to_cpu() on the new slot:

    while (1) {
        leaf = path->nodes[0];
        slot = path->slots[0];
        btrfs_item_key_to_cpu(leaf, &found_key, slot);

Since the pre-patch logic that safely decremented the slot was removed,
there is no check to ensure slot < btrfs_header_nritems(leaf) before the
item is accessed.

Could this read uninitialized or unrelated memory into found_key, causing
it to be incorrectly parsed as a valid raid extent if the garbage data
happens to satisfy the range checks?
