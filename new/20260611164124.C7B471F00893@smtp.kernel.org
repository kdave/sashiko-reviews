[Severity: High]
This isn't a bug introduced by this patch, but does adding this
clear_reloc_root() call here create a triggerable race window for
concurrent snapshot operations?

Looking at reloc_root_is_dead(), the smp_rmb() is placed before the
test_bit(), which fails to provide the required ordering:

fs/btrfs/relocation.c:reloc_root_is_dead() {
    smp_rmb();
    if (test_bit(BTRFS_ROOT_DEAD_RELOC_TREE, &root->state))
        return true;
}

Because there is no barrier between the test_bit() load and the subsequent
root->reloc_root load in have_reloc_root(), the CPU can reorder these
loads.

If have_reloc_root() races with this newly added clear_reloc_root(), the
CPU might fetch the old, non-NULL root->reloc_root, then read the updated
BTRFS_ROOT_DEAD_RELOC_TREE bit.

Since rc->merge_reloc_tree is still true here, a racing
btrfs_reloc_pre_snapshot() could return true from have_reloc_root(),
proceed past the merge_reloc_tree check, and then re-read root->reloc_root
as NULL, potentially causing a NULL pointer dereference.

[Severity: High]
This is also a pre-existing issue, but should the success path in
merge_reloc_roots() be updated to use the new clear_reloc_root() helper
as well?

Currently, when btrfs_root_refs is 0, the success path in
merge_reloc_roots() clears the reloc root manually without a memory
barrier:

fs/btrfs/relocation.c:merge_reloc_roots() {
    ...
    } else {
        if (!IS_ERR(root)) {
            if (root->reloc_root == reloc_root) {
                root->reloc_root = NULL;
                btrfs_put_root(reloc_root);
            }
            clear_bit(BTRFS_ROOT_DEAD_RELOC_TREE, &root->state);
    ...
}

Because the CPU can reorder these writes, a concurrent
btrfs_reloc_pre_snapshot() may observe the bit as cleared but still read
the old, non-NULL root->reloc_root.

This could lead to it dereferencing root->reloc_root and hitting a
kernel panic because the orphan root has 0 refs.
