[Severity: High]
Is it safe to unconditionally clear BLOCK_GROUP_FLAG_ZONED_DATA_RELOC here
when bg->alloc_offset > 0?

On zoned filesystems, data relocation preallocates extents in data_reloc_bg
via prealloc_file_extent_cluster() -> btrfs_prealloc_file_range(). In
do_allocation_zoned(), allocating for data relocation advances
bg->alloc_offset and sets BLOCK_GROUP_FLAG_ZONED_DATA_RELOC so that regular
REQ_OP_ZONE_APPEND allocations and btrfs_zone_finish() are blocked until all
preallocated relocation extents have been physically written via
BTRFS_ORDERED_PREALLOC writes. Normally, btrfs_zoned_release_data_reloc_bg()
only clears BLOCK_GROUP_FLAG_ZONED_DATA_RELOC when the ordered extent at the
end of the preallocated range completes:

fs/btrfs/zoned.c:btrfs_zoned_release_data_reloc_bg() {
	...
	/* All relocation extents are written. */
	if (block_group->start + block_group->alloc_offset == logical + length) {
		clear_bit(BLOCK_GROUP_FLAG_ZONED_DATA_RELOC,
			  &block_group->runtime_flags);
	}
}

However, btrfs_prealloc_file_range() inserts the preallocated file extent and
queues BTRFS_ADD_DELAYED_EXTENT delayed refs before the folios are dirtied
and written in relocate_one_folio(). When those delayed refs run (for example
during btrfs_commit_current_transaction() in relocate_block_group()),
alloc_reserved_file_extent() -> btrfs_update_block_group(..., true) moves the
preallocated bytes from bg->reserved to bg->used, so bg->reserved becomes 0
before the data is written to disk.

If relocate_file_extent_cluster() then fails or is canceled (for example due
to -ENOSPC on a subsequent extent after fs_info->data_reloc_bg switched away

Can migrating a populated block group via zoned_move_bg_to_space_info()
without holding bg->lock race with concurrent extent freeing, unpinning, or
zone finishing and corrupt space_info accounting?

Unlike btrfs_set_data_reloc_bg(), which only migrates completely empty block
groups (alloc_offset == 0 && used == 0 && reserved == 0),
btrfs_zoned_return_data_reloc_bgs() migrates populated block groups (with
bg->used > 0 and bg->alloc_offset > 0) that remain reachable via
fs_info->block_group_cache_tree, fs_info->zone_active_bgs, and
fs_info->unused_bgs after bg->list is unlinked and both bg->lock and
reloc_sinfo->groups_sem are dropped:

fs/btrfs/zoned.c:zoned_move_bg_to_space_info() {
	...
	spin_lock(&from->lock);
	from->total_bytes -= bg->length;
	from->disk_total -= bg->length * factor;
	from->bytes_used -= bg->used;
	from->disk_used -= bg->used * factor;
	from->bytes_readonly -= bg->bytes_super;
	btrfs_space_info_update_bytes_zone_unusable(from, -(s64)bg->zone_unusable);
	spin_unlock(&from->lock);

	bg->space_info = to;
	if (!to->block_group_kobjs[index])
		btrfs_sysfs_add_block_group_type(bg);

	btrfs_add_bg_to_space_info(bg);
}

holding groups_sem:

1. Concurrent delayed ref execution freeing extents in bg (including delayed
refs queued by iput(rc->data_inode) at the end of
btrfs_relocate_block_group()) calls btrfs_update_block_group(trans, bytenr,
num_bytes, false), which looks up bg in block_group_cache_tree and caches
space_info = cache->space_info before locking space_info->lock and
cache->lock:
   - If btrfs_update_block_group() (or btrfs_pin_extent()) runs after
     btrfs_zoned_return_data_reloc_bgs() drops bg->lock and before
