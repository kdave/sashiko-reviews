btrfs: disable direct IOs to avoid dirty folios without fs knowing

This patch disables direct I/O for non-experimental builds by returning
-EOPNOTSUPP in the VFS read and write iterators. It aims to prevent an
issue where direct reads into memory mapped from page cache result in
dirty folios without the filesystem knowing, corrupting ordered extent
accounting.

Link: https://lore.kernel.org/linux-btrfs/f12f70e5-d84d-4a9f-ac94-693be4c863ac@linux.ibm.com/

[Severity: High]
Does returning -EOPNOTSUPP during write iteration break applications that
probe for O_DIRECT support?

In btrfs_file_open(), FMODE_CAN_ODIRECT is still set unconditionally:

fs/btrfs/file.c:btrfs_file_open() {
        ...
        filp->f_mode |= FMODE_NOWAIT | FMODE_CAN_ODIRECT;
        ...
}

Because of this, an application calling open() with O_DIRECT will succeed,
but will subsequently error out on read or write. VFS does not fall back
to buffered I/O when iterators return -EOPNOTSUPP. Can we report unsupported
features during open() instead?

[Severity: High]
Does this blanket rejection of IOCB_DIRECT break BTRFS_IOC_ENCODED_WRITE
when the file descriptor is opened with O_DIRECT?

If a user calls BTRFS_IOC_ENCODED_WRITE on a file descriptor opened with
O_DIRECT, init_sync_kiocb() initializes the kiocb with the IOCB_DIRECT flag.

reject valid encoded writes?

[Severity: Critical]
This isn't a bug introduced by this patch, but does disabling btrfs direct
I/O actually prevent the underlying problem with dirty folios?

A user can still mmap a btrfs file, then use that memory mapping as the
buffer for an O_DIRECT read from a different filesystem (like ext4) or a
raw block device. The other filesystem will call get_user_pages(), which
pins the btrfs folios and initiates DMA, bypassing this mitigation entirely.

Can we prevent cross-filesystem get_user_pages() vectors using this
approach?

>  	if (iocb->ki_flags & IOCB_DIRECT) {
>  		ret = btrfs_direct_read(iocb, to);
