btrfs: drain replace writes before freeing the target on cancel

A device replace can be left SUSPENDED while the filesystem stays mounted
and writable. If the replace is then canceled, the cancel path frees the
target device but does not wait for the duplicated write bios to drain,
leading to a use-after-free. This patch mirrors the finishing error path
by draining the in-flight bios before destroying the target.

[Severity: High]
This isn't a bug introduced by this patch, but does this drain logic fully
prevent the use-after-free of the target device when an I/O error occurs?

In the bio completion handlers for the target device, such as
orig_write_end_io_work() for normal mirrored writes, btrfs_bio_counter_dec()
is called before the handler has finished using the device:

fs/btrfs/bio.c:orig_write_end_io_work() {
    ...
	btrfs_bio_counter_dec(bioc->fs_info);

	if (bio->bi_status) {
		atomic_inc(&bioc->error);
		btrfs_log_dev_io_error(bio, stripe->dev);
	}
    ...
}

If the decrement drops the bio_counter to zero, could the cancel thread
wake up and immediately free the target device before btrfs_log_dev_io_error()
dereferences stripe->dev?

A similar pattern exists in btrfs_simple_end_io() for single-mirror
repair writes:

fs/btrfs/bio.c:btrfs_simple_end_io() {
    ...
	btrfs_bio_counter_dec(fs_info);

	if (bio->bi_status)
		btrfs_log_dev_io_error(bio, dev);
    ...
}

Should the decrement in these completion handlers be deferred until after
all device accesses are complete?
