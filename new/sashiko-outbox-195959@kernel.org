[Severity: Low]
Can inode->prop_compress ever be non-zero when execution reaches this
FS_COMPR_FL branch in btrfs_fileattr_set()?

Earlier in btrfs_fileattr_set(), if neither FS_COMPR_FL nor FS_NOCOMP_FL
changed between old_fsflags and fsflags, execution jumps directly to
update_flags without modifying the btrfs.compression property:

	if (!((fsflags ^ old_fsflags) & (FS_COMPR_FL | FS_NOCOMP_FL))) {
		/* 1 item for the inode */
		trans = btrfs_start_transaction(root, 1);
		if (IS_ERR(trans))
			return PTR_ERR(trans);
		goto update_flags;
	}

Because check_fsflags() rejects having both FS_COMPR_FL and FS_NOCOMP_FL set,
entering the else if (fsflags & FS_COMPR_FL) branch requires that FS_COMPR_FL
was not set in old_fsflags.

However, prop_compression_apply() in fs/btrfs/props.c is the only place that
sets inode->prop_compress to a non-zero value, and it always sets
BTRFS_INODE_COMPRESS and clears BTRFS_INODE_NOCOMPRESS on inode->flags:

	inode->flags &= ~BTRFS_INODE_NOCOMPRESS;
	inode->flags |= BTRFS_INODE_COMPRESS;
	inode->prop_compress = type;
	inode->prop_compress_level = level;

Since compress_file_range() only sets BTRFS_INODE_NOCOMPRESS when
!inode->prop_compress, and clearing FS_COMPR_FL or setting FS_NOCOMP_FL clears
inode->prop_compress to BTRFS_COMPRESS_NONE, isn't inode->prop_compress
guaranteed to be BTRFS_COMPRESS_NONE here (making the property reconstruction
and comp_buf unreachable dead code since commit 862e41245f393f)?

[Severity: Low]
As reported by Sashiko on v6 [1], does passing inode->prop_compress_level by
value to btrfs_compress_typelevel2str() in btrfs_fileattr_set() read an
uninitialized field when FS_COMPR_FL is set on an inode that has not had a
compression algorithm property applied?

In fs/btrfs/inode.c, btrfs_alloc_inode() allocates struct btrfs_inode from
btrfs_inode_cachep without __GFP_ZERO and initializes ei->prop_compress, but
leaves ei->prop_compress_level uninitialized:

	ei->runtime_flags = 0;
	ei->prop_compress = BTRFS_COMPRESS_NONE;
	ei->defrag_compress = BTRFS_COMPRESS_NONE;

Similarly, in fs/btrfs/props.c, prop_compression_apply() resets
inode->prop_compress to BTRFS_COMPRESS_NONE without initializing
inode->prop_compress_level when clearing compression or setting "no" / "none":

	if (len == 0) {
		inode->flags &= ~BTRFS_INODE_COMPRESS;
		inode->flags &= ~BTRFS_INODE_NOCOMPRESS;
		inode->prop_compress = BTRFS_COMPRESS_NONE;
		return 0;
	}

Even though btrfs_compress_typelevel2str() returns NULL when type is
BTRFS_COMPRESS_NONE without inspecting level, wouldn't evaluating
inode->prop_compress_level at the call site pass an uninitialized value across
a function boundary and trigger a KMSAN uninit-value report when
CONFIG_KMSAN_CHECK_PARAM_RETVAL is enabled?
