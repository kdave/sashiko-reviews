btrfs: release extent lock per folio in readahead

This patch changes the extent locking behavior in btrfs_readahead() to unlock
extents on a per-folio basis rather than in bulk at the end of the operation.
This is intended to prevent other threads from blocking on the extent lock for
the entire readahead range if a partial read failure occurs.

[Severity: Critical]
This is a pre-existing issue, but does this call to btrfs_do_readpage()
leave newly expanded readahead folios unlocked?

When btrfs_do_readpage() expands the readahead window via
btrfs_readahead_expand(), it adds new folios to the page cache without
acquiring the extent lock for the expanded range:

fs/btrfs/extent_io.c:btrfs_do_readpage() {
    ...
    if (bio_ctrl->ractl &&
        !btrfs_is_subpage(fs_info, folio) &&
        compress_type != BTRFS_COMPRESS_NONE)
        btrfs_readahead_expand(bio_ctrl->ractl, em);
    ...
}

Since btrfs_readahead() only locked the original [start, end] range, can a
concurrent direct IO write safely acquire the extent lock for the expanded
range, invalidate the page cache, and write new data, while the readahead
thread populates the page cache with stale data using the old extent map?

> +		/* Only unlock the range we locked, even if readahead expands. */
> +		if (folio_start >= start && folio_end <= end)
> +			btrfs_unlock_extent(&inode->io_tree, folio_start, folio_end, NULL);

[Severity: High]
Can this piecemeal unlocking cause an infinite loop and thread hang under
memory pressure?

Since the extent was initially locked in bulk, unlocking a sub-range forces
the extent IO tree to split the extent_state node. Splitting requires a memory
allocation.

If alloc_extent_state_atomic() fails during the split in
btrfs_clear_extent_bit_changeset(), it jumps to search_again, dropping the
spin lock and looping indefinitely:

fs/btrfs/extent-io-tree.c:btrfs_clear_extent_bit_changeset() {
    ...
        prealloc = alloc_extent_state_atomic(prealloc);
        if (!prealloc)
            goto search_again;
    ...
search_again:
    spin_unlock(&tree->lock);
    if (gfpflags_allow_blocking(mask))
        cond_resched();
    goto again;
}

Since the thread would hang in this retry loop while still holding the
extent lock for the remaining folios, will this deadlock any concurrent
readers or writers trying to lock the overlapping range?
