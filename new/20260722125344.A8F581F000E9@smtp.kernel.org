btrfs: move condition for log commit wait into wait_log_commit()

Instead of having every caller check for root->log_commit[] being non-zero
and then call wait_log_commit(), move the check into wait_log_commit() and

[Severity: High]
Can this cause an out-of-bounds array access if transid is negative?

When log_transid is 0 (e.g. during the first log sync), wait_log_commit()
receives -1 for transid. Under C rules, -1 % 2 evaluates to -1, which
causes index to become -1.

This would lead to accessing root->log_commit[-1] and later
root->log_commit_wait[-1]. While this might structurally alias adjacent fields
like log_writers without causing an immediate panic, it remains an out-of-bounds
memory access.

[Severity: High]
Since this call is now unconditional, it passes -1 to wait_log_commit() when
log_transid is 0.

The previous code avoided this by guarding the call with (index1 + 1) % 2.
Similar unconditional calls now happen in start_log_trans() and
join_running_log_trans() for zoned filesystems.

Could wait_log_commit() return early if transid < 0, or is there a preferred
way to handle the initial log sync?
