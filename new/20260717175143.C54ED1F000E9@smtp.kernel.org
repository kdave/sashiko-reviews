btrfs: handle ENOMEM from btrfs_insert_dir_item() without aborting

This commit updates btrfs_create_new_inode() and btrfs_add_link() to handle
-ENOMEM gracefully instead of aborting the transaction. When adding a link
fails due to memory pressure, it converts the newly created inode into an
orphan to ensure it is cleaned up during eviction or crash recovery.

[Severity: High]
When we clear the in-memory nlink and add an orphan item, do we also need
to call btrfs_update_inode() to persist the nlink=0 state to the b-tree
before the transaction ends?

If a crash occurs before the eviction finishes, could the transaction commit
with the b-tree containing an inode item with nlink=1 alongside the new
orphan item?

During the next mount, wouldn't btrfs_orphan_cleanup() assume an on-disk
inode with nlink > 0 is a legacy truncate orphan, delete the orphan item,
and leave the actual inode untouched, resulting in a permanent metadata
leak?
