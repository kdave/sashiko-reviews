btrfs: add verity Merkle folio to page cache after reading it

This commit avoids installing the folio in the page cache until after the
Merkle tree read has succeeded. This keeps the failure path simple and prevents
later reads from finding a locked, not-uptodate folio if read_key_bytes()
fails.

[Severity: High]
This is a pre-existing issue, but can this lead to data corruption on 32-bit
HIGHMEM systems?

On systems with CONFIG_HIGHMEM, the folio allocated by filemap_alloc_folio()
can be a highmem folio, in which case folio_address(folio) returns NULL.

When NULL is passed as the dest parameter to read_key_bytes() just before this
folio_zero_segment() call:

    ret = read_key_bytes(BTRFS_I(inode), BTRFS_VERITY_MERKLE_ITEM_KEY, off,
                         folio_address(folio), PAGE_SIZE, folio);

It triggers the !dest fallback path intended for dry-run length calculations
in read_key_bytes():

fs/btrfs/verity.c:read_key_bytes() {
    ...
		/* desc = NULL to just sum all the item lengths */
		if (!dest)
			copy_end = item_end;
		else
			copy_end = min(offset + len, item_end);
    ...
		if (dest) {
			if (dest_folio)
				kaddr = kmap_local_folio(dest_folio, 0);

			data = btrfs_item_ptr(leaf, path->slots[0], void);
			read_extent_buffer(leaf, kaddr + dest_offset,
					   (unsigned long)data + copy_offset,
					   copy_bytes);
    ...
}

This skips the kmap_local_folio() and data copy block entirely. Additionally,
because copy_end is not clamped to len when dest is NULL, copy_bytes can
exceed len, causing the unsigned len variable to underflow and creating an
unbounded loop iterating over the btree.

Ultimately, the function returns success without copying any data, leaving the
uninitialized folio to be marked uptodate and inserted into the page cache,
which could break fs-verity and potentially expose uninitialized memory.
