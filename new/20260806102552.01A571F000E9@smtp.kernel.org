btrfs: don't stash uring encoded data across -EAGAIN

This commit attempts to fix a memory leak of driver PDU allocations when
io_uring requests are cancelled or the ring exits before reissue. It modifies
the read and write paths to free the data on -EAGAIN, or return -EAGAIN early.

[Severity: Critical]
By freeing the data on -EAGAIN in btrfs_uring_encoded_read(), does this
force the async worker to re-allocate and re-execute copy_from_user() on
the request arguments when the request is reissued?

If userspace submitted the command with the ioctl arguments allocated on the
stack and subsequently returned from the submission function, wouldn't the
async worker's copy_from_user() read from potentially overwritten stack memory?
This could lead to memory corruption by importing a garbage iov array.

If the goal is to prevent memory leaks on cancellation, could this keep the
synchronous allocation and use io_uring_cmd_mark_cancelable() instead?
