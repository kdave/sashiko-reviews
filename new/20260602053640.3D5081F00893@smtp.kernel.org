btrfs: output a message when a missing device re-appear

This patch adds an informational log message when a previously missing
device re-appears during device scanning. This is intended to aid debugging
situations where a missing device shows up but has no block device pointer.

[Severity: Medium]
Will this unconditionally log spurious messages for normal unmounted devices?

For unmounted filesystems, device->bdev is NULL for all scanned devices
because the block device isn't opened yet. If an existing, unmounted device
is scanned again via a different path, such as udev discovering multiple
symlinks:

!is_same_device(device, path) branch is taken
device->bdev is NULL

Could this incorrectly trigger the "re-appeared" log message and spam the
kernel log with false messages during normal system boot?

[Severity: High]
This is a pre-existing issue, but does clearing the missing state without
opening the block device lead to a kernel panic in concurrent operations?

When a missing device is rescanned slightly later in device_list_add(), the
state is updated:

if (test_bit(BTRFS_DEV_STATE_MISSING, &device->dev_state)) {
    fs_devices->missing_devices--;
    clear_bit(BTRFS_DEV_STATE_MISSING, &device->dev_state);
}

By clearing the missing state while leaving device->bdev as NULL, concurrent
operations like fstrim that iterate over devices might skip checking for the
missing state. Will they then unconditionally dereference the NULL
device->bdev pointer?
