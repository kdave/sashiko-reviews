Subject: btrfs: pre-allocate delayed dir index before btree modification

Move the delayed dir index allocation in btrfs_insert_dir_item() before
the insert_with_overflow() call that modifies the btree.

> With the pre-allocation, if the GFP_NOFS allocations fail, -ENOMEM is
> returned before any on-disk state has changed. The caller can then
> handle the error gracefully. If the btree insertion itself fails, the
> pre-allocated resources are freed.

[Severity: Medium]
Does the implementation match this commit message claim?

Looking at the callers btrfs_add_link() in fs/btrfs/inode.c and
create_pending_snapshot() in fs/btrfs/transaction.c, an -ENOMEM return value
from btrfs_insert_dir_item() still falls through to a branch that
unconditionally calls btrfs_abort_transaction().

Should these callers be updated to actually handle the error gracefully?

[Severity: Medium]
If a caller provides a preallocated struct in the prealloc parameter, will the
name be initialized correctly?

If need_delayed_index is true but prealloc is not NULL, this block is skipped,
including the memcpy() that initializes the name. Since
btrfs_prealloc_delayed_dir_index() only uses the name length for allocation
and doesn't copy the name itself, does this mean uninitialized kernel memory
would be used for the directory index name?

[Severity: Medium]
Will this leak the caller-provided prealloc parameter on error paths?

The commit message states that ownership of a non-NULL prealloc transfers to
btrfs_insert_dir_item(). However, if btrfs_alloc_path() fails earlier in the
function, it returns -ENOMEM immediately without freeing prealloc.

Additionally, if need_delayed_index is false, the success path below at
second_insert returns without consuming or freeing prealloc, and the error
path below after insert_with_overflow() explicitly skips freeing it.

[Severity: High]
This is a pre-existing issue, but does this error handling correctly manage
directory state on a name collision?

If insert_with_overflow() returns -EEXIST due to an exact name match in the
directory, the error is intercepted and execution jumps to second_insert.
At this point, btrfs_insert_delayed_dir_index_prealloc() is executed
despite the primary DIR_ITEM insertion failing.

Could this lead to directory corruption and phantom delayed DIR_INDEX
entries on disk if a name collision occurs?
