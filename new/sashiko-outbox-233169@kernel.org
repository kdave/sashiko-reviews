[Severity: Medium]
Can flush_work(&fs_info->reclaim_bgs_work) stall
btrfs_async_reclaim_data_space until the entire fs_info->reclaim_bgs list is
drained, and then relocate up to BTRFS_ZONED_SYNC_RECLAIM_BATCH more block
groups unconditionally?

btrfs_reclaim_bgs_work() calls btrfs_reclaim_block_groups(fs_info, -1) with
no batch limit, so waiting for the work item to finish reintroduces the
unbounded __flush_work() stall that ad0c23c97b4e ("btrfs: zoned: limit
number of zones reclaimed in flush_space()") removed.  When flush_work()
returns, RECLAIM_ZONES also does not check whether the worker already freed
zones or satisfied pending tickets before running btrfs_reclaim_sweep()
(replaced by btrfs_zoned_reclaim_sweep() in commit "btrfs: zoned: provide
zoned specific reclaim sweep" later in the series) and synchronous
btrfs_reclaim_block_groups(fs_info, BTRFS_ZONED_SYNC_RECLAIM_BATCH).
