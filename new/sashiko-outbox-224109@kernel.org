[Severity: High]
This problem wasn't introduced by this patch, but can
btrfs_load_block_group_zone_info() leave cache linked on
fs_info->zone_active_bgs with cache->physical_map set to NULL when post-load
validation fails [1]?

btrfs_load_block_group_raid1() and the other RAID loaders can call
btrfs_zone_activate(), which increments the block group refcount and adds
it to fs_info->zone_active_bgs.  If a later check in
btrfs_load_block_group_zone_info() fails, such as cache->alloc_offset >
cache->zone_capacity, the error path clears cache->physical_map without
removing the block group from fs_info->zone_active_bgs:

fs/btrfs/zoned.c:btrfs_load_block_group_zone_info() {
    ...
	if (unlikely(cache->alloc_offset > cache->zone_capacity)) {
		...
		ret = -EIO;
	}
	...
	if (!ret) {
		...
	} else {
		btrfs_free_chunk_map(cache->physical_map);
		cache->physical_map = NULL;
	}
}

When do_zone_finish() later walks fs_info->zone_active_bgs, it
dereferences block_group->physical_map and hits a NULL pointer
dereference.  In addition, if btrfs_zone_activate() fails mid-loop when
btrfs_dev_set_active_zone() returns false, it returns without clearing the
active zone reservations taken on earlier stripes in the loop, leaking
active zone accounting on those devices.
