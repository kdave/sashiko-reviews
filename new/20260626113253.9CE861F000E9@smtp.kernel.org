btrfs: add EM_WARN_ON_ONCE() to dump the extent map on a warning

This commit adds an EM_WARN_ON_ONCE macro and a btrfs_dump_extent_map helper.
These allow the kernel to dump the geometry, flags, refcount, and list/tree
membership of an offending extent map before triggering a warning and stack
trace.

[Severity: Medium]
Could multiple threads concurrently hitting this condition evaluate !__warned
as true and race through this block before the __warned flag is updated?

Setting the rate-limiting flag after the btrfs_dump_extent_map call leaves a
wide race window because the dump involves multiple log print operations.
If multiple threads enter the block simultaneously, the intended rate limiting
could be defeated, resulting in duplicate log spam.

Should __warned = true be moved before calling the dump function, similar to
how the VM_WARN_ON_ONCE_FOLIO macro handles its warning flags?
