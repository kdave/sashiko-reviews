btrfs: zoned: reuse block groups emptied by reclaim as relocation target

This commit resets data block groups emptied by zoned reclaim in place and
promotes them as the next data relocation target instead of removing the
chunk.

conventional or emulated zones, or on stripes with a missing device?

btrfs_zoned_bg_is_append_only() returns true for every

sequential zones, and zoned_reset_bg_in_place() calls
blkdev_zone_mgmt(stripe->dev->bdev, REQ_OP_ZONE_RESET, ...) on every stripe

Can a concurrent scrub race with btrfs_zoned_reuse_reclaimed_bg() after
bg->lock is dropped here?

btrfs_relocate_chunk() calls btrfs_scrub_continue() before calling
btrfs_relocate_chunk_finish() -> btrfs_zoned_reuse_reclaimed_bg():

CPU0 (reclaim)                    CPU1 (scrub)
btrfs_zoned_reuse_reclaimed_bg()
  spin_lock(&bg->lock)
  btrfs_zoned_can_reuse_bg(bg)
    /* sees bg->ro == 2 */
  spin_unlock(&bg->lock)
                                  scrub_enumerate_chunks()
                                    btrfs_inc_block_group_ro(bg, ...)
                                      /* bg->ro becomes 3 */
  btrfs_dec_block_group_ro(bg)
  btrfs_dec_block_group_ro(bg)
    /* bg->ro is still 1 */
  zoned_reset_bg_in_place(bg, ...)
    blkdev_zone_mgmt(..., REQ_OP_ZONE_RESET, ...)
    spin_lock(&bg->lock)
    if (bg->ro)
      return 0;  <-- physical zone reset while bg->alloc_offset stays full

zoned_reset_bg_in_place() resets the device zones before checking bg->ro,
so if scrub takes a read-only reference in that window, the hardware write
pointer is reset to 0 while bg->alloc_offset remains at bg->zone_capacity.
Similarly, if scrub increments and decrements bg->ro while
zoned_reset_bg_in_place() is sleeping in blkdev_zone_mgmt() with
bg->ro == 0, scrub_enumerate_chunks() sees an empty read-write block group
and calls btrfs_mark_bg_unused(bg), allowing a concurrent
btrfs_reset_unused_block_groups() to run a second zoned_reset_bg_in_place()
on the same block group and hit ASSERT(*reclaimed == bg->zone_capacity).

[Severity: High]
Does passing !fs_info->data_reloc_bg here prevent the reclaimed block group
from becoming a relocation target whenever the previous relocation block
group was not completely filled?

Relocating a partially used block group into fs_info->data_reloc_bg usually
leaves the destination fs_info->data_reloc_bg only partially full.
btrfs_relocate_block_group() and btrfs_relocate_chunk_finish() finish the
source block group bg, whereas fs_info->data_reloc_bg is only cleared when
ordered extent completion fills the relocation zone all the way to
zone_capacity:

fs/btrfs/zoned.c:do_zone_finish() {
    ...
	btrfs_clear_data_reloc_bg(block_group);
    ...
}

As a result, fs_info->data_reloc_bg is still non-zero when
btrfs_zoned_reuse_reclaimed_bg() runs.  zoned_reset_bg_in_place() is called
with promote == false (and btrfs_set_data_reloc_bg() also rejects promotion
while fs_info->data_reloc_bg is set), so bg stays in data_sinfo and its
free space is handed out to regular data writes via
btrfs_return_free_space(), while btrfs_zoned_reuse_reclaimed_bg() still
returns true and skips btrfs_remove_chunk().  When a subsequent relocation
in btrfs_reclaim_block_groups() needs more space than remains in the
partially filled fs_info->data_reloc_bg and no unallocated device zones are
left, relocating into reloc_sinfo fails with -ENOSPC.

[Severity: Low]
When zoned_reset_bg_in_place() resets bg in place inside data_sinfo without
removing the chunk, does periodic reclaim miss that space was reclaimed and
re-queue the freshly reset block group on the first sweep?

In btrfs_reclaim_block_group(), btrfs_set_periodic_reclaim_ready(space_info,
true) is only called when space_info->total_bytes < old_total, which does
not happen when bg is reset in place instead of removed via
btrfs_remove_chunk().  In addition, zoned_reset_bg_in_place() does not
clear bg->reclaim_mark, so a block group marked by do_reclaim_sweep() keeps
bg->reclaim_mark == true after being reset to bg->used == 0 and will be
queued onto fs_info->reclaim_bgs on the very next sweep.
