[Severity: High]
This isn't a bug introduced by this patch, but making this call
unconditionally async exposes a pre-existing memory reclaim deadlock vector.

By promoting the experimental feature, btrfs_bio_csum() now unconditionally
calls btrfs_csum_one_bio() with async set to true. This function uses
schedule_work() to offload the checksum calculations to the generic
system_wq:

fs/btrfs/file-item.c:btrfs_csum_one_bio() {
        ...
        INIT_WORK(&bbio->csum_work, csum_one_bio_work);
        schedule_work(&bbio->csum_work);
        return 0;
}

Since system_wq lacks the WQ_MEM_RECLAIM flag, if the system is under memory
pressure and tasks on system_wq block on memory allocations, could the
filesystem writeback path stall indefinitely waiting for csum_work?

[Severity: High]
Did this patch miss removing the CONFIG_BTRFS_EXPERIMENTAL guard in
should_async_write()?

In standard non-experimental builds, should_async_write() evaluates to true
due to the remaining guard:

fs/btrfs/bio.c:should_async_write() {
#ifdef CONFIG_BTRFS_EXPERIMENTAL
        return false;
#endif
        ...
}

This causes btrfs_submit_chunk() to defer the bio to fs_info->workers. Then,
on the worker thread, run_one_async_start() calls btrfs_bio_csum(), which
now unconditionally calls btrfs_csum_one_bio() with async = true, causing
a second offload via schedule_work() to system_wq.

Could this result in a severe double-offload performance regression on the
write path for standard builds?

[Severity: Low]
Does making btrfs_bio_csum() unconditionally pass true render the
synchronous path in btrfs_csum_one_bio() unreachable dead code?

fs/btrfs/file-item.c:btrfs_csum_one_bio() {
        ...
        if (!async) {
                csum_one_bio(bbio);
                return 0;
        }
        ...
}

Since btrfs_bio_csum() is the sole caller of btrfs_csum_one_bio(), would
it be cleaner to remove this unused synchronous execution branch?
