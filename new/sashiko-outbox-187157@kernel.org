vfs: add provenance time (ptime)

This commit adds provenance time (ptime) to represent when a file's contents
were created, making it user-settable via file_setattr() with FS_XFLAG_PTIME
and retrievable via statx() with STATX_PTIME or file_getattr().

[Severity: Medium]
What happens when userspace calls file_setattr() with FS_XFLAG_PTIME on a
filesystem that implements .fileattr_set() but does not support provenance
time?

In file_attr_to_fileattr(), FS_XFLAG_PTIME is allowed into fa->fsx_xflags via
FS_FILE_ATTR_XFLAGS_MASK, and fileattr_fill_xflags() sets fa->fsx_valid = true
and fa->flags_valid = false. When vfs_fileattr_set() then invokes
inode->i_op->fileattr_set():

1. In XFS (xfs_fileattr_set() -> xfs_ioctl_setattr_xflags()),
   xfs_flags2diflags() and xfs_flags2diflags2() only check known XFS flags:

   fs/xfs/xfs_ioctl.c:xfs_ioctl_setattr_xflags() {
       ...
       i_flags2 = xfs_flags2diflags2(ip, fa->fsx_xflags);
       if (i_flags2 && !xfs_has_v3inodes(mp))
           return -EINVAL;

       ip->i_diflags = xfs_flags2diflags(ip, fa->fsx_xflags);
       ip->i_diflags2 = i_flags2;
       ...
   }

   This ignores FS_XFLAG_PTIME, commits the transaction (updating ctime and
   stripping S_ISUID/S_ISGID if the caller lacks CAP_FSETID), and returns 0
   without setting ptime.

2. In ext4 (ext4_fileattr_set()) and f2fs (f2fs_fileattr_set()), only
   fa->flags and fa->fsx_projid are inspected, so the call also succeeds and
   silently drops fa_ptime_sec and fa_ptime_nsec.

   fa->fsx_xflags (including FS_XFLAG_PTIME) into struct fsxattr for a
   legacy FS_IOC_FSSETXATTR request that has no ptime field:

[Severity: High]
Can an unprivileged file owner bypass immutable or append-only restrictions
to modify ptime via file_setattr()?

In may_setattr(), setting explicit timestamps (ATTR_TIMES_SET) via
utimensat() on an immutable or append-only inode is rejected with -EPERM.
However, in fileattr_set_prepare(), the existing check only verifies whether
FS_APPEND_FL or FS_IMMUTABLE_FL is being toggled:

fs/file_attr.c:fileattr_set_prepare() {
	if ((fa->flags ^ old_ma->flags) & (FS_APPEND_FL | FS_IMMUTABLE_FL) &&
	    !capable(CAP_LINUX_IMMUTABLE))
		return -EPERM;
}

If the owner of an immutable or append-only file calls file_setattr() and
keeps the file's existing FS_XFLAG_IMMUTABLE or FS_XFLAG_APPEND flag in
fa_xflags while also passing FS_XFLAG_PTIME, fileattr_set_prepare() allows
the operation to proceed and update ptime (as well as ctime/iversion) on the
inode.

Should fileattr_set_prepare() reject FS_XFLAG_PTIME with -EPERM when
IS_IMMUTABLE(inode) or IS_APPEND(inode) is true?

[Severity: Medium]
Should fileattr_set_prepare() also normalize fa->fsx_ptime with
timestamp_truncate(fa->fsx_ptime, inode) when FS_XFLAG_PTIME is set?

In fs/attr.c:notify_change(), user-supplied timestamps are clamped to the
superblock's supported range [sb->s_time_min, sb->s_time_max] and truncated
to sb->s_time_gran via timestamp_truncate():

fs/attr.c:notify_change() {
    ...
	if (ia_valid & ATTR_ATIME_SET)
		attr->ia_atime = timestamp_truncate(attr->ia_atime, inode);
	else
		attr->ia_atime = now;
	if (ia_valid & ATTR_CTIME_SET)
		attr->ia_ctime = timestamp_truncate(attr->ia_ctime, inode);
	else
		attr->ia_ctime = now;
	if (ia_valid & ATTR_MTIME_SET)
		attr->ia_mtime = timestamp_truncate(attr->ia_mtime, inode);
}

Without calling timestamp_truncate() in fileattr_set_prepare(), fa->fsx_ptime
is passed directly to inode->i_op->fileattr_set() without being clamped to
the filesystem's timestamp bounds or granularity.
