btrfs: zoned: drop stranded dirty metadata on transaction abort

This patch addresses an issue on zoned filesystems where freed tree blocks are
kept dirty and flagged for zero-out. If a transaction aborts before writeback,
these stranded dirty metadata buffers survive to the final iput() and hang
unmount. The fix introduces a cleanup step to clear the dirty state of such
buffers during transaction cleanup.

[Severity: High]
Does this check miss dirty metadata extents that failed writeback mid-commit?

If an I/O error causes a transaction abort during
btrfs_write_and_wait_transaction(), btrfs_write_marked_extents() breaks out
early. At that point, it has already converted the extent's tracking bit from
EXTENT_DIRTY to EXTENT_NEED_WAIT:

fs/btrfs/transaction.c:btrfs_write_marked_extents() {
	...
	ret = btrfs_convert_extent_bit(dirty_pages, start, end,
				       EXTENT_NEED_WAIT,
				       mark, &cached_state);
	...
}

During the subsequent cleanup_transaction(), btrfs_destroy_marked_extents()
only processes EXTENT_DIRTY bits, skipping the failed extent. As a result,
btrfs_clear_buffer_dirty() is never called, and the extent never receives the
EXTENT_BUFFER_ZONED_ZEROOUT flag.

Because this new logic explicitly requires EXTENT_BUFFER_ZONED_ZEROOUT, will it
bypass these extents, leaving them stranded and still hanging the unmount?
