btrfs: trigger cow fixup via dirty_folio()

This commit reintroduces a writepage fixup mechanism for btrfs to handle
folios that are dirtied without a prior space reservation. It adds a
new dirty_folio callback that queues asynchronous space reservation
workers during writeback.

Link: https://lore.kernel.org/linux-btrfs/20260721191152.101118-1-borntraeger@linux.ibm.com/

[Severity: Critical]
Does this bypass fsync waiting and risk data loss upon power failure?

When fsync initiates a WB_SYNC_ALL writeback pass, returning 1 here
skips I/O submission without setting the writeback flag on the folio.

Because the writeback flag is not set, filemap_fdatawait_range will return
immediately and fsync will report success to userspace while the data
remains only dirty in memory.

[Severity: Critical]
Will this lead to silent data loss and busy inodes during unmount?

During unmount, sync_filesystem flushes dirty data, but writepage_fixup
defers folios to this asynchronous worker. sync_filesystem completes
without waiting for these workers. The worker only reserves space here
and does not initiate a new writeback pass. 

Because VFS writeback has already ended, evict_inodes fails to tear down
the inode due to the worker's reference, and the dirty folio is
ultimately discarded when unmount completes.

[Severity: High]
Can this result in a NULL pointer dereference on the folio private data?

If memory reclaim attempts to evict a pinned folio, release_folio is called
which detaches and clears the private pointer. If a GUP caller then dirties
the folio, btrfs_data_dirty_folio calls btrfs_folio_set_fixup_dirty, which
reaches this point.

Since the private data is now NULL, folio_get_private returns NULL and the
spin_lock_irqsave dereferences it. Consider calling set_folio_extent_mapped
in btrfs_data_dirty_folio to re-validate private state after cache lookups.
