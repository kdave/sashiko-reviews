btrfs: zoned: return finished relocation block groups to the data space_info

After each block-group reclaim run on a zoned filesystem, this patch moves
written but empty data relocation block groups that are no longer the active
relocation target back from the data relocation sub-space_info to the primary
data space_info, and reserves a new data relocation block group if needed.

Also, is it safe to call btrfs_zoned_return_data_reloc_bgs() and
btrfs_zoned_reserve_data_reloc_bg() here after releasing
fs_info->reclaim_bgs_lock?

In btrfs_reclaim_block_groups(), fs_info->reclaim_bgs_lock is unlocked
before these two calls. Meanwhile, cleaner_kthread() runs
btrfs_delete_unused_bgs(), which serializes via fs_info->reclaim_bgs_lock
and does not take BTRFS_EXCLOP_BALANCE.

Both btrfs_zoned_return_data_reloc_bgs() and btrfs_zoned_reserve_data_reloc_bg()
operate on unused block groups (!btrfs_is_block_group_used(bg)) that may
already be queued on fs_info->unused_bgs, and call
zoned_move_bg_to_space_info() to overwrite bg->space_info and move
bg->list between reloc_sinfo and data_sinfo.

However, btrfs_delete_unused_bgs() caches block_group->space_info in a
local variable before taking space_info->groups_sem and space_info->lock,
and never rechecks whether block_group->space_info changed:

btrfs_delete_unused_bgs() locks groups_sem and lock on the old space_info

bytes_pinned and bytes_readonly on the stale space_info.

Similarly, inc_block_group_ro() reads sinfo = cache->space_info before
acquiring sinfo->lock and cache->lock:

inc_block_group_ro() accounts bytes_readonly and links cache->ro_list onto
the old space_info while a subsequent btrfs_dec_block_group_ro() uses the
new cache->space_info, corrupting bytes_readonly and ro_bgs across both

[Severity: High]
Does btrfs_zoned_return_data_reloc_bgs() leave relocation block groups and
their space stranded in three cases?

First, the commit message states that filled relocation block groups
accumulate in the data relocation sub-space_info and their space is never
available to regular data again. However, right after a block-group
reclaim run finishes relocating live extents into a relocation block group
and clears fs_info->data_reloc_bg (either in do_zone_finish() or in
do_allocation_zoned()), that relocation block group holds the newly
relocated extents, so btrfs_is_block_group_used(bg) is true. Because both
btrfs_zoned_return_data_reloc_bgs() and zoned_move_bg_to_space_info()
require !btrfs_is_block_group_used(bg), filled or partially-filled
relocation block groups are not returned after reclaim, while
btrfs_zoned_reserve_data_reloc_bg() immediately moves or allocates another
block group into reloc_sinfo.

Second, when a former relocation block group in reloc_sinfo later has all
of its extents deleted and becomes unused, btrfs_mark_bg_unused() places it
on fs_info->unused_bgs. In btrfs_reclaim_block_groups(),
btrfs_delete_unused_bgs(fs_info) runs in the reclaim loop before
btrfs_zoned_return_data_reloc_bgs(fs_info) is called at the end. When that
block group is the sole entry in reloc_sinfo->block_groups[raid],
btrfs_delete_unused_bgs() pops it from fs_info->unused_bgs and skips it at
list_is_singular(&block_group->list) without re-queuing it:

fs/btrfs/block-group.c:btrfs_delete_unused_bgs() {
		block_group = list_first_entry(&fs_info->unused_bgs,
					       struct btrfs_block_group,
					       bg_list);
		list_del_init(&block_group->bg_list);
		...
		if (btrfs_is_block_group_used(block_group) ||
		    (block_group->ro && !(block_group->flags & BTRFS_BLOCK_GROUP_REMAPPED)) ||
		    list_is_singular(&block_group->list) ||
		    ...) {
			...
			goto next;
		}
}

When btrfs_zoned_return_data_reloc_bgs() then moves found to data_sinfo and
calls zoned_dec_bg_ro(found) -> btrfs_dec_block_group_ro(found), its
zone_unusable is restored to:

	found->alloc_offset + (found->length - found->zone_capacity)

When found was filled (alloc_offset == zone_capacity), zone_unusable equals
found->length (0 free bytes), while zoned_move_bg_to_space_info() sets
data_sinfo->full = false. Because found was already removed from
fs_info->unused_bgs, has used == 0, and has 0 free space for new
allocations, nothing will ever call btrfs_mark_bg_unused(found) again,
stranding the unreset block group in data_sinfo and preventing both
btrfs_reset_unused_block_groups() and btrfs_delete_unused_bgs() from
reclaiming it.

Third, if btrfs_reset_unused_block_groups() resets an unused block group in
reloc_sinfo while another relocation block group is already active
(promote == false), zoned_reset_bg_in_place() resets its zones and sets
bg->alloc_offset = 0 while leaving bg in reloc_sinfo:

fs/btrfs/zoned.c:zoned_reset_bg_in_place() {
	*reclaimed = bg->alloc_offset;
	bg->zone_unusable = bg->length - bg->zone_capacity;
	bg->alloc_offset = 0;
}

Because btrfs_zoned_return_data_reloc_bgs() requires bg->alloc_offset != 0
and btrfs_zoned_reserve_data_reloc_bg() only searches
data_sinfo->block_groups[index], won't a block group reset in place inside
reloc_sinfo be permanently stranded in reloc_sinfo?
