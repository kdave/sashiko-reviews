btrfs: keep a logged extent allocated when its ordered extent fails

This commit keeps the disk range of a failed ordered extent allocated when a
fast fsync has already logged it, and sets a filesystem error so the
transaction that logged the extent cannot commit and drop the log.

[Severity: High]
Does gating the BTRFS_ORDERED_LOGGED check and btrfs_handle_fs_error() call
behind !BTRFS_ORDERED_NOCOW && !BTRFS_ORDERED_PREALLOC allow the transaction
to commit and wipe the log when completing a logged prealloc or nocow
ordered extent fails?

For a write into a preallocated range, btrfs_create_io_em() creates an
extent map without EXTENT_FLAG_PREALLOC on modified_extents, so a fast fsync
logs it as BTRFS_FILE_EXTENT_REG along with its checksums and sets
BTRFS_ORDERED_LOGGED.  Until btrfs_finish_one_ordered() joins the
transaction and runs btrfs_mark_extent_written(), add_pending_csums(), and
btrfs_update_inode_fallback(), the subvolume tree still has the unwritten
BTRFS_FILE_EXTENT_PREALLOC item and no checksums.

If btrfs_join_transaction() fails to allocate a handle (-ENOMEM),
btrfs_finish_one_ordered() skips this block, never acquires
inode->ordered_tree_lock to synchronize with btrfs_log_changed_extents(),
and never calls btrfs_handle_fs_error().  Once btrfs_remove_ordered_extent()
decrements pending_ordered, the transaction can commit and drop the log
tree, losing the fsynced data and leaving the extent marked unwritten so
subsequent reads return zeroes.
