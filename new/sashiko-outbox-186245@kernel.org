[Severity: Medium]
Can this leak the fs_info->zoned_seq_meta_bgs or fs_info->zoned_conv_meta_bgs
count if block group initialization fails after
btrfs_load_block_group_zone_info() succeeds?

In both read_one_block_group() and btrfs_make_block_group(), subsequent steps
can still fail before the block group is inserted into
fs_info->block_group_cache_tree, for example in btrfs_make_block_group():

	ret = btrfs_load_block_group_zone_info(cache, true);
	if (ret) {
		btrfs_put_block_group(cache);
		return ERR_PTR(ret);
	}

	ret = exclude_super_stripes(cache);
	if (ret) {
		/* We may have excluded something, so call this just in case */
		btrfs_free_excluded_extents(cache);
		btrfs_put_block_group(cache);
		return ERR_PTR(ret);
	}
	...
	ret = btrfs_add_new_free_space(cache, chunk_offset, chunk_offset + size, NULL);
	btrfs_free_excluded_extents(cache);
	if (ret) {
		btrfs_put_block_group(cache);
		return ERR_PTR(ret);
	}

	ret = btrfs_add_block_group_cache(cache);
	if (ret) {
		btrfs_remove_free_space_cache(cache);
		btrfs_put_block_group(cache);
		return ERR_PTR(ret);
	}

Because btrfs_zoned_account_meta_bg(block_group, -1) is only called from
btrfs_remove_block_group() when erasing a block group from
fs_info->block_group_cache_tree, freeing cache on these error paths leaves
zoned_seq_meta_bgs or zoned_conv_meta_bgs permanently elevated, which can
cause btrfs_zoned_meta_is_append_only() to take the wrong fast-path decision
or needlessly look up the block group on every btrfs_clear_buffer_dirty()
call.

Would it be better to account the metadata block group when adding it to
fs_info->block_group_cache_tree in btrfs_add_block_group_cache() (or after all
fallible initialization steps have succeeded) so that the increment and
decrement are symmetrically paired with rbtree insertion and removal?
