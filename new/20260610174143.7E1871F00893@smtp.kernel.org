btrfs: reject free space cache with more entries than pages

When loading a v1 free space cache, __load_free_space_cache() takes
num_entries and num_bitmaps straight from the on-disk
btrfs_free_space_header. That header is stored in the tree_root under a key
with type 0, which the tree-checker has no case for, so neither count is
validated before the load trusts it.

[Severity: High]
This isn't a bug introduced by this patch, but could an attacker crafting a
cache inode with a massive i_size underflow the length passed to crc32c()
and cause an out-of-bounds read here?

In fs/btrfs/free-space-cache.c:io_ctl_init(), the bounds check ensuring that
the CRC array and generation header fit within a single page is restricted to
the write path:

    if (write && (num_pages * sizeof(u32) + sizeof(u64)) > PAGE_SIZE)
            return -ENOSPC;

On the read path, an arbitrarily large i_size produces a massive num_pages
that bypasses this validation.

When offset is calculated as sizeof(u32) * io_ctl->num_pages in
io_ctl_check_crc(), it can exceed PAGE_SIZE. This causes PAGE_SIZE - offset
to underflow to a massive unsigned value when passed as the length parameter
to crc32c(), triggering an immediate out-of-bounds memory read of unmapped
memory.

[Severity: Medium]
This is a pre-existing issue, but does the error path in
fs/btrfs/free-space-cache.c:load_free_space_cache() leak memory if
copy_free_space_cache() fails?

In load_free_space_cache(), the free space cache is read from disk into a
stack-allocated temporary structure tmp_ctl. Once verified,
copy_free_space_cache() is called to drain entries from tmp_ctl and insert
them into the block group using btrfs_add_free_space().

If btrfs_add_free_space() returns an error, the copying loop terminates
early and returns the error code.

Back in load_free_space_cache(), the code jumps to the out label on error:

    out:
        if (ret < 0) {
            /* This cache is bogus, make sure it gets cleared */

Unlike the else branch for mismatched free space, the error path handles
the disk cache state clearing but fails to call
__btrfs_remove_free_space_cache(&tmp_ctl).

As a result, all dynamically allocated nodes remaining in tmp_ctl's rbtree
are permanently leaked.
