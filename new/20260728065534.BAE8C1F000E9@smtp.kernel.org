btrfs: use proper inclusive end in extent_fiemap()

The @end parameter for all extent io tree helpers is inclusive, but
the call site in extent_fiemap() is passing exclusive end.

[Severity: Critical]
This is a pre-existing issue, but can this lead to an inverted range being
passed to btrfs_lock_extent() and corrupting the extent io tree?

If FIEMAP encounters an explicit hole or prealloc extent that spans beyond the
requested range (start + len), and multiple delalloc extents exist within that
extent, a cache flush could cause len to underflow.

Unlike the implicit hole case, explicit holes and prealloc extents pass
extent_end - 1 without bounding it to range_end:

fs/btrfs/fiemap.c:extent_fiemap() {
...
		} else if (disk_bytenr == 0) {
			/* We have an explicit hole. */
			ret = fiemap_process_hole(inode, fieinfo, &cache,
						  &delalloc_cached_state,
						  backref_ctx, 0, 0, 0,
						  key.offset, extent_end - 1);
...
}

This allows the scan to exceed the requested range. When the fiemap cache
fills, emit_fiemap_extent() returns BTRFS_FIEMAP_FLUSH_CACHE with
next_search_offset greater than the originally requested start + len.

When the flush handler runs, it updates len and start:

fs/btrfs/fiemap.c:extent_fiemap() {
...
out_unlock:
	btrfs_unlock_extent(&inode->io_tree, range_start, range_end, &cached_state);

	if (ret == BTRFS_FIEMAP_FLUSH_CACHE) {
		btrfs_release_path(path);
		ret = flush_fiemap_cache(fieinfo, &cache);
		if (ret)
			goto out;
		len -= cache.next_search_offset - start;
		start = cache.next_search_offset;
		goto restart;
...
}

This would underflow len. On the next iteration at restart, range_start
becomes the new next_search_offset but range_end would be calculated based
on the underflowed len (which evaluates to the original end). This
results in range_start > range_end.

Would this corrupted range then be passed down to set_extent_bit() via
btrfs_lock_extent(), potentially causing tree operations to hit WARN_ON_ONCE
and panic or deadlock?
