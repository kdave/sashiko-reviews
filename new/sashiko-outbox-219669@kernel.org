[Severity: High]
Does promoting a block group that already belongs to reloc_sinfo skip
waking pending tickets on reloc_sinfo?

Both data_sinfo and reloc_sinfo have BTRFS_BLOCK_GROUP_DATA set in
space_info->flags.  When an unused block group in reloc_sinfo is reset
while fs_info->data_reloc_bg is 0, promote is true, so
zoned_reset_bg_in_place() skips btrfs_return_free_space() before dropping
space_info->lock.  Inside btrfs_set_data_reloc_bg(), migrate is false
because bg->space_info is already reloc_sinfo:

fs/btrfs/zoned.c:btrfs_set_data_reloc_bg() {
	const bool migrate = (bg->space_info == data_sinfo);
...
	if (migrate)
		zoned_dec_bg_ro(bg);

	btrfs_zone_activate(bg);

	return true;
}

Because zoned_dec_bg_ro() is the only path in btrfs_set_data_reloc_bg()
that calls btrfs_try_granting_tickets(reloc_sinfo), and
btrfs_set_data_reloc_bg() returns true, neither btrfs_return_free_space()
nor btrfs_try_granting_tickets() is called on reloc_sinfo.
do_async_reclaim_data_space() then sees no ticket progress during
RESET_ZONES and fails waiting relocation reservations with -ENOSPC.

from bg in do_allocation_zoned(); if bg is already in reloc_sinfo
(migrate == false), btrfs_set_data_reloc_bg() does not re-check that bg
remained empty and read-write.

[Severity: High]
Does resetting an unused reloc_sinfo block group when another
data_reloc_bg is already active strand the block group in reloc_sinfo and
shortchange data_sinfo reclaim?

Once a data block group is promoted into reloc_sinfo, later filled, and
eventually freed onto fs_info->unused_bgs,
btrfs_reset_unused_block_groups() matches it by BTRFS_BLOCK_GROUP_TYPE_MASK
even when called for data_sinfo.  If another block group is already set as
fs_info->data_reloc_bg, zoned_reset_bg_in_place() resets the zone, sets
bg->alloc_offset = 0, and returns *reclaimed to bg->space_info
(reloc_sinfo) without moving bg back to data_sinfo.

btrfs_reset_unused_block_groups() also subtracts reclaimed from num_bytes
even when the reset block group was promoted into (or already belonged to)
reloc_sinfo rather than returning space to the caller's space_info.  And
because commit "btrfs: zoned: return finished relocation block groups to
the data space_info" later in this series only returns relocation block
groups with bg->alloc_offset != 0, a relocation block group reset to
bg->alloc_offset == 0 here while another data_reloc_bg is active stays
stranded in reloc_sinfo, draining usable data zones toward -ENOSPC.
