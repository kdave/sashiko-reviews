btrfs: introduce the skeleton of delayed bbio endio function

This patch introduces the skeleton for delayed bbio endio, queuing delayed 
bios into a workqueue for compression. It implements the main endio function 
and a helper to queue workloads, reusing btrfs_bio::pending_ios for lifespan 
tracking.

[Severity: High]
Can this allocation cause an ABBA deadlock during memory reclaim?

In btrfs_submit_delayed_write(), kzalloc_obj() defaults to using GFP_KERNEL.
Since this function is called from the folio writeback path (via
extent_writepage_io() -> submit_one_bio()), allocating with GFP_KERNEL under
memory pressure can trigger direct reclaim.

Direct reclaim may then attempt to lock the same folios or wait on
filesystem writeback, resulting in a deadlock.

Should this allocation use GFP_NOFS or be protected with
memalloc_nofs_save()?

[Severity: High]
Could queuing this work to the generic system_percpu_wq lead to a memory
reclaim deadlock?

The schedule_work() call queues the delayed bio for compression to the
global system_percpu_wq. This queue is allocated without the WQ_MEM_RECLAIM
flag, meaning it has no rescuer thread.

Because this happens in the dirty page writeback path, which memory reclaim
depends on to free pages, severe memory pressure could cause the workqueue
to stall waiting for memory allocations to spawn workers. Meanwhile, memory
reclaim would be waiting for this writeback work item to complete, creating
a circular dependency.

Does Btrfs need to queue these IO workloads to its dedicated WQ_MEM_RECLAIM
workqueues (e.g., using btrfs_queue_work() with fs_info->delalloc_workers)?
