btrfs: wait for an RCU grace period before freeing a device on add error

This commit adds a synchronize_rcu() call in the error_sysfs unwind path
of btrfs_init_new_device() to ensure readers under rcu_read_lock() don't
dereference a freed device. This matches the behavior of other device
removal paths.

[Severity: High]
This is a pre-existing issue, but does this error path also need to revert
the pointer assignments made earlier when adding a seeding device?

If btrfs_init_new_device() adds a device to a seed filesystem, it calls
btrfs_setup_sprout() and btrfs_assign_next_active_device() earlier in
the function:

    btrfs_assign_next_active_device(fs_info->fs_devices->latest_dev,
                                    device);

This overwrites fs_info->fs_devices->latest_dev with the new device and
fs_info->sb->s_bdev with device->bdev.

If a subsequent step fails (such as init_first_rw_device() or
btrfs_add_dev_item()), the code jumps to error_sysfs. The unwind path
frees the device and puts the block device, but doesn't seem to revert
latest_dev, sb->s_bdev, or the sprout list changes.

Could this leave the filesystem with dangling pointers to a freed device
and a closed block device, leading to a use-after-free if VFS or Btrfs
subsequently accesses them?
