[Severity: Critical]
Does forcing an initial read-only mount for 'usebackuproot' prevent the space
cache from being cleared upon a later read-write remount?

The 'usebackuproot' option is intended to clear the space cache because the
on-disk cache is untrusted when rolling back to an older tree root (the legacy
option explicitly sets CLEAR_CACHE). 

Prior to this patch, mounting read-write directly allowed
btrfs_start_pre_rw_mount() to see the CLEAR_CACHE flag and safely invalidate
the space tree before writes occurred. 

By forcing 'usebackuproot' to be mounted read-only, btrfs_start_pre_rw_mount()
is bypassed during the initial mount. Immediately after, oneshot options are
cleared:

btrfs_clear_oneshot_options() {
        ...
        btrfs_clear_opt(fs_info->mount_opt, CLEAR_CACHE);
        ...
}

When the filesystem is subsequently remounted read-write to perform repairs,
the CLEAR_CACHE flag is already gone. The cache is never cleared, and the
filesystem could begin allocating blocks using an untrusted space cache,
overwriting valid blocks.

While a subsequent patch in this series removes the legacy option, the modern
'rescue=usebackuproot' option fails to set CLEAR_CACHE at all. This patch
ensures that even if 'rescue=usebackuproot' is fixed to properly set
CLEAR_CACHE, the forced read-only requirement structurally guarantees the flag
will be stripped before a read-write remount can act on it.
