attempting to separate metadata I/O into a different workqueue to prevent

Can the strict inequalities in xfs_read_ioend_compare() miss metadata at

If the file size is a multiple of XFS_FSVERITY_START_ALIGN, the metadata
offset exactly equals i_size. The strict inequality ia->io_offset > i_size

the newly added xfs_end_ioend_read() calls fsverity_verify_bio(), which
synchronously waits for the metadata page to become uptodate. But the
metadata ioend that would unlock the page is stuck behind the data ioend
in the same list, deadlocking the worker.

[Severity: Critical]
Does this queueing logic introduce a work_struct collision or a list
piggybacking deadlock?

If a data read completes, ip->i_ioend_work is queued to
fsverity_read_workqueue. The worker starts and blocks in
fsverity_verify_bio() waiting for a metadata Merkle tree page.

When the metadata bio completes, xfs_end_bio() will attempt to queue the
same ip->i_ioend_work to m_unwritten_workqueue. Because the workqueue
subsystem prevents concurrent execution of the same work_struct, the
metadata completion is deferred until the current worker finishes. This
would permanently block the current worker waiting for that metadata
completion to unlock the page.

Furthermore, the destination workqueue is only chosen on the 0-to-1 list
transition. If a metadata read completes first, it queues to
m_unwritten_workqueue. A concurrent data read will append to the same list.
The data read is then processed on m_unwritten_workqueue, issuing further
synchronous metadata I/O from a workqueue that the commit message explicitly
warns will cause a deadlock.
