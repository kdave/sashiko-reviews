btrfs: fix inline reflink deadlock at non-zero offset

This patch attempts to resolve a deadlock where an inline extent copied
into a page beyond the end of a file gets invalidated by concurrent writeback.
It does this by updating i_size after the early non-zero offset path calls
copy_inline_to_page(), matching the behavior of the existing copy_to_page
path.

[Severity: High]
This is a pre-existing issue, but does this create a race window that can
still trigger the deadlock?

In copy_inline_to_page(), the dirtied folio is unlocked before returning:

copy_inline_to_page() {
    ...
    btrfs_folio_set_dirty(fs_info, folio, file_offset, block_size);
out_unlock:
    if (!IS_ERR(folio)) {
        folio_unlock(folio);
        folio_put(folio);
    ...
}

Once unlocked, the folio becomes immediately visible to concurrent writeback
tasks. If writeback locks the folio before the reflink task updates i_size
here, could it read the old i_size and incorrectly conclude the folio is
past the end of the file?

If this happens, extent_writepage() calls folio_invalidate(), which then
attempts to lock the extent range already held by the reflink task:

extent_writepage() {
    ...
    if (folio->index > end_index ||
       (folio->index == end_index && !pg_offset)) {
        folio_invalidate(folio, 0, folio_size(folio));
    ...
}

The reflink task then updates i_size too late, and attempts to start a
transaction which blocks on the commit waiting for writeback, resulting in
a deadlock.

Could i_size be updated inside copy_inline_to_page() before folio_unlock()
is called to prevent this race?
