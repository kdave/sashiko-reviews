btrfs: zoned: track only sequential zones as active

This commit addresses an issue where active zone accounting diverges across
remounts because conventional zones report as NOT_WP and are excluded at
mount, yet they decrease reserved_active_zones during mount recovery. To
keep both counters aligned on the same physical resource, it restricts
active-zone tracking solely to sequential stripes.

This is a pre-existing issue, but does unconditionally adding the block group
to the active list here cause list corruption?

When mounting a zoned Btrfs filesystem, if a multi-stripe block group has
inconsistent active bits, btrfs_load_block_group_by_raid_type() recovers it
by calling btrfs_zone_activate().

btrfs_zone_activate() adds the block group to fs_info->zone_active_bgs. When
btrfs_load_block_group_by_raid_type() returns success,
btrfs_load_block_group_zone_info() sees BLOCK_GROUP_FLAG_ZONE_IS_ACTIVE is
set and calls list_add_tail() again using the exact same list node.

Can this lead to severe linked list corruption and kernel hangs during list
traversal?

This is a pre-existing issue, but does this error path bail out without
rolling back previously activated stripes in the same loop?

When activating a multi-stripe block group, if an early stripe succeeds but a
later stripe fails, the function returns false without rolling back the
successful stripes.

On a subsequent retry, btrfs_dev_set_active_zone() returns true for the
already-active stripes, causing the code to execute this decrement a
second time:

Does this leak active zone slots and underflow reserved_active_zones,
allowing data block groups to incorrectly consume zones reserved for metadata?
