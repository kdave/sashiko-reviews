btrfs: keep the exclusive op held while a dev-replace is suspended in-mount

This commit prevents concurrent balance and dev-replace operations by keeping
the exclusive operation token held when a device replace is suspended. It
updates btrfs_dev_replace_finishing() to report suspension status and modifies
callers to retain the token accordingly.

[Severity: High]
This is a pre-existing issue, but does leaving dev_replace->replace_task set
when returning an error here lead to a lock bypass?

If the task that initiated the replace exits, its task_struct is freed. If a
new thread is later spawned and its task_struct happens to be allocated at the
same memory address, could it bypass the lock in btrfs_map_block()?

fs/btrfs/volumes.c:btrfs_map_block() {
	...
	if (dev_replace->replace_task != current)
		down_read(&dev_replace->rwsem);
	...
}

Because the replace state is suspended, btrfs_dev_replace_is_ongoing() remains
true. This allows the new lock-bypassing thread to execute
handle_ops_on_dev_replace() concurrently with btrfs_dev_replace_cancel().

Since btrfs_dev_replace_cancel() clears the device pointers without resetting
replace_task:

fs/btrfs/dev-replace.c:btrfs_dev_replace_cancel() {
	...
		dev_replace->tgtdev = NULL;
		dev_replace->srcdev = NULL;
		dev_replace->replace_state =
				BTRFS_IOCTL_DEV_REPLACE_STATE_CANCELED;
	...
}

Could the lock-bypassing thread evaluate dev_replace->tgtdev != NULL just
before cancel clears it, and then dereference the newly zeroed
dev_replace->srcdev in handle_ops_on_dev_replace()?

The same dangling pointer can also occur if btrfs_start_transaction() fails
at the end of btrfs_dev_replace_start(). Should replace_task be explicitly
cleared to NULL on all error, suspension, and cancel paths?
