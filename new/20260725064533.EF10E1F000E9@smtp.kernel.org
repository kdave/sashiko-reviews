btrfs: trigger cow fixup via dirty_folio()

This commit introduces a COW fixup mechanism for folios dirtied without
delalloc reservations. It introduces a fixup worker and modifies the writepage
path to enqueue work for these unnotified dirty blocks.

Link: https://lore.kernel.org/linux-btrfs/20260721191152.101118-1-borntraeger@linux.ibm.com/

[Severity: High]
Does allocating this as an ordered workqueue introduce a deadlock under space
pressure?

In btrfs_writepage_fixup_worker(), the worker calls
btrfs_delalloc_reserve_space(). This can block and trigger space reclaim,
which flushes delalloc roots and initiates writeback on other dirty folios.

If those other folios also have unnotified dirty blocks, writepage_fixup()
will attempt to queue more items to fixup_workers via
btrfs_queue_writepage_fixup(). Since the workqueue is ordered, the newly
queued tasks cannot run until the current blocked worker completes, creating
an ABBA circular dependency.

[Severity: High]
Can this ignored return value lead to an infinite writeback retry loop?

The allocation in btrfs_queue_writepage_fixup() uses GFP_NOFS and can return
-ENOMEM under heavy memory pressure. If that error is ignored, the folio is
left dirty but without a queued fixup worker.

During the next pass, the writeback loop finds the dirty folio again, calls
writepage_fixup(), and attempts the allocation again. If memory pressure
persists, it will repeatedly fail and redirty the folio, potentially stalling
the system and preventing the memory pressure from resolving.

[Severity: High]
Is it possible for folio_get_private() to return NULL here, causing a NULL
pointer dereference?

If a clean, subpage-formatted folio is mapped shared and pinned by GUP,
memory pressure or truncation operations could trigger filemap_release_folio().
This will free the private btrfs_folio_state (bfs) and return success, even
though the folio remains in the page cache due to the GUP pin.

When the I/O completes and set_page_dirty() is called, this callback will
unconditionally dereference the now-NULL bfs pointer via
!READ_ONCE(bfs->reserving_dirty). Does this path need to re-validate or
re-attach the private data, perhaps by calling set_folio_extent_mapped()
before accessing it?
