btrfs: introduce more accurate usebackuproot options
    
Previously we had no way to tell btrfs to use which backup slot, but
always use the newest backup, and retry until all backup roots are
exhausted.

This doesn't give any control to the end user, even if the end user
wants to use a specific backup slot.

To address this problem, allow more fine-control on usebackuproot rescue
option by introducing the following 4 rescue mount options:

- rescue=usebackuproot_0
- rescue=usebackuproot_1
- rescue=usebackuproot_2
- rescue=usebackuproot_3

The number 0 means the newest backup slot, 1/2/3 means the
second/third/fourth(oldest) backup slot to use.

The existing "rescue=usebackuproot" is just an alias of
"rescue=usebackuproot_1".

This will allow users to choose which backup root to use.

[Severity: High]
Does rescue=all cause a crash or mount failure here?

When rescue=all is processed in btrfs_parse_param(), it sets USEBACKUPROOT but
does not initialize ctx->use_backup_slot:

fs/btrfs/super.c:btrfs_parse_param() {
...
        case Opt_rescue_parameter_all:
            btrfs_set_opt(ctx->mount_opt, IGNOREDATACSUMS);
            ...
            btrfs_set_opt(ctx->mount_opt, USEBACKUPROOT);
            break;
...
}

Since fs_info->use_backup_slot remains -1, this will trigger the ASSERT above
or cause read_backup_root() to fail with -EINVAL when -1 is cast to u8.

[Severity: High]
Does rescue=usebackuproot_0 silently fail to load the backup root?

When fs_info->use_backup_slot is 0, read_backup_root() returns early without
copying the backup metadata:

fs/btrfs/disk-io.c:read_backup_root() {
...
    if (priority < BTRFS_NUM_BACKUP_ROOTS && backup_index >= 0) {
        if (priority == 0)
            return backup_index;
...
}

This skips copying the backup root metadata into the working super_copy,
causing the filesystem to mount using the main superblock roots instead of
the requested backup.

[Severity: Medium]
Will this specific slot selection be lost during remounts or when checking
mount options?

Currently, btrfs_show_options() unconditionally prints the rescue=usebackuproot
alias for any set USEBACKUPROOT flag:

fs/btrfs/super.c:btrfs_show_options() {
...
    if (btrfs_test_opt(info, USEBACKUPROOT))
        print_rescue_option(seq, "usebackuproot", &printed);
...
}

This means if a user mounts with rescue=usebackuproot_2, /proc/mounts will
display rescue=usebackuproot (which strictly maps to slot 1). Tools parsing
this or performing remounts will mistakenly inherit the default alias behavior
instead of the actually selected slot.
