btrfs: fix use-after-free on reloc root after error in insert_dirty_subvol()

If during relocation we fail in insert_dirty_subvol() because
btrfs_update_reloc_root() returned an error, we will leave a root's
reloc_root field pointing to a reloc root that was freed instead of NULL,
resulting later in a use-after-free, or double free attempt during
unmount.

[Severity: Medium]
If merge_reloc_root() fails early (for example, with -ENOMEM from
btrfs_alloc_path()), does this error path leak a reference to the reloc root?

When btrfs_init_reloc_root() initializes the reloc root, it has two
references: one for the rc->reloc_roots list and one for the
root->reloc_root pointer.

If merge_reloc_root() fails without removing the root from the list, calling
clear_reloc_root(root) sets root->reloc_root to NULL without dropping the
reference it held. 

Because the reloc root is still on the list, list_empty() evaluates to false,
skipping the block that transfers the reference. Then at the out label,
free_reloc_roots() drops the list's single reference, but the second reference
formerly held by root->reloc_root appears to be left unaccounted for.
