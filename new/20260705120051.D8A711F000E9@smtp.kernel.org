[Severity: High]
This is a pre-existing issue, but since this code is being refactored here,
could concurrent bio completions cause a data race when updating these bitmaps?

If multiple bios are submitted for a single stripe (e.g., during repair reads
or due to gaps in has_extent), their btrfs_bio_end_io work items can execute
concurrently on different CPUs. Because these scrub_bitmap_* functions
eventually use non-atomic bitmap_set() and bitmap_clear() on the shared
stripe->bitmaps array, couldn't concurrent read-modify-write operations
overwrite each other?

For example, if one CPU sets an error bit while another clears a neighboring
bit in the same unsigned long word, could scrub silently lose error flags
and leave corrupted data unrepaired?

Notice that scrub_write_endio() uses stripe->write_error_lock to protect its
bitmap updates. Does scrub_read_endio_common() need a similar lock to safely
update the read error bitmaps?
