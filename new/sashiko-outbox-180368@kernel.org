non-active data relocation block groups from the data relocation

[Severity: High]
Is it safe to unconditionally clear BLOCK_GROUP_FLAG_ZONED_DATA_RELOC here
on a non-empty relocation block group (bg->alloc_offset > 0)?

Normally, btrfs_zoned_release_data_reloc_bg() only clears
BLOCK_GROUP_FLAG_ZONED_DATA_RELOC when ordered-extent writeback reaches the
end of the preallocated range:

	/* All relocation extents are written. */
	if (block_group->start + block_group->alloc_offset == logical + length) {
		clear_bit(BLOCK_GROUP_FLAG_ZONED_DATA_RELOC,
			  &block_group->runtime_flags);
	}

During relocate_file_extent_cluster() -> prealloc_file_extent_cluster() ->
btrfs_prealloc_file_range(), do_allocation_zoned() sets
BLOCK_GROUP_FLAG_ZONED_DATA_RELOC and advances block_group->alloc_offset,
while btrfs_prealloc_file_range() inserts BTRFS_FILE_EXTENT_PREALLOC items
and decrements block_group->reservations before any folio in rc->data_inode
is dirtied or written.

If a subsequent extent in the cluster does not fit in the remaining zone
capacity, do_allocation_zoned() clears fs_info->data_reloc_bg = 0 (or
switches to a new relocation block group). If prealloc_file_extent_cluster(),
setup_relocation_extent_mapping(), relocate_one_folio(), or
btrfs_fdatawrite_range() then fails or is canceled before all preallocated
extents up to bg->alloc_offset complete writeback,
btrfs_zoned_release_data_reloc_bg() never clears
BLOCK_GROUP_FLAG_ZONED_DATA_RELOC on that block group.

However, relocate_block_group() still commits the transaction via
btrfs_commit_current_transaction(), which moves the preallocated bytes from
bg->reserved to bg->used (making bg->reserved == 0), and iput(rc->data_inode)
only queues delayed refs (which later move those bytes to bg->zone_unusable
without resetting bg->alloc_offset).

When btrfs_zoned_return_data_reloc_bgs() then sees !bg->ro && !bg->reserved
&& !bg->pinned && bg->start != READ_ONCE(fs_info->data_reloc_bg), clearing
BLOCK_GROUP_FLAG_ZONED_DATA_RELOC and moving bg to data_sinfo exposes a zone
whose physical write pointer is still behind bg->alloc_offset to regular
REQ_OP_ZONE_APPEND allocations or btrfs_zone_finish_one_bg(), causing
btrfs_record_physical_zoned() / btrfs_rewrite_logical_zoned() to rewrite new
extents into the unwritten preallocated range (-EEXIST) or triggering zone
IO errors.

Can migrating a populated block group via zoned_move_bg_to_space_info()
after dropping bg->lock and reloc_sinfo->groups_sem race with concurrent
extent freeing, zone finishing, or zone resetting and corrupt space_info

Unlike btrfs_set_data_reloc_bg(), which only moves completely empty block
groups (alloc_offset == 0 && used == 0), btrfs_zoned_return_data_reloc_bgs()
moves block groups that already contain extents and remain reachable via
fs_info->block_group_cache_tree, fs_info->zone_active_bgs, and
fs_info->unused_bgs after list_del_init(&bg->list):

1. In fs/btrfs/block-group.c:btrfs_update_block_group(), freeing an extent
   via delayed refs looks up cache in block_group_cache_tree without
   groups_sem and reads space_info = cache->space_info before locking:

	space_info = cache->space_info;
	factor = btrfs_bg_type_to_factor(cache->flags);
	...
	spin_lock(&space_info->lock);
	spin_lock(&cache->lock);

   dropped in btrfs_zoned_return_data_reloc_bgs() and before
   zoned_move_bg_to_space_info() locks from->lock, it increments bg->pinned
   and reloc_sinfo->bytes_pinned. Because zoned_move_bg_to_space_info()
   does not transfer bg->pinned, unpin_extent_range() at transaction commit

freed, bg->used drops to 0 while bg->pinned > 0, so
btrfs_zoned_return_data_reloc_bgs() cannot move it until the transaction

btrfs_mark_bg_unused().
