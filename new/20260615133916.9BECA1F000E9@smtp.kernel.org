btrfs: deny freezing devices undergoing a replace

This patch denies freezing of block devices while they are undergoing a
device replace operation. It tracks the replace state and appropriately
releases the deny references when the operation finishes, is suspended,
or encounters an error. This guarantees that devices cannot be frozen
while teardown or reconfiguration is in progress.

[Severity: High]
This is a pre-existing issue, but I noticed a potential regression in how
cancellations are handled in the BTRFS_IOCTL_DEV_REPLACE_STATE_STARTED case
located just above this modified code in btrfs_dev_replace_cancel().

If btrfs_dev_replace_finishing() hits an early error (for example,
btrfs_start_delalloc_roots() fails), it returns the error but leaves the
replace state as BTRFS_IOCTL_DEV_REPLACE_STATE_STARTED. The scrub thread
then exits and releases BTRFS_EXCLOP_DEV_REPLACE.

When a user subsequently calls the btrfs replace cancel ioctl,
btrfs_dev_replace_cancel() will execute the STARTED case:

	case BTRFS_IOCTL_DEV_REPLACE_STATE_STARTED:
		...
		ret = btrfs_scrub_cancel(fs_info);
		if (ret < 0) {
			result = BTRFS_IOCTL_DEV_REPLACE_RESULT_NOT_STARTED;
		}

Since the scrub thread already exited, btrfs_scrub_cancel() returns an
error, causing this path to silently abort and skip cleaning up the
wedged target device.

Does this leave the device replace state permanently wedged in STARTED
until the filesystem is unmounted?

With the new changes introduced in this patch, the deny_freeze references
would remain held while in this wedged STARTED state, which might prevent
the filesystem from being frozen. Since BTRFS_EXCLOP_DEV_REPLACE is
released, could users also erroneously start a concurrent balance
operation, leading to potential chunk corruption?
