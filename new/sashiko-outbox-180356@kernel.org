avail == chunk_bytes (one unallocated zone left on the device), reloc_sinfo
(data_sinfo->sub_group[0]) may hold a partially filled active relocation
block group (bg_r1) from a previous relocation.

During btrfs_reclaim_block_groups() -> btrfs_reclaim_block_group() ->

the remaining free space in bg_r1, do_allocation_zoned() fills bg_r1 and

Because the maximum supported zone size (8 GiB) is smaller than the distance
between btrfs_sb_offset(2) (256 GiB) and the superblock log zones (0B,
512 GiB, and 4 TiB), the zone containing btrfs_sb_offset(2) is always
disjoint from the superblock log zones on devices larger than 256 GiB.
Likewise, when zone_size is 32 MiB or smaller, the zone containing
btrfs_sb_offset(1) (64 MiB) lies outside zones 0 and 1.

Since btrfs_find_allocatable_zones() skips these zones, they can never be
allocated as device extents and are never included in device->bytes_used.

avail >= 2 * chunk_bytes to evaluate to true when only one allocatable zone

[Severity: Medium]
How does summing avail across all devices and comparing against
2 * chunk_bytes account for per-device stripe placement constraints?

In btrfs_zoned_data_chunk_allowed(), avail is computed as a flat sum across
all devices in fs_devices->alloc_list and compared against 2 * chunk_bytes,
where chunk_bytes uses btrfs_bg_type_to_num_stripes():

fs/btrfs/volumes.c:btrfs_bg_type_to_num_stripes() {
	const int index = btrfs_bg_flags_to_raid_index(flags);
	int ndevs;

	if (btrfs_raid_array[index].devs_max)
		ndevs = btrfs_raid_array[index].devs_max;
	else
		ndevs = fs_info->fs_devices->rw_devices;

	return btrfs_raid_array[index].dev_stripes * ndevs;
}

During chunk allocation, gather_device_info() and decide_dev_extent_size()
require at least ctl->devs_min distinct devices (rounded down to a multiple
of ctl->devs_increment, up to ctl->devs_max) to each have at least
zone_size * ctl->dev_stripes of contiguous allocatable space:

fs/btrfs/volumes.c:decide_dev_extent_size() {
    ...
	ctl->ndevs = rounddown(ctl->ndevs, ctl->devs_increment);

	if (ctl->ndevs < ctl->devs_min) {
    ...
		return -ENOSPC;
	}
    ...
}

For profiles like raid1 (devs_min = 2, devs_max = 2, dev_stripes = 1), if
free zones are unevenly distributed across devices (for example, 3 free
zones on dev0 and 1 free zone on dev1, so avail = 4 * zone_size >=
2 * chunk_bytes), btrfs_zoned_data_chunk_allowed() returns true and
do_chunk_alloc() consumes 1 zone on dev0 and the last free zone on dev1.
That leaves 2 free zones on dev0 and 0 on dev1, so a subsequent raid1 chunk
allocation for data relocation fails in decide_dev_extent_size() because
ctl->ndevs (1) < ctl->devs_min (2). A similar issue occurs with dup
(dev_stripes = 2) on multiple devices when dev0 has 3 free zones and dev1
has 1 free zone, leaving 1 free zone on each device after one dup allocation.

Conversely, for profiles with devs_max == 0 (raid0, raid10),
btrfs_bg_type_to_num_stripes() always uses fs_info->fs_devices->rw_devices.
On a raid10 filesystem with an odd number of devices, or on a raid0/raid10
filesystem where some devices are full while at least ctl->devs_min devices
still have free zones, decide_dev_extent_size() can allocate narrower chunks
across the remaining devices, whereas requiring 2 * chunk_bytes based on
rw_devices will reject btrfs_chunk_alloc() prematurely.
