[Severity: Medium]
Can this leak a count in fs_info->zoned_seq_meta_bgs or
fs_info->zoned_conv_meta_bgs if block group setup fails after
btrfs_load_block_group_zone_info() succeeds?

In fs/btrfs/block-group.c, both btrfs_make_block_group() (via
btrfs_chunk_alloc() -> do_chunk_alloc() -> btrfs_create_chunk() ->
create_chunk()) and read_one_block_group() (via btrfs_read_block_groups())
call btrfs_load_block_group_zone_info() before finishing setup and inserting
the block group into fs_info->block_group_cache_tree:

fs/btrfs/block-group.c:btrfs_make_block_group() {
	...
	ret = btrfs_load_block_group_zone_info(cache, true);
	if (ret) {
		btrfs_put_block_group(cache);
		return ERR_PTR(ret);
	}

	ret = exclude_super_stripes(cache);
	if (ret) {
		/* We may have excluded something, so call this just in case */
		btrfs_free_excluded_extents(cache);
		btrfs_put_block_group(cache);
		return ERR_PTR(ret);
	}
	...
	ret = btrfs_add_new_free_space(cache, chunk_offset, chunk_offset + size, NULL);
	btrfs_free_excluded_extents(cache);
	if (ret) {
		btrfs_put_block_group(cache);
		return ERR_PTR(ret);
	}

	ret = btrfs_add_block_group_cache(cache);
	if (ret) {
		btrfs_remove_free_space_cache(cache);
		btrfs_put_block_group(cache);
		return ERR_PTR(ret);
	}
	...
}

If exclude_super_stripes(), btrfs_add_new_free_space(), or
btrfs_add_block_group_cache() fails, the block group is freed via
btrfs_put_block_group(cache) without ever being added to
fs_info->block_group_cache_tree. Since the only matching
btrfs_zoned_account_meta_bg(block_group, -1) call is in
btrfs_remove_block_group() when erasing from block_group_cache_tree, the
incremented counter is never decremented, which can leave both
zoned_seq_meta_bgs and zoned_conv_meta_bgs non-zero and disable the fast path
in btrfs_zoned_meta_is_append_only().

Would it make sense to account the metadata block group in
btrfs_add_block_group_cache() when it is inserted into
fs_info->block_group_cache_tree, symmetric with where
btrfs_remove_block_group() decrements the counter?
