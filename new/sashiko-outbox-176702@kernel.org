[Severity: Low]
Earlier in the series, the commit "btrfs: add a new 'stripe_len' parameter to
btrfs_stripe_nr_to_offset()" updated the helper in fs/btrfs/volumes.h to
require two parameters and assert these stripe_len bounds:

static inline u64 btrfs_stripe_nr_to_offset(u32 stripe_nr, u32 stripe_len)
{
	ASSERT(is_power_of_2(stripe_len) && stripe_len <= BTRFS_STRIPE_LEN);
	return (u64)stripe_nr << ilog2(stripe_len);
}

Immediately following this stripe_len validation in btrfs_check_chunk_valid()
in fs/btrfs/tree-checker.c, the two calls to btrfs_stripe_nr_to_offset()
still pass only U32_MAX:

	if (unlikely(length >= btrfs_stripe_nr_to_offset(U32_MAX))) {
		chunk_err(fs_info, leaf, chunk, logical,
			  "chunk length too large: have %llu limit %llu",
			  length, btrfs_stripe_nr_to_offset(U32_MAX));
		return -EUCLEAN;
	}

Should these two calls pass stripe_len as the second argument so that
fs/btrfs/tree-checker.c compiles when CONFIG_BTRFS_FS is enabled?
