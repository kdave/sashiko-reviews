This is a pre-existing issue, but if btrfs_add_swapfile_pin() fails here,
does this error path leak the bg->swap_extents counter?

The counter is incremented via btrfs_inc_block_group_swap_extents(bg) prior
to calling btrfs_add_swapfile_pin(). If btrfs_add_swapfile_pin() returns an
error (e.g. -ENOMEM) and the code jumps to out, btrfs_swap_deactivate() is
invoked for cleanup.

Since btrfs_swap_deactivate() iterates over fs_info->swapfile_pins to
decrement swap_extents, and this block group was never added to the tree
due to the failure, the counter isn't decremented. Could this permanently
pin the block group until unmount?
