btrfs: skip hole detection during full fsync for files without holes

This patch adds an optimization to skip searching for holes during a full
fsync if the file has no prealloc extents and its uncompressed disk space
used matches its i_size.

[Severity: Critical]
Is this optimization vulnerable to a race condition with a concurrent
shrinking truncate?

During a shrinking truncate, truncate_setsize() updates i_size before
btrfs_truncate() decrements the bytes used via inode_get_bytes().

Concurrently, if a directory fsync() is triggered on the parent directory, it
can call log_new_dir_dentries(), which recursively logs the child file via
btrfs_log_inode() without holding the child's VFS inode_lock.

Under these conditions, could i_size == inode_get_bytes() temporarily
evaluate to true in btrfs_log_holes(), causing the hole logging to be
completely bypassed?

For example, if a user punches a hole from 0-4K, writes from 4K-8K, and then
truncates the file to 4K, the new i_size (4K) could temporarily match the
current inode_get_bytes() (4K) during this window.

If hole logging is skipped, would this result in failing to apply the hole
during log replay, leaving stale data accessible after a crash?
