[Severity: High]
Can this cause find_free_extent_update_loop() to skip LOOP_WRONG_SIZE_CLASS
and return a premature -ENOSPC when concurrent allocations of different size
classes race?

During LOOP_UNSET_SIZE_CLASS or LOOP_ALLOC_CHUNK, ffe_ctl->size_class_skipped
has been reset to false at the end of the previous
find_free_extent_update_loop() call. A block group with bg->size_class set to
BTRFS_BG_SZ_NONE passes the lockless find_free_extent_check_size_class()
check, leaving ffe_ctl->size_class_skipped as false.

If two concurrent allocations with different size classes race on that
BTRFS_BG_SZ_NONE block group, both pass find_free_extent_check_size_class()
and allocate space in do_allocation(). In btrfs_add_reserved_bytes() ->
btrfs_use_block_group_size_class(), the first task to acquire bg->lock sets
bg->size_class, while the second task fails with -EAGAIN because
force_wrong_size_class (ffe_ctl->loop >= LOOP_WRONG_SIZE_CLASS) is false:

fs/btrfs/block-group.c:btrfs_use_block_group_size_class() {
	...
	if (bg->size_class != BTRFS_BG_SZ_NONE) {
		if (force_wrong_size_class)
			return 0;
		return -EAGAIN;
	}
	bg->size_class = size_class;
	return 0;
}

In find_free_extent(), the -EAGAIN path returns the free space and jumps to
loop without setting ffe_ctl->size_class_skipped = true:

fs/btrfs/extent-tree.c:find_free_extent() {
		...
		ret = btrfs_add_reserved_bytes(block_group, ffe_ctl->ram_bytes,
					       ffe_ctl->num_bytes,
					       ffe_ctl->delalloc,
					       ffe_ctl->loop >= LOOP_WRONG_SIZE_CLASS);
		if (ret == -EAGAIN) {
			btrfs_add_free_space_unused(block_group,
					ffe_ctl->found_offset,
					ffe_ctl->num_bytes);
			goto loop;
		}
}

A similar situation can also happen in find_free_extent_update_loop() when a
previous loop finishes with ffe_ctl->size_class_skipped == false (for
instance, all existing block groups matched ffe_ctl->size_class and were
full) while a concurrent task allocates the last remaining chunk on the
device and assigns it a different size class. When
find_free_extent_update_loop() skips LOOP_UNSET_SIZE_CLASS and enters
LOOP_ALLOC_CHUNK, btrfs_chunk_alloc() returns -ENOSPC and advances
ffe_ctl->loop directly to LOOP_WRONG_SIZE_CLASS without a search pass to set
ffe_ctl->size_class_skipped:

fs/btrfs/extent-tree.c:find_free_extent_update_loop() {
		...
		ret = btrfs_chunk_alloc(trans, space_info, ffe_ctl->flags,
					CHUNK_ALLOC_FORCE_FOR_EXTENT);

		/* Do not bail out on ENOSPC since we can do more. */
		if (ret == -ENOSPC) {
			ret = 0;
			ffe_ctl->loop++;
		}
}

In both cases, find_free_extent_update_loop() then sees
ffe_ctl->loop == LOOP_WRONG_SIZE_CLASS && !ffe_ctl->size_class_skipped, skips
LOOP_WRONG_SIZE_CLASS, and advances to LOOP_NO_EMPTY_SIZE, returning -ENOSPC
when empty_size == 0 and empty_cluster == 0 even though a block group with a
different size class has free space available.

Should the -EAGAIN path in find_free_extent() set
ffe_ctl->size_class_skipped = true, and should LOOP_WRONG_SIZE_CLASS still
run when transitioning straight from a failed LOOP_ALLOC_CHUNK?
