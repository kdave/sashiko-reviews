btrfs: scrub: wake up cancel_dev waiters after clearing dev->scrub_ctx

btrfs_scrub_cancel_dev() waits on fs_info->scrub_pause_wait for
dev->scrub_ctx to become NULL. btrfs_scrub_dev() wakes that queue right
after dropping scrubs_running, several statements before it clears the
pointer, and never wakes it again. This patch adds a wakeup after the
store to prevent waiters from hanging indefinitely.

[Severity: High]
This is a pre-existing issue, but can this teardown path cause a use-after-free
if it races with btrfs_scrub_progress()?

If btrfs_scrub_progress() is called via the BTRFS_IOC_SCRUB_PROGRESS ioctl, it
locks device_list_mutex and reads dev->scrub_ctx:

fs/btrfs/scrub.c:btrfs_scrub_progress() {
    ...
	mutex_lock(&fs_info->fs_devices->device_list_mutex);
	dev = btrfs_find_device(fs_info->fs_devices, &args);
	if (dev)
		sctx = dev->scrub_ctx;
    ...
}

If this thread is then preempted, btrfs_scrub_dev() can finish, clear
dev->scrub_ctx under scrub_lock (which doesn't serialize with
device_list_mutex), and unconditionally free sctx via scrub_put_ctx() here.

When btrfs_scrub_progress() resumes, it dereferences the freed sctx:

fs/btrfs/scrub.c:btrfs_scrub_progress() {
    ...
	if (sctx)
		memcpy(progress, &sctx->stat, sizeof(*progress));
	mutex_unlock(&fs_info->fs_devices->device_list_mutex);
    ...
}

Should btrfs_scrub_progress() hold a refcount on sctx, or should the teardown
path synchronize with device_list_mutex before freeing sctx?
