iomap: follow the alignment requirement for iomap_dio_hole_iter()

This commit modifies iomap_dio_hole_iter() to round down the copied length
to the filesystem block size and revert the unaligned portion. This is
intended to fix a btrfs assertion failure when iov_iter_zero() fails at a
page boundary not aligned to the filesystem block size.

[Severity: Critical]
Will this cause a NULL pointer dereference for filesystems that leave
iter->iomap.bdev as NULL for IOMAP_HOLE mappings?

For filesystems like f2fs, erofs, and nilfs2, there is no underlying physical
block allocated for a hole, so they don't populate iter->iomap.bdev. Since
they also don't set IOMAP_DIO_FSBLOCK_ALIGNED, calling iomap_dio_alignment()
will fall back to bdev_logical_block_size(bdev) and dereference the NULL
pointer:

fs/iomap/direct-io.c:iomap_dio_alignment() {
	if (dio_flags & IOMAP_DIO_FSBLOCK_ALIGNED)
		return i_blocksize(inode);
	return bdev_logical_block_size(bdev);
}

[Severity: Critical]
Could unconditionally rounding down the copied length break direct I/O reads
at EOF and cause an infinite loop?

If a userspace program performs a direct I/O read that hits a hole at the
end of a file where the file size is not aligned to the block size,
__iomap_dio_rw() clamps the length to EOF.

The copied value will be unaligned, and rounding it down will result in 
aligned_copied == 0. This causes the code to return -EFAULT. In btrfs,
btrfs_direct_read() intercepts -EFAULT, attempts to fault in the pages,
and jumps to retry the direct I/O, resulting in an infinite loop that
locks up the CPU.
