btrfs: use on-disk uuid for s_uuid in temp_fsid mounts

When mounting a cloned filesystem with a temporary fsuuid, layered modules
like overlayfs require a persistent identifier. This commit ensures that
sb->s_uuid carries the original on-disk UUID instead of the temporary random
fs_devices->fsid.

[Severity: High]
This isn't a bug introduced by this patch, but since you are fixing
sb->s_uuid semantics here, does btrfs_setup_sprout() in fs/btrfs/volumes.c
also need attention?

When a read-only seed device is sprouted into a read-write filesystem, a new
random UUID is generated for the filesystem:

fs/btrfs/volumes.c:btrfs_setup_sprout() {
    ...
    generate_random_uuid(fs_devices->fsid);
    memcpy(fs_devices->metadata_uuid, fs_devices->fsid, BTRFS_FSID_SIZE);
    memcpy(disk_super->fsid, fs_devices->fsid, BTRFS_FSID_SIZE);
    ...
}

However, the VFS superblock's UUID (sb->s_uuid) is not updated. Layered
security modules like EVM could calculate HMACs for new or modified files
using the stale seed UUID during the sprouted session.

Upon unmounting and remounting, the mount process will correctly set
sb->s_uuid to the new sprouted UUID, which can cause EVM to fail validation
of the previously created HMACs.

This is reachable when adding a device to a seeded Btrfs filesystem via:
btrfs_ioctl_add_dev() -> btrfs_init_new_device() -> btrfs_setup_sprout()

Should btrfs_setup_sprout() also update sb->s_uuid to prevent this state
inconsistency?
