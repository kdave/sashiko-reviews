btrfs: test that we don't create pointless compressed inline extents

This patch adds a new fstest to verify that we avoid creating compressed
inline extents when the compressed data size is not smaller than the
uncompressed data size. It exercises a regression introduced in kernel 7.1.

[Severity: Medium]
Should the return value of _scratch_mount be checked here?

If the mount fails (for example, if the compression algorithm returned
by _btrfs_compression_algos is not supported by the current kernel),
the script will continue executing. Because the exit code is ignored,
the script blindly proceeds and writes the test file directly to the
host filesystem instead of the scratch device, which can lead to
test environment pollution.

[Severity: Medium]
Could this integer comparison result in a bash syntax error if the grep
commands above find no matches?

If the mount fails, or if the test environment is configured to disable
inline extents (e.g. using max_inline=0 mount options), the grep command
will match nothing. The variables extent_size and ram_size will then be
empty strings. 

This causes bash to evaluate [ "" -gt "" ], which results in a syntax
error (integer expression expected) and causes the test to fail
ungracefully.

> +		echo "inline extent size ($extent_size) greater than ram_size ($ram_size) for algo $algo"
> +	fi
> +done
