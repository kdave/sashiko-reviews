btrfs: fix transaction use-after-free in raid stripe insertion

If allocation of a RAID stripe extent fails,
btrfs_insert_one_raid_extent() aborts and ends the transaction before
returning -ENOMEM.

btrfs_finish_one_ordered(), the production caller through
btrfs_insert_raid_extent(), still owns the transaction handle. It handles
the error by aborting the transaction and then reaches the common exit
path, which ends the transaction again.

[Severity: High]
This isn't a bug introduced by this patch, but looking at
update_raid_extent_item(), which is called further down in
btrfs_insert_one_raid_extent() when btrfs_insert_item() returns -EEXIST:

fs/btrfs/raid-stripe-tree.c:update_raid_extent_item() {
	...
	ret = btrfs_search_slot(trans, trans->fs_info->stripe_root, key, path,
				0, 1);
	if (ret)
		return (ret == 1 ? ret : -EINVAL);

Are we returning a positive error code or squashing actual errors here?

If btrfs_search_slot() returns 1, this propagates up to
btrfs_insert_one_raid_extent(), which calls btrfs_abort_transaction(trans, 1)
and violates the API requirement for negative error codes. If it returns a
genuine negative error, does it get incorrectly squashed into -EINVAL?

fs/btrfs/raid-stripe-tree.c:update_raid_extent_item() {

	write_extent_buffer(leaf, stripe_extent, btrfs_item_ptr_offset(leaf, slot),

Can this result in a metadata buffer overflow?

We don't check if item_size is less than or equal to
btrfs_item_size(leaf, slot) before calling write_extent_buffer(). If the
existing item is smaller, it seems this would write past the item boundaries
and overwrite adjacent b-tree items.

[Severity: High]
This is a pre-existing issue, but in the same code block above:

fs/btrfs/raid-stripe-tree.c:update_raid_extent_item() {
	...
	write_extent_buffer(leaf, stripe_extent, btrfs_item_ptr_offset(leaf, slot),
			    item_size);

Are we missing a call to btrfs_mark_buffer_dirty(trans, leaf) here?

The leaf buffer is modified in-place, but without re-dirtying it, the new
changes might not be flushed to disk when the transaction commits if the
buffer's dirty bit was cleared due to memory pressure, potentially causing
silent metadata corruption.
