btrfs: zstd: fix hang when the workspace preallocation fails

zstd_alloc_workspace_manager() only warns when the max level workspace it
preallocates cannot be allocated, and the mount comes up with none. This
counts the max level workspaces and retries the allocation instead of
sleeping when there are none, backing off with memalloc_retry_wait().

> btrfs_get_workspace() guards the same preallocation failure the same way,
> using total_ws.

[Severity: High]
This isn't a bug introduced by this patch, but does btrfs_get_workspace()

When alloc_workspace() fails under severe memory pressure, and

[Severity: High]
This is a pre-existing issue, but is there a time-of-check to time-of-use
(TOCTOU) race condition in zstd_get_workspace() that causes a lost wakeup?

If the workspace allocation fails, the task calls prepare_to_wait() and
unconditionally calls schedule() without re-checking the wait condition
(e.g., verifying if an idle workspace is now available).

If a concurrent zstd_put_workspace() calls cond_wake_up() between the failed
allocation and prepare_to_wait(), will the wakeup be lost, leaving this
thread in TASK_UNINTERRUPTIBLE indefinitely?

[Severity: High]
This is a pre-existing issue, but are workspaces of lower compression levels
incorrectly hidden from the LRU reclaim list if the max-level workspace is in
use?

In zstd_put_workspace(), the code checks if the max-level idle list is empty
to hide the max-level workspace from reclaim:

fs/btrfs/zstd.c:zstd_put_workspace() {
    ...
    /* A node is only taken off the lru if we are the corresponding level */
    if (clip_level(workspace->req_level) == workspace->level) {
        /* Hide a max level workspace from reclaim */
        if (list_empty(&zwsm->idle_ws[ZSTD_BTRFS_MAX_LEVEL - 1])) {
            INIT_LIST_HEAD(&workspace->lru_list);
        } else {
    ...
}

This applies the logic based solely on the emptiness of the max-level idle
list, without verifying that the currently returned workspace is actually a
max-level workspace. If the max-level workspace is in use, ANY returned
workspace (e.g. level 3) will execute INIT_LIST_HEAD(&workspace->lru_list)
instead of being added to zwsm->lru_list.

Could this lead to a permanent memory leak of lower level ZSTD workspaces by
bypassing the timer-based reclaim mechanism?
