btrfs: zoned: avoid ordered_operations_mutex when finishing a zone

This commit introduces btrfs_wait_ordered_roots_nolock() to wait for ordered
extents in a block group without taking the ordered_operations_mutex. This
aims to prevent a deadlock that occurs when an ordered extent flush worker
attempts to finish a zone while the reclaim task holds the mutex.

[Severity: High]
Does this fallback path reintroduce the exact deadlock this patch is trying
to fix?

If memory pressure causes kvmalloc_array() with GFP_NOFS to fail, the code
falls back to calling btrfs_wait_ordered_roots(). 

If this is reached from an ordered extent flush worker (e.g., via
do_zone_finish()), btrfs_wait_ordered_roots() will attempt to acquire the
ordered_operations_mutex, which is already held by the reclaim task waiting
for this flush worker.

[Severity: High]
Can this bounded loop silently skip roots that were concurrently rotated to
the end of the list?

The code computes cap = list_count_nodes(&fs_info->ordered_roots), drops the
ordered_root_lock to allocate memory, and then collects up to cap roots.

If a concurrent btrfs_add_ordered_root() adds a new root to the tail of the
list, and a concurrent btrfs_wait_ordered_roots() rotates an existing, older
root to the tail (after the newly added one), this loop will hit the
nr_roots >= cap break condition when encountering the newly added root.

finishing a zone prematurely while ordered extents are still pending?
