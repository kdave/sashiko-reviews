btrfs: zoned: don't activate conventional zones of mixed block groups

This patch skips conventional stripes when activating, finishing, and
reserving active zones in zoned btrfs, and propagates the active state of
sequential stripes to conventional stripes when loading mixed block groups.
It also skips fully conventional block groups in btrfs_zone_finish_one_bg().

[Severity: High]
Could setting active on stripe 0 here cause btrfs_load_block_group_raid1(),
btrfs_load_block_group_raid0(), and btrfs_load_block_group_raid10() in
fs/btrfs/zoned.c to skip activating inactive sequential stripes?

When a mixed multi-stripe block group has a conventional zone at stripe 0, at
least one active sequential stripe, and another sequential stripe that is
still inactive (such as an empty sequential stripe in a partially written
RAID0 or RAID10 block group, or a RAID1/RAID1C3/RAID1C4 block group with an
activeness mismatch), this loop sets bit 0 in active.

When the RAID loader then iterates over the stripes starting at i = 0,
test_bit(0, active) != test_bit(0, active) is false, so the else branch runs
on the first iteration and sets BLOCK_GROUP_FLAG_ZONE_IS_ACTIVE before later
stripes are checked:

fs/btrfs/zoned.c:btrfs_load_block_group_raid0() {
    ...
		if (test_bit(0, active) != test_bit(i, active)) {
			if (unlikely(!btrfs_zone_activate(bg)))
				return -EIO;
		} else {
			if (test_bit(0, active))
				set_bit(BLOCK_GROUP_FLAG_ZONE_IS_ACTIVE, &bg->runtime_flags);
		}
    ...
}

When a subsequent iteration reaches an inactive sequential stripe where
test_bit(0, active) != test_bit(i, active), it calls btrfs_zone_activate(bg),
which sees BLOCK_GROUP_FLAG_ZONE_IS_ACTIVE already set and returns early:

fs/btrfs/zoned.c:btrfs_zone_activate() {
    ...
	if (test_bit(BLOCK_GROUP_FLAG_ZONE_IS_ACTIVE, &block_group->runtime_flags)) {
		ret = true;
		goto out_unlock;
	}
    ...
}

As a result, the inactive sequential stripe is not recorded in
zone_info->active_zones and active_zones_left is not decremented.  Subsequent
writes to that stripe will open the hardware zone without btrfs accounting for
it, which can exceed max_active_zones and fail with -EIO.

In addition, for active metadata or system block groups,
btrfs_check_active_zone_reservation() decrements reserved_active_zones for
every sequential stripe, while call_zone_finish() only increments
reserved_active_zones when btrfs_dev_clear_active_zone() returns true.
Wouldn't that permanently leak the active zone reservation when the unrecorded
sequential stripe finishes?
