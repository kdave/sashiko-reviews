[Severity: Critical]
This isn't a bug introduced by this patch, but this pre-existing issue looks 
like it might cause a similar use-after-free just before the code modified
here.

When adding a seeding device, init_first_rw_device() allocates metadata and
system chunks, adding their maps to the global fs_info->mapping_tree. These
chunk maps hold pointers to the newly allocated device.

If a subsequent step fails, like btrfs_add_dev_item() or 
btrfs_finish_sprout(), the transaction is aborted and the code jumps to the 
error_sysfs label:

fs/btrfs/volumes.c:btrfs_init_new_device() {
        ...
        ret = btrfs_add_dev_item(trans, device);
        if (unlikely(ret)) {
                btrfs_abort_transaction(trans, ret);
                goto error_sysfs;
        }
        ...

The error_sysfs path removes the device from the device lists and frees it 
via btrfs_free_device().

However, the successfully created chunks are never removed from the in-memory 
mapping_tree. Since the filesystem remains mounted in an aborted, read-only 
state, won't any subsequent block mappings via btrfs_map_block() look up 
these chunks and dereference the freed btrfs_device pointer?
