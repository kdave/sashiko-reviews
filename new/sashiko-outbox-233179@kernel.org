[Severity: Medium]
Does calculating target with btrfs_bg_type_to_num_stripes() mix physical
stripe bytes with logical garbage bytes on mirrored profiles?

btrfs_bg_type_to_num_stripes() returns the total number of physical
device stripes across all mirrors (dev_stripes * ndevs), whereas
bg->length, bg->zone_capacity, and bg->zone_unusable in
zoned_bg_garbage() are measured in logical block-group bytes (dividing
num_stripes by ncopies).  On DUP, RAID1, RAID1C3, RAID1C4, or RAID10
data profiles, comparing logical garbage against physical target inflates
target by ncopies (2x to 4x), queuing up to 4 to 8 block groups worth of
logical garbage instead of 2.  Should target divide the stripe count by
btrfs_bg_type_to_factor(profile)?

[Severity: Medium]
Should btrfs_zoned_reclaim_sweep() also include
data_sinfo->sub_group[BTRFS_SUB_GROUP_DATA_RELOC] in total_bytes and
sweep it with zoned_sweep_space_info()?

The commit message notes that the sweep considers the block groups of the
data relocation sub-group, and zoned_bg_reclaimable() checks
BLOCK_GROUP_FLAG_ZONED_DATA_RELOC to skip the active relocation block
group.  However, btrfs_zoned_reclaim_sweep() only sweeps data_sinfo.  If
fs_info->data_reloc_bg fills to zone_capacity on the final extent of a
relocation pass, btrfs_zoned_release_data_reloc_bg() clears
BLOCK_GROUP_FLAG_ZONED_DATA_RELOC while fs_info->data_reloc_bg still
points to bg->start, so btrfs_zoned_return_data_reloc_bgs() leaves that
full block group in data_sinfo->sub_group[BTRFS_SUB_GROUP_DATA_RELOC]:
