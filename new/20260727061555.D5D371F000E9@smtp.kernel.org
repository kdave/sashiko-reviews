Subject: btrfs: trigger cow fixup via dirty_folio()

This commit reintroduces the COW fixup mechanism for folios dirtied without
a space reservation, adding support for subpage block sizes. It intercepts
out-of-band dirtying to mark blocks for fixup and queues an async worker to
reserve space before writeback proceeds.

[Severity: High]
Does this sequence leave a race window during writeback?

If a concurrent out-of-band dirty operation (like zap_pte_range() locklessly
calling set_page_dirty()) occurs after btrfs_copy_subpage_dirty_bitmap()
but before writepage_fixup(), it will set the folio's dirty bit and the
fixup_pending flag.

When writepage_fixup() runs, it will see the fixup_pending flag is set, but
since it iterates over the stale bio_ctrl->submit_bitmap snapshot, it won't
find any bits requiring fixup. This falls through to the failure path, prints
a warning, and returns -EUCLEAN, spuriously aborting writeback.

[Severity: High]
Can this lead to a permanent space reservation leak in production kernels?

The collision resolution logic here clears the fixup bit when it detects both
EXTENT_DELALLOC and fixup are set. However, it is guarded by
IS_ENABLED(CONFIG_BTRFS_DEBUG), which is compiled out in production builds.

If a reserving write races with the lockless folio_test_dirty() check in
btrfs_folio_set_fixup_dirty() for non-subpage folios, it can incorrectly set
fixup_pending on a folio that already has EXTENT_DELALLOC.

When that happens in a production kernel, the collision check is skipped, and
the worker proceeds to set the bit in delalloc_bitmap. At the end of the
worker function, it will skip releasing the space it reserved for this block,
permanently double-accounting and leaking the reserved space.

[Severity: High]
Is it safe to use ihold() on the inode here?

Background writeback frequently operates on inodes residing on the LRU list
with an i_count of 0 (protected by I_SYNC).

Calling ihold() directly on an inode with a zero reference count will trigger
VFS_BUG_ON_INODE. If assertions are disabled, it un-safely increments the
count to 1. When the fixup worker completes, btrfs_add_delayed_iput() will
drop the count back to 0, prematurely freeing the inode while the writeback
thread might still be operating on it.

[Severity: High]
Could this cause writeback to fail with -EUCLEAN for partially uptodate
subpage folios?

If an out-of-band dirtying path (like a DIO read) dirties a subpage folio
that is only partially uptodate, btrfs_folio_set_fixup_dirty() will bail out
early because folio_test_uptodate() is false. The master PG_uptodate flag
is only set when the entire subpage folio is uptodate.

However, filemap_dirty_folio() is then unconditionally called, setting the
master PG_dirty flag.

During writeback, writepage_delalloc() copies an empty subpage dirty bitmap.
Then, writepage_fixup() sees the folio is dirty but has an empty
submit_bitmap, causing it to fail its sanity check and return -EUCLEAN.
