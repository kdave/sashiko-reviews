btrfs: zoned: requeue block group if zone reset bails out

btrfs_reset_unused_block_groups() drops the block-group from
fs_info->unused_bgs before performing the work that can actually fail,
the actual submission of a REQ_OP_ZONE_RESET. Every failed operation
after this leaves the block-group dangling. Instead of bailing out,
re-add this block-group to fs_info->unused_bgs list.

[Severity: Critical]
Does this code incorrectly resurrect a deleted block group if it was
concurrently relocated and deleted?

If a concurrent balance or reclaim operation relocates and deletes the
block group while btrfs_reset_unused_block_groups() has dropped the list
lock, the block group will have bg->ro set.

By taking the requeue path here, the fully deleted block group gets added
back to the retry_list instead of being safely discarded.

[Severity: Critical]
Can adding this block group back to the unused list via retry_list lead to
data corruption or kernel panics?

Since the physical space might have been freed and reallocated to a new
chunk by the concurrent deletion, a subsequent run of
btrfs_reset_unused_block_groups() could pick this logically deleted block
group again.

Issuing REQ_OP_ZONE_RESET to its old physical sectors would destroy the
new chunk's data. Alternatively, btrfs_delete_unused_bgs() could try to
delete it again and crash at an ASSERT(map != NULL) since the chunk map
is already deleted.

Can we ensure that concurrently deleted block groups are safely discarded
instead of requeued?
