[Severity: Medium]
In fs/btrfs/block-group.c:caching_thread(), ctl->free_space is populated
under ctl->tree_lock, followed by spin_unlock(&ctl->tree_lock), and then
block_group->cached is updated under block_group->lock with a plain store:

fs/btrfs/block-group.c:caching_thread() {
	...
	spin_lock(&block_group->lock);
	block_group->caching_ctl = NULL;
	block_group->cached = ret ? BTRFS_CACHE_ERROR : BTRFS_CACHE_FINISHED;
	spin_unlock(&block_group->lock);
	...
}

Because a spin_unlock(&ctl->tree_lock) release followed by a
spin_lock(&block_group->lock) acquire is not a full memory barrier, and
spin_unlock(&block_group->lock) happens after the assignment to
block_group->cached, prior stores to ctl->free_space and the plain store
to block_group->cached can be reordered on weakly-ordered architectures.

Without pairing smp_load_acquire(&block_group->cached) with
smp_store_release(&block_group->cached, ...) in caching_thread(), could
find_free_extent_skip_block_group() observe BTRFS_CACHE_FINISHED while
reading a stale pre-finished value of free_space (such as 0), skipping a
block group that has space without setting ffe_ctl->have_caching_bg?

On zoned filesystems (BTRFS_EXTENT_ALLOC_ZONED), all block groups have

block_group->zone_capacity - block_group->alloc_offset. Previously, when
an active data block group had ffe_ctl->min_alloc_size <= avail < num_bytes,
do_allocation_zoned() updated both ffe_ctl->max_extent_size and
ffe_ctl->total_free_space:

fs/btrfs/extent-tree.c:do_allocation_zoned() {
	...

			ffe_ctl->max_extent_size = avail;
			ffe_ctl->total_free_space = avail;
		}

		goto out;
	}

only updates ffe_ctl->total_free_space, do_allocation_zoned() is bypassed
and ffe_ctl->max_extent_size remains 0 during find_free_extent_update_loop()
(since find_free_extent() only copies total_free_space to max_extent_size
