btrfs: wait for ordered extents before buffered write fallback in direct IO

When btrfs_direct_write() falls back to buffered IO after a failed DIO
attempt, it may race with the asynchronous completion of DIO ordered
extents. This patch waits for pending ordered extents before starting
the buffered write to prevent overlapping extents.

Does this introduce a Time-Of-Check to Time-Of-Use (TOCTOU) race?

Because this while loop executes after dropping the VFS inode lock, a
concurrent thread could issue a direct IO write, acquire the lock, create a
new ordered extent, and drop the lock before btrfs_buffered_write()
