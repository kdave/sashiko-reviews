Subject: btrfs: zoned: drop stale dirty btree buffers at close_ctree()

This patch drops the dirty state of stale, freed-but-dirty btree buffers at
close_ctree() on zoned filesystems. It prevents unmount hangs that occur
when these buffers are queued for writeback after the block groups and
workqueues have been destroyed.

[Severity: Medium]
Does this broad check risk masking legitimately leaked dirty metadata buffers?

By checking only EXTENT_BUFFER_DIRTY, this intercepts any dirty metadata and
silently drops its state. If a filesystem bug causes an unwritten dirty
metadata buffer (without EXTENT_BUFFER_ZONED_ZEROOUT set) to survive until
unmount, this will clear its dirty bit and bypass the extent_buffer_under_io()
check later in invalidate_and_check_btree_folios(), suppressing the
WARN_ON_ONCE intended for detecting leaked metadata.

Should this condition explicitly verify if EXTENT_BUFFER_ZONED_ZEROOUT is
set so it only targets the intended deferred zero-out buffers?
