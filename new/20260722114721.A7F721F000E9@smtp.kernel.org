btrfs: zoned: drop stranded dirty metadata buffers at unmount

This commit adds a call to btrfs_zoned_release_dirty_metadata() during
unmount on zoned filesystems to drop stranded dirty metadata buffers from
freed tree blocks. This prevents a hang in folio_wait_writeback() during
the final iput() of the btree inode.

[Severity: High]
Does this new call unconditionally clear the dirty state for all metadata
extent buffers?

Looking at btrfs_zoned_release_dirty_metadata() in fs/btrfs/extent_io.c, it
appears to process every dirty extent buffer without checking if the
EXTENT_BUFFER_ZONED_ZEROOUT bit is actually set:

fs/btrfs/extent_io.c:btrfs_zoned_release_dirty_metadata() {
    ...
    while (buffer_tree_get_ebs_tag(fs_info, &index, ULONG_MAX,
                                   PAGECACHE_TAG_DIRTY, &batch)) {
        struct extent_buffer *eb;

        while ((eb = eb_batch_next(&batch)) != NULL) {
            btrfs_tree_lock(eb);
            clear_bit(EXTENT_BUFFER_ZONED_ZEROOUT, &eb->bflags);
            clear_extent_buffer_dirty(eb);
            btrfs_tree_unlock(eb);
        }
    ...
}

Will exposing the normal unmount path to this unconditional clearing allow
valid dirty data that failed to write to be silently dropped? 

This seems like it would bypass the checks in
invalidate_and_check_btree_folios() called immediately after this,
potentially masking data loss or filesystem corruption bugs.
