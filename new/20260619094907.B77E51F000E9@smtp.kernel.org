btrfs: implement delete of parity stripes

This commit retains data and parity items for partially freed RAID56
stripes to ensure degraded reads can still reconstruct correctly. It
defers deleting these retained items until the entire block group is
removed.

[Severity: Critical]
Does this loop prematurely exit when it encounters a hole or an interleaved
key type, preventing cleanup of subsequent fragmented partial stripes?

Because the new caller in btrfs_remove_block_group() passes the full logical
range of the block group, it expects this function to scan and delete all
remaining sparse partial stripe items.

However, if the block group has a hole at the start (e.g., the first few
stripes were already fully deleted), the backwards step on the path slots
will land on an item from a previous block group where found_end <= start.
This causes the loop to break entirely.

Similarly, when searching for the parity type, if a data stripe exists at
the same objectid, stepping back can land on the data stripe instead of the
parity stripe. This will trigger the key.type != type condition and also
break the loop.

Will breaking out of the loop in these cases instead of skipping ahead
permanently leak all remaining partial stripe items in the deleted block
group?
