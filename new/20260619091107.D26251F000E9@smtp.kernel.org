btrfs: zoned: align max_zone_append_size to the stripe length for RST

This commit aligns the maximum zone append size down to the BTRFS stripe
length when the raid-stripe-tree feature is enabled to prevent mid-stripe
writes and subsequent mapping corruption. It also guards against a zero
result if the device's append limit is smaller than a stripe.

[Severity: Critical]
This is a pre-existing issue, but does this logic leave the filesystem
vulnerable to the exact corruption it tries to prevent?

Looking at btrfs_check_zoned_mode(), if a device has a zone append limit
smaller than BTRFS_STRIPE_LEN (e.g., 32KB on some NVMe ZNS drives vs a 64KB
stripe length), ALIGN_DOWN() will return 0.

By skipping the update when aligned == 0, max_zone_append_size remains at
its original unaligned value. As the commit message notes, if this size is
not a multiple of BTRFS_STRIPE_LEN, bios will end mid-stripe and corrupt
the stripe-tree mapping.

Should the mount be rejected instead (e.g., returning -EINVAL) when
aligned == 0, since RAID_STRIPE_TREE requires the ability to append at
least one full stripe?
