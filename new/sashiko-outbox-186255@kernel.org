[Severity: Medium]
Can this cause btrfs_reset_unused_block_groups() to stop reclaiming early
without freeing space for the caller's space_info?

On zoned filesystems, create_space_info() creates sub-group space_info
instances for data relocation and tree-log that share the same
space_info->flags as their parent primary space_info, and block groups from
both are placed on the shared fs_info->unused_bgs list.

In fs/btrfs/zoned.c, btrfs_reset_unused_block_groups() selects candidates
from fs_info->unused_bgs by comparing flags rather than matching
bg->space_info:

	spin_lock(&fs_info->unused_bgs_lock);
	list_for_each_entry(bg, &fs_info->unused_bgs, bg_list) {
		if ((bg->flags & BTRFS_BLOCK_GROUP_TYPE_MASK) != space_info->flags)
			continue;

Previously, btrfs_reset_unused_block_groups() updated bytes_zone_unusable and
called btrfs_return_free_space() on the caller-provided space_info, whereas
zoned_reset_bg_in_place() now uses bg->space_info:

	ret = zoned_reset_bg_in_place(bg, &reclaimed);
	if (ret || !reclaimed)
		goto requeue;

	btrfs_put_block_group(bg);

	if (num_bytes <= reclaimed)
		break;
	num_bytes -= reclaimed;

When flush_space() calls btrfs_reset_unused_block_groups() for a primary
space_info and encounters an unused block group belonging to a sub-group
space_info (or vice versa), zoned_reset_bg_in_place() credits the reclaimed
space and wakes tickets on bg->space_info, while
btrfs_reset_unused_block_groups() still subtracts reclaimed from num_bytes
and breaks out of the loop without reclaiming space for the target
space_info.

Should the loop in btrfs_reset_unused_block_groups() check
bg->space_info != space_info instead of comparing the block group type flags?
