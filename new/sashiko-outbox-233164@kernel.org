btrfs: zoned: don't wait for a zone finish after a filesystem error

This commit clears and wakes waiters on BTRFS_FS_NEED_ZONE_FINISH when a
filesystem error or emergency shutdown occurs, and makes cow_file_range()
and btrfs_new_extent_direct() bail out with the recorded error after
waiting.

[Severity: High]
Can this cause a double unlock of locked_folio when cow_file_range()
fails on the second or later iteration of run_delalloc_cow()?

fs/btrfs/inode.c:run_delalloc_cow() {
	while (start <= end) {
		ret = cow_file_range(inode, locked_folio, start, end,
				     &done_offset, COW_FILE_RANGE_KEEP_LOCKED);
		if (ret)
			return ret;
		extent_write_locked_range(&inode->vfs_inode, locked_folio,
					  start, done_offset, wbc);
		start = done_offset + 1;
	}
}

If the first cow_file_range() call makes partial progress before running
out of active zones, it returns 0 with done_offset < end, and
extent_write_locked_range() calls btrfs_folio_end_lock() on locked_folio
for [start, done_offset].  On the next iteration of run_delalloc_cow(),
start == orig_start inside cow_file_range(), so -EAGAIN waits on
BTRFS_FS_NEED_ZONE_FINISH.

If that wait wakes on a filesystem error and cow_file_range() returns a
negative error via out_unlock (which leaves locked_folio untouched),
run_delalloc_cow() propagates the error to extent_writepage() or
submit_uncompressed_range().  Both callers assume locked_folio is still
locked across the entire initial range on error and unlock it again via
btrfs_folio_end_lock_bitmap() or btrfs_folio_end_lock(), triggering
VM_BUG_ON_FOLIO(!folio_test_locked(folio), folio) or underflowing
bfs->nr_locked in subpage mode and leaking the folio lock.
