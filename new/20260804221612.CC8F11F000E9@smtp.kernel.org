iomap: follow the alignment requirement for iomap_dio_hole_iter()

This commit aligns the copied length down to the filesystem block size in
iomap_dio_hole_iter() and reverts any excess, to prevent unaligned extent state
assertions in Btrfs when a page fault interrupts zeroing.

[Severity: High]
Does this unconditional filesystem block size alignment break valid sub-block
direct I/O reads from holes on filesystems like XFS and ext4?

If an application performs a sub-blocksize (e.g., 512 bytes) sector-aligned
O_DIRECT read from a file hole on XFS or ext4 (which typically have a
4096-byte block size), iov_iter_zero() successfully zeroes 512 bytes.

However, aligned_copied = round_down(512, 4096) evaluates to 0. This reverts
the iterator and returns -EFAULT directly to user space.

Should this logic be explicitly guarded by the IOMAP_DIO_FSBLOCK_ALIGNED
flag, which is only used by Btrfs?

> -	return iomap_iter_advance(iter, length);
> +	return iomap_iter_advance(iter, aligned_copied);
>  }
