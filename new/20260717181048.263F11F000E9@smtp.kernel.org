btrfs: pre-allocate delayed dir index for non-overwrite rename

This patch pre-allocates the delayed dir index for rename() without an
overwrite target before modifying the btree. It introduces a prealloc
parameter to btrfs_add_link() and btrfs_insert_dir_item() which takes
ownership of the preallocated resources.

[Severity: Medium]
Does this code leak the preallocated delayed dir index on path allocation failure?

If btrfs_alloc_path() fails inside btrfs_insert_dir_item(), it returns -ENOMEM
early without freeing the prealloc structure:

fs/btrfs/dir-item.c:btrfs_insert_dir_item() {
	...
	path = btrfs_alloc_path();
	if (!path)
		return -ENOMEM;
	...
}

However, the caller in btrfs_rename() clears its reference right after calling
btrfs_add_link(), transferring ownership and assuming the prealloc is fully
consumed or freed:

fs/btrfs/inode.c:btrfs_rename() {
	...
	ret = btrfs_add_link(trans, BTRFS_I(new_dir), ...
			     prealloc.item ? &prealloc : NULL);
	prealloc.item = NULL;
	...
}

Since btrfs_insert_dir_item() drops the pointer on an early failure, and the
caller already cleared its local reference, will this memory be permanently
leaked?

>  	if (ret == -EEXIST || ret == -EOVERFLOW || ret == -ENOMEM)
>  		goto fail_dir_item;
