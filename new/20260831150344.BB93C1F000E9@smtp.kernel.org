btrfs: balance: fix potential bg lookup failure in btrfs_may_alloc_data_chunk()

Running btrfs balance can trigger a null pointer dereference before relocating
a data chunk when metadata corruption leaves a chunk in the chunk tree
without a corresponding block group in the in-memory cache. This adds
a NULL check after btrfs_lookup_block_group() in
btrfs_may_alloc_data_chunk() and prints an error message for clarity.

> diff --git a/fs/btrfs/volumes.c b/fs/btrfs/volumes.c
> index 2bec544d8ba30..69cddb6cfc8d8 100644
> --- a/fs/btrfs/volumes.c
> +++ b/fs/btrfs/volumes.c
> @@ -3597,7 +3597,11 @@ static int btrfs_may_alloc_data_chunk(struct btrfs_fs_info *fs_info,
>  	u64 chunk_type;
>

> -	ASSERT(cache);

> +	}

[Severity: High]
This isn't a bug introduced by this patch, but I noticed there are other places
in fs/btrfs/volumes.c that might be vulnerable to the same crash.

Since metadata corruption can cause btrfs_lookup_block_group() to return NULL,
do we also need similar NULL checks in the balance filters? For example, in
chunk_usage_range_filter():

	cache = btrfs_lookup_block_group(fs_info, chunk_offset);
	chunk_used = cache->used;

And similarly in chunk_usage_filter():

	cache = btrfs_lookup_block_group(fs_info, chunk_offset);
	chunk_used = cache->used;

I also see a similar pattern during device replace on zoned filesystems in
is_block_group_to_copy(), where the return value is passed to test_bit()
without a check:

	cache = btrfs_lookup_block_group(fs_info, logical);

	ret = test_bit(BLOCK_GROUP_FLAG_TO_COPY, &cache->runtime_flags);

Could these paths also trigger a kernel oops if a corrupted filesystem is
administered with balance usage filters or device replace?
