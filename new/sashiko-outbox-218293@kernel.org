[Severity: Medium]
Can a file extent item with disk_bytenr == 0 and compression !=
BTRFS_COMPRESS_NONE bypass this check with disk_num_bytes == 0?

During an incremental send with BTRFS_SEND_FLAG_COMPRESSED, if a parent
snapshot had a data extent at that offset, process_extent() sees the extent
as changed and calls send_write_or_clone() -> send_extent_data():

fs/btrfs/send.c:send_extent_data() {
	...
		} else if (!is_inline &&
			   btrfs_file_extent_disk_num_bytes(leaf, ei) <= len) {
			return send_encoded_extent(sctx, path, offset, len);
		}
	...
}

send_encoded_extent() then calls btrfs_encoded_read_regular_fill_pages()
with disk_io_size == 0 and submits an empty bio to btrfs_submit_bbio(),
triggering the length != 0 assertion failure in assert_bbio_alignment().

Also, check_extent_data_item() allows BTRFS_FILE_EXTENT_PREALLOC items to
have compression != BTRFS_COMPRESS_NONE, which causes
btrfs_extent_item_to_extent_map() to mark the extent map as compressed
instead of setting EXTENT_FLAG_PREALLOC, so reads attempt to decompress
unwritten preallocated blocks.

Should check_extent_data_item() require compression == BTRFS_COMPRESS_NONE
for holes (disk_bytenr == 0) and BTRFS_FILE_EXTENT_PREALLOC extents, and
require disk_num_bytes == 0, offset == 0, and fi_type ==
BTRFS_FILE_EXTENT_REG when disk_bytenr == 0?
