[Severity: High]
Can this cause a deadlock during memory reclaim?

When a user sets the btrfs.compression property, btrfs_ioctl_setflags()
starts a Btrfs transaction before calling btrfs_set_prop(), which then calls
this validation handler:

fs/btrfs/ioctl.c:btrfs_ioctl_setflags()
    trans = btrfs_start_transaction(root, 1);
    ...
    ret = btrfs_set_prop(trans, inode, "btrfs.compression", ...);

fs/btrfs/props.c:btrfs_set_prop()
    ret = handler->validate(inode, value, value_len);

Using GFP_KERNEL here allows direct memory reclaim, which can recurse into
Btrfs to free memory. If the reclaim process attempts to acquire transaction
locks already held by the current thread, it will deadlock.

[Severity: High]
This is a pre-existing issue, but can this result in an out-of-bounds heap
read when processing a maliciously crafted disk image?

When loading an inode from disk, btrfs_load_inode_props() delegates to
iterate_object_props(), which dynamically allocates value_buf based exactly
on the data length read from the disk:

fs/btrfs/props.c:iterate_object_props() {
    ...
    value_buf = kmalloc(data_len, GFP_NOFS);
    ...
    read_extent_buffer(leaf, value_buf, data_ptr, data_len);
    iterator(ctx, handler, value_buf, data_len);
}

The iterator eventually calls prop_compression_apply():

fs/btrfs/props.c:prop_compression_apply() {
    ...
    if (!strncmp("lzo", value, 3)) {
        type = BTRFS_COMPRESS_LZO;
}

If data_len is artificially small (e.g., 1 byte) and contains a partial
match (like 'l'), strncmp() will read past the 1-byte heap allocation since
the value buffer is not null-terminated.
