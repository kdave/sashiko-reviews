btrfs: zoned: reuse block groups emptied by reclaim as relocation target

This commit marks block groups undergoing zoned reclaim with
BLOCK_GROUP_FLAG_ZONED_RECLAIM and resets emptied data block groups in place
via btrfs_zoned_reuse_reclaimed_bg() instead of removing their chunks, aiming
to reuse them as the next data relocation target.

[Severity: High]
What prevents scrub_enumerate_chunks() in fs/btrfs/scrub.c from racing with
btrfs_zoned_reuse_reclaimed_bg() after bg->lock is dropped here?

In fs/btrfs/volumes.c, btrfs_relocate_chunk() calls btrfs_scrub_continue() as
soon as btrfs_relocate_block_group() returns, before calling
btrfs_relocate_chunk_finish() -> btrfs_zoned_reuse_reclaimed_bg(). In
addition, scrub_enumerate_chunks() freezes the block group via
btrfs_freeze_block_group() before calling btrfs_inc_block_group_ro(), which
is not checked by btrfs_zoned_can_reuse_bg().

Once btrfs_zoned_can_reuse_bg() drops bg->lock and btrfs_dec_block_group_ro()
drops bg->ro to 0, zoned_reset_bg_in_place() sleeps in blkdev_zone_mgmt().
During that window, a concurrent scrub_enumerate_chunks() can call
btrfs_inc_block_group_ro(bg), find no extents in the commit root, call
btrfs_dec_block_group_ro(bg), and re-add bg to fs_info->unused_bgs:

fs/btrfs/scrub.c:scrub_enumerate_chunks() {
	...
	spin_lock(&cache->lock);
	if (!test_bit(BLOCK_GROUP_FLAG_REMOVED, &cache->runtime_flags) &&
	    !cache->ro && cache->reserved == 0 && cache->used == 0) {
		spin_unlock(&cache->lock);
		if (btrfs_test_opt(fs_info, DISCARD_ASYNC))
			btrfs_discard_queue_work(&fs_info->discard_ctl,
						 cache);
		else
			btrfs_mark_bg_unused(cache);
	}
	...
}
