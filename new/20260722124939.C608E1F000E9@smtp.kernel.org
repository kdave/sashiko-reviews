btrfs: check for log writers count first in wait_for_writer()

This commit attempts to optimize wait_for_writer() by checking the
number of log writers before adding the wait queue entry, avoiding
unnecessary wait queue locking overhead when there are no log writers.

[Severity: High]
Does this sequence open a race window that can result in a lost wakeup?

By checking the sleep condition before calling prepare_to_wait(), if a
concurrent lockless wakeup occurs between the check and prepare_to_wait(),
the wakeup will be missed.

For example, if Thread A in wait_for_writer() evaluates
atomic_read(&root->log_writers) == 0 as false:

Thread B concurrently completes its write in btrfs_end_log_trans():
	if (atomic_dec_and_test(&root->log_writers)) {
		/* atomic_dec_and_test implies a barrier */
		cond_wake_up_nomb(&root->log_writer_wait);
	}

Because Thread A has not yet added itself to the wait queue with
prepare_to_wait(), the waitqueue is inactive and the wakeup is lost.

Thread A then calls prepare_to_wait(), unlocks the mutex, and calls
schedule(), sleeping indefinitely since the condition is already met.

Can this lead to a task performing btrfs_sync_log() hanging forever in
TASK_UNINTERRUPTIBLE?

>  		mutex_unlock(&root->log_mutex);
>  		schedule();
>  		mutex_lock(&root->log_mutex);
