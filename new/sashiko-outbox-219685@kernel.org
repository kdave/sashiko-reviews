btrfs: zoned: return finished relocation block groups to the data space_info

This commit adds btrfs_zoned_return_data_reloc_bgs() to return finished
relocation block groups from the data relocation sub-space_info back to the
primary data space_info after each block-group reclaim run, followed by
reserving a new data relocation block group.

[Severity: High]
Does btrfs_zoned_return_data_reloc_bgs() leave relocation block groups
stranded instead of returning their space to data_sinfo?

When a relocation block group is retired during btrfs_reclaim_block_groups(),
it contains the newly relocated live extents, so btrfs_is_block_group_used(bg)
is true.  Both btrfs_zoned_return_data_reloc_bgs() and
zoned_move_bg_to_space_info() require !btrfs_is_block_group_used(bg), so
filled or partially-filled relocation block groups stay in reloc_sinfo while
btrfs_zoned_reserve_data_reloc_bg() reserves another one.

When all extents in that former relocation block group are later freed,
btrfs_delete_unused_bgs() runs inside btrfs_reclaim_block_groups() before
btrfs_zoned_return_data_reloc_bgs().  If the block group is the only entry
in reloc_sinfo->block_groups[raid], btrfs_delete_unused_bgs() pops it from
fs_info->unused_bgs and skips it at list_is_singular(&block_group->list)
without re-queuing it.  btrfs_zoned_return_data_reloc_bgs() then moves found
to data_sinfo without resetting its zones or calling
btrfs_mark_bg_unused(found), and zoned_dec_bg_ro() restores
found->zone_unusable to found->alloc_offset + (found->length -
found->zone_capacity).  Because found has used == 0 and is off
fs_info->unused_bgs, it is never reset or deleted.

Finally, if btrfs_reset_unused_block_groups() resets an unused block group
in reloc_sinfo in place while fs_info->data_reloc_bg is already set,
zoned_reset_bg_in_place() sets bg->alloc_offset = 0.  The bg->alloc_offset
check here then skips it, and btrfs_zoned_reserve_data_reloc_bg() only
searches data_sinfo, stranding the reset empty block group in reloc_sinfo.
