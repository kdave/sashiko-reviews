btrfs: write back a folio extent-by-extent instead of block-by-block

This commit optimizes dirty folio writeback to submit ranges extent-by-extent
rather than block-by-block. It introduces truncate_ordered_extents_beyond_eof()
and find_next_write_range() to iterate efficiently over larger ordered extents.

[Severity: High]
Could this min() calculation cause an unsigned underflow if there is an
ordered extent gap?

While there is an ASSERT() above that expects no gaps, if an ordered extent
failed to be allocated earlier on an error path, btrfs_lookup_first_ordered_range()
might return an ordered extent where ordered->file_offset > cur.

If that occurs in a production build where ASSERTs are disabled, 
cur - ordered->file_offset will underflow to a huge unsigned value.
This bypasses the truncation logic because min() will just leave
ordered->truncated_len unmodified instead of shrinking it.

When the extent completes without truncation and without I/O submitted for
the beyond-EOF range, could this insert unwritten disk blocks into the
filesystem tree and expose stale disk data if the file is extended later?
