[Severity: High]
Can calling btrfs_kill_delayed_inode_items() before checking ret corrupt
the on-disk subvolume tree when btrfs_commit_inode_delayed_inode() fails
without aborting the transaction?

In __btrfs_unlink_inode(), unlinking the last link of an inode defers the
nlink = 0 inode update (BTRFS_DELAYED_NODE_INODE_DIRTY) and the
BTRFS_INODE_REF_KEY deletion (BTRFS_DELAYED_NODE_DEL_IREF) in the
inode's delayed_node.  btrfs_commit_inode_delayed_inode() can fail with
-ENOMEM (for example when btrfs_alloc_path() returns NULL) while the
running transaction remains healthy:

fs/btrfs/delayed-inode.c:btrfs_commit_inode_delayed_inode() {
    ...
	trans = btrfs_join_transaction(delayed_node->root);
	if (IS_ERR(trans)) {
		ret = PTR_ERR(trans);
		goto out;
	}

	path = btrfs_alloc_path();
	if (!path) {
		ret = -ENOMEM;
		goto trans_out;
	}
    ...
}

Running btrfs_kill_delayed_inode_items() -> __btrfs_kill_delayed_node()
on that error path discards both the uncommitted nlink = 0 update and the
delayed INODE_REF deletion in memory, and jumping to out then skips
btrfs_truncate_inode_items().  When the transaction commits, the unlinked
inode stays on disk with nlink = 1 and a dangling INODE_REF, so
btrfs_orphan_cleanup() on the next mount sees i_nlink > 0 and only
deletes the orphan item, leaking the inode and its extents.
