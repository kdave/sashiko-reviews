btrfs: tree-checker: validate INODE_REF's namelen

The patch adds an extra namelen verification for INODE_REF items to prevent
an out-of-boundary access. A crafted btrfs image could otherwise provide a
namelen larger than the available memory buffer.

[Severity: Critical]
This is a pre-existing issue, but the patch fixes a stack buffer overflow for
INODE_REF items, while btrfs_get_name() remains vulnerable to the exact same
overflow via BTRFS_ROOT_BACKREF_KEY.

In fs/btrfs/tree-checker.c:check_leaf_item(), BTRFS_ROOT_BACKREF_KEY is
completely missing from the validation switch:

    switch (key->type) {
    case BTRFS_EXTENT_DATA_KEY:
    ...
    // BTRFS_ROOT_BACKREF_KEY is missing here
    }

The complete absence of BTRFS_ROOT_BACKREF_KEY in the metadata validation switch
allows oversized subvolume names to bypass tree-checker.

This then leads to an out-of-bounds stack write in
fs/btrfs/export.c:btrfs_get_name():

    name_len = btrfs_root_ref_name_len(leaf, rref);
    // ...
    read_extent_buffer(leaf, name, name_ptr, name_len);
    name[name_len] = '\0';

Does this mean a maliciously crafted filesystem image with an oversized
name_len inside a BTRFS_ROOT_BACKREF_KEY item could still trigger a stack buffer
overflow when accessed via NFS?

[Severity: Critical]
This is a pre-existing issue, but btrfs_get_name() blindly decrements
path->slots[0] and interprets the resulting item as a BTRFS_ROOT_BACKREF_KEY
without bounds or type checks:

In fs/btrfs/export.c:btrfs_get_name():

    ret = btrfs_search_slot(NULL, root, &key, path, 0, 0);
    if (ret < 0) {
        return ret;
    } else if (ret > 0) {
        if (ino == BTRFS_FIRST_FREE_OBJECTID)
            path->slots[0]--;
        else
            return -ENOENT;

    leaf = path->nodes[0];

    if (ino == BTRFS_FIRST_FREE_OBJECTID) {
        rref = btrfs_item_ptr(leaf, path->slots[0],

not found, and path->slots[0] is 0, doesn't path->slots[0]-- underflow to -1?
