btrfs: remove verity Merkle folio from page cache on error

This commit modifies btrfs_read_merkle_tree_page() to properly clean up
when read_key_bytes() fails. Instead of leaving a locked, not-uptodate folio
in the page cache, it drops the folio from the page cache and unlocks it
before releasing the reference.

[Severity: High]
This is a pre-existing issue, but does this missing mapping re-validation
cause spurious -EIO errors earlier in btrfs_read_merkle_tree_page()?

When a concurrent thread fails to read the data, the new error handling added
by this patch correctly removes the folio from the page cache and unlocks it.
If another thread is waiting on folio_lock() earlier in this function:

		folio_lock(folio);
		/* If it's not uptodate after we have the lock, we got a read error. */
		if (!folio_test_uptodate(folio)) {
			folio_unlock(folio);
			folio_put(folio);
			return ERR_PTR(-EIO);
		}

It wakes up and sees the folio is not uptodate, returning -EIO. Could this be
resolved by checking if folio->mapping == NULL after acquiring the lock, and
jumping back to retry?

[Severity: High]
This isn't a bug introduced by this patch, but does calling folio_address()
here cause silent uninitialized memory exposure on 32-bit systems with HIGHMEM?

For HIGHMEM folios, folio_address() returns NULL. When this NULL is passed
as the dest argument to read_key_bytes(), it treats it as a dry-run size
calculation:

fs/btrfs/verity.c:read_key_bytes() {
    ...
		if (dest) {
			if (dest_folio)
				kaddr = kmap_local_folio(dest_folio, 0);

			data = btrfs_item_ptr(leaf, path->slots[0], void);
			read_extent_buffer(leaf, kaddr + dest_offset,
					   (unsigned long)data + copy_offset,
					   copy_bytes);
    ...
}

Because dest is NULL, the entire data copy block is skipped, returning a
success length and marking the folio as uptodate despite it containing
uninitialized memory.
