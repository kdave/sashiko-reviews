[Severity: High]
This isn't a bug introduced by this patch, but looking at the error path just
below this hunk in btrfs_insert_one_raid_extent(), is there a risk of a
use-after-free and double-free on the transaction handle?

When kzalloc fails to allocate stripe_extent, the code currently calls
btrfs_end_transaction(trans) and returns -ENOMEM:

	stripe_extent = kzalloc(item_size, GFP_NOFS);
	if (unlikely(!stripe_extent)) {
		btrfs_abort_transaction(trans, -ENOMEM);
		btrfs_end_transaction(trans);
		return -ENOMEM;
	}

Since btrfs_insert_one_raid_extent() receives trans as an argument and does
not own it, the caller will handle the error by calling
btrfs_abort_transaction(trans, ret) and then btrfs_end_transaction(trans)
again.

Does this result in a use-after-free when dereferencing trans in the caller's
abort path, followed by a double free when ending it again?
