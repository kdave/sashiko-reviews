[Severity: High]
Could this cause degraded RAID1 or RAID10 mounts to fail with -EIO when a
surviving device has reached max_active_zones?

During mount in open_ctree() -> btrfs_get_dev_zone_info_all_devices() ->
btrfs_get_dev_zone_info(), hardware zones that are already open or closed on
a present device are recorded in zinfo->active_zones and subtracted from
zinfo->active_zones_left.

When btrfs_read_block_groups() -> read_one_block_group() ->
btrfs_load_block_group_zone_info() -> btrfs_load_zone_info() loads a block
group with a missing device (or an offline/readonly zone), that stripe gets
info->alloc_offset = WP_MISSING_DEV and its bit in the active bitmap stays 0,
while the surviving active sequential stripe has its bit set to 1.

Previously, btrfs_load_block_group_raid1() skipped WP_MISSING_DEV stripes
before comparing active bits and also guarded btrfs_zone_activate() with
!btrfs_test_opt(fs_info, DEGRADED):

	for (i = 0; i < map->num_stripes; i++) {
		if (zone_info[i].alloc_offset == WP_MISSING_DEV)
			continue;
		...
		if (test_bit(0, active) != test_bit(i, active)) {
			if (unlikely(!btrfs_test_opt(fs_info, DEGRADED) &&
				     !btrfs_zone_activate(bg))) {
				return -EIO;
			}
		}

With the centralized check in btrfs_load_block_group_by_raid_type(),
!bitmap_empty(active, map->num_stripes) is true and
bitmap_full(active, map->num_stripes) is false whenever a stripe is
WP_MISSING_DEV, so btrfs_zone_activate(bg) is called even on a DEGRADED
mount.

In btrfs_zone_activate(), atomic_read(&zinfo->active_zones_left) <= reserved
is checked before btrfs_dev_set_active_zone() tests whether the zone is
already marked active in zinfo->active_zones:

			ret = false;
			goto out_unlock;
		}

		if (!btrfs_dev_set_active_zone(device, physical, &new)) {

(active_zones_left == 0), btrfs_zone_activate() returns false even though
the surviving stripe's zone is already active and needs no additional active
zone slot. In addition, if WP_MISSING_DEV came from an offline or readonly
zone on a present device (device->bdev != NULL), btrfs_zone_activate() will
call btrfs_dev_set_active_zone() on that broken zone and consume an active

[Severity: High]
Won't btrfs_zone_activate() also activate sequential stripes whose hardware
zones are already in BLK_ZONE_COND_FULL when loading a mixed or striped
block group?

In btrfs_get_dev_zone_info(), zones in BLK_ZONE_COND_FULL are not counted as
active in zinfo->active_zones, and btrfs_load_zone_info() leaves their bit in
the active bitmap as 0 while setting info->alloc_offset = info->capacity.

In a mixed RAID0 or RAID10 block group where a sequential stripe precedes a
conventional stripe, the sequential stripe can already be BLK_ZONE_COND_FULL
while the conventional stripe still has space remaining in the final stripe
row (or after btrfs_zone_finish() / do_zone_finish() finished the sequential
stripe on disk, leaving cache->alloc_offset at
cache->zone_capacity - stripe_len on next mount). Similarly, in a RAID0 or
RAID10 block group in its last stripe row, an earlier sequential stripe can
be BLK_ZONE_COND_FULL (active bit 0) while a later sequential stripe is still
open (active bit 1).

In both cases, 0 < cache->alloc_offset < cache->zone_capacity, so
btrfs_load_block_group_by_raid_type() or btrfs_load_block_group_zone_info()
calls btrfs_zone_activate(). Because btrfs_zone_activate() only checks
btrfs_dev_is_sequential(device, physical) and does not skip full sequential
zones, it calls btrfs_dev_set_active_zone() on the BLK_ZONE_COND_FULL zone,
either failing mount with -EIO if active_zones_left <= reserved or consuming
zinfo->active_zones_left and zinfo->reserved_active_zones for a zone that is
already full on hardware.
