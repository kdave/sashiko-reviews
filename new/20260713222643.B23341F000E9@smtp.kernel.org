btrfs: fix a lockdep caused by path resolution during device scan

This commit avoids a circular locking dependency between device_list_mutex,
tree_log_mutex, and path resolution locks. It replaces the full path lookup
with a dev_t comparison to check if two device paths refer to the same
block device.

[Severity: High]
If a block device is accessed via a different path or symlink but still
has the same underlying devt, does this condition skip updating the device
path?

Since device->devt == path_devt in that scenario, we will bypass this block
and device->name remains unchanged. Could this cause mount failures if the
original path is renamed or deleted?

[Severity: High]
Is the path update logic for already-mounted devices in this block now
unreachable?

For an already-mounted device (device->bdev != NULL), device->name is
guaranteed to be non-NULL. This means we only enter this block if
device->devt != path_devt.

However, looking at the code later in this same block:

		if (device->bdev) {
			if (device->devt != path_devt) {
				mutex_unlock(&fs_devices->device_list_mutex);
				btrfs_warn(NULL, ...);
				return ERR_PTR(-EEXIST);
			}
			btrfs_info(NULL, ...);

Since device->devt != path_devt must be true to reach this code, it will
always take the ERR_PTR(-EEXIST) path. Does this prevent the path from
ever being updated and logged for mounted devices?
