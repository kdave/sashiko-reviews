btrfs: remove the trailing zeros from compressed inline extent

This commit changes the compression input range for inlined extents from
[0, sectorsize) back to [0, i_size) to reduce the extra space usage caused
by a previous refactoring. It relies on a separate fix in the lzo path to
properly handle inlined extents without trailing zeros.

Link: https://lore.kernel.org/linux-btrfs/c97652a5-ac6b-4de6-aa23-3cdebc01d00b@gmail.com/

[Severity: High]
Since i_size is read locklessly earlier in run_delalloc_inline() via
i_size_read(), can it change concurrently before being passed here?

If a concurrent truncate-to-zero sets i_size to 0, it appears this could
pass len = 0 to btrfs_compress_bio(), which then triggers an ASSERT(len)
panic in lzo_compress_bio().

Additionally, if i_size increases concurrently or for holes in sparse files,
could passing an unvalidated i_size cause out-of-bounds page cache accesses
and unbounded CPU waste on uncompressed data?

It looks like btrfs_compress_filemap_get_folio() might attempt to read
non-existent folios beyond the first sector, logging "failed to get page
cache" via btrfs_crit(). Could this be used by local users to trivially spam
the kernel log?
