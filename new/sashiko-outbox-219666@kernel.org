[Severity: Medium]
Can btrfs_reset_unused_block_groups() deduct space reclaimed for a sibling
space_info from the caller's num_bytes target and stop before freeing space
in the requested space_info?

Previously, btrfs_reset_unused_block_groups() updated bytes_zone_unusable
and called btrfs_return_free_space() on the caller-passed space_info, while
zoned_reset_bg_in_place() now uses bg->space_info.  On zoned filesystems,
sub-group space_infos (BTRFS_SUB_GROUP_TREELOG under METADATA and
BTRFS_SUB_GROUP_DATA_RELOC under DATA) share the same space_info->flags as
their parent space_info and place unused block groups on the shared
fs_info->unused_bgs list, where btrfs_reset_unused_block_groups() filters
candidates only by BTRFS_BLOCK_GROUP_TYPE_MASK:

fs/btrfs/zoned.c:btrfs_reset_unused_block_groups() {
	...
		list_for_each_entry(bg, &fs_info->unused_bgs, bg_list) {
			if ((bg->flags & BTRFS_BLOCK_GROUP_TYPE_MASK) != space_info->flags)
				continue;
	...
		ret = zoned_reset_bg_in_place(bg, &reclaimed);
		if (ret || !reclaimed)
			goto requeue;

		btrfs_put_block_group(bg);

		if (num_bytes <= reclaimed)
			break;
		num_bytes -= reclaimed;
}

When flushing a primary or sub-group space_info in the RESET_ZONES state
hits an unused block group belonging to its sibling space_info, the
reclaimed bytes are returned to bg->space_info, but subtracted from the
caller's num_bytes.  The loop then exits early without granting tickets in
the caller's space_info, which can cause premature -ENOSPC failures.

Checking bg->space_info != space_info when scanning fs_info->unused_bgs
would ensure only block groups belonging to the requested space_info are
reset.
