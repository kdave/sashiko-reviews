btrfs: handle ENOMEM from btrfs_insert_dir_item() without aborting

This commit modifies btrfs_add_link and btrfs_create_new_inode to handle
-ENOMEM gracefully instead of aborting the transaction. It clears nlink and
orphans the newly-created inode under memory pressure.

[Severity: High]
Does skipping the on-disk inode update here cause a permanent metadata leak
on system crash?

When clear_nlink(inode) is called, it only updates the in-memory state.
Because the code jumps to discard without calling btrfs_update_inode(), the
on-disk inode still has an nlink count of 1.

If the system crashes after this transaction commits, btrfs_orphan_cleanup()
will run on the next mount. Because it sees nlink > 0, it assumes the file
is valid and only pending a truncate. It will delete the orphan item and
leave the inode intact:

fs/btrfs/inode.c:btrfs_orphan_cleanup() {
        if (!inode || inode->vfs_inode.i_nlink) {
                if (inode) {
                        ...
                }
                trans = btrfs_start_transaction(root, 1);
                ...
                ret = btrfs_del_orphan_item(trans, root, found_key.objectid);
                btrfs_end_transaction(trans);
                continue;
        }
}

Should btrfs_update_inode() be called before jumping to discard so the
on-disk nlink matches the in-memory state?
