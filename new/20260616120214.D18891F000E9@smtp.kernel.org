the target device during a btrfs_dev_replace_start() failure. It adds calls

[Severity: Critical]
This is a pre-existing issue, but does this completely prevent the
use-after-free?

Looking at fs/btrfs/bio.c:orig_write_end_io_work(), the bio_counter is
decremented before the device is accessed:

fs/btrfs/bio.c:orig_write_end_io_work() {
    ...
	btrfs_bio_counter_dec(bioc->fs_info);

	if (bio->bi_status) {
		atomic_inc(&bioc->error);
		btrfs_log_dev_io_error(bio, stripe->dev);
	}
    ...
}

If bio_counter drops to zero here, btrfs_rm_dev_replace_blocked() will unblock
and btrfs_destroy_dev_replace_tgtdev() can free the target device while the
workqueue thread is still inside orig_write_end_io_work() and about to call
btrfs_log_dev_io_error(bio, stripe->dev).

Since orig_write_end_io_work() runs in a workqueue, the synchronize_rcu() inside
btrfs_destroy_dev_replace_tgtdev() wouldn't wait for it to finish, leaving a
window where stripe->dev is accessed after being freed.

Can the decrement of bio_counter in orig_write_end_io_work() be moved after
the device access, or is there another way to safely synchronize this drain?
