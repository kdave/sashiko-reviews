btrfs: fix deadlocks with transaction commit when cloning inline extents

This commit addresses deadlock windows between reflink operations and
transaction commits by starting transactions earlier and updating destination
i_size while the folio is still locked. It also completely removes the
BTRFS_INODE_NO_DELALLOC_FLUSH runtime flag.

[Severity: High]
Could the removal of this exclusion logic lead to a self-deadlock when
space reclaim is triggered during a clone operation?

Since BTRFS_INODE_NO_DELALLOC_FLUSH is completely removed here and in
btrfs_clone(), if a reflink operation clones an inline extent and proceeds
to punch a trailing hole via btrfs_replace_file_extents(), calling
btrfs_start_transaction() can trigger shrink_delalloc().

This would queue writeback for the destination inode's dirty folio, and
extent_writepage() would attempt to acquire the exact same extent lock
that is already held by the clone ioctl, resulting in an AB-BA inversion
and hanging the task.

[Severity: Critical]
Will this new goto out_unlock trigger a NULL pointer dereference if
btrfs_start_transaction() fails?

At this point in copy_inline_to_page(), the folio variable is still
initialized to NULL. If the transaction start fails, such as from ENOSPC,
we jump to the out_unlock label where the cleanup code checks
if (!IS_ERR(folio)).

Because IS_ERR(NULL) evaluates to false, !IS_ERR(NULL) is true. The
cleanup path will then unconditionally call folio_unlock(NULL) and
folio_put(NULL), crashing the kernel.

Since unprivileged users can trigger ENOSPC conditions via the FICLONE
ioctl, can this be exploited to cause a local DoS?
