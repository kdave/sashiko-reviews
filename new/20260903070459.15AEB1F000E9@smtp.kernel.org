btrfs: split sectorsize into datasize and sectorsize

This commit separates the minimal data IO size (datasize) from the sector
size to prepare for incoming features. While all data IO will use datasize,
data checksum calculations will continue to respect sectorsize.

[Severity: Critical]
Does unconditionally stepping and reading by datasize cause the read
loop to ignore the actual physical extent length (em->len)?

If a file has physical extents or holes smaller than datasize (e.g., from
legacy filesystems or unaligned clones), it seems this loop will unconditionally
submit a bio for datasize bytes. This could read past the physical extent
boundary, mapping unrelated disk data into the page cache, and completely
skipping subsequent file extents. Can this cause data corruption or an
information leak?

[Severity: High]
Does clearing the EXTENT_NODATASUM flag for the entire block upon the
completion of a single sector introduce a race condition with other in-flight
bios for the same block?

When relocating a data block where datasize is greater than sectorsize, the
read operation might be split across multiple bios. If the bio containing the
final sector completes first, it will clear the flag for the entire datasize
block. Subsequent bio completions for earlier sectors in the same block would
then evaluate btrfs_test_range_bit() to false, attempting checksum verification
on an inode that lacks checksums. Could this lead to spurious data relocation
failures?

[Severity: High]
Does padding the disk I/O size to datasize for uncompressed reads force
out-of-bounds disk reads?

If an unprivileged user issues a BTRFS_IOC_ENCODED_READ ioctl for an
uncompressed extent whose length is not aligned to datasize (like legacy
extents), it appears this will arbitrarily pad the physical read size. The
block layer might then read past the actual physical extent and fetch unrelated
disk data, which could be returned to userspace.
