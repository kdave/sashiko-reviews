[Severity: Medium]
Does btrfs_zoned_dev_avail_bytes() also need to exclude the zones containing
the regular superblock offsets at btrfs_sb_offset(i)?

In btrfs_find_allocatable_zones(), the zoned allocator skips both the
log-structured superblock zones at sb_zone_number() and any zone covering
btrfs_sb_offset(i):

fs/btrfs/zoned.c:btrfs_find_allocatable_zones() {
	...
			/* We also need to exclude regular superblock positions */
			sb_pos = btrfs_sb_offset(i);
			if (!(pos + num_bytes <= sb_pos ||
			      sb_pos + BTRFS_SUPER_INFO_SIZE <= pos)) {
				have_sb = true;
				pos = ALIGN(sb_pos + BTRFS_SUPER_INFO_SIZE,
					    zinfo->zone_size);
				break;
			}
	...

Because btrfs_sb_offset(2) (256 GiB) never overlaps with the log-structured
superblock zone pairs (at 0 B, 512 GiB, and 4 TiB), and btrfs_sb_offset(1)
(64 MiB) falls outside the primary log zones when zone_size < 64 MiB,
btrfs_calc_avail_data_space() will over-report available data space by one
or two zones per device.

[Severity: Medium]
Can a trailing partial zone that overlaps a superblock log zone cause
btrfs_zoned_dev_avail_bytes() to under-count available space by a full zone?

device->total_bytes is only guaranteed to be sector-aligned (for example via
btrfs_grow_device() or btrfs_shrink_device()), whereas device->bytes_used is
a multiple of zinfo->zone_size.  If total ends part-way through a superblock
log zone, zone_start_physical(sb_zone + j, zinfo) < total is true and adds a
full zinfo->zone_size to sb_bytes even though avail only includes the
partial tail from that zone.  Subtracting sb_bytes from avail before
round_down(avail, zinfo->zone_size) then borrows from the preceding full
zone and rounds the remainder down, losing one allocatable zone.
