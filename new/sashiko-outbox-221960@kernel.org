[Severity: Medium]
Can calling cancel_work_sync(&fs_info->reclaim_bgs_work) here under
sb->s_umount trigger a lockdep circular dependency splat?

btrfs_reclaim_bgs_work() calls btrfs_reclaim_block_groups(), which takes
sb_start_write(fs_info->sb) (sb_writers[SB_FREEZE_WRITE - 1]) while
reclaim_bgs_work is running.  freeze_super() orders
sb_writers[SB_FREEZE_WRITE - 1] before sb->s_umount, and flushing a
running reclaim_bgs_work from reconfigure_super() -> btrfs_remount_ro()
acquires reclaim_bgs_work.lockdep_map under sb->s_umount:

CPU0                         CPU1                         CPU2
----                         ----                         ----
process_one_work()
  lock(reclaim_bgs_work)
                             freeze_super()
                               sb_wait_write(...,
                                 SB_FREEZE_WRITE)
                                                          reconfigure_super()
                                                            lock(&sb->s_umount)
                                                            btrfs_remount_ro()
                                                              cancel_work_sync(
                                                                &reclaim_bgs_work)
                               __super_lock_excl(sb)
  btrfs_reclaim_block_groups()
    sb_start_write(sb)

 *** DEADLOCK ***

reconfigure_super() and freeze_super() cannot actually deadlock at
runtime because reconfigure_super() rejects frozen filesystems under
sb->s_umount, so this only trips lockdep when cancel_work_sync() catches
reclaim_bgs_work executing (for example while iterating remaining block
groups or running btrfs_delete_unused_bgs() after dropping
reclaim_bgs_lock) on a kernel that has also run freeze_super().
