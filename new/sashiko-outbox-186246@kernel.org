btrfs: zoned: prepare reserving the data relocation block group at runtime

This commit updates btrfs_zoned_reserve_data_reloc_bg() to walk the block
group list under groups_sem and factors out btrfs_set_data_reloc_bg() and
zoned_move_bg_to_space_info() so the data relocation block group can be
reserved at runtime concurrently with extent allocations.

[Severity: Medium]
If fs_info->data_reloc_bg = bg->start is published before
zoned_move_bg_to_space_info() moves bg into data_sinfo->sub_group[0], can a
concurrent relocation allocation miss the relocation block group?

In the original code in btrfs_zoned_reserve_data_reloc_bg(),
fs_info->data_reloc_bg = bg->start was set after bg->space_info = reloc_sinfo
and btrfs_add_bg_to_space_info(bg). With fs_info->data_reloc_bg published
before zoned_move_bg_to_space_info(), a concurrent relocation extent
allocation (find_free_extent() with ffe_ctl->for_data_reloc == true) will:

1. Read fs_info->data_reloc_bg == bg->start in prepare_allocation_zoned()
   and set ffe_ctl->hint_byte = bg->start.
2. Reject the hinted bg in find_free_extent() because bg->space_info is
   still data_sinfo (or list_empty(&bg->list) is true).
3. Walk data_sinfo->sub_group[0]->block_groups[index], where bg has not been
   added yet, while do_allocation_zoned() skips every other block group
   because bytenr != fs_info->data_reloc_bg.
4. Fall through to allocate an unnecessary chunk in sub_group[0] or fail
   with -ENOSPC if no free device zones remain.

Should zoned_move_bg_to_space_info() complete before publishing
fs_info->data_reloc_bg = bg->start?
