[Severity: High]
Does this unintentionally override the filesystem-wide compression mount
options when a user sets a compression property without a level?

If a user specifies a property without a level, the parsing in
btrfs_compress_str2level() will return the algorithm's default level
(for example, 3 for zstd) rather than 0.

This means prop_compress_level becomes 3 instead of 0, which triggers this
branch and overwrites the fs_info->compress_level, breaking the fallback
behavior described in the comment.

[Severity: Critical]
Can this allocation cause a kernel panic or a filesystem reclaim deadlock?

The btrfs property system guarantees that the apply callback will not fail
if validation succeeds. This is enforced by an assertion in btrfs_set_prop()
when applying the property:

btrfs_set_prop() {
        ...
        ret = handler->apply(inode, value, value_len);
        /* We validated before, so it should not fail here. */
        ASSERT(ret == 0);
}

If this GFP_KERNEL allocation fails under memory pressure, apply() will
return -ENOMEM and immediately trigger the assertion, crashing the system.

Additionally, since this runs while holding a transaction handle or b-tree
lock, a GFP_KERNEL allocation could recurse into the filesystem memory
reclaim path and deadlock.

[Severity: High]
Are the explicitly configured compression levels lost during property
inheritance for new files and directories?

When new files inherit properties, btrfs_inode_inherit_props() extracts
the parent's properties using the extract() callback. Since this patch does
not update prop_compression_extract() to include the new level, it continues
to only return the base algorithm string via btrfs_compress_type2str().

As a result, it seems that newly created children will only inherit the
algorithm type and silently lose the specific level configuration.
