btrfs: fix delayed_refs_rsv leak when realloc shrinks an extent

This commit adjusts pending_csums and delayed_refs_rsv csum leaf
reservations in update_existing_head_ref() when a freed data extent is
reallocated with a different size before its delayed refs are processed.

Link: https://lore.kernel.org/linux-btrfs/6ae88b9e.64e51036.15cf6a.0027.GAE@google.com/

[Severity: High]
Can this underflow fs_info->delayed_refs_rsv.size and leak
delayed_refs_rsv.reserved when a freed data extent is reallocated at the
same bytenr with a larger size spanning more csum leaves (new_leaves >
old_leaves)?

When btrfs_alloc_reserved_file_extent() reallocates a freed extent where
existing->total_ref_mod == -1, init_delayed_ref_head() sets
update->must_insert_reserved = true and update->ref_mod = 1.

In update_existing_head_ref(), the new check runs before
existing->total_ref_mod is updated:

  existing->total_ref_mod == -1 (< 0)
  new_leaves > old_leaves
  trans->delayed_ref_csum_deletions += new_leaves - old_leaves;
  existing->num_bytes = update->num_bytes;

However, trans->delayed_ref_csum_deletions is not added to
fs_info->delayed_refs_rsv.size until btrfs_update_delayed_refs_rsv() runs at
the end of add_delayed_ref() after dropping delayed_refs->lock.

Before update_existing_head_ref() returns, existing->total_ref_mod is
updated from -1 to 0, which immediately triggers the release path using the
newly updated existing->num_bytes:

fs/btrfs/delayed-ref.c:update_existing_head_ref() {
	...
	old_ref_mod = existing->total_ref_mod;
	existing->ref_mod += update->ref_mod;
	existing->total_ref_mod += update->ref_mod;
	...
	if (existing->is_data) {
		u64 csum_leaves =
			btrfs_csum_bytes_to_leaves(fs_info,
						   existing->num_bytes);

		if (existing->total_ref_mod >= 0 && old_ref_mod < 0) {
			delayed_refs->pending_csums -= existing->num_bytes;
			btrfs_delayed_refs_rsv_release(fs_info, 0, csum_leaves);
		}
}

Because only old_leaves was added to delayed_refs_rsv.size for this head
ref, calling btrfs_delayed_refs_rsv_release() with new_leaves subtracts more
bytes than were added. In block_rsv_release_bytes():

fs/btrfs/block-rsv.c:block_rsv_release_bytes() {
	...
	block_rsv->size -= num_bytes;
	if (block_rsv->reserved >= block_rsv->size) {
		num_bytes = block_rsv->reserved - block_rsv->size;
		block_rsv->reserved = block_rsv->size;
		block_rsv->full = true;
	} else {
		num_bytes = 0;
	}
}

If delayed_refs_rsv.size is smaller than the byte size of new_leaves,
block_rsv->size wraps around as an unsigned u64, causing
(block_rsv->reserved >= block_rsv->size) to evaluate to false and releasing
0 bytes from delayed_refs_rsv.reserved. When btrfs_update_delayed_refs_rsv()
then runs at the end of add_delayed_ref(), it wraps delayed_refs_rsv.size
back around and migrates additional reserved bytes from trans->delayed_rsv
into delayed_refs_rsv.reserved without releasing them, leaving
delayed_refs_rsv.reserved leaked (or if other pending delayed refs prevent
the u64 wrap-around, prematurely releasing reservations belonging to other
delayed refs).
