btrfs: load raid56 block-groups

This commit adds support for loading RAID5/6 block-groups on mount for zoned

[Severity: Critical]
Does skipping WP_MISSING_DEV here artificially shrink wp_sum by the missing
device's contribution?

Because row_bytes later correctly accounts for all num_stripes devices,
dividing a deficient wp_sum by row_bytes and subtracting the parity size can
compute a dangerously low logical allocation offset.

Will the allocator start at this rewound offset on subsequent zone append
operations and overwrite previously committed data and parity stripes?

> +
> +	if (has_conventional) {
> +		bg->alloc_offset = last_alloc;
> +	} else {
> +		u64 row_bytes = (u64)map->num_stripes << BTRFS_STRIPE_LEN_SHIFT;
> +		u64 nr_rows = div64_u64(wp_sum + row_bytes - 1, row_bytes);
> +
> +		bg->alloc_offset = wp_sum -
> +			(((u64)nr_rows * nr_parity) << BTRFS_STRIPE_LEN_SHIFT);
> +	}

[Severity: Critical]
Can this subtraction underflow for partially written rows?

Since nr_rows rounds up, a partially written row will subtract a full row's
worth of parity bytes from a wp_sum that only includes the partial bytes.

Could this cause an unsigned integer underflow that rewinds the allocation
pointer to near U64_MAX?

> +
> +	for (int i = 0; i < nr_data; i++) {
> +		if (zone_info[i].alloc_offset == WP_MISSING_DEV)
> +			continue;
> +		bg->zone_capacity += zone_info[i].capacity;
> +	}

[Severity: High]
Is this loop inconsistently reducing bg->zone_capacity on degraded mounts
depending on the missing device's array index?

Since the loop rigidly bounds to nr_data, a missing device within the data
index range shrinks the block group's usable logical capacity. However, if a
parity device is missing, it is completely ignored and capacity is unaffected.

Because RAID5/6 rotates data and parity physically across all devices,
shouldn't the block group's total logical capacity remain constant regardless
of which physical device is missing?

> +	for (int i = 0; i < map->num_stripes; i++) {

[Severity: High]
Could requiring alloc_offset != 0 cause us to skip explicitly opened zones
where no data has been written yet?

On a zoned block device, a zone can be explicitly opened (consuming an active
zone resource) while its alloc_offset is still 0.

By rejecting these zones, is it possible the block group avoids being added
to fs_info->zone_active_bgs, preventing Btrfs from finishing it to reclaim
the device's active zone limit?
