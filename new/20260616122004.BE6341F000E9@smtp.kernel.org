btrfs: deny freezing devices undergoing a replace

This commit adds logic to deny freezing of devices during a device replace 
operation. It makes both the source and target devices unfreezable for the 
whole replace process by holding a deny on each device while in the STARTED 
state.

[Severity: High]
Does this early return bypass the cleanup logic? 

The comment mentions that every leave unwind sees both denied, but if
mark_block_group_to_copy() fails, the code returns directly instead of
using the goto leave path.

It seems this could leak the target device structure and leave the
freeze deny counts elevated on both block devices, which would render
them unfreezable until reboot. Should this be updated to jump to the
leave label?

[Severity: High]
This isn't a bug introduced by this patch, but if btrfs_start_transaction()
fails synchronously, it leaves the replace state as STARTED while the
kthread exits.

Since btrfs_dev_replace_cancel() requires an active scrub to cancel, does
this leave the replace permanently stuck in the STARTED state?

The dev_replace->replace_task pointer isn't cleared, which might leave a
dangling pointer to the freed task_struct.

Additionally, with this patch, this error path now permanently leaks the
freeze denies on both block devices, as they are intentionally kept denied
here but cannot be cleaned up if the state is stuck.

[Severity: Critical]
Could this introduce a race condition with concurrent unmount? 

The bdev_allow_freeze() call is placed outside the
lock_finishing_cancel_unmount mutex. 

If the filesystem is concurrently unmounted,
btrfs_dev_replace_suspend_for_unmount() might acquire the lock, see the
state as FINISHED, and return without waiting.

The unmount process would then call btrfs_close_devices() and
btrfs_close_one_device(tgt_device), which closes the file and sets
tgt_device->bdev to NULL.

When the preempted kthread resumes and calls
bdev_allow_freeze(tgt_device->bdev), could it dereference NULL or access
a freed bdev?
