fs: add a global device to super block hash table

This commit introduces a global dev_t-keyed rhltable mapping each block
device to the superblock(s) using it. This allows multiple superblocks to
share a single block device by using the block layer's exclusivity token
rather than tying it to a single superblock.

[Severity: High]
Do block device walkers need to verify that fs_bdev_active > 0 before
applying events to the superblock?

When a filesystem releases a device, fs_bdev_active drops to 0, logically
deleting the claim. However, the entry remains in the hash table as long as
any walker holds a passive pin. If a device is removed from a filesystem,
but the filesystem itself remains mounted, could a racing walker find this
passively pinned dead entry and freeze the filesystem?

If the dead entry is subsequently freed, a later fs_bdev_thaw() might fail
to find it, potentially leaving the filesystem permanently frozen.

[Severity: Critical]
Are we missing checks for SB_ACTIVE and s_root here that were present in the
original get_bdev_super() implementation?

The previous code explicitly verified that sb->s_root and sb->s_flags &
SB_ACTIVE were set. If a freeze races with a filesystem mount, s_active is
incremented. If the mount then fails, deactivate_locked_super() sees the
elevated s_active and skips calling kill_sb(), permanently leaking the
superblock.

Could this also result in fs_super_freeze() attempting to freeze and
sync a failed, partially initialized superblock, resulting in a kernel crash?

Is there a Time-of-Check to Time-of-Use (TOCTOU) race here since the lookup
happens without mutual exclusion?

Because the RCU read lock is dropped before memory allocation and insertion,
could two threads concurrently opening a block device for the same superblock
both fail the lookup and insert a new entry into the hash table?

This might result in duplicate rhltable nodes for the same device and
superblock, which could cause iterators to execute multiple times on the
same superblock.
