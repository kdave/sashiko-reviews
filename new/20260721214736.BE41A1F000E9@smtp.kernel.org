[Severity: High]
Does xfs_read_ioend_compare() fail to correctly identify metadata ioends when their
offset exactly equals i_size?

If an unprivileged user creates an fsverity file with an i_size exactly a multiple
of 65536 (XFS_FSVERITY_START_ALIGN), xfs_fsverity_metadata_offset() returns an offset
equal to i_size. When comparing the metadata ioend (io_offset == i_size) and data
ioend (io_offset < i_size), both greater-than and less-than checks fail, returning 0.

Could this leave the data ioend ahead of the metadata ioend in the completion list,
causing the worker thread to self-deadlock while waiting for metadata folio locks?

[Severity: Critical]
Is it possible for xfs_fsverity_get_descriptor() to leak uninitialized kernel memory
to userspace?

If a maliciously crafted XFS image has an unallocated hole for the fsverity
descriptor block, this triggers an iomap read with IOMAP_F_FSVERITY set. Because
ctx->vi is NULL during initialization, iomap_read_folio_iter() skips 
fsverity_fill_zerohash() and bypasses the hole-zeroing logic:
