btrfs: add LOGICAL_INO_V2 flag for avoiding the tree modification log

This commit adds the BTRFS_LOGICAL_INO_ARGS_COMMIT_ROOT flag to the
LOGICAL_INO_V2 ioctl, allowing userspace to resolve backrefs against the
commit roots instead of the current trees. This avoids enabling the tree
modification log, reducing filesystem-wide lock contention and overhead.

[Severity: Medium]
Will this lead to a state inconsistency when the target extent is modified
in the current transaction?

The path is zero-initialized via btrfs_alloc_path(), which means
path->search_commit_root is false. Consequently, extent_from_logical() will
query the active tree for the extent boundaries, even when userspace requests
the commit root view via the BTRFS_LOGICAL_INO_ARGS_COMMIT_ROOT flag.

[Severity: Medium]
Does this create a structural mismatch between the initial extent lookup
and the subsequent backref walk?

The backref walk is instructed to use the commit root via the passed
search_commit_root flag. Because the prior extent_from_logical() call
retrieved its coordinates from the active tree, if the extent boundaries
have changed or been relocated during the active transaction, the backref
walk could silently fail or return incorrect results (such as missing inodes
or spurious ENOENT) due to the coordinate mismatch.

Would it be better to conditionally set path->search_commit_root =
search_commit_root before calling extent_from_logical() to ensure both lookups
query the same view of the filesystem?
