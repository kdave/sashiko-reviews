[Severity: Medium]
The commit message mentions loosening size and version checks to allow
older kernels to mount future newer qgroup expansions. Does this strict flag
mask check contradict that intent?

If a future kernel introduces a new persistent flag, this check will reject
the qgroup tree with -EUCLEAN, breaking forward compatibility and causing a
hard mount failure when reading valid future metadata.

[Severity: High]
This is a pre-existing issue, but this newly added check_qgroup_status_item()
misses an opportunity to validate the SIMPLE_QUOTA incompat feature.

If a crafted filesystem image has the BTRFS_QGROUP_STATUS_FLAG_SIMPLE_MODE
flag set but lacks the SIMPLE_QUOTA incompat feature flag in the superblock,
can it trigger a kernel panic on systems compiled with CONFIG_BTRFS_ASSERT?

Later in the mount process, btrfs_read_qgroup_config() will process this
item and call qgroup_read_enable_gen(), which hits:
ASSERT(btrfs_fs_incompat(fs_info, SIMPLE_QUOTA))

Should this tree-checker cross-check the incompat feature to prevent a
potential DoS from untrusted input?
