[Severity: Medium]
Does bounding ram_bytes alone suffice for compressed extents without also
checking that offset + num_bytes <= ram_bytes?

btrfs_extent_item_to_extent_map() populates em->offset and em->len from the
on-disk offset and num_bytes fields, and btrfs_submit_compressed_read()
derives cb->start = em->start - em->offset from them rather than
em->ram_bytes.  If offset + num_bytes exceeds ram_bytes,
validate_extent_map() hits ASSERT(0) on CONFIG_BTRFS_DEBUG=y builds, and on
non-debug builds u32 bvec_offset in zstd_map_dest() can still wrap 32 bits
and trigger ASSERT(off < bvec.bv_len) or an out-of-bounds kmap write.

[Severity: Medium]
Can a non-hole file extent with disk_bytenr != 0 and disk_num_bytes == 0
still pass check_extent_data_item()?

IS_ALIGNED(0, sectorsize) is true and this check only enforces an upper
bound.  Because btrfs_extent_item_to_extent_map() only treats disk_bytenr ==
0 as EXTENT_MAP_HOLE, a compressed extent with disk_bytenr != 0 and
disk_num_bytes == 0 creates a non-hole extent_map with em->disk_num_bytes ==
0, which causes btrfs_submit_compressed_read() to submit an empty bio and
hit the same length != 0 assertion in assert_bbio_alignment(), or causes
btrfs_encoded_read_regular() to allocate ZERO_SIZE_PTR for pages and
dereference pages[0].
