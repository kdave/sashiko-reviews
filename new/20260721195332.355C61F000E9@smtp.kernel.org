xfs: introduce fsverity on-disk changes

Introduce XFS_DIFLAG2_VERITY for inodes with fsverity. This flag indicates
that the inode has fs-verity enabled. The patch also introduces
XFS_SB_FEAT_RO_COMPAT_VERITY for filesystems having fsverity inodes.

This is a pre-existing issue, but does the online scrub repair logic in
fs/xfs/scrub/inode_repair.c:xrep_inode_flags() correctly handle corrupted
flags?

When an inode's flags are corrupted with unknown bits, the scrub repair
logic attempts to clear them like this:

fs/xfs/scrub/inode_repair.c:xrep_inode_flags() {
    if (sc->ip->i_diflags & ~XFS_DIFLAG_ANY)
        sc->ip->i_diflags &= ~XFS_DIFLAG_ANY;
        
    if (sc->ip->i_diflags2 & ~XFS_DIFLAG2_ANY)
        sc->ip->i_diflags2 &= ~XFS_DIFLAG2_ANY;
}

Does this bitwise AND with the inverted mask destroy all valid flags
while leaving the corruption intact?

[Severity: Critical]
Does setting S_VERITY here safely handle read operations?

XFS does not yet initialize the fsverity_info structure via
fsverity_file_open() or similar. The iomap buffered read path skips
fsverity_verify_blocks() when this structure is missing, returning
completely unverified data from the disk.

Could an attacker who modifies the underlying block device have their
tampered data served to userspace without detection, bypassing the
integrity protection of fs-verity?
