[Severity: Medium]
Does this loop leave the secondary superblock unblocked, allowing it to be
written with the new generation?

Because only the 64 KiB primary superblock range is blocked by dm-dust,
btrfs_commit_super() can successfully write the new generation to dev1's 64 MiB
superblock. User-space tools scanning the device will then see the newer
generation at 64 MiB, leaving the device in a state with mismatched
superblocks. Should all superblock copies be blocked here?

> +echo "Step 4: simulate recovery"
> +_scratch_mount -o notreelog

> +_btrfs_buffered_read_on_mirror 0 2 "$testfile" 0 2K

[Severity: High]
Can this mount and read sequence cause the test to become flaky based on the
PID of the mount command?

When _scratch_mount is executed, Btrfs reads and caches the root tree block
using the default RAID1 metadata read policy (current->pid % num_stripes). If
the mount command has an even PID, it caches dev1's root block (expecting the
0xaa child leaf checksum). If it has an odd PID, it caches dev2's root block
(expecting the 0xbb child leaf checksum).

Later, _btrfs_buffered_read_on_mirror forces the child leaf to be read from
dev2. If dev1's root block was cached during mount, the 0xbb leaf will fail
the parent's expected checksum check, triggering a read-repair that returns
0xaa and causes the test to fail.
