btrfs: zoned: promote reset data block groups to the relocation target

This commit updates zoned_reset_bg_in_place() and
btrfs_reset_unused_block_groups() to promote a reset data block group
directly to the data relocation block group when none is currently set,
deferring btrfs_return_free_space() unless promotion is skipped or fails.

[Severity: High]
What happens to waiting tickets on reloc_sinfo when an unused block group that
already belongs to the data relocation sub space_info is reset and promoted
here?

On a zoned filesystem, both fs_info->data_sinfo and
reloc_sinfo (fs_info->data_sinfo->sub_group[0]) have
BTRFS_BLOCK_GROUP_DATA set in space_info->flags. When a former relocation
block group in reloc_sinfo has all of its extents freed and becomes fully
zone_unusable, btrfs_mark_bg_unused() places it on fs_info->unused_bgs while
bg->space_info remains reloc_sinfo.

When btrfs_reset_unused_block_groups() resets that block group while
fs_info->data_reloc_bg is 0, zoned_reset_bg_in_place() sees
(space_info->flags & BTRFS_BLOCK_GROUP_DATA) != 0, sets promote to true, and
skips btrfs_return_free_space(space_info, *reclaimed).

It then calls btrfs_set_data_reloc_bg(fs_info, bg):

fs/btrfs/zoned.c:btrfs_set_data_reloc_bg() {
	struct btrfs_space_info *data_sinfo = fs_info->data_sinfo;
	struct btrfs_space_info *reloc_sinfo = data_sinfo->sub_group[0];
	const bool migrate = (bg->space_info == data_sinfo);
	...
	fs_info->data_reloc_bg = bg->start;
	spin_unlock(&fs_info->relocation_bg_lock);
	set_bit(BLOCK_GROUP_FLAG_ZONED_DATA_RELOC, &bg->runtime_flags);

	if (migrate)
		zoned_dec_bg_ro(bg);

	btrfs_zone_activate(bg);

	return true;
}

Because bg->space_info is already reloc_sinfo, migrate is false, so
btrfs_set_data_reloc_bg() skips zoned_dec_bg_ro(bg) (which would otherwise
call btrfs_try_granting_tickets(reloc_sinfo)) and returns true. Since
btrfs_set_data_reloc_bg() succeeded, zoned_reset_bg_in_place() also skips the
fallback btrfs_return_free_space() block.

As a result, neither btrfs_return_free_space() nor
btrfs_try_granting_tickets() is called for reloc_sinfo, leaving
reloc_sinfo->tickets_id unchanged during the RESET_ZONES flush state in
do_async_reclaim_data_space() and causing waiting relocation tickets to fail
with -ENOSPC in maybe_fail_all_tickets().

Should promote check (space_info == fs_info->data_sinfo), or should
btrfs_return_free_space(reloc_sinfo, *reclaimed) still be called when
bg->space_info is already reloc_sinfo?
