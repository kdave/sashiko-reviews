btrfs: fix use-after-free after relocation failure with concurrent COW

This commit addresses a use-after-free on the reloc control structure during
a relocation failure when a concurrent task is COWing a subvolume leaf. It
implements a refcount for the reloc control structure to ensure it remains
alive while concurrent tasks hold a reference.

[Severity: Critical]
Does this global fetch of fs_info->reloc_ctl lead to cross-relocation state
corruption?

Because put_reloc_control() lazily frees the structure when rc->refs drops to
zero, it calls free_reloc_roots() which in turn calls __del_reloc_root(). If
the last reference is dropped asynchronously after the original relocation has
ended, fs_info->reloc_ctl might point to a newly started relocation control
structure.

Could this incorrectly lock and erase nodes from the new, active relocation's
RB-tree using the old root's metadata, causing unrecoverable state corruption?

[Severity: High]
Can this ASSERT trigger a NULL pointer dereference if the control structure
is freed early?

Looking at btrfs_relocate_block_group(), rc is allocated and then
reloc_chunk_start() is called before rc->extent_root is initialized. If
reloc_chunk_start() fails (for example, due to cancellation), it jumps to the
error path and calls put_reloc_control(rc) while rc->extent_root is still
NULL. Evaluating this ASSERT would crash the kernel.

[Severity: High]
Does this shallow refcounting leave the block_group and data_inode vulnerable
to a use-after-free?

When the structure is made refcounted, a concurrent COW task can safely retain
a reference to rc. However, in btrfs_relocate_block_group(), the references to
rc->block_group (via btrfs_put_block_group()) and rc->data_inode (via iput()
earlier in the exit path) are unconditionally dropped right before exiting.

If a COW task executing replace_file_extents() continues after this, will it
dereference the freed rc->block_group and pass the freed rc->data_inode to
get_new_location(), resulting in a use-after-free for both objects?
