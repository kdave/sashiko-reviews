Subject: btrfs: compute RAID stripe-tree RAID5 parity for sub-stripe writes

The RAID5 write path accumulates a full stripe's parity and submits it once
all of its data columns have been folded. A sub-stripe tail - a file tail
shorter than a full stripe - never fills its stripe, so its parity would
never be submitted and the tail would be left unprotected.

[Severity: Critical]
Can this premature finalization destroy parity for earlier writes in the same
logical stripe? The stripe_set is globally shared by full_stripe_logical.
If File A writes 4KB and finishes, the extent reaches its i_size and
finalizes the set. If File B later writes to the adjacent space in the same
stripe, btrfs_rst_raid56_write() will allocate a new, zero-initialized set
because the first was finalized. File B's parity overwrite would then destroy
the parity protection for File A's data without a read-modify-write.

[Severity: Critical]
Will this also cause interior partial writes to bypass parity finalization
entirely? If an interior partial overwrite occurs, the condition evaluates
to true and the parity bio is never submitted. If the user then calls fsync(),
this would leave the data on disk without its parity protection, breaking
durability guarantees.
