btrfs: fix dangling nodes in tree-mod-log after error in btrfs_tree_mod_log_insert_root()

If in btrfs_tree_mod_log_insert_root() there is an error in the call to
tree_mod_log_insert() we free all the nodes in the 'tm_list' array but we
don't remove them from the tree-mod-log rbtree. So make sure we remove the
nodes from the rbtree before freeing them after an error.

[Severity: High]
Does this perform an unlocked rbtree modification?

If tree_mod_log_insert() fails, the error path jumps to out_unlock:

fs/btrfs/tree-mod-log.c:btrfs_tree_mod_log_insert_root() {
    ...
out_unlock:
	write_unlock(&fs_info->tree_mod_log_lock);
	if (ret)
		goto free_tms;
    ...
}

This means we drop tree_mod_log_lock before jumping to free_tms, making this
rb_erase() call on the shared fs_info->tree_mod_log completely unlocked, which
could lead to data races and memory corruption.

[Severity: High]
Can this logic also result in a double-erase of rbtree nodes?

If tree_mod_log_insert() fails inside the helper tree_mod_log_free_eb(), the
helper proactively erases previously inserted nodes without calling
RB_CLEAR_NODE():

fs/btrfs/tree-mod-log.c:tree_mod_log_free_eb() {
    ...
			for (j = nritems - 1; j > i; j--)
				rb_erase(&tm_list[j]->node,
					 &fs_info->tree_mod_log);
			return ret;
}

Because RB_CLEAR_NODE() is not called on the erased nodes, RB_EMPTY_NODE()
evaluates to false when we reach free_tms. This causes the code to
unconditionally call rb_erase() on them again, resulting in a double-erase.
