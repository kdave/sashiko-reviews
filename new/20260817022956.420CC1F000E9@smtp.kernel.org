btrfs: handle highmem folios in read_key_bytes

This patch fixes an issue on 32-bit systems with highmem where folio_address()
can return NULL for unmapped folios. By updating the conditions in
read_key_bytes(), it ensures the data is correctly mapped and copied when
dest_folio is provided.

[Severity: High]
This isn't a bug introduced by this patch, but looking at how read_key_bytes()
is used in btrfs_read_merkle_tree_page() in fs/btrfs/verity.c, the error
handling appears to miss an unlock:

btrfs_read_merkle_tree_page() {
    ...
	ret = read_key_bytes(BTRFS_I(inode), BTRFS_VERITY_MERKLE_ITEM_KEY, off,
			     folio_address(folio), PAGE_SIZE, folio);
	if (ret < 0) {
		folio_put(folio);
		return ERR_PTR(ret);
	}
    ...
}

Does this error path leave the folio permanently locked in the page cache?

Since filemap_add_folio() adds the folio to the page cache and leaves it
locked, dropping the reference with folio_put() without first calling
folio_unlock() would cause subsequent attempts to lock this folio to hang.
