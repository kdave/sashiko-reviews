[Severity: High]
This is a pre-existing issue, but can tasks sleep indefinitely in
zstd_get_workspace() if the max-level fallback workspace fails to preallocate
at mount time?

In zstd_alloc_workspace_manager(), preallocation failure is logged but
otherwise ignored without establishing the fallback workspace:

    ws = zstd_alloc_workspace(fs_info, ZSTD_BTRFS_MAX_LEVEL);
    if (IS_ERR(ws)) {
        btrfs_warn(NULL, "cannot preallocate zstd compression workspace");
    } else {
        ...
    }

If this fails, later under memory pressure zstd_get_workspace() will fail
to allocate a workspace and block on zwsm->wait.

However, zstd_put_workspace() only wakes the queue when a max-level
workspace is returned:

    if (workspace->level == clip_level(ZSTD_BTRFS_MAX_LEVEL))
        cond_wake_up(&zwsm->wait);

Since no max-level workspace was preallocated, and none might be allocated
dynamically (if no level-15 requests are made or if they also fail), is it
possible the wakeup is never triggered and writers hang in
TASK_UNINTERRUPTIBLE forever?

[Severity: High]
This is also a pre-existing issue, but does the idle list check in
zstd_put_workspace() permanently exempt arbitrary workspaces from LRU reclaim?

Looking at zstd_put_workspace():

    /* Hide a max level workspace from reclaim */
    if (list_empty(&zwsm->idle_ws[ZSTD_BTRFS_MAX_LEVEL - 1])) {
        INIT_LIST_HEAD(&workspace->lru_list);
    } else {

This checks the global max-level idle list rather than checking the level of
the current workspace being returned.

Because zstd_find_workspace() can borrow higher-level workspaces as
fallbacks, the max-level workspace can frequently be in use under load,
making its idle list empty.

If a lower-level workspace is returned during this window, it passes this
check, its lru_list is re-initialized, and it bypasses insertion into
zwsm->lru_list.

Since the timer only scans lru_list, does this mean these dynamically
allocated workspaces are never reclaimed, causing a memory leak?
