btrfs: lzo: reject compressed segment that overflows the compressed input

This commit adds a check in lzo_decompress_bio() to ensure the segment length
does not exceed the available compressed input. This prevents a null pointer
dereference when copy_compressed_segment() walks off the last folio.

This is a pre-existing issue, but I noticed a potential flaw in how the overall
compressed extent length (len_in) is validated earlier in lzo_decompress_bio().

When len_in is read, the validation check looks like this:

fs/btrfs/lzo.c:lzo_decompress_bio() {
    ...
	if (unlikely(len_in > min_t(size_t, BTRFS_MAX_COMPRESSED, compressed_len) ||

    ...
}

Does this check fail to reject structurally invalid extents where len_in
is <= 4 when compressed_len is exactly 1 sector? For example, round_up(4, 4096)
is 4096, which is not less than 4096, so the check passes.

If len_in <= LZO_LEN (4), the decompression loop condition evaluates to false
immediately because cur_in is initialized to LZO_LEN (4):

fs/btrfs/lzo.c:lzo_decompress_bio() {
    ...
	/* Go through each lzo segment */
	while (cur_in < len_in) {
    ...
}

Could this cause lzo_decompress_bio() to return 0 (success) without
decompressing any data, resulting in silent data corruption on read when the
uncompressed bio is subsequently zero-filled instead of returning an I/O error?
