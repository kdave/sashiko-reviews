[Severity: High]
This isn't a bug introduced by this patch, but while looking at
xfs_fsverity_delete_metadata() just above this new function, I noticed
a potential lock ordering issue.

In xfs_fsverity_delete_metadata(), truncate_inode_pages() is called while
holding XFS_ILOCK_EXCL and a transaction log space reservation:

fs/xfs/xfs_fsverity.c:xfs_fsverity_delete_metadata() {
        error = xfs_trans_alloc(mp, &M_RES(mp)->tr_itruncate, 0, 0, 0, &tp);
        ...
        xfs_ilock(ip, XFS_MMAPLOCK_EXCL | XFS_ILOCK_EXCL);
        truncate_inode_pages(VFS_I(ip)->i_mapping, XFS_ISIZE(ip));
        ...
}

Could this create an ABBA deadlock with background writeback?

If a user process fails to enable fsverity and triggers this cleanup path,
and simultaneously background writeback starts writing the dirty fsverity
merkle tree pages, the writeback thread holds the page lock and tries to
acquire XFS_ILOCK_SHARED.

At the same time, xfs_fsverity_delete_metadata() holds XFS_ILOCK_EXCL and
calls truncate_inode_pages(), which attempts to acquire the page lock. This
appears to invert the standard XFS lock order.
