btrfs: check for exit condition after waking in wait_log_commit()

The commit moves the exit condition check in wait_log_commit() to after
the task is woken up and the log_mutex is reacquired. This optimizes the
loop by avoiding a redundant check during the first iteration.

This is a pre-existing issue, but can this sequence lead to a lost wakeup
resulting in a D-state hang?

Looking at wait_for_writer() right below the modified function, the condition
check occurs before prepare_to_wait():

fs/btrfs/tree-log.c:wait_for_writer() {
	for (;;) {
		if (atomic_read(&root->log_writers) == 0)
			break;

		prepare_to_wait(&root->log_writer_wait, &wait,
				TASK_UNINTERRUPTIBLE);
		...
}

If a concurrent call to btrfs_end_log_trans() executes after the condition
check but before prepare_to_wait():

CPU1                                      CPU2
wait_for_writer()                         btrfs_end_log_trans()
  if (atomic_read(&root->log_writers) == 0)
                                            if (atomic_dec_and_test(&root->log_writers))
                                              cond_wake_up_nomb(&root->log_writer_wait);
  prepare_to_wait(...)
  mutex_unlock(&root->log_mutex);

Wouldn't CPU2 observe an empty wait queue and not wake anything, causing CPU1
to unconditionally sleep forever in TASK_UNINTERRUPTIBLE?
