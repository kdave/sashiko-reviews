[Severity: Medium]
Does this force a full transaction commit when fsyncing an open file whose
last link was unlinked in the current transaction?

When inode->vfs_inode.i_nlink == 0, btrfs_unlink() has set
inode->last_unlink_trans = trans->transid, and btrfs_log_inode() has already
flushed the delayed inode to remove the last BTRFS_INODE_REF_KEY from the
subvolume tree.  Skipping the fast path here enters the subvolume tree search
for (ino, BTRFS_INODE_REF_KEY, 0), where btrfs_search_slot() returns ret = 1
and the loop breaks without resetting ret when any item follows the inode
item in the leaf:

fs/btrfs/tree-log.c:log_all_new_ancestors() {
	...
	ret = btrfs_search_slot(NULL, root, &search_key, path, 0, 0);
	if (ret < 0)
		goto out;
	if (ret == 0)
		path->slots[0]++;

	while (true) {
		...
		btrfs_item_key_to_cpu(leaf, &found_key, slot);
		if (found_key.objectid != ino ||
		    found_key.type > BTRFS_INODE_EXTREF_KEY)
			break;
	...
out:
	trace_btrfs_log_all_new_ancestors_exit(trans, inode, ret);
	return ret;
}

log_all_new_ancestors() then returns 1 (BTRFS_LOG_FORCE_COMMIT) to
btrfs_log_inode_parent(), causing btrfs_sync_file() to fall back to a full
transaction commit instead of syncing the log tree.  Taking the fast path (or
returning early) when inode->vfs_inode.i_nlink == 0, and resetting ret = 0
before breaking out of the loop, would avoid this regression.
