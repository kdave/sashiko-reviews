[Severity: High]
Does taking uuid_mutex here while holding an open transaction invert the
lock order against btrfs_init_new_device()?

btrfs_rm_device() starts a transaction before reaching this block and only
commits it at the end of the function.  When sprouting a seed filesystem,
btrfs_init_new_device() acquires uuid_mutex before starting and committing
a transaction, which can cause an ABBA deadlock:

----                              ----
btrfs_start_transaction()
                                  mutex_lock(&uuid_mutex)
mutex_lock(&uuid_mutex)
                                  btrfs_start_transaction()

CPU0: btrfs_ioctl_rm_dev() -> btrfs_rm_device()
CPU1: btrfs_ioctl_add_dev() -> btrfs_init_new_device()

[Severity: High]
Can a caller of the non-RCU btrfs_find_device() race with this removal and
trigger a use-after-free on cur_devices?

Callers such as btrfs_get_dev_stats() and btrfs_scrub_progress() call the
non-RCU btrfs_find_device() while holding only
fs_devices->device_list_mutex, outside an RCU read-side critical section:

fs/btrfs/volumes.c:btrfs_get_dev_stats() {
	...
	mutex_lock(&fs_devices->device_list_mutex);
	args.devid = stats->devid;
	dev = btrfs_find_device(fs_info->fs_devices, &args);
	mutex_unlock(&fs_devices->device_list_mutex);
	...
}

Because btrfs_rm_device() drops fs_devices->device_list_mutex earlier and
only takes uuid_mutex here, and synchronize_rcu() does not wait for threads
holding a mutex outside RCU, cur_devices can be unlinked and freed while
btrfs_find_device() is walking fs_devices->seed_list:

[Severity: Medium]
Can btrfs_ioctl_dev_info() dereference seed_devices after
btrfs_rollback_sprout() frees it?

list_splice_init_rcu() calls synchronize_rcu() before linking the devices
back onto fs_devices->devices, while each device->fs_devices still points
to seed_devices.  Once spliced, an RCU reader in btrfs_ioctl_dev_info() can
find a device on fs_devices->devices and load dev->fs_devices before the
loop resets device->fs_devices to fs_devices, after which
btrfs_rollback_sprout() immediately calls free_fs_devices(seed_devices)
without waiting for another RCU grace period:
