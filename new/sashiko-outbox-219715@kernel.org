[Severity: High]
Can zoned_bg_reclaimable() count block groups that
btrfs_reclaim_block_group() will refuse to relocate?

btrfs_reclaim_block_group() skips any block group with bg->used == 0,
bg->pinned > 0, or bg->reserved > 0 without relocating it or putting it on
retry_list.  Because flush_space() calls btrfs_zoned_reclaim_sweep()
before btrfs_delete_unused_bgs(), a full block group whose extents were
just unpinned by the preceding COMMIT_TRANS state still has bg->used == 0
and sits on fs_info->unused_bgs.  Also, a block group still on unused_bgs
has a non-empty bg->bg_list, so btrfs_mark_bg_to_reclaim() is a no-op on
it.

In all of these cases, zoned_sweep_space_info() and
btrfs_zoned_reclaim_sweep() still add bg_garbage toward the two-zone
target, which stops the sweep from queuing actual relocatable candidates
from cands[] and can leave RECLAIM_ZONES reclaiming nothing before failing
waiting data tickets with -ENOSPC.

[Severity: Medium]
Should the threshold check scale by bg->zone_capacity instead of
bg->length, matching __btrfs_add_free_space_zoned()?

On zoned devices where zone_capacity is smaller than zone_size (for
example, ZNS SSDs where bg->zone_capacity is below 75% of bg->length),
bg->used can never exceed bg->zone_capacity.  Comparing bg->used against
mult_perc(bg->length, thresh_pct) makes below true for every full block
group with any garbage, queueing all of them for immediate reclaim instead
of sorting candidates up to target.

[Severity: High]
What happens after a block group from data_sinfo->sub_group[0] is
relocated?

When btrfs_relocate_chunk_finish() finishes relocating a block group, it
calls btrfs_zoned_reuse_reclaimed_bg(), which rejects anything not in
fs_info->data_sinfo:

fs/btrfs/zoned.c:btrfs_zoned_reuse_reclaimed_bg() {
	...
	if (space_info != fs_info->data_sinfo)
		return false;
	...
}

Because that returns false for data_sinfo->sub_group[0],
btrfs_relocate_chunk_finish() falls back to btrfs_remove_chunk().  The
freed device zone then remains pinned until transaction commit (after
btrfs_reclaim_block_groups() finishes), so subsequent relocations in the
batch cannot reuse it as the next data_reloc_bg and can fail with -ENOSPC.
In addition, when btrfs_remove_block_group() removes the last block group
from data_sinfo->sub_group[0]->block_groups[index], it calls
clear_avail_alloc_bits(), clearing fs_info->avail_data_alloc_bits even
though data_sinfo still has block groups of that profile.

> +	struct zoned_gc_candidate *cands;
> +	const u64 target = 2 * fs_info->zone_size;

[Severity: Medium]
Does target need to scale with the number of data stripes on RAID0 and
RAID10 filesystems?

On multi-stripe zoned profiles, zoned_bg_garbage() returns logical bytes
across all data_stripes zones in the block group, and both
btrfs_zoned_data_chunk_allowed() and data_reloc_bg require space across
all stripes (chunk_bytes = fs_info->zone_size * num_stripes).  With target
fixed at 2 * fs_info->zone_size, a 4-disk RAID0 array stops queuing
candidates after half a block group's worth of garbage, which is not
enough to free a single multi-stripe block group.
