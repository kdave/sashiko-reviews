btrfs: don't force the filesystem read-only on EDQUOT/ENOSPC verity rollback

This commit attempts to prevent forcing the filesystem read-only when
rolling back fsverity enable hits a quota or space limit. It skips
btrfs_handle_fs_error() for -EDQUOT and -ENOSPC during verity item
deletion, leaving the orphan item in place for cleanup on the next mount.

[Severity: High]
This isn't a bug introduced by this patch, but will leaving this orphan item
cause the filesystem to permanently fail to mount read-write?

If btrfs_drop_verity_items() fails with -EDQUOT here, the patch relies on
btrfs_orphan_cleanup() to handle the leftover orphan items during the next
mount.

During the next mount, btrfs_orphan_cleanup() in fs/btrfs/inode.c will
call btrfs_drop_verity_items() again:

fs/btrfs/inode.c:btrfs_orphan_cleanup() {
    ...
    if (inode) {
        ret = btrfs_drop_verity_items(inode);
        iput(&inode->vfs_inode);
        inode = NULL;
        if (ret)
            goto out;
    }
    ...
}

Since the qgroup limit is persistent across reboots, this drop will
likely fail with -EDQUOT again.

This error propagates to btrfs_start_pre_rw_mount() in fs/btrfs/disk-io.c:

fs/btrfs/disk-io.c:btrfs_start_pre_rw_mount() {

    if ((ret = btrfs_orphan_cleanup(fs_info->fs_root)) ||

        up_read(&fs_info->cleanup_work_sem);
        return ret;
    }
    ...
}

Could this cause the RW mount to abort entirely, resulting in a persistent
Denial of Service where the filesystem is unmountable for writes?

[Severity: High]
This is a pre-existing issue, but does the error path immediately following
this defeat the purpose of the patch?

If btrfs_drop_verity_items() succeeds (or returns 0), the code attempts
to start a transaction to delete the orphan item and update the inode:

fs/btrfs/verity.c:rollback_verity() {
...
	trans = btrfs_start_transaction(root, 2);
	if (IS_ERR(trans)) {
		ret = PTR_ERR(trans);
		trans = NULL;
		btrfs_handle_fs_error(root->fs_info, ret,
			"failed to start transaction in verity rollback %llu",
			inode->vfs_inode.i_ino);

	}
...
}

Under the same quota or space limits that motivated this patch, reserving
2 units of metadata in btrfs_start_transaction() is highly likely to fail
with -EDQUOT or -ENOSPC.

If it fails, it hits the unpatched btrfs_handle_fs_error() call.

Would this unconditionally force the entire filesystem read-only, triggering
the exact issue this patch attempts to prevent?
