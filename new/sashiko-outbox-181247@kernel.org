[Severity: Medium]
Does running the full fsync right before _flakey_drop_and_remount mask
failures in the preceding fast fsync?

The kernel fix forces a full transaction commit via
btrfs_sync_file() -> btrfs_commit_transaction() when fsyncing raid stripe
tree extents. Because a btrfs transaction commit is filesystem-wide, it
finishes all pending ordered extents and commits both the subvolume root and
the raid stripe tree root for the entire running transaction.

If the fast fsync path in log_one_extent() fails to force a transaction
commit and only writes to the log tree, the uncommitted raid stripe tree
entries for the "fast" file remain in the running transaction. The
immediately following full fsync on the "full" file in copy_items() will
then commit that same running transaction before _flakey_drop_and_remount
drops writes, persisting the stripe tree mappings for the "fast" file as a
side effect.

Should the fast fsync and full fsync cases each have their own
_flakey_drop_and_remount and _hexdump verification cycle so that both paths
are tested independently?
