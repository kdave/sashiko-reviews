Subject: btrfs: implement RAID stripe-tree RAID5 writes

This commit implements RAID5 write support using the new stripe-tree. It
accumulates data across device segments into a shared parity buffer and
writes the parity to the parity device once all columns are folded. It then
inserts both data and parity locations into the stripe-tree.

[Severity: High]
Does completing the data bio here break fsync durability guarantees? This
finishes the data ordered extent immediately upon data write completion,
allowing an fsync to report success to userspace. However, the parity bio
might still be accumulating, in-flight, or waiting to insert its stripe tree
metadata asynchronously. If a crash occurs right after fsync returns, the

[Severity: Critical]
Does storing a direct pointer to bioc->stripes here risk a use-after-free?
The stripe set structure does not increment the reference count on bioc.
Because bioc is freed when the data bios finish, the asynchronous parity bio
completion and its workqueue task (insert_parity_stripe_work) will
dereference pstripe->dev and pstripe->physical after the memory has been
released.

[Severity: High]
For a standard 64KB BTRFS_STRIPE_LEN on a system with 4KB pages, this
requests an order-4 allocation. Is it safe to use __GFP_NOFAIL here? The
MM subsystem prohibits __GFP_NOFAIL for allocations larger than
PAGE_ALLOC_COSTLY_ORDER (order 3), causing the page allocator to warn and
ignore the flag. If the allocation fails under fragmentation, folio will
be NULL, which will crash in the subsequent bio_add_folio_nofail() call.
