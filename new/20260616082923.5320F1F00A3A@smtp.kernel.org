[Severity: High]
This isn't a bug introduced by this patch, but while reviewing the bounce
buffer changes, I noticed a potential memory leak in how unaligned writes
are handled at the end of this function.

When bio_iov_iter_bounce_write allocates kernel folios via
folio_alloc_greedy, they are added to the bio. If the total write size
is unaligned, the function calls bio_iov_iter_align_down before returning:

block/bio.c:bio_iov_iter_bounce_write() {
    ...
    if (!bio->bi_iter.bi_size)
        return -ENOMEM;
    return bio_iov_iter_align_down(bio, iter, minsize - 1);
}

If bio_iov_iter_align_down needs to remove bytes that span an entire
bvec, it silently drops the bvec by decrementing bio->bi_vcnt:

block/bio.c:bio_iov_iter_align_down() {
    ...
    if (bio_flagged(bio, BIO_PAGE_PINNED))
        unpin_user_page(bv->bv_page);

    bio->bi_vcnt--;
    ...
}

Because BIO_PAGE_PINNED is not set for these kernel bounce buffers, the
underlying folio reference is never put. 

Furthermore, since bio->bi_vcnt is reduced, subsequent cleanup routines
like bio_free_folios will iterate up to the new bi_vcnt and miss the
dropped bvec entirely.

Does this code leak the allocated kernel folio when an unaligned direct I/O
write causes a bvec to be fully truncated?
