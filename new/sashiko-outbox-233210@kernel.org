[Severity: Medium]
Does checking fs_info->data_reloc_bg here cause
btrfs_zoned_reuse_reclaimed_bg() to almost always return false?

During btrfs_relocate_block_group(), do_allocation_zoned() sets
fs_info->data_reloc_bg to the destination relocation block group, and
btrfs_zone_finish_endio() only clears it via do_zone_finish() when that
destination block group reaches zone_capacity:

fs/btrfs/zoned.c:btrfs_zone_finish_endio() {
    ...
	/* Bail out if we can allocate more data from this block group. */
	if (logical + length + min_alloc_bytes <=
	    block_group->start + block_group->zone_capacity)
		goto out;

	ret = do_zone_finish(block_group, true);
    ...
}

Unless the relocated extents happen to fill the destination block group to
zone_capacity on the final extent of bg, fs_info->data_reloc_bg is still
non-zero when btrfs_relocate_chunk_finish() runs.  As a result,
btrfs_zoned_reuse_reclaimed_bg() bails out and
btrfs_relocate_chunk_finish() discards and deletes bg via
btrfs_remove_chunk() instead of reusing it.

[Severity: Medium]
Can concurrent data writes claim the reset block group or its space before
zoned_reset_bg_in_place() promotes it to fs_info->data_reloc_bg?

Dropping both read-only references leaves bg->ro == 0 on data_sinfo.
Inside zoned_reset_bg_in_place(), bg->alloc_offset is reset to 0 and
*reclaimed is subtracted from data_sinfo->bytes_zone_unusable before
bg->lock and space_info->lock are unlocked to call
btrfs_set_data_reloc_bg():

    spin_unlock(&bg->lock)

If a concurrent writer reserves the newly available space in data_sinfo
(or find_free_extent() allocates directly from bg) during that window,
btrfs_set_data_reloc_bg() fails, leaving bg in data_sinfo and
fs_info->data_reloc_bg unset so the next relocation in the reclaim run can
fail with -ENOSPC.
