Subject: btrfs: emit BTRFS_SEND_C_FILEATTR during full mode

This patch modifies the btrfs send mechanism to emit BTRFS_SEND_C_FILEATTR
during full sends and for newly created inodes. Previously, this attribute
was only emitted during incremental sends when file attributes changed
between snapshots.

[Severity: High]
This is a pre-existing issue, but does forcing need_fileattr = true here
break receiving full snapshots that contain immutable files or directories?

Looking at finish_inode_if_needed(), send_fileattr() is called when
need_fileattr is true:

	if (need_fileattr) {
		ret = send_fileattr(sctx, sctx->cur_ino, sctx->cur_inode_gen,
				    left_fileattr);
		...
	}

For regular files, send_utimes() is emitted shortly after this:

		if (S_ISDIR(sctx->cur_inode_mode) && sctx->cur_inode_size > 0)
			ret = cache_dir_utimes(sctx, sctx->cur_ino, ...);
		else
			ret = send_utimes(sctx, sctx->cur_ino, sctx->cur_inode_gen);

If the fileattr contains restrictive flags like FS_IMMUTABLE_FL
(BTRFS_INODE_IMMUTABLE), will the receiving side apply this attribute
immediately, causing the subsequent utimes update to fail with -EPERM?

Similarly, for directories, the sender finishes the parent directory and
emits its file attributes before processing its child inodes. If the
directory is made immutable at this point, will creating children inside it
on the receiver also fail with -EPERM?
