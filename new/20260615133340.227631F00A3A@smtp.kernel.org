[Severity: Critical]
This is a pre-existing issue, but does this error path tear down the
device structure after it has already been durably committed to disk?

In btrfs_init_new_device(), after a seeding device is fully processed,
the transaction is committed via btrfs_commit_transaction() earlier in
this block. At this point, the device is permanently embedded in the
filesystem's chunk and device trees, and active btrfs_chunk_map
structures hold pointers to it.

If btrfs_attach_transaction() subsequently fails and takes this goto,
the code unwinds through error_sysfs, unlinks the device, and frees it.
Could this cause a use-after-free during subsequent I/O targeting those
chunks, since the freed btrfs_device pointer is still referenced by
the active maps?

[Severity: High]
This isn't a bug introduced by this patch, but does this error rollback
free the device without waiting for an RCU grace period?

During device addition, the new device is added to fs_devices->devices
via list_add_rcu(). If a subsequent step fails and unwinds through the
error_sysfs label, it unlinks the device using list_del_rcu() and cascades
down to btrfs_free_device(), which immediately calls kfree().

There are numerous places traversing fs_devices->devices under
rcu_read_lock(). Without a synchronize_rcu() or kfree_rcu(), will
these concurrent readers dereference the freed device pointer?
