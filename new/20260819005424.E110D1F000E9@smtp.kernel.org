btrfs: abort transaction before releasing tree_log_mutex on commit failure

This commit fixes a TOCTOU race in btrfs_commit_transaction() where a commit
failure would drop tree_log_mutex before aborting the transaction. This
allowed a waiting log sync to write out a superblock pointing to uncommitted
trees, so it explicitly aborts the transaction before releasing the mutex.

> +++ b/fs/btrfs/transaction.c
> @@ -2585,6 +2585,12 @@ int btrfs_commit_transaction(struct btrfs_trans_handle *trans)

> +		 * Abort before releasing tree_log_mutex, so a log sync waiting

[Severity: Critical]
This is a pre-existing issue, but does the TOCTOU race fixed by this patch still
exist if write_all_supers() fails from backup_super_roots()?

Looking at write_all_supers(), if backup_super_roots() fails, it returns the
error immediately without aborting the transaction:

fs/btrfs/disk-io.c:write_all_supers() {
    ...
		ret = backup_super_roots(fs_info);
		if (ret < 0)
			return ret;
    ...
}

If this happens, btrfs_commit_transaction() unlocks tree_log_mutex and jumps to
the scrub_continue label, leaving BTRFS_FS_ERROR unset because
btrfs_abort_transaction() hasn't been called yet.

Could a concurrent btrfs_sync_log() then acquire tree_log_mutex, see no FS
error, and incorrectly write out the super_for_commit for the failed
transaction?
