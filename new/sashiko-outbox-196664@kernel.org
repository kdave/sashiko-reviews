btrfs: move async data csum generation out of experimental

This commit enables asynchronous data checksum generation unconditionally by
moving it out of CONFIG_BTRFS_EXPERIMENTAL, removing the synchronous path in
btrfs_csum_one_bio(), and deleting the fs_info->workers workqueue along with
the BTRFS_FS_CSUM_IMPL_FAST flag.

[Severity: High]
With btrfs_csum_one_bio() now unconditionally queuing bbio->csum_work onto
fs_info->endio_workers, is the single flush_workqueue(fs_info->endio_workers)
call immediately below sufficient to drain all write bio completions during
close_ctree()?

During unmount, a compressed write work item running on
fs_info->delalloc_workers (for example when compress_file_range() already
cleared PAGECACHE_TAG_DIRTY before submit_compressed_extents() allocated the
btrfs_ordered_extent, or when BTRFS_FS_ERROR(fs_info) caused
btrfs_start_delalloc_roots() to return early) can submit a write bio while
btrfs_flush_workqueue(fs_info->delalloc_workers) runs:

  submit_compressed_extents()
    submit_one_async_extent()
      btrfs_submit_compressed_write()
        btrfs_submit_bbio()
          btrfs_submit_chunk()
            btrfs_bio_csum()
              btrfs_csum_one_bio()
                bio_inc_remaining(bio);
                INIT_WORK(&bbio->csum_work, csum_one_bio_work);
                queue_work(fs_info->endio_workers, &bbio->csum_work);

If the underlying device I/O completes or fails immediately (such as via
bio_io_error() in btrfs_submit_dev_bio()) before csum_one_bio_work() finishes,
the device completion's bio_endio() only decrements bio->__bi_remaining from 2
to 1.

When close_ctree() then calls flush_workqueue(fs_info->endio_workers) once, it
only waits for the current work batch containing bbio->csum_work. When
csum_one_bio_work() executes on fs_info->endio_workers, it calls
bio_endio(&bbio->bio), which drops bio->__bi_remaining to 0 and invokes
btrfs_simple_end_io() (or btrfs_orig_write_end_io()):

  csum_one_bio_work()
    bio_endio()
      btrfs_simple_end_io()
        INIT_WORK(&bbio->end_io_work, simple_end_io_work);
        queue_work(btrfs_end_io_wq(fs_info, bio), &bbio->end_io_work);

Because btrfs_end_io_wq() returns fs_info->endio_workers for data writes,
bbio->end_io_work is queued back onto fs_info->endio_workers in the next work
color batch. A single flush_workqueue(fs_info->endio_workers) call can return
as soon as csum_one_bio_work() finishes without waiting for the newly queued
bbio->end_io_work.

Could bbio->end_io_work then run after btrfs_flush_workqueue(fs_info->endio_write_workers),
btrfs_run_delayed_iputs(), set_bit(BTRFS_FS_STATE_NO_DELAYED_IPUT, ...), and
kthread_stop(fs_info->cleaner_kthread), leading to late ordered extent
completions, late btrfs_add_delayed_iput() calls, or a use-after-free waking
cleaner_kthread?

[Severity: Critical]
Can unconditional async checksum generation in btrfs_csum_one_bio() race with
log_extent_csums() during a fast fsync and write zeroed or partially computed
checksums into the log tree?

In btrfs_csum_one_bio(), sums is allocated with kvzalloc() and immediately
added to ordered->csum_list via btrfs_add_ordered_sum(ordered, sums) before
csum_one_bio_work() is queued onto fs_info->endio_workers to populate
sums->sums[]:

  btrfs_csum_one_bio()
    sums = kvzalloc(btrfs_ordered_sum_size(fs_info, bio->bi_iter.bi_size),
                    GFP_KERNEL);
    ...
    btrfs_add_ordered_sum(ordered, sums);
    bbio->csum_saved_iter = bio->bi_iter;
    bio_inc_remaining(bio);
    INIT_WORK(&bbio->csum_work, csum_one_bio_work);
    queue_work(fs_info->endio_workers, &bbio->csum_work);

For write paths that create an ordered extent and modified extent map without
marking pagecache folios with PAGECACHE_TAG_WRITEBACK in
inode->vfs_inode.i_mapping - such as btrfs_do_encoded_write() (which submits
private folios with cb->writeback == false) or an asynchronous O_DIRECT bounce
write via btrfs_direct_write() / btrfs_dio_write() - a subsequent or
O_SYNC/O_DSYNC fast fsync in btrfs_sync_file() does:

  btrfs_sync_file()
    btrfs_get_ordered_extents_for_logging(inode, &ctx.ordered_extents);
    ret = filemap_fdatawait_range(inode->vfs_inode.i_mapping, start, end);
    ...
    btrfs_log_dentry_safe()
      btrfs_log_inode_parent()
        btrfs_log_inode()
          btrfs_log_changed_extents()
            log_one_extent()
              log_extent_csums()

Because filemap_fdatawait_range() only waits on pagecache writeback in
i_mapping, it returns without waiting for the in-flight bio or
bbio->csum_work. Then log_extent_csums() walks ordered->csum_list and logs
sums->sums[] into the log tree:

while csum_one_bio_work() -> csum_one_bio() has not yet run or is concurrently
