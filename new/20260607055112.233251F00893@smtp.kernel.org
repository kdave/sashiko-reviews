btrfs: fix use-after-free of reloc_control in btrfs_reloc_cow_block

This commit attempts to fix a use-after-free vulnerability of the reloc_control
object by adding a transaction commit barrier before freeing it. This ensures
concurrent callers finish their transactions before the memory is released.

Link: https://syzkaller.appspot.com/bug?extid=0eea49bba18051dea35e

[Severity: Critical]
This is a pre-existing issue, but does placing the barrier here leave
rc->data_inode vulnerable to a use-after-free?

Just before this hunk at the "out:" label, iput(rc->data_inode) is called.
If concurrent threads are still executing btrfs_reloc_cow_block(),
they can enter get_new_location() and dereference the freed inode:

fs/btrfs/relocation.c:get_new_location() {
    struct btrfs_root *root = BTRFS_I(reloc_inode)->root;
    ...
}

Should the barrier be placed before we drop the reference to rc->data_inode?

[Severity: Critical]
This isn't a bug introduced by this patch, but does this barrier actually
wait if the filesystem has encountered an error?

If the filesystem is in an error state (e.g. from an aborted transaction),
start_transaction() immediately returns -EROFS. This causes
btrfs_commit_current_transaction() to propagate the error without waiting:

fs/btrfs/transaction.c:btrfs_commit_current_transaction() {
    trans = btrfs_attach_transaction_barrier(root);
    if (IS_ERR(trans)) {
        int ret = PTR_ERR(trans);
        return (ret == -ENOENT) ? 0 : ret;
    }
    ...
}

Because btrfs_relocate_block_group() ignores the return value of
btrfs_commit_current_transaction() here, it will proceed directly to
free_reloc_control(rc). 

Will concurrent threads still using rc then trigger a use-after-free?

>  	free_reloc_control(rc);
>  	return ret;
>  }
