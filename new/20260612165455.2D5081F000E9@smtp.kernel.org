Subject: btrfs: release extent lock per folio in readahead

This commit alters the extent locking behavior in the btrfs readahead path.
Instead of unlocking the entire readahead range in one shot at the end, it
unlocks the extent per folio inside the readahead loop to prevent stale
page cache issues on overlapping reads when readahead fails.

[Severity: High]
Does this unconditionally unlock extent ranges that were never initially
locked if the readahead window is dynamically expanded?

btrfs_readahead() calculates start and end based on the initial
readahead_length() and locks exactly this range before the loop via
lock_extents_for_read().

However, inside the loop, btrfs_do_readpage() can dynamically expand the
readahead window when encountering compressed extents:

btrfs_do_readpage() {
    ...
    if (bio_ctrl->ractl &&
        !btrfs_is_subpage(fs_info, folio) &&
        compress_type != BTRFS_COMPRESS_NONE)
        btrfs_readahead_expand(bio_ctrl->ractl, em);
    ...
}

This expands the rac outwards, adding new folios to the readahead control.
When the while loop yields these newly added folios, they fall outside the
originally locked range, meaning their extents were never locked by this
thread.

If another concurrent thread (like a DIO write or truncate) holds the
extent lock for that expanded range, could calling btrfs_unlock_extent()
on these expanded folios silently drop their lock and break mutual
exclusion?
