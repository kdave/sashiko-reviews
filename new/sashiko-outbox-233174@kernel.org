> btrfs: zoned: recover active non-data block group roles on mount
> 
> Mount restores active sequential non-data block groups and their
> reservations, but leaves active_meta_bg and active_system_bg unset.
> Writing to a recovered block group does not set its role pointer:
> check_bg_is_active() returns early because ZONE_IS_ACTIVE is already
> set, skipping the role assignment.
> 
> These block groups can still be finished through other paths, but
> metadata/system write-time switching cannot identify the previous
> block group when the corresponding role pointer is NULL.
> 
> Restore these roles during mount so write-time switching can identify
> and finish the previous non-data block group.
> 
> Keep the active block group with the largest writable tail for each
> metadata/system role and finish the others. Since the tree-log role
> is not persisted, leave a reservation for a new tree-log block group.
> 
> Account for the abandoned tails in do_zone_finish().
>

> Tested-by: Jochen Philipp <a2jphilipp@gmail.com>

Does calling btrfs_restore_active_nondata_bgs() before the sb_rdonly(sb)

After any workload that used fsync, both a normal metadata block group and
a dedicated tree-log metadata block group are active on disk.  During a
read-only mount, btrfs_restore_active_nondata_bgs() ->
finish_extra_active_nondata_bgs() -> do_zone_finish() ->
call_zone_finish() calls blkdev_zone_mgmt(..., REQ_OP_ZONE_FINISH, ...).

returns -EPERM and aborts the mount; on a writable block device, a
read-only mount permanently finishes zones on disk.

Can finishing a former tree-log block group here before btrfs_replay_log()
overflow block_group->zone_unusable past block_group->length when log
replay commits?

Tree-log extent allocations do not increment block_group->used on disk, so
btrfs_calc_zone_unusable() during btrfs_read_block_groups() initializes
zone_unusable to alloc_offset + (length - zone_capacity), which already
includes the [0, alloc_offset) region containing live log tree blocks.

block_group->zone_unusable becomes equal to block_group->length.

btrfs_pin_extent_for_log_replay() and commits the transaction, which

[Severity: High]
Can this select an unused former tree-log block group (used == 0) or a
read-only block group (ro > 0) as active_meta_bg or active_system_bg and
finish the live writable block group instead?

A dedicated tree-log block group from the previous mount has used == 0 on
disk and typically has a smaller alloc_offset (larger avail) than the
normal metadata block group (used > 0).  Earlier in open_ctree(),
btrfs_read_block_groups() -> read_one_block_group() already queues any
writable block group with used == 0 && remap_bytes == 0 onto
fs_info->unused_bgs (or discard_ctl) and marks non-writable or deprecated
SINGLE/RAID0 block groups read-only via inc_block_group_ro().

Because the selection here only compares avail without checking
block_group->used == 0 or block_group->ro, it picks the unused former
tree-log block group (or a read-only block group) as active_meta_bg and
finish_extra_active_nondata_bgs() finishes the live used > 0 metadata
block group.  Meanwhile, the selected used == 0 active_meta_bg remains on
fs_info->unused_bgs, so btrfs_delete_unused_bgs() can zone-finish and
delete it while fs_info->active_meta_bg still points to it.
