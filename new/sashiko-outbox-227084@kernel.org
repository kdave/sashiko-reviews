[Severity: Medium]
Should uncompressed extents check offset + num_bytes against
disk_num_bytes instead of ram_bytes?

For uncompressed extents, btrfs_extent_item_to_extent_map() ignores the
on-disk ram_bytes field and sets em->ram_bytes from disk_num_bytes:

fs/btrfs/file-item.c:btrfs_extent_item_to_extent_map() {
    ...
		if (compress_type == BTRFS_COMPRESS_NONE) {
			/*
			 * Older kernels can create regular non-hole data
			 * extents with ram_bytes smaller than disk_num_bytes.
			 * Not a big deal, just always use disk_num_bytes
			 * for ram_bytes.
			 */
			em->ram_bytes = em->disk_num_bytes;
    ...
}

Because check_extent_data_item() does not enforce ram_bytes ==
disk_num_bytes on non-debug builds (and only warns under
CONFIG_BTRFS_DEBUG), checking against ram_bytes causes two problems for
uncompressed extents:

1. An uncompressed extent with disk_num_bytes < offset + num_bytes <=
   ram_bytes passes check_extent_data_item(), and then triggers ASSERT(0)
   in validate_extent_map() -> dump_extent_map() (or reads past
   disk_num_bytes on non-debug builds).

2. Valid uncompressed extents written by older kernels with
   ram_bytes < offset + num_bytes <= disk_num_bytes (which the comment in
   btrfs_extent_item_to_extent_map() notes can exist on disk) will be
   rejected with -EUCLEAN.
