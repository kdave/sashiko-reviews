btrfs: wait for block group relocation on remount read-only

This commit serializes read-only remounts against in-progress block group
relocation under reclaim_bgs_lock, stops the zoned repair kthread when the
filesystem becomes read-only, and cancels reclaim_bgs_work after waiting for
the cleaner thread.

[Severity: High]
This problem wasn't introduced by this patch, but can acquiring the super
write lock in btrfs_reclaim_block_groups() cause a freeze deadlock
[1] when invoked from async_data_reclaim_work?

When a writer holding SB_FREEZE_WRITE runs low on data space on a zoned
filesystem, reserve_bytes() queues async_data_reclaim_work and sleeps in
wait_reserve_ticket().  If freeze_super() starts concurrently, it blocks in

[Severity: High]
Can waiting on reclaim_bgs_lock after canceling async_reclaim_work and
async_data_reclaim_work at the top of btrfs_remount_ro() deadlock when an
in-progress relocation is waiting on a space reservation ticket?

While holding reclaim_bgs_lock, btrfs_relocate_block_group() reserves space
with BTRFS_RESERVE_FLUSH_ALL (for example via btrfs_block_rsv_refill()).  When
space is tight, reserve_bytes() sets space_info->flush = true, queues
async_reclaim_work, and sleeps in wait_reserve_ticket():

CPU0 (relocation)                   CPU1 (remount,ro)
btrfs_reclaim_bgs_work()
  mutex_lock(&reclaim_bgs_lock)
  ...
  btrfs_block_rsv_refill()
    reserve_bytes()
      space_info->flush = true
      queue_work(async_reclaim_work)
                                    btrfs_remount_ro()
                                      cancel_work_sync(&async_reclaim_work)
                                      ...
                                      mutex_lock(&reclaim_bgs_lock)
      wait_reserve_ticket()
        <-- never woken

If cancel_work_sync() cancels async_reclaim_work before the worker runs,
space_info->flush stays true and the ticket is never served, leaving both
threads blocked.  Conversely, if relocation queues async_reclaim_work or
async_data_reclaim_work after the initial cancel_work_sync() calls while
btrfs_remount_ro() is waiting on reclaim_bgs_lock, nothing cancels those works
again before btrfs_commit_super(), so they can start transactions after the
last commit.

Does calling cancel_work_sync(&fs_info->reclaim_bgs_work) under sb->s_umount
trigger a lockdep circular dependency report with sb_writers?

[Severity: Critical]
This problem wasn't introduced by this patch, but nothing waits for the

use-after-free of cache, fs_info, and fs_info->sb [2]:

CPU0 (unmount)                      CPU1 (repair kthread)
                                    [spawned via btrfs_repair_one_zone()]
close_ctree()
  btrfs_stop_all_workers()
  ...

                                    relocating_repair_kthread()

kthread_run() outside the btrfs workqueues, close_ctree() can finish tearing
down the filesystem before the kthread starts running.
